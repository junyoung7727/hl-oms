# 구성 (arc42 §5 구성 요소 뷰)

![hl-oms 구성: 주문 경로와 안전 장치](architecture/architecture.svg)

- 초록 굵은 선이 주문이 가는 길이다: 전략 → 로컬 소켓 → ① 코어 → ② 저널 → ③ 게이트웨이 → Bybit. 저널의 fdatasync가 성공하기 전에는 응답도 전송도 나가지 않는다(2절).
- 빨간 점선이 워처다. OMS와 코드를 나누지 않고 거래소와 저널을 따로 읽는다. 차이를 확정하면 보류를 걸고, OMS가 10초 답하지 않으면 킬한다(6절 12, 9절).
- 보라 점선은 읽기만 하는 옆길이다. 관측(프로젝터, VictoriaMetrics, Grafana), 거래 표(`oms-export`, 그림에 없음), 시세 수집은 멈춰도 주문과 킬에 영향이 없다.
- 전략도 공개 시세를 `md-feed`로 Bybit에서 직접 받는다(그림에 없음). 수집기도 텔레그램으로 직접 알린다.
- 그림 원본은 [architecture.archify.json](architecture/architecture.archify.json)이다. 상자마다 근거 코드 위치가 있다. Archify로 다시 그려 SVG로 내보낸다.

# 상황별 동작 (arc42 §6 런타임 뷰)

대상: Bybit USDT 무기한 선물(linear). 숫자는 기본값이고, 바꿀 수 있는 값은 그렇다고 적었다.
공통 용어. 저널: OMS가 내린 모든 결정을 순서대로 적는 파일. 내구화: 기록에 대한 fdatasync가 성공한 상태. 예약: 아직 체결될 수 있어서 한도 계산에서 이미 쓴 것으로 치는 수량. 일반 주문: 감소 전용(포지션을 줄이기만 하는 주문)이 아닌 주문. 증거금 정책: 설정의 `policy.margin` 구역. mainnet은 이것 없이 시작하지 않는다. 정책이 있으면 "일반 주문만 막는" 차단이 감소 전용 주문을 통과시킨다.

## 1. 응답이 안 오는 주문
1. 전략이 주문에 만료 시각(expires_at)을 붙인다. 만료가 지금부터 60초보다 멀면 받지 않는다.
2. 게이트웨이는 보내는 순간의 로컬 시각 + recv_window(기본 5초, 1~20초로 설정) + 1초 ≤ expires_at 일 때만 보낸다. 요청 한도를 기다렸으면 기다린 뒤 다시 잰다. 아니면 NotSent. Bybit는 요청 시각 + recv_window가 서버 시각보다 이른 요청을 거절하고, 서버 시각보다 1초 넘게 앞선 요청도 거절한다.
3. 그래서 우리 시계가 Bybit보다 크게 앞서면 안 된다. 게이트웨이는 Bybit 시각을 재서(응답을 받은 뒤의 로컬 시각 − Bybit 시각. 왕복 시간도 앞섬으로 친다) 500ms를 넘으면 새 주문 전송을 막는다. 왕복이 250ms를 넘는 측정은 판정하지 않는다. 취소와 스트림은 막지 않는다(ADR-028 R0). 시작 전, 60초마다, 막힌 동안은 10초마다 잰다.
4. 분류:
   - NotSent: 바이트가 하나도 나가지 않은 것이 확실할 때만(접속 실패, 막힘, 2의 규칙 탈락, 거래하지 않는 종목, 킬 중, 서명을 만들지 못함).
   - Rejected: 거래소가 오류 문서에 있는 코드로 명시적으로 거절했을 때만.
   - 나머지는 모두 Unknown: 시간 초과(기본 3초), 연결 끊김, 2xx가 아닌 HTTP, 읽을 수 없는 응답, 문서에 없는 코드, 성공인데 orderId가 없는 응답, 그리고 결과를 알 수 없는 코드 12개(10016 서버 오류, 110072 같은 orderLinkId의 주문이 이미 있을 수 있음 등).
   - 결과가 30초 안에 아무것도 오지 않아도 Unknown이다.
5. Unknown이면:
   - 그 주문이 체결될 수 있는 최대량(주문 수량 − 이미 기장된 체결)을 예약으로 둔다.
   - 계좌 전체의 새 일반 주문을 막는다. 감소 전용 주문은 지나간다(증거금 정책이 있을 때).
   - 다시 보내지 않는다. WS Trade와 REST 어느 경로로도 보내지 않는다.
6. orderLinkId(우리가 붙인 고객 주문번호)로 상태를 묻는다. 한 번의 조회는 실시간 조회, 기간 없는 주문 이력(최근 7일), 주문을 받은 시각 1분 전부터 7일의 주문 이력을 차례로 본다. 곧바로 묻고, 풀리지 않으면 0.5초, 1초, 2초 간격으로, 그 뒤로는 5초마다 다시 묻는다. 어디서든 찾으면 정상 주문이다. 체결이나 스트림 통보가 먼저 와도 그렇다.
7. "없음"은 셋 다에서 없을 때만 나온다. 그리고 expires_at + 10초(absence_margin) 뒤에 보낸 조회일 때만 센다. 앞에 센 조회보다 10초 이상 뒤에 보낸 조회의 "없음"이 두 번째로 세지면 NotPlaced로 닫고 예약을 푼다(ADR-024). 그래서 가장 빨라야 expires_at + 20초에 닫힌다.
8. 이미 접수된 주문에 "없음"이 오면 닫지 않는다. 운영자가 보도록 불일치로 올린다.
9. 닫은 뒤에 주문이나 체결이 나타나면 체결은 기장하고, 불일치로 올리고 새 일반 주문을 막는다.
10. 재시작하면 결과가 기록되지 않은 보낸 주문은 모두 Unknown으로 시작한다.
- 시험: V-DOUBT-1, V-DOUBT-2, V-DOUBT-3, V-ABSENCE-N-1, V-BYBIT-ORDERS-1, V-BYBIT-TRADE-1, V-BYBIT-NODE-1, V-BOOT-1, V-BYBIT-LIVE-1, V-BYBIT-LIVE-2, V-BYBIT-RSA-1
- 가정과 상태: A-01(만료가 지난 요청을 거래소가 놓지 않는다. Bybit에서는 recv_window 거절이 이 역할을 한다) 테스트넷에서 확인함: 5초 넘게 지났거나 1초 넘게 앞선 요청은 10002로 거절되고 주문이 없다(V-BYBIT-LIVE-1). 110072도 테스트넷에서 확인함: 같은 orderLinkId의 두 번째 요청은 주문을 만들지 않고, 주문이 끝난 뒤에도 그 orderLinkId는 다시 받지 않는다(V-BYBIT-LIVE-2). A-02(시계 차이 + 조회 지연이 10초보다 작다) 테스트넷 확인 안 함: 실제 차이를 잰 적이 없다. A-08(NotSent면 한 바이트도 나가지 않았다) 문서로만: HTTP 라이브러리의 소스를 읽은 판단이다. A-13(조회 응답이 보낸 시각보다 오래된 상태를 주지 않는다) 테스트넷 확인 안 함. 서명 실패의 NotSent는 시험으로 일으키지 못했다(코드로만 본다). 5~10(조회로 결과 불명을 닫기, 재시작)은 가짜 거래소와 가짜 Bybit에 붙인 노드 프로세스로만 시험했다. 노드를 테스트넷에 붙여 돌리지 않았다.

## 2. OMS 프로세스가 죽는다
1. 입력 하나(새 주문, 체결, 취소, 운영 명령)는 이 순서를 지난다: 코어가 판단해 자기 메모리 상태를 바꾼다 → 기록을 저널에 쓴다 → fdatasync 성공(이 순간이 확정이다) → 읽기 모델(조회 API와 대시보드가 보는 상태)에 적용 → 전략에 응답 → 게이트웨이에 전송 명령 → 거래소로 전송.
2. 확정 전에는 밖으로 아무것도 나가지 않는다. 코어의 메모리 상태만 확정보다 앞서 있고, 죽으면 그 몫은 사라진다.
3. 코어는 한 번에 입력 256개까지 판단한다. 기다리는 배치를 합쳐 fdatasync 한 번에 입력 4096개까지 묶는다. 시간 제한은 없다. 디스크가 느리면 뒤가 기다린다.
4. 죽은 지점별 결과(SIGKILL 수준):
   - 쓰기 전: 요청이 없었던 것이 된다.
   - 쓴 뒤 fdatasync 전: 기록이 디스크에 남았을 수도, 잘렸을 수도 있다. 남았으면 주문은 있고 보낸 적이 없다. 잘렸으면 주문이 없다.
   - fdatasync 뒤, 거래소 전송 전: 주문은 있고 보낸 적이 없다. 재시작 뒤 Unknown이 되고 1절의 조회로 NotPlaced로 닫힌다.
   - 전송 중이나 전송 뒤, 결과 기록 전: Unknown. 조회로 찾으면 정상 주문, 못 찾으면 NotPlaced.
   - 어느 경우든 전략이 같은 키로 다시 보내면 기록이 있을 때 duplicate로 답하고 주문은 하나다.
5. fdatasync가 오류를 내면(프로세스는 살아 있음) 그 배치의 응답과 전송은 하나도 나가지 않는다. 입력을 닫고 종료 코드 2로 멈춘다. 다시 시도하지 않는다. 열린 주문은 거래소에 남는다.
6. 재시작: 가장 새 스냅샷(어느 순번까지의 상태 사본)부터 검사한다(길이, 체크섬, 스키마, 인스턴스, 상태 다이제스트). 통과한 첫 것을 쓰고 그 뒤 저널을 기록마다 체크섬과 순번을 확인하며 다시 적용한다. 스냅샷이 모두 무효면 저널을 처음부터 재생한다. 복구는 거래소에 아무것도 보내지 않는다.
7. 덜 쓰인 끝(잘린 꼬리)은 원본을 torn/에 보존한 뒤 잘라내고 시작한다. 그 밖의 손상은 10절이다.
8. 복구 직후: 링크를 내려간 상태로 두어 새 주문을 막고(3절의 다시 읽기가 끝나야 풀린다), 결과 없는 전송은 Unknown, 진행 중이던 취소는 잃은 것으로 적고 링크가 오면 다시 보낸다. 새 주문은 다시 보내지 않고 전략에 응답도 다시 하지 않는다.
9. 스냅샷: 마지막 스냅샷 뒤 기록이 5만 건을 넘을 때, 운영자 요청, 정상 종료 때 쓴다. 별도 스레드가 임시 파일 → fsync → 이름 바꾸기 → 디렉터리 fsync로 쓴다. 실패해도 거래는 계속한다. 스냅샷은 지름길일 뿐이다.
10. 정상 종료(SIGTERM, SIGINT)는 큐에 있던 입력까지 내구화하고 마지막 스냅샷을 쓴다. 열린 주문은 거래소에 남는다.
11. 관측 쪽(ADR-037, 설치하지 않음): OMS 자신은 지표를 넣지 않는다. 프로젝터가 상태 API에 묻고 `oms_up`을 넣으며, 30초 동안 답이 없으면 `OmsDown`(P1)이다. 워처의 W5(10초)가 먼저 킬한다. 저널의 마지막 상태(`oms_holds`)는 OMS가 꺼진 동안에도 남으므로, 래치 보류는 그대로 P1이고 스스로 풀리는 보류와 `unmonitored`는 OMS가 살아 있을 때만 알린다. 프로젝터가 죽으면 스택은 OMS가 살았는지 모른다(`ProjectorDown` P2만): 그때는 OMS와 워처의 직접 알림이 길이다.
- 시험: V-COMMIT-1, V-COMMIT-2, V-COMMIT-4, V-COMMIT-5, V-BOOT-1, V-BOOT-2, V-JRN-4, V-REPLAY-1
- 가정과 상태: A-05(fdatasync 성공 = 장치에 남음) 확인 방법 없음: 강제 종료 시험은 이것을 검증하지 않고 전원 장애는 시험하지 않았다. A-06(같은 저널로 도는 프로세스는 하나) 같은 호스트만 시험했다. 다른 호스트는 확인 방법 없음(운영 절차). A-12(과거 시점의 사본으로 거래를 재개하지 않는다) 확인 방법 없음(운영 절차). A-11(표준 라이브러리와 tokio의 채널) 문서로만. 강제 종료 시험은 가상 거래소(simvenue)에 붙인 실제 프로세스로 했다. Bybit 게이트웨이로는 가짜 Bybit에서 flush 실패 뒤 재시작 하나만 시험했다. 11의 규칙은 배치 검사(`crates/xtask/tests/deploy`)와 이 PC의 `vmalert-tool unittest`로만 확인했고 설치하지 않았다.

## 3. 거래소 연결이 끊긴다
비공개 스트림: 우리 계좌의 주문 통보와 실행(체결 등) 통보가 오는 Bybit 웹소켓. 링크: OMS가 보는 그 스트림의 상태.
1. 게이트웨이는 5초(ping_interval)마다 ping을 보낸다. ping 뒤 5초 안에 pong이 없거나, 소켓이 닫히거나, 읽을 수 없는 메시지가 오면 끊김이다. 코어 입력 큐를 기다린 시간은 빼고 잰다.
2. 끊기면 링크를 내린다. 그때부터 새 주문은 모두 거절한다(감소 전용 포함). 응답을 기다리던 전송은 각각 Unknown이 된다(1절).
3. 취소 요청은 받아서 기록하고, 링크가 돌아오면 보낸다.
4. 다시 붙기: 0.5초부터 두 배씩 10초까지 기다린 뒤 접속한다. 접속, 인증, 구독은 10초 안에 끝나야 한다. 인증 메시지는 키 파일의 HMAC 비밀(hex)이나 RSA 키(base64)로 서명하고, 서명을 만들지 못하면 인증을 보내지 않고 다시 붙는다. 인증이 거부되면(키 거부) 재시작까지 다시 붙지 않는다. HTTP 403(IP 차단)이면 600초 동안 모든 요청과 접속을 멈춘다.
5. 구독이 확인되면 더 큰 세션 번호로 링크를 올린다. 새 주문은 아직 막혀 있다(재확인 대기).
6. 다시 읽기(REST): 이번 세션에서 아래 넷이 모두 끝나야 새 주문을 다시 받는다.
   - 열린 주문 하나하나의 상태(주문별 조회 또는 열린 주문 목록에 있음).
   - 체결: 마지막으로 맞춘 시각 − 2분부터 지금 − 2초(fills_lag)까지, 7일 이하의 창으로 실행 목록의 모든 쪽을 읽는다. 다 읽은 뒤에만 "여기까지 다 받았다"고 선언한다.
   - 열린 주문 목록 전체(우리가 모르는 주문이 없는지).
   - 포지션: 장부 포지션 q에 대해 q − 매도 예약 ≤ 거래소 포지션 ≤ q + 매수 예약 인지. 조회를 보낸 뒤 체결을 기장했으면 판정을 다음 회차로 미룬다.
7. 그 뒤로도 열린 주문 목록, 체결, 포지션은 15초마다 다시 훑는다.
8. 어긋나면 불일치로 올리고 운영자가 확인(ack)할 때까지 새 일반 주문을 막는다.
9. 킬 트리거: 마지막 생존 증거(구독 확인, pong, 시작 확인의 첫 통과) 뒤 10초(kill_after_ms)가 넘도록 링크가 내려가 있으면 끊김 하나에 한 번 킬을 건다(6절). 250ms마다 본다. 끊김을 알아챈 때가 아니라 마지막 pong에서 잰다. 시작 확인을 통과하기 전에는 걸지 않는다. ping에 답하는 조용한 스트림은 킬하지 않는다.
10. 한계: 구독은 되지만 pong에 답하지 않는 연결이 되풀이되면, 올라갈 때마다 증거가 새로 정해져 킬이 늦거나 걸리지 않을 수 있다.
- 시험: V-LINK-1, V-RECON-1, V-RECON-2, V-BYBIT-STREAM-1, V-BYBIT-READ-1, V-KILL-1, V-BYBIT-RSA-1
- 가정과 상태: A-03(체결 동기화를 선언하면 그 시각까지의 체결을 모두 전달했다) 테스트넷 확인 안 함: Bybit 실행 목록의 쪽 규칙(빈 커서의 뜻)은 문서에도 없다. A-13 테스트넷 확인 안 함. 재연결 뒤 놓친 메시지를 Bybit가 다시 주는지도 확인하지 않았다(그래서 REST로 다시 읽는다). RSA 서명의 비공개 스트림 인증은 저장소 밖의 테스트넷 측정 한 번으로만 안다. WS Trade의 RSA 인증은 보내 본 적이 없다. 1~10의 Bybit 부분은 가짜 Bybit 스트림과 가짜 HTTP 서버로만, 6~8의 대조는 가상 거래소로만 시험했다.

## 4. 전략 프로세스가 죽거나 조용해진다
전략: OMS 거래 소켓에 붙어 주문을 내는 별도 프로세스.
1. 감시하는 전략은 설정 `[liveness]`에 적힌 전략뿐이다. 전략마다 시간 liveness_ms를 적는다(1~60초, 기본값 없음, 설계의 예는 5초). mainnet은 사용 중인 전략이 모두 적혀 있어야 시작한다.
2. 생존 증거: 그 전략으로 hello한 연결에서 읽어 해석한 요청 줄 하나하나다. ping도 요청이다. 전략은 liveness_ms보다 짧은 간격으로 ping해야 한다.
3. 잃음: 그 전략의 마지막 거래 연결이 닫히면 곧바로, 어느 연결에서도 liveness_ms 넘게 요청이 없으면 250ms 타이머가 잡는다(늦어도 liveness_ms + 250ms + 큐 대기).
4. 잃으면 한 기록에서:
   - 그 전략의 일반 주문을 거절하는 보류를 건다(감소 전용은 받는다. 증거금 정책이 없으면 감소 전용도 거절).
   - 그 전략의 걸린 일반 주문마다 취소를 요청한다. 감소 전용 주문과 다른 전략의 주문은 건드리지 않는다. 결과 불명 주문은 접수가 확인되면 취소가 나간다.
5. 취소는 요청이지 확인이 아니다. 1초 간격으로 5번까지 시도하고, 그래도 확인이 없으면 불일치(취소 막힘)로 운영자에게 넘긴다.
6. 복구: 그 전략이 다시 hello하면 보류가 풀린다. hello의 답은 풀림이 내구화된 뒤에 간다. 운영자 clear-hold로는 풀지 않는다.
7. 재시작: 보류는 저널에서 돌아온다. 걸린 일반 주문이 있는 적힌 전략은 시작부터 감시한다. 그 시간 안에 다시 붙지 않으면 그 주문을 취소한다.
8. 노드 자신이 멈춰(코어나 저널이 막혀) 줄을 읽지 못한 시간도 침묵으로 친다. 멈춤이 liveness_ms보다 길면 ping하던 전략도 잃음이 된다(안전한 쪽).
9. 적히지 않은 전략은 죽어도 주문이 거래소에 남는다(testnet과 가상 거래소에서만 가능).
- 시험: V-LIVE-1, V-LIVE-2, V-LIVE-3, V-CANCEL-1
- 가정과 상태: registry의 가정 가운데 이 절이 기대는 것은 없다. 감시는 단조 시계로 잰다. 가상 거래소(simvenue)에 붙인 실제 oms-node 프로세스와 코어 시험으로만 시험했다. Bybit 게이트웨이로는 시험하지 않았다.

## 5. 거래소가 스스로 포지션을 바꾼다
ADL(자동 감축): 반대편 청산을 메우려고 거래소가 이익 난 포지션을 강제로 줄이는 것. 미귀속 장부: 어느 전략의 것도 아닌 포지션을 적는 장부.
1. Bybit는 우리 주문의 체결과 같은 흐름(실행 스트림, 실행 목록)으로 거래소가 만든 실행도 보낸다. 게이트웨이가 실행 종류(execType)로 나눈다. 스트림과 조회가 같은 분류표를 쓴다.
2. Trade이고 orderLinkId가 우리 것: 우리 체결이다. Trade이고 우리 것이 아님: 외부 체결이다. 계좌와 미귀속 장부에 기장하고 불일치로 올린다(종목마다 한 건).
3. Funding(펀딩): 현금으로만 적는다. 포지션, 주문, 예약은 그대로다. 막지 않는다.
4. AdlTrade, BustTrade, Delivery, Settle: 거래소 포지션 변경이다. 이 저장소는 넷을 ADL, 청산 포지션 인수, 인도, 정산으로 부른다. 부호 있는 수량을 계좌와 미귀속 장부에 더하고, 불일치로 올리고, 거래소 변경 보류를 건다.
5. 분류표에 없는 실행 종류: 기장하지 않는다. 불일치로 올리고 같은 보류를 건다.
6. 보류와 불일치는 새 일반 주문을 막는다. 감소 전용은 지나간다(증거금 정책이 있을 때).
7. 맞춤: 그 종목은 "거래소 포지션 대기"가 된다. 변경을 적은 뒤에 보낸 이번 세션의 포지션 조회 가운데, 그 종목에 열린 수량과 주인을 기다리는 체결이 없을 때의 첫 응답으로 장부를 맞춘다. 다르면 미귀속 장부에 조정을 적고, 같으면 맞음을 적는다. 그 전에는 3절의 범위 검사를 받는다.
8. 풀기: 운영자가 불일치 확인(ack)과 clear-hold --reason venue_change를 둘 다 해야 한다. 대기가 끝나지 않았으면 clear-hold를 거절한다.
9. 같은 실행이 스트림과 REST로 두 번 와도 키(<symbol>:<execId>)로 한 번만 적는다.
10. 저널만 읽어도 포지션 = 체결 + 외부 체결 + 거래소 변경 + 조정의 합이다. 워처의 W2가 이 식을 쓴다(9절).
11. 거래소는 우리 주문도 스스로 끝낼 수 있다. 같은 계좌의 두 주문이 서로 반대로 만나면 Bybit는 걸려 있던 주문을 취소한다(cancelType CancelBySmp, 체결 없음). 그래서 한 전략의 주문이 다른 전략의 주문 때문에 취소될 수 있다. OMS에는 전략 사이의 자기 체결 검사가 없다(요구 R10, 정책 미정).
- 시험: V-VENUE-EXEC-1, V-HOLD-5, V-HOLD-1, V-EXT-1, V-MIS-1, V-BYBIT-READ-1, V-BYBIT-LIVE-4, V-BYBIT-LIVE-5
- 가정과 상태: A-04(계좌에 OMS가 내지 않은 주문과 포지션 변화가 없다)는 이 절에서 깨지는 가정이다. 깨짐을 잡는 것은 시뮬레이션으로만 시험했다. A-13 테스트넷 확인 안 함: 7의 맞춤은 포지션 응답이 변경을 이미 반영했다고 본다. 우리 체결(Trade) 행의 번역은 테스트넷의 실제 행으로 확인함(V-BYBIT-LIVE-4). ADL, BustTrade, 펀딩 행이 실제로 어떤 모양으로 오는지, 우리 포지션의 청산이 BustTrade로 오는지는 테스트넷 확인 안 함(만들 수 없다). 11은 테스트넷에서 이 계좌의 기본 설정으로 본 것이다(V-BYBIT-LIVE-5).

## 6. 킬
킬: 모든 새 주문을 막고 거래소의 미체결 주문이 0건이 될 때까지 일괄 취소를 되풀이하는 비상 정지. 래치: 한 번 걸리면 운영자만 푸는 상태.
1. 킬을 거는 것은 셋이다: Bybit 비공개 스트림 끊김 10초(3절의 9), admin.sock(운영 소켓)으로 온 watcher_kill, 시작할 때 킬 마커 파일이 있음(파일을 읽을 수 없어도 건다). 운영자용 킬 명령은 없다. 운영자가 킬하려면 마커 파일을 만들고 OMS를 다시 시작한다. mainnet은 마커 설정 없이 시작하지 않는다.
2. 래치가 내구화된 뒤에만 게이트웨이에 킬 명령이 간다. 걸려 있는 동안 새 주문은 감소 전용을 포함해 모두 거절한다. 취소는 받는다.
3. 게이트웨이는 킬 명령을 받는 즉시 새 주문 전송을 끈다. 래치 전에 이미 큐에 있던 주문도 NotSent가 된다.
4. 회차: 1초(kill_round_ms)마다 일괄 취소(linear, USDT 전체. OMS가 내지 않은 주문도) 하나를 보내고, 곧바로 실시간 조회로 열린 주문(New, PartiallyFilled, Untriggered)을 센다. 일괄 취소는 따로 둔 예산으로 어느 1초에도 2개를 넘지 않는다. 회차 수에는 상한이 없다.
5. 셈이 실패하면(5xx, 읽을 수 없는 행, 1,000건 넘음) 0으로 보지 않고 다음 회차를 돈다.
6. 첫 0 뒤 30초(kill_watch_ms) 동안 5초마다 다시 센다. 늦게 나타난 주문이 있으면 곧바로 회차로 돌아간다. 30초 동안 모두 0이면 "확인됨"으로 끝난다. 30초면 되는 이유: 래치 전에 나간 주문은 요청 시각 + 6초(recv_window + 1초) 안에 처리되거나 버려진다.
7. 알림(텔레그램 P1): 시작, 남은 수가 바뀔 때, 60초마다, 끝. 알림마다 포지션(크기, 미실현 손익, 마크 가격, 청산가까지의 거리)이 붙는다. 킬은 포지션을 닫지 않는다. 사람이 닫는다.
8. 해제는 omsctl clear-hold --reason kill --note 하나뿐이다. 거절 조건: 래치가 없음, 메모가 없음, 이 프로세스의 루프가 0건을 확인하지 않음, 코어 장부에 열린 주문이 남음(먼저 omsctl cancel-all). 강제 해제는 없다.
9. 해제가 내구화되면 루프를 멈추고 새 주문 전송을 다시 열고, 그다음 마커 파일을 지운다. 지우기 전에 죽으면 다음 시작이 다시 래치를 건다(안전한 쪽).
10. 재시작: 래치는 저널에 남는다. 시작할 때마다 확인을 지우고 루프를 다시 돈다. 확인 뒤 새 계기(스트림 끊김, watcher_kill)가 오면 확인을 지우고 새 루프를 돈다.
11. 끝나지 못하는 경우: 키 거부(키를 폐기하고 새 키로 다시 시작해야 한다), IP 차단 중(요청이 나가지 않아 회차가 계속 실패한다).
12. 워처 자신의 킬(W5): 워처는 OMS 상태 API에 1초마다 묻고, 10초 동안 정상 답이 없고 그 사이 실패한 물음이 하나라도 있으면 한 번 킬한다. 순서: 킬 마커 쓰기(2초 한도) → admin.sock으로 watcher_kill → 그것이 래치하지 못했을 때만 systemctl stop으로 OMS 단위 멈춤 → 그 뒤에야 워처 자신의 키로 1초마다 일괄 취소해 미체결 0건을 확인하고 30초 지켜본다. OMS의 루프와 같은 계정에서 함께 돌면 둘을 합쳐 초당 2개 이하다(Bybit 한도는 초당 10). 킬 동안 워처의 검사와 하트비트는 쉰다.
13. 빚진 정지: 래치도, OMS가 읽는 경로를 확인한 마커와 함께 멈춤도 확인하지 못한 킬은 정지를 빚진다. 빚이 있는 동안 루프에서 5초마다 watcher_kill을 다시 보내고, 루프 뒤에는 OMS가 다시 정상으로 답할 때 하나를 보낸다. watcher_kill 연결은 둘이 함께 열리지 않는다. 래치하면 알리고 다시 지킨다. 실패하면 한 번 알리고 다음 정상 답에 다시 보낸다.
14. 킬이 끝나는 다른 길: 워처가 킬 중에 종료되면(SIGTERM) 중단 알림 하나로 끝낸다. 마커와 systemctl은 그대로 둔다. OMS가 다른 킬 마커 경로를 읽는다고 답하면 워처는 시작을 거부하고 종료 코드 2로 꺼지는데, 정지를 빚졌으면 그 전에 watcher_kill 하나를 보내고 결과를 거부 알림에 적는다. 빚과 킬의 진행은 메모리에만 있어 워처를 다시 시작하면 잊는다. 다시 뜬 워처는 OMS가 그때도 답하지 않으면 다시 킬한다.
15. 서비스 단위(파일만 있고 설치하지 않았다, ADR-036): OMS 단위는 다시 띄우지 않고(`Restart=no`) 부팅 때 시작하지 않는다. 킬이나 충돌 뒤의 시작은 늘 사람이다. 워처 단위는 부팅 때 시작하고 실패하면 5초 뒤 다시 뜬다(종료 코드 2는 제외). 그래서 저널이 마운트된 재부팅 뒤에는 워처가 꺼진 OMS를 킬한다: 마커를 쓰고, 꺼진 단위를 멈추고, 자기 키로 남은 주문을 일괄 취소한다. OMS가 이 프로세스에서 답한 적이 없어 마커 경로를 확인하지 못했으므로 정지를 빚고(13), 사람이 OMS를 띄워 첫 답이 오면 `watcher_kill`로 래치한다. 저널이 마운트되지 않았으면 워처도 OMS도 시작하지 않는다(마운트 확인): 그때는 킬도 일괄 취소도 없다. K3의 `systemctl stop`은 polkit 규칙 하나가 `oms-node.service`의 `stop`만 허락한다. 킬 마커는 재부팅 뒤에도 남는 `/var/lib/hl-oms`에 있다.
- 시험: V-KILL-2, V-KILL-3, V-KILL-4, V-KILL-5, V-HOLD-2, V-HOLD-3, V-HOLD-4, V-WATCH-12, V-WATCH-13, V-BYBIT-LIVE-3
- 가정과 상태: A-05 확인 방법 없음: 래치가 전원 장애 뒤에도 남는다는 것. A-13 테스트넷 확인 안 함: 0건 셈이 최신 상태라는 것. 일괄 취소가 걸린 주문을 모두 취소하고 열린 주문 수가 0이 되는 것은 테스트넷에서 확인함(V-BYBIT-LIVE-3). 일괄 취소의 초당 한도는 Bybit 문서로만 안다. 루프 전체(래치, 회차, 30초 지켜보기, 알림)는 가짜 Bybit(loopback), 수동 시계, 가짜 텔레그램으로만 시험했고 테스트넷에 붙여 돌리지 않았다. 12~14는 loopback 가짜(Bybit, 상태 API), 시험의 admin.sock, 가짜 systemctl 스크립트로만 시험했다. 진짜 OMS를 멈춘 적이 없다. 15의 단위와 polkit 규칙은 배치 검사(`crates/xtask/tests/deploy`)와 `systemd-analyze verify`로만 확인했고 설치하지 않았다. 설치 전에는 systemctl stop의 권한이 없어 그 단계는 실패하고 정지를 빚진다. A-22(systemd가 polkit에 단위 이름과 동작을 넘김) 확인 안 함: 틀리면 설치 뒤에도 K3가 실패한다. A-23(읽기 전용 바인드 위의 소켓에 연결됨) 이 PC에서 bwrap으로만 확인. A-24(`LimitCORE=0`이면 코어 덤프가 디스크에 남지 않음) 이 PC의 apport 소스로만 확인: 틀리면 OMS·워처의 abort가 API 비밀이 든 메모리를 디스크에 쓴다.

## 7. 증거금이 위험해진다
감소 전용 상태: 계좌가 포지션을 줄이는 주문만 받는 상태. 계좌 가치: Bybit 통합 계좌의 totalEquity.
1. 규칙은 증거금 정책이 있을 때만 돈다. Bybit 설정은 교차 증거금(계좌 모드 REGULAR_MARGIN)만 받고, 계좌 유지증거금률 한도를 반드시 적어야 한다(기본 판단 50%).
2. 5초마다 증거금 보고를 읽는다: 지갑(계좌 가치, 유지증거금 totalMaintenanceMargin, 증거금 잔고 totalMarginBalance), 계좌 정보, 포지션 목록.
3. 신선도: 보고의 나이(지금 − 조회 시각)가 30초 이하면 신선하다. 신선한 보고가 없으면 새 일반 주문을 거절한다. 노출이 있는 종목의 참조 가격(마크 가격)이 15초보다 오래돼도 거절한다. 감소 전용은 둘 다 면제된다.
4. 레버리지: 종목마다 노출 = max(롱 쪽, 숏 쪽)이고 걸린 주문의 예약을 max(지정가, 마크)로 더한다. 받은 뒤 계좌 노출이 2.0 × 계좌 가치를 넘고 받기 전보다 커지면 거절한다. 정확히 같으면 받는다. 받을 때만 본다. 가격이 움직여 넘어도 취소하지 않는다.
5. 일 손실: UTC 날마다 첫 보고의 계좌 가치가 기준이다. 기준보다 5% 넘게 줄면(100에서 94.99) 감소 전용 상태로 들어간다. 수수료, 펀딩, 출금도 손실로 읽힌다.
6. 계좌 유지증거금률: 유지증거금 ≥ 50% × 증거금 잔고 이면 감소 전용 상태로 들어간다(Bybit는 100%에서 청산한다). 격리 포지션용 유지증거금 여유 규칙은 교차 계좌라 Bybit에서는 걸리지 않는다.
7. 들어갈 때 같은 기록에서 감소 전용이 아닌 모든 열린 주문에 취소를 요청한다. 그 뒤 일반 주문은 거절하고 감소 전용만 받는다. OMS는 포지션을 닫지 않는다. 상태는 계좌에 하나이고 새 날, 재시작, 회복으로 풀리지 않는다.
8. 해제: omsctl clear-reduce --note. 보고가 신선해야 하고, 유지증거금률 조건이 지금도 참이면 거절한다. 강제 해제는 없다. 해제하면 지금의 계좌 가치가 새 기준이 된다.
9. 보고 끊김: 링크가 올라와 있는데 마지막 보고의 조회 시각(또는 링크가 올라온 시각)에서 60초가 넘으면, 감소 전용이 아닌 열린 주문마다 취소를 한 번 요청한다. 래치는 없다. 새 보고가 오면 끝나고 일반 주문을 다시 받는다.
10. 계좌 모드를 이번 링크 세션에서 아직 읽지 못했거나 REGULAR_MARGIN이 아니면 계좌의 일반 주문을 막는다. 종목의 거래소 레버리지가 설정(기본 2)과 다르거나 아직 모르면 그 종목의 일반 주문을 막는다. OMS는 거래소 설정을 바꾸지 않는다.
- 시험: V-MARGIN-1, V-MARGIN-3, V-MARGIN-4, V-MARGIN-5, V-MARGIN-6, V-MARGIN-7, V-MARGIN-9, V-MARGIN-13
- 가정과 상태: A-13 테스트넷 확인 안 함(보고가 조회 시각보다 오래된 상태가 아니라는 것). 그 밖의 가정은 registry에 없고 T1~T11(ADR-018 §8, docs/verification/README.md §11)에 있다. 모두 테스트넷 확인 안 함이고, totalMaintenanceMargin이 Bybit의 청산 판정과 같은 숫자라는 것은 문서로만 안다. 50%는 판단이다. 규칙은 가상 거래소와 시뮬레이션으로만 시험했고, 증거금 조회(지갑, 계좌, 포지션)는 테스트넷의 실제 응답으로 읽히는 것을 확인함(V-BYBIT-LIVE-6). 손실이나 유지증거금률이 문턱을 넘는 경우는 테스트넷에서 만들지 않았다.

## 8. 요청이 몰린다
1. 전략마다 입구 빈도 한도: 새 주문 초당 50(순간 100), 취소 초당 200(순간 400). 넘으면 곧바로 overloaded로 답하고 아무것도 기록하지 않는다. 같은 키로 다시 보내면 된다. 운영자 취소는 이 한도를 받지 않는다.
2. 입력 큐: 주문 1024, 제어(취소, 운영 명령) 256. 가득 차면 곧바로 overloaded. 두 큐는 서로 영향을 주지 않고 배치마다 둘 다 몫을 받는다. 거래소 입력 큐(4096)는 거절하지 않고 게이트웨이가 기다린다.
3. 코어 안의 상한: 열린 주문 500, 거래소 증거 전의 진행 중 전송 64, 메모리의 주문 100,000. 넘으면 그 이유로 거절한다.
4. Bybit 요청 한도: 주문과 취소가 1초 창 하나를 WS Trade와 REST를 합쳐 나눠 쓴다. 주문은 세는 요청이 8개 미만일 때, 취소는 10개 미만일 때 나간다. 그래서 주문이 8개를 다 써도 취소 2개는 바로 나간다.
5. 요청은 자리를 잡은 때부터 응답(또는 실패) + 1초까지 센다. 응답이 없으면 요청 시각 + recv_window + 1초 + 1초까지 센다(그때까지 거래소에 닿을 수 있다). 바이트가 나가지 않은 요청은 곧바로 빠진다. 조회는 세지 않는다.
6. 창이 차면 기다린다. 버리지 않는다. 기다린 뒤 막힘과 1절의 보내는 시각 규칙을 다시 본다. 오래 기다린 주문은 그 규칙에서 NotSent가 된다.
7. 취소는 어떤 차단(연결 끊김, 결과 불명, 불일치, 킬, 감소 전용)에서도 받는다. 그러나 취소도 1의 빈도 한도와 2의 제어 큐가 차면 overloaded로 거절된다.
8. 킬의 일괄 취소는 이 창과 따로 초당 2개 예산을 쓴다.
9. 압력의 방향: 디스크가 느려지면 커밋이 밀리고, 코어가 기다리고, 입력 큐가 차고, 새 주문이 거절된다. 거래소 입력 큐가 차면 게이트웨이가 소켓을 읽지 않고, 길어지면 거래소가 끊고, 3절의 다시 읽기가 빠진 것을 메운다.
10. HTTP 403이면 600초 동안 모든 요청을 멈춘다. retCode 10018(IP 요청 한도)은 거절이면서 같은 멈춤을 건다.
11. 저장 공간 부족은 10절이다.
- 시험: V-OVL-1, V-OVL-2, V-PERF-2, V-BYBIT-ORDERS-1, V-BYBIT-TRADE-1, V-CANCEL-1, V-NEW-1
- 가정과 상태: A-11(채널의 상한과 순서) 문서로만. WS Trade와 REST가 Bybit에서 같은 한도를 나눠 쓰는지는 테스트넷 확인 안 함. 같은 UID로 워처가 보내는 요청은 이 창에 세지 않는다. 입구와 큐는 가상 거래소에 붙인 실제 프로세스로, Bybit 한도는 가짜 Bybit와 시각 입력으로만 시험했다.

## 9. 워처가 차이를 찾는다
워처: OMS와 코드를 나누지 않는 별도 프로그램. 자기 Bybit 키로 거래소를 읽고, 자기 코드로 OMS 저널을 읽어 둘을 비교한다.
1. 한 라운드: 거래소 쪽을 먼저 다 읽고, OMS 상태 API에서 내구화된 순번을 받아 그 순번까지 저널을 읽고, 비교한다. OMS는 내구화 전에 아무것도 보내지 않으므로 거래소에 보이는 우리 주문은 그 저널에 이미 있다. OMS가 답하지 않으면 아무것도 판단하지 않는다.
2. W1 열린 주문(1초마다): 거래소에만 열린 주문, 저널에서 닫혔는데 거래소에 열린 주문, 종결 통보 뒤에도 열린 주문, 종목이나 방향이 다른 주문, 저널에서 접수됐고 열려 있는데 거래소에 없는 주문. 수량은 비교하지 않는다.
3. W2 포지션(1초마다): 종목마다 거래소 포지션 − 저널 포지션(5절의 10)이 0이 아니면 차이다.
4. W3 지갑(2초마다): 계좌 유지증거금률 ≥ 50%, 오늘 기준보다 5% 넘는 손실. 식은 OMS와 같고 한도는 워처 설정에 따로 있다.
5. W4 체결(5초마다): 실행 목록을 저널의 체결, 거래소 변경, 펀딩과 키로 맞춘다. 분류표에 없는 실행 종류는 곧바로 확정한다.
6. 두 라운드 규칙: 같은 차이(검사, 종류, 대상, 값)를 연달아 완료된 두 라운드에서 보고, 두 번째 라운드에서 그 차이의 나이가 2초 이상이면 확정한다. 나이는 저널의 그 기록 시각, 저널이 모르면 처음 본 시각에서 잰다. W2는 변경 시각이 2초 안이면 첫 라운드부터 미룬다. W3에는 나이 규칙이 없다. 실패한 라운드는 셈을 지우지 않는다. 값이 바뀌면 처음부터 센다.
7. 확정되면 admin.sock으로 watcher_mismatch를 보낸다. OMS는 보류를 내구화한 뒤 "held"로 답하고, 새 일반 주문을 거절한다(감소 전용은 받는다).
8. 워처는 "held"를 받을 때까지 그 차이를 빚으로 든다. 운영자가 clear-hold --reason watcher_mismatch로 풀었는데 차이가 남아 있으면 10초마다 다시 보내 보류가 돌아온다.
9. 하트비트 게이트(OMS 쪽): 워처는 5초마다 monitor.sock으로 W1~W4의 마지막 성공 시각을 보낸다. OMS는 기록 시각으로 판정한다. 하트비트가 30초 넘게 없거나, 마지막 하트비트에서 W1이나 W2의 성공이 10초 넘게 이전이면 "감시 안 됨"이 되어 새 일반 주문을 거절한다. 그 상태가 60초 더 가면 걸린 일반 주문마다 취소를 한 번 요청한다. 신선한 하트비트가 오면 풀린다. 판정은 250ms마다 한다. 두 실제 프로그램을 함께 돌린 합동 시험에서 끝에서 끝으로 쟀다(짧은 시간값: 하트비트 10초, 검사 5초, 취소 10초, 판정 50ms, 워처 하트비트 1초): 멈춘 워처는 마지막 하트비트 기록 뒤 약 10.0초에 관문을 닫고 그 기록 뒤 약 10.0초에 걸린 일반 주문을 한 번 취소하며, W1·W2가 실패하는 워처는 하트비트를 계속 보내 오래된 성공 시각 뒤 약 5.1초에 닫는다. 둘 다 워처가 돌아오면 다시 열린다.
10. 모든 시작은 "감시 안 됨"으로 시작한다. 워처가 시작 뒤 30초 안에 하트비트를 보내지 않으면 알림이 가고, 60초 안에 보내지 않으면 재시작 전의 걸린 일반 주문이 취소된다.
11. 워처의 킬은 6절의 12~14다. 실제 OMS 프로세스와 함께 상태가 있는 가짜 Bybit 하나에 붙여 돌린 것(합동 시험): 정상 수명 주기(배포 기본 시간값: 차이 없음, 첫 신선한 하트비트의 기록에서 게이트가 열림), 거래소에만 있는 주문과 체결(두 라운드와 2초 전에는 보류 없음, 그 뒤 보류, 새 일반 주문 거절, 취소는 감, 운영자의 해제로 거래 재개), 게이트 닫힘(9의 측정). 킬은 아직 두 실제 프로그램을 함께 돌려 보지 않았다. 워처는 실제 Bybit에 붙여 돌린 적이 없고, 서비스로 설치되어 있지 않다.
12. 관측 쪽(ADR-038, 설치하지 않음): 워처가 넣는 값이 1분 동안 없으면 `WatcherDown`(P1)이다: 그동안 대사도 킬도 없다. 확정된 차이, 도는 킬, 빚진 정지, 거절된 키는 워처 자신의 `[WATCH P1]`과 별도로 스택도 곧바로 P1으로 알린다. 키 만료 14일 전이면 P2다. OMS가 꺼진 동안(`OmsDown`) 검사 경과·하트비트·W5 무장 안 됨의 P2는 막는다: 셋 다 꺼진 OMS를 따라 나빠지기 때문이다. 재부팅 뒤 사람이 OMS를 띄울 때까지 빚진 정지의 P1이 30분마다 오는 것은 정상이다(6절 15). 사건 타임라인(D4)은 프로젝터가 넣은 저널 이벤트 줄을 보여 주고, 이벤트 종류마다 두 패널 중 하나에 있거나 뺀 목록에 있다.
- 시험: V-WATCH-5, V-WATCH-6, V-WATCH-7, V-WATCH-8, V-WATCH-9, V-GATE-1, V-GATE-2, V-HOLD-1, V-JOINT-1, V-JOINT-2, V-JOINT-6
- 가정과 상태: A-13 테스트넷 확인 안 함(워처의 거래소 읽기에도 같다). 하트비트의 시각은 같은 호스트의 시계라고 믿는다. 틀린 시각을 보내는 워처는 게이트를 열어 둘 수 있고, 이것은 확인 방법 없음. 워처 전체를 loopback 가짜(Bybit, 상태 API, 두 소켓)와 시험 저널로 시험했고, 실제 OMS 프로세스와는 합동 시험에서 정상 수명 주기(V-JOINT-1), 거래소에만 있는 주문과 체결(V-JOINT-2), 게이트 닫힘(V-JOINT-6)을 함께 돌렸다. 게이트는 시험의 클라이언트가 하트비트를 넣어, 그리고 합동 시험에서 짧은 시간값으로 시험했다(배포 기본값의 닫힘 시각은 재지 않았다). 12의 규칙과 화면은 배치 검사(`crates/xtask/tests/deploy`), 이 PC의 `vmalert-tool unittest`, loopback의 임시 Alertmanager·VictoriaLogs·Grafana로만 확인했고 설치하지 않았다. `WatcherDown`은 워처 `export_ms` ≤ 20 000에 기대고, 그 값은 아무것도 검사하지 않는다.

## 10. 저널이 손상되거나 디스크가 찬다
1. 저널은 64 MiB 세그먼트 파일들이다. 기록마다 CRC-32 체크섬과 순번이 붙는다.
2. 시작할 때 손상의 위치로 나눈다. 마지막 세그먼트 끝의 덜 쓰인 기록(뒤에 온전한 기록이 없음)은 잘린 꼬리다. 원본을 torn/에 보존 → fsync → 자르기 → fsync 뒤 시작한다. 이 순서라 어디서 죽어도 원본이 남는다.
3. 중간 손상(뒤에 온전한 기록이 있음), 순번 빈틈, 빠진 세그먼트, 다른 인스턴스의 저널, 읽을 수 없는 스키마, 스냅샷보다 짧은 저널이면 시작을 거부한다(종료 코드 3). 파일은 건드리지 않는다. 기록을 건너뛰지 않는다.
4. 손상된 스냅샷은 건너뛰고 더 오래된 스냅샷이나 저널 처음부터 복구한다. 시작을 거부하지 않는다.
5. 같은 데이터 디렉터리는 두 프로세스가 쓰지 못한다(디렉터리 잠금. 같은 호스트에서만 막는다).
6. oms-node verify는 잠금 없이 읽기만 하며 모든 체크섬과 순번, 기록마다의 불변조건을 검사한다.
7. 디스크 여유가 1 GiB보다 작으면(5초마다 잰다) 새 주문을 모두 거절한다(감소 전용 포함). 체결 기장, 취소, 대조, 운영 명령은 계속한다. 여유가 돌아오면 풀린다.
8. 쓰기나 fdatasync가 오류를 내면(디스크가 가득 찬 경우도 같은 길이다) 그 배치는 아무것도 내보내지 않고 프로세스가 종료 코드 2로 멈춘다. 다시 시도하지 않고, 메모리만으로 계속하지 않고, 저널 없이 취소를 보내지도 않는다. 열린 주문은 거래소에 남는다.
9. 다시 시작하면 마지막 내구 기록부터 복구하고, 그 뒤의 체결은 3절의 다시 읽기가 거래소에서 가져온다.
10. 전원 장애로 여러 쪽에 걸친 배치가 순서 없이 디스크에 닿으면 중간 손상으로 읽혀 시작을 거부할 수 있다. 그 기록들은 응답도 전송도 나간 적이 없으므로 지나치게 보수적인 쪽이다. 실제로 그런 모양이 생기는지는 모른다.
11. 7의 하한보다 먼저 알린다(ADR-037, 설치하지 않음): 프로젝터가 저널 파일 시스템의 여유를 10초마다 넣고, 지난 24시간의 속도로 7일 안에 차면 P2, 2일 안이면 P1이다(12시간 준비 시간 뒤). 그 값이 5분 동안 없으면 P2다. 프로젝터가 죽어 있으면 이 알림들은 없다(`ProjectorDown` P2만).
- 시험: V-JRN-1, V-JRN-2, V-JRN-3, V-JRN-4, V-JRN-5, V-OVL-3, V-COMMIT-1, V-BOOT-2
- 가정과 상태: A-05 확인 방법 없음. A-06 같은 호스트만 시험, 다른 호스트는 확인 방법 없음. A-12 확인 방법 없음(운영 절차로만 막는다). 손상은 파일을 조작해 흉내 냈고 실제 전원 장애가 남기는 모양이 아니다. 디스크를 실제로 채운 시험은 없고, 저장 공간 보고는 시험이 넣었다. 11의 규칙은 배치 검사(`crates/xtask/tests/deploy`)와 이 PC의 `vmalert-tool unittest`로만 확인했고 설치하지 않았다.
