# C-GW 게이트웨이 계약

게이트웨이는 OMS 안에서 거래소와 통신하는 부분이다. 구현마다 다른 것은 프로토콜이고, 아래 계약은 같다.
설계 근거: [ADR-005](../adr/ADR-005-unknown-outcome.md), [ADR-014](../adr/ADR-014-reconciliation.md), [ADR-017](../adr/ADR-017-hyperliquid-gateway.md), [ADR-021](../adr/ADR-021-venue-gateway-trait.md).
구현: `crates/oms-node/src/venue/mod.rs`(채널, `VenueGateway` trait, 구동기 `start`), `simnet.rs`(가상 거래소), `hyperliquid/`(Hyperliquid), `bybit/`(Bybit, 만드는 중).

## trait과 구동기

게이트웨이는 `VenueGateway`를 구현한다: `send_order`, `send_cancel`, `query`, `spawn_tasks`(스트림 등 상시 작업, 한 번), 상수 `QUERY_CONCURRENCY`.
`venue::start`가 상시 작업 → 명령 루프 → 조회 루프 순으로 시작한다. 명령과 조회는 하나씩 별도 작업으로 돌고, 동시에 도는 수는 명령 `max_concurrent`(진행 중 전송 상한 + 16), 조회 `QUERY_CONCURRENCY`(가상 거래소 8, Hyperliquid 4)로 묶인다. 넘치는 것은 기다리고 버리지 않는다(V-GW-SEAM-1).

## 채널

| 방향 | 채널 | 내용 | 상한 |
|---|---|---|---|
| 커밋 단계 → 게이트웨이 | `commands` | `SendOrder`, `SendCancel` | 진행 중 전송 상한 + 열린 주문 상한 + 64 |
| 대조기 → 게이트웨이 | `queries` | 상태, 체결, 열린 주문, 포지션 조회 | 256 |
| 게이트웨이 → 코어 | venue 입력 큐 | `VenueInput` | 4096. 가득 차면 게이트웨이가 기다린다 |

## 게이트웨이가 지켜야 하는 것

| ID | 의무 | 어기면 |
|---|---|---|
| G-1 | `SendOrder` 하나에 `SendResult` 하나를 반드시 돌려준다(프로세스가 살아 있는 한) | 주문이 30초 뒤 결과 불명이 된다(코어의 안전망) |
| G-2 | 결과를 보수적으로 분류한다. `NotSent`는 요청의 어떤 바이트도 호스트를 떠나지 않았음이 확실할 때만. `Rejected`는 거래소의 명시적 거부일 때만. 그 밖은 `Unknown` | `NotSent`를 잘못 쓰면 예약 없이 주문이 놓인다. 가장 위험한 위반 |
| G-3 | 주문 요청을 스스로 다시 보내지 않는다. 라이브러리가 대신 다시 보내는 경로(리디렉션 따라가기)도 끈다 | 중복 주문 |
| G-4 | 전송에 `expires_at`을 거래소의 만료 필드로 싣는다. 이미 지났으면 보내지 않고 `NotSent` | 부재 판정의 전제(A-01)가 무너진다 |
| G-5 | `SendCancel` 하나에 `CancelResult` 하나 | 30초 뒤 코어가 그 시도를 결과 불명으로 기록하고 다음 시도를 보낸다 |
| G-6 | 스트림이 붙으면 이전보다 큰 세션 번호로 `Link up`, 끊기면 `Link down` | 재확인이 일어나지 않는다 |
| G-7 | `FillsSynced { up_to }`는 `up_to` 이하의 체결을 모두 전달한 뒤에만, 그리고 `up_to`는 조회 평가 시각보다 엄격히 앞으로 | 체결을 빠뜨린 채 주문이 닫힌다 |
| G-8 | 체결 키는 같은 체결에 항상 같고 다른 체결과 겹치지 않는다 | 중복 기장 또는 누락 |
| G-9 | 거래소 입력을 버리지 않는다. 입력 큐가 차면 기다린다. 읽을 수 없는 주문·체결 통보를 만나면 조용히 넘기지 않고 스트림을 끊어 다시 붙는다(재확인이 조회로 메운다) | 체결 유실 |
| G-10 | `queried_at`은 조회를 보내기 직전의 로컬 시각이다 | 스냅샷 시점 판정이 틀어진다 |
| G-11 | 최종 누적 수량(`cum`)은 거래소가 신뢰할 수 있게 알려 줄 때만 채운다. 아니면 비운다 | 예약을 너무 일찍 푼다 |
| G-12 | 비밀정보(서명 키)를 입력·로그·저널에 싣지 않는다 | 키 노출 |
| G-13 | 문서에 없는 응답에서 결론을 내지 않는다. 주문 응답이면 `Unknown`, 상태 이름이면 전달하지 않고 오류로 남긴다 | 놓인 주문을 없다고 보거나 열린 주문을 닫는다 |

코어는 G-1, G-5, G-6의 위반을 시간 초과와 재확인으로 견딘다. G-2, G-3, G-7, G-8, G-13은 코어가 대신할 수 없다.

## 계약의 질문들

| 질문 | 답 |
|---|---|
| 중간에 멈추면 무엇이 남는가 | 게이트웨이에는 영속 상태가 없다. 진행 중이던 전송은 결과가 기록되지 않은 채 남고, 재시작한 코어가 결과 불명으로 표시한다. 아래 "게이트웨이의 중단 지점" |
| 같은 입력이 다시 오면 | 같은 명령이 두 번 오는 경로는 없다(코어가 주문당 한 번만 낸다). 조회는 몇 번이든 같은 뜻이다. 거래소가 같은 통보를 두 번 보내면 그대로 두 번 넘기고 코어가 중복을 거른다 |
| 순서가 바뀌면 | 게이트웨이는 순서를 고치지 않는다. 받은 대로 넘긴다. 순서 역전은 코어의 계약(C-FILL, C-TERM)이 다룬다 |
| 누가 언제 보는가 | 게이트웨이가 넘긴 입력은 코어가 처리해 내구화한 뒤에야 밖에서 보인다 |
| 외부 결과를 아는가 | 응답을 받은 것만 안다. 그 밖은 모른다고 보고한다(G-2, G-13) |
| 복구 뒤 무엇을 다시 하는가 | 접속과 구독, 조회. 주문 전송은 다시 하지 않는다. 취소는 코어가 다시 명령하면 보낸다 |

## 게이트웨이의 중단 지점

`SendOrder`를 받은 뒤의 경계다.

| 중단 위치 | 거래소 | 코어가 받는 것 | 이후 |
|---|---|---|---|
| 명령을 꺼내기 전 | 없음 | 없음(프로세스 중단 시) | 재시작 → 결과 불명 → 만료 뒤 `NotPlaced` |
| 만료 확인에서 탈락 | 없음 | `NotSent` | 종결 |
| 접속 실패 | 없음 | `NotSent` | 종결 |
| 요청을 쓰는 중 오류 | 일부가 나갔을 수 있음 | `Unknown` | 결과 불명 → 조회 |
| 요청을 다 보낸 뒤 응답 대기 중 시간 초과 | 있을 수도 | `Unknown` | 결과 불명 → 조회 |
| 응답을 받음: 놓임 | 있음 | `Placed` | 접수 |
| 응답을 받음: 거부 | 없음 | `Rejected` | 종결 |
| 응답을 읽을 수 없음 | 모름 | `Unknown` | 결과 불명 → 조회 |
| 응답을 받고 코어에 넘기기 전 프로세스 중단 | 있음 | 없음 | 재시작 → 결과 불명 → 조회로 발견 |

## 구현별 대응

| 의무 | 가상 거래소 게이트웨이 | Hyperliquid 게이트웨이 |
|---|---|---|
| G-2 | 접속 실패만 `NotSent`. 쓰기 오류·시간 초과·읽을 수 없는 응답은 `Unknown` | 접속 단계 오류만 `NotSent`. HTTP 오류 상태·시간 초과·해석 불가·최상위 오류(`status: "err"`)는 `Unknown`. 주문별 `error` 문자열만 `Rejected`. 최상위 오류를 거부로 믿을지는 설정(`trust_top_level_error`, 기본 꺼짐)이다 |
| G-3 | 재시도 코드 없음 | 재시도 코드 없음. 리디렉션을 따라가지 않는다. `reqwest` 0.13의 기본 재시도는 서버가 처리하지 않았다고 프로토콜 수준에서 알린 요청에 한한다(가정 A-08) |
| G-4 | `expires_at` 필드 | `expiresAfter`(ms) |
| G-7 | 응답의 `venue_now − 1` | 조회 종료 시각을 과거(2초)로 잡고 그 직전을 `up_to`로. 받은 쪽이 500건보다 짧을 때만 마지막 쪽으로 본다. 새 체결이 1만 건에 이르거나, 가득 찬 쪽에 새 체결이 하나도 없으면 완료를 선언하지 않는다 |
| G-9 | 해당 없음(형식을 우리가 정했다) | 읽을 수 없는 `orderUpdates`·`userFills`, 구독 오류 통보, 15초 안에 확인되지 않은 구독은 스트림을 끊고 다시 붙는 사유다. perp 종목 목록에 없는 종목(spot 등)의 체결은 넘기지 않고 경고를 남긴다 |
| G-13 | 해당 없음 | 상태 이름은 문서의 표에 있는 것만 해석한다 |
| G-8 | `t<tid>` | `<time>:<coin>:<tid>:<oid>` |
| G-11 | 채움(가상 거래소는 정확하다) | 비움(`sz`의 의미가 문서에서 엇갈린다) |

### Bybit 게이트웨이(만드는 중, [ADR-028](../adr/ADR-028-bybit-gateway.md))

U17c까지 있는 것: 서명, REST 클라이언트, 시작 확인, IP 확인, cancel-all, 조회 일곱 가지(`query.rs`), 실행 분류표(`exec.rs`), 비공개 스트림(`stream.rs`), `VenueGateway` 구현과 노드 연결(`gateway.rs`, `node.venue = bybit:<network>`), 주문·취소(`orders.rs`, WS Trade 먼저 `trade.rs`, 아니면 REST)와 응답 분류표(`answer.rs`), 요청 한도(`oms-core::rate`), 참조 가격(`ticker.rs`, 공개 스트림의 mark price, U17c). 교차 계좌의 유지증거금 규칙은 U17d다.

| 의무·규칙 | Bybit 게이트웨이 |
|---|---|
| G-2(REST 응답 분류) | 접속 단계 오류만 "보내지 않음". retCode `10003, 10004, 10005, 10007, 10010, 33004`와 HTTP 401은 키 거부(`auth_rejected`). `10006`, HTTP 429는 요청 한도. HTTP 403은 IP 차단(`IpBanned`): 모든 요청을 10분 이상 멈춘다. `10002`는 시각 창 밖. `10016`, HTTP 5xx, 읽을 수 없는 본문, retCode 없는 본문은 응답 없음. 그 밖의 0 아닌 retCode는 그 코드로 거부. 조회에만 쓴다. 주문·취소는 아래 줄 |
| G-2(주문·취소 응답) | 접속 단계 오류(REST), WS Trade가 한 바이트도 쓰지 않았고 REST도 나가지 못함, 막힘, 보내는 시각 규칙 탈락, 거래하지 않는 종목(생성만)만 "보내지 않음". retCode 0 = 생성 `Placed { Open }`(접수만, `orderId`가 없으면 결과 불명), 취소 `Confirmed`. 오류 문서의 0 아닌 코드는 거부, 단 `10000, 10014, 10016, 10019, 10429, 429, 20006, 40004, 110030, 110072, 110079, 3400214`는 결과 불명. 문서에 없는 코드, 2xx가 아닌 HTTP 상태, 시간 초과, 읽을 수 없는 본문은 결과 불명. HTTP 403은 결과 불명이면서 IP 차단 멈춤, retCode 10018(IP 요청 한도)은 거부이면서 IP 차단 멈춤, HTTP 401과 키 거부 retCode는 키 거부도 건다([ADR-028 §7d](../adr/ADR-028-bybit-gateway.md)). WS Trade 응답은 같은 표로 분류한다(`classify(200, 본문)`). 10403(WS의 IP 한도)은 표대로의 결과(문서에 없는 코드라 결과 불명)이면서 IP 차단 멈춤, 10019(WS Trade 재시작)는 결과 불명이고 연결을 다시 연다. WS Trade에 쓴 요청이 `request_timeout_ms` 안에 응답이 없거나 그 사이 연결이 내려가면 결과 불명([§7e](../adr/ADR-028-bybit-gateway.md)) |
| 주문 경로(U17b) | 한도 자리, 막힘, 보내는 시각 규칙을 마친 요청은 WS Trade(`/v5/trade`, 인증된 연결이 있을 때)로 간다. REST로는 WS Trade 연결 작업이 "쓰지 않음"(연결 없음, 쓰기 전 막힘)을 돌려줄 때만, 막힘을 다시 보고, 같은 자리와 같은 요청 시각으로 간다. 쓰기를 시작한 요청은 어느 경로로도 다시 보내지 않는다. `reqId` = 생성 `c` + 고객 주문번호, 취소 `x` + 시도 번호(36진) + 고객 주문번호(36자 이하). 키 거부·IP 차단 응답은 연결 작업이 다음 쓰기 전에 효과를 건다. 늦은 응답은 결과를 기록하고 버리되 그 효과는 건다. WS Trade 연결은 비공개 스트림과 같은 규칙(IPv4, 막힘이 없을 때만, 업그레이드 403 = IP 차단, auth retCode 0이 아니면 키 거부, ping-pong, 기다림)을 따르고 `Link`를 움직이지 않는다 |
| 요청 한도 | 창 하나를 주문과 취소가, WS Trade와 REST가 나눠 쓴다(요청마다 자리 하나, 경로와 상관없이). 요청은 자리를 잡은 때부터 응답(또는 실패) + 1초까지 센다(거래소는 도착 시각으로 센다). 보낸 뒤 응답이 없으면 `요청 시각 + recv_window + 1초` + 1초까지 센다(그때까지 도착할 수 있다). 주문은 세는 요청이 8개 미만일 때, 취소는 10개 미만일 때 나간다. 아무 바이트도 나가지 않은 요청은 바로 빠진다. 차 있으면 기다린다(버리지 않는다). 기다린 뒤 막힘과 보내는 시각 규칙을 다시 본다. 조회는 세지 않는다 |
| G-3 | 재시도 코드 없음. 리디렉션을 따라가지 않는다. 키 거부는 프로세스가 다시 시작될 때까지 다시 시도하지 않는다 |
| G-12 | 키와 비밀은 데이터 디렉터리 밖의 소유자 전용 파일(0600, OMS 사용자 소유, 심볼릭 링크 아님)에서 한 번 열어 읽는다. `Debug`는 비밀을 찍지 않는다. 파일을 못 읽어도 오류 문장에 내용을 넣지 않는다 |
| 서명 | `hex(HMAC_SHA256(secret, timestamp + api_key + recv_window + payload))`. GET은 키 순서로 정렬한 질의 문자열, POST는 본문. 보내는 바이트와 서명한 바이트가 같다. 질의 값은 인코딩하지 않고 보내며, 뜻을 바꾸는 문자가 있으면 보내지 않는다 |
| 시작 확인(읽기만) | 키: 서브계정(`isMaster = false`), 설정의 `sub_account_uid`, 쓰기 가능, `ContractTrade`의 `Order`·`Position`, 바인딩된 IP가 있고 그중에 지금의 공인 IP. 계좌: `REGULAR_MARGIN`, 통합 계좌(`unifiedMarginStatus` 3–6). 종목마다: `settleCoin = USDT`, 단방향(`positionIdx = 0`), 설정의 `px_tick`·`qty_step`이 `tickSize`·`qtyStep`의 배수(U17a). 시계: 로컬이 거래소(`/v5/market/time`)보다 500ms 넘게 앞설 수 있으면 생성만 막힘(`clock`, 시작 확인 전과 IP 확인 주기마다, 막힌 동안은 10초마다, 왕복 250ms 넘는 측정은 판정 안 함, U17a). 하나라도 어긋나면 막힘(`Block`). 거래소 설정을 바꾸지 않는다 |
| IP 확인 | 시작할 때와 `ip_check_secs`(60초)마다 공인 IP(`ip_echo_url`, https)와 키의 IP를 비교한다. 다르면 키 거부와 같이 막고, 다시 시작할 때까지 풀지 않는다. IP 확인 통과는 시작 확인의 막힘을 풀지 않는다(막힘은 출처마다 따로). 확인 서비스와 Bybit 요청은 IPv4로만 나간다 |

Bybit 게이트웨이의 G-4(U17a, [ADR-024](../adr/ADR-024-absence-count-and-market-ref.md)): Bybit에는 만료 필드가 없고, 요청 시각(`X-BAPI-TIMESTAMP`) + `X-BAPI-RECV-WINDOW`가 서버 시각보다 이르면 요청을 거절한다. 게이트웨이는 요청 시각을 보내는 순간의 로컬 시각으로 하고(서명도 그 시각으로) `요청 시각 + recv_window + 1초 ≤ expires_at`일 때만 보낸다. 요청 한도를 기다렸으면 기다린 뒤에 잰다. 아니면 보내지 않고 `NotSent`. 1초는 Bybit가 받아 주는 요청 시각 앞섬의 한도다(`요청 시각 < 서버 시각 + 1000`). 이것이 만료 뒤 처리를 막으려면 로컬 시계가 거래소보다 크게 앞서지 않아야 하므로, 게이트웨이가 시계를 재서 500ms 넘게 앞설 수 있으면 생성을 막는다(취소와 스트림은 막지 않는다). 이 조건으로 거래소가 만료를 강제하므로 Bybit 설정은 `venue_enforces_expiry = true`, `absence_not_found_needed = 2`를 쓴다. 횟수는 조회 사본의 짧은 불일치만 막는다. realtime 조회는 닫힌 주문을 최근 500건까지만 들고 있고 서비스 재시작 때 비우므로, 게이트웨이는 realtime과 주문 내역(`/v5/order/history`) 모두에서 없을 때만 `StatusNotFound`를 보낸다(필수, U16c에 있음).

고객 주문번호의 형식은 게이트웨이 상수 `WIRE_ID`다([ADR-022](../adr/ADR-022-wire-id-form.md)). 가상 거래소와 Hyperliquid는 `Hex128`(`0x` + 32 hex). Bybit 게이트웨이는 `Base32Pair`(27자)를 쓰고, G-8 체결 키는 `<symbol>:<execId>`(69자 이하)로 정해 두었다. `execId`의 전역 유일성은 문서에 없어 종목을 앞에 붙인다.

## 검증

가상 거래소 게이트웨이: `e2e` 전체가 이 구현을 통과한다. 응답 유실(`drop_responses`), 요청 유실(`drop_requests`), 지연(`delay_ms`), 스트림 단절(`kick_streams`)을 가상 거래소에서 주입한다.
시뮬레이션의 게이트웨이 모델은 같은 계약의 결정적 판본이다.
Hyperliquid 게이트웨이의 검증 범위는 [verification](../verification/README.md)의 실제 거래소 절에 있다. 단위 시험: 응답과 상태 이름의 해석(`wire::tests`), 체결 쪽 판정(`a_fill_page_proves_completeness_only_when_it_is_certainly_the_last`).

확인하지 않은 것: Hyperliquid 게이트웨이의 스트림 재접속 사유들(읽을 수 없는 통보, 구독 오류, 구독 시간 초과), 예약 취소의 거부 처리, 리디렉션 차단. 코드만 있고 네트워크를 흉내 낸 시험이 없다.
