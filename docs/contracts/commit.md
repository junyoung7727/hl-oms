# C-COMMIT 기록·내구화·적용·응답·전송의 순서

설계 근거: [ADR-003](../adr/ADR-003-journal-record.md), [ADR-004](../adr/ADR-004-commit-gate.md).
구현: `crates/oms-node/src/pipeline.rs` (`core_loop`, `Committer::commit`).

## 순서

한 입력이 겪는 단계다. 번호가 경계다.

```text
① 입력 큐에 들어감                         (I/O 스레드)
② 코어가 꺼냄, 시각 부여
③ 판단: 이벤트 결정, 코어의 메모리 상태에 적용
④ 기록을 인코딩, 배치에 담아 커밋 단계로
⑤ write (페이지 캐시)                      (커밋 스레드)
⑥ fdatasync 성공  ← 확정 시점
⑦ 읽기 모델에 적용
⑧ 응답을 요청자에게
⑨ 전송 명령을 게이트웨이 큐에
⑩ 구독자에게 이벤트
⑪ 게이트웨이가 거래소로 전송              (I/O 스레드)
```

⑦~⑩은 ⑥이 성공한 뒤에만 실행된다. 코드에서 `writer.sync()`의 `Ok` 뒤에 놓여 있다.

## 단위 계약

| 항목 | 내용 |
|---|---|
| 입력과 전제 | 큐에서 꺼낸 `CoreMsg`. 전제 없음 |
| 읽는 상태 | 코어 스레드의 `Core`(판단). 커밋 단계는 상태를 읽지 않는다 |
| 상태 소유자 | `Core`는 코어 스레드, 저널과 읽기 모델은 커밋 스레드 |
| 변경 내용 | ③에서 코어의 메모리 상태, ⑥에서 저널, ⑦에서 읽기 모델 |
| 확정 시점 | ⑥. 그 전에 일어난 것은 장애 시 없었던 일이 된다 |
| 외부 효과 | ⑧ 응답, ⑨⑪ 거래소 전송, ⑩ 구독 이벤트. 모두 ⑥ 뒤 |
| 자원 상한 | 배치당 입력 256(설정). 커밋 채널 8배치. 한 번의 flush가 묶는 입력 4096 |

## 누가 언제 이 변경을 볼 수 있는가

| 관찰자 | 볼 수 있는 시점 |
|---|---|
| 같은 배치의 다음 입력 | ③ 직후(코어의 메모리 상태) |
| 조회 API, 대시보드, 대조기 | ⑦ 이후 |
| 요청한 전략 | ⑧ 이후. 이때 읽기 모델에는 이미 반영돼 있다 |
| 거래소 | ⑪ 이후 |
| 재시작한 프로세스 | ⑥ 이후의 것만 |

## 경계별 장애 결과

"프로세스 중단"은 SIGKILL 수준이다. 전원 장애는 가정 A-05에 기댄다.
마지막 열은 그 행을 겨냥한 시험이다. `crash_points`는 그 경계에서 프로세스를 `abort()`시키는 시험(주장 V-COMMIT-4), `e2e`는 실제 프로세스 시험이다.

| 중단 위치 | 저널 | 코어 메모리 | 응답 | 거래소 | 재시작 후 | 전략이 같은 요청을 다시 보내면 | 시험 |
|---|---|---|---|---|---|---|---|
| ① 이전 | 없음 | — | 없음(연결 오류) | 없음 | 요청 없음 | 새로 평가 | 없음(코드 경로가 없다) |
| ①~③ | 없음 | 반영 전 또는 후(소실) | 없음 | 없음 | 요청 없음 | 새로 평가 | 아래 행과 결과가 같다 |
| ④~⑤ (write 전) | 없음 | 반영(소실) | 없음 | 없음 | 요청 없음 | 새로 평가 | `crash_points::stopped_before_the_write_…` |
| ⑤~⑥ (write 후, flush 전) | 있을 수도, 꼬리가 잘릴 수도 | 반영(소실) | 없음 | 없음 | 기록이 온전하면 주문이 있고 전송 결과 불명으로 표시. 잘렸으면 버려진다 | 있으면 `duplicate`, 없으면 새로 평가. 어느 쪽이든 주문은 하나 | 기록이 남는 쪽: `crash_points::stopped_after_the_write_…`. 잘리는 쪽: 저널 crate의 꼬리 절단 시험 |
| ⑥~⑧ | 있음 | 반영(소실) | 없음 | 없음 | 주문 있음. 전송 결과 불명(사유: 재시작) | `duplicate` | `crash_points::stopped_after_the_flush_…` |
| ⑧~⑨ | 있음 | 반영(소실) | 받음 | 없음 | 위와 같음. 만료 뒤 조회로 부재를 확인해 `NotPlaced` | `duplicate` | `crash_points::stopped_after_the_reply_…` |
| ⑨~⑪ (게이트웨이 큐) | 있음 | 반영(소실) | 받음 | 없음 | 위와 같음 | `duplicate` | 따로 겨냥한 시험 없음. 위 행과 아래 행 사이다 |
| ⑪ 전송 중 | 있음 | 반영(소실) | 받음 | 있을 수도 없을 수도 | 전송 결과 불명. 조회로 찾으면 정상 주문, 못 찾으면 만료 뒤 `NotPlaced` | `duplicate` | `e2e::a_kill_during_send_does_not_duplicate_the_order`(거래소가 응답을 늦추는 동안 종료) |
| ⑪ 뒤, 결과 기록 전 | 주문만 | 반영(소실) | 받음 | 있음 | 조회 또는 열린 주문 목록에서 찾아 접수 처리 | `duplicate` | 위와 같은 시험, `e2e::random_kills_…` |

⑤~⑥에서 "기록이 온전하면 주문이 있다"는 점에 주의한다. flush를 확인하지 못했어도 커널이 데이터를 디스크에 썼을 수 있다.
그 경우 응답도 전송도 나가지 않았으므로 주문은 결과 불명으로 남았다가 만료 뒤 `NotPlaced`로 닫힌다. 모순은 없다.

flush가 **오류를 반환**한 경우(프로세스는 살아 있음): 그 배치의 ⑦~⑩은 실행되지 않는다. 치명 상태가 걸리고 입력 큐가 닫힌다.
순서: 치명 표시(사유 포함) → 큐 닫기 → 그 배치의 응답 채널 닫기. 요청자가 "확인되지 않음"을 받는 시점에는 노드가 이미 멈춘 것으로 보인다.
프로세스는 상태 2로 종료한다. 재시작 뒤는 위 표의 ⑤~⑥ 행과 같다.
시험: 쓰기 전에 주입한 오류는 `pipeline::outputs_follow_durability_*`, 쓴 뒤에 주입한 오류는 `crash_points::a_flush_error_after_the_write_stops_the_node_and_the_record_may_survive`.

코어나 커밋 스레드의 panic: 프로세스 전체가 abort한다. 재시작 뒤는 중단 위치에 따라 위 표의 행과 같다. 시험은 없다.

코어 판단 중 내부 불변조건 위반(`CoreFault`): 그 배치 전체가 커밋 단계로 가지 않는다. 치명 상태. 재시작 뒤는 ①~③ 행과 같다.

## 변형 입력에 대한 동작

| 상황 | 동작 |
|---|---|
| 같은 입력이 두 번 | 코어의 판단에 따른다(각 계약 참조). 이벤트가 없으면 기록도 없고 순번도 쓰지 않는다. 응답은 그때까지의 기록이 내구화된 뒤에 나간다 |
| 두 입력의 순서 | 큐에서 꺼낸 순서가 저널 순서다. 큐 간 우선순위는 꺼내는 순서에만 영향을 주고, 재생은 저널 순서를 따른다 |
| 시간 초과 | 이 단계에는 시간 초과가 없다. flush가 느리면 뒤가 기다린다 |
| 태스크 취소 | 요청한 연결이 끊겨도 기록은 유지된다. 응답만 버려진다 |
| 재실행 | 복구는 ⑥까지 온 기록의 이벤트만 적용한다. ⑧~⑪을 다시 하지 않는다 |

## 시스템은 외부 처리 결과를 실제로 알고 있는가

이 단계가 아는 것은 "저널에 내구화됐다"까지다. 전송 명령을 게이트웨이 큐에 넣었다는 사실은 기록하지 않는다.
거래소 결과는 게이트웨이가 돌려주는 `SendResult` 입력으로만 안다([C-SEND](order-lifecycle.md#c-send-전송-결과)).

## 기록되지 않는 것

이벤트를 만들지 않은 입력: 시간 경과, 변화 없는 저장 공간 보고, 중복 통보, 중복 요청.
이들의 응답은 "그 시점까지 배정된 순번이 내구화된 뒤"에 나간다(같은 배치의 flush 뒤).
시간 경과와 저장 공간 보고를 뺀 나머지는 최근 500건까지 휘발성 진단 목록에 남는다.

## 검증

| 주장 | 시험 |
|---|---|
| flush 실패 시 응답·명령·읽기 모델 변경 없음, 재시작 상태는 실패 전 | `pipeline::outputs_follow_durability_with_a_commit_thread`, `…_with_inline_commit` |
| 응답 시점에 읽기 모델에 이미 반영 | 같은 시험의 앞부분 |
| 강제 종료 뒤 장부가 거래소와 일치, 중복 전송 없음 | `e2e::random_kills_under_load_keep_books_consistent`, `e2e::a_kill_during_send_does_not_duplicate_the_order` |
| 미내구 기록과 출력이 함께 사라져도 성질 유지 | 시뮬레이션 `crashy`, `weak_evidence`, `purge`, `skewed` 프로파일 |

확인하지 않은 것: 전원 장애에서 ⑥의 의미. ⑤~⑥에서 꼬리가 실제로 어떤 모양으로 남는지(파일 조작으로 흉내만 냈다).
