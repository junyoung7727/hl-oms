# C-OVERLOAD 과부하와 저장 공간

설계 근거: [ADR-010](../adr/ADR-010-overload-storage.md). 구현: `crates/oms-node/src/queues.rs`, `server.rs`, `node.rs`(저장 공간 감시), `crates/oms-core/src/decide.rs`(코어 안의 상한).

## 상한의 전체 목록

| 대상 | 상한(기본) | 설정 | 넘었을 때 |
|---|---|---|---|
| 한 줄의 길이 | 64 KiB | 고정 | `bad_request` 후 연결 종료 |
| 연결 수(거래 소켓) | 64 | `api.max_connections` | 접속 거절 |
| 연결 수(운영 소켓) | 8 | `api.admin_max_connections` | 접속 거절. 거래 소켓과 따로 센다 |
| `hello` 전의 연결 | 10초 | `api.hello_timeout_ms` | 연결 종료 |
| 연결당 구독 | 1 | 고정 | 두 번째 요청은 변화 없음 |
| 구독자당 이벤트 버퍼 | 4096 | `api.subscriber_buffer` | 그 구독을 끊고 연결을 닫는다 |
| 연결당 진행 중 요청 | 32 | `api.window` | 다음 줄을 읽지 않는다 |
| 연결당 응답 버퍼 | 128 | 창 × 2 + 64 | 응답 전달이 기다린다 |
| 전략당 신규 주문 빈도 | 초당 50, 순간 100 | `limits.*` | `overloaded` |
| 전략당 취소 빈도 | 초당 200, 순간 400 | `limits.*` | `overloaded` |
| orders 큐 | 1024 | `runtime.orders_queue` | `overloaded` |
| control 큐 | 256 | `runtime.control_queue` | `overloaded`. 시간 경과 입력은 건너뛴다 |
| venue 큐 | 4096 | `runtime.venue_queue` | 게이트웨이가 기다린다 |
| 배치 | 256 | `runtime.max_batch` | 다음 배치로 |
| 코어 → 커밋 | 8 배치 | 고정 | 코어 스레드가 기다린다 |
| 한 번의 flush가 묶는 입력 | 4096 | 고정 | 다음 flush로 |
| 게이트웨이 명령 큐 | 진행 중 전송 상한 + 열린 주문 상한 + 64 | 파생 | 커밋 스레드가 기다린다 |
| 진행 중 전송(거래소 증거 전) | 64 | `policy.max_inflight_sends` | 거절 `GatewayBusy` |
| 열린 주문 | 500, 전략별 설정 | `policy.max_open_orders` | 거절 |
| 메모리의 주문 | 100,000 | `policy.max_orders_in_memory` | 거절 `CapacityExhausted` |
| 대기 체결 | 1024 | `policy.max_parked_fills` | 외부 체결로 기장 + 불일치 |
| 취소 시도 | 5 | `policy.cancel_max_attempts` | `CancelStuck` 불일치 |
| 게이트웨이 동시 실행 | 진행 중 전송 상한 + 16 | 파생 | 세마포어 대기 |
| 대조 조회 큐 | 256 | 고정 | 이번 회차 생략 |
| 주문별 추적 | 200 | 고정 | 오래된 것 삭제, `truncated` 표시 |
| 최근 기록 / 이벤트 없는 입력 | 2000 / 500 | 고정 | 오래된 것 삭제 |

상한이 없는 것: 미확인 불일치 목록(대상마다 한 건으로 묶이고 외부 체결은 종목마다 한 건이지만, 대상이 계속 늘면 자란다). 체결 키 집합(시간으로만 제한된다: 동기화 시점 기준 24시간분). 로그.

메모리의 주문 상한(100,000)에 대해: 종결 주문이 1시간 남으므로 기본값에서 초당 약 27.8건을 넘는 수용이 한 시간 이어지면 닿는다. 닿으면 신규 주문이 `capacity_exhausted`로 거절된다.

## 입력 종류별 동작

| 입력 | 가득 찼을 때 | 기록 | 다시 보낼 수 있는가 |
|---|---|---|---|
| 신규 주문 | 즉시 `overloaded` | 없음. 키도 쓰이지 않는다 | 같은 키로 |
| 취소 | 즉시 `overloaded` | 없음 | 예 |
| 운영 명령 | 즉시 `overloaded` | 없음 | 예 |
| 체결·상태·전송 결과 | 게이트웨이가 기다린다 | 처리되면 기록 | 버려지지 않으므로 필요 없다 |
| 시간 경과 | 건너뛴다(이미 하나가 대기 중이면 추가하지 않는다) | — | 다음 주기에 |
| 저장 공간 보고 | 건너뛴다 | — | 5초 뒤 |

## 압력이 전달되는 방향

```text
전략 → [창] → [빈도 제한] → orders/control 큐 → 코어 → [커밋 채널] → 커밋 → [명령 큐] → 게이트웨이 → 거래소
                                    ▲                                                       │
                                    └──────────── venue 큐 ◄───────────────────────────────┘
```

커밋이 느려지면 커밋 채널이 차고, 코어가 멈추고, 입력 큐가 차고, 신규 주문이 거절된다.
venue 큐가 차면 게이트웨이가 소켓을 읽지 않는다. 그 상태가 길어지면 거래소가 연결을 끊고, 링크 단절로 처리된 뒤 재접속 대조가 빠진 것을 메운다.

고리(게이트웨이 → venue 큐 → 코어 → 커밋 → 명령 큐 → 게이트웨이)가 닫히려면 venue 큐와 명령 큐가 동시에 가득 차야 한다.
명령 큐는 코어의 상한(진행 중 전송, 열린 주문)으로 크기를 잡았으므로 정상적인 주문 흐름으로는 차지 않는다.

## 저장 공간과 저장 실패

| 상황 | 입력 | 코어의 변경 | 허용되는 것 | 막히는 것 |
|---|---|---|---|---|
| 여유 < 기준(1 GiB) | `Storage { low: true }`(5초마다 측정) | `StorageLowChanged` → `StorageLow` 차단 | 체결 기장, 취소, 대조, 운영 명령 | 신규 주문 |
| 여유 회복 | `Storage { low: false }` | `StorageLowChanged` | 전부 | — |
| write/fdatasync 오류 | — | 없음(그 배치는 버려진다) | 없음 | 전부. 프로세스가 상태 2로 종료 |

저장 실패 뒤에 **하지 않는 것**: flush 재시도, 메모리만으로 계속 처리, 저널 없는 취소 전송.
저장 실패 뒤 재시작하면 마지막 내구 기록부터 복구하고, 그 뒤의 체결은 대조가 거래소에서 다시 가져온다. 체결이 유실되는 경로는 없다.
거래소에 남은 주문에 대한 선택지는 U-05다.

## 변형 상황

| 상황 | 동작 |
|---|---|
| 한 전략이 폭주 | 그 전략의 토큰 버킷이 먼저 막는다. 다른 전략의 버킷은 영향 없다. 큐 안에서는 선착순이다 |
| 신규 주문 폭주 중 취소 | 취소는 control 큐와 별도 빈도 한도를 쓴다. 배치마다 control에 지분이 있다 |
| 느린 구독자 | 버퍼가 차면 구독을 끊고 연결을 닫는다. 전략은 재접속 후 조회로 맞춘다 |
| 연결이 끊긴 요청 | 이미 큐에 들어간 요청은 처리되고 기록된다. 응답만 버려진다 |
| 프로세스 재시작 | 큐는 비어서, 토큰 버킷은 가득 찬 상태(순간 허용량만큼 바로 받는 상태)로 시작한다. 큐에 있던 요청은 사라졌고 응답도 가지 않았다. 전략이 같은 키로 다시 보낸다 |
| 침묵하는 연결이 자리를 차지 | `hello` 없는 연결은 10초 뒤 닫힌다. `hello`를 한 연결은 시간 제한이 없다(구독자는 조용히 기다리는 것이 정상이다). 운영 소켓은 자리를 따로 가진다 |
