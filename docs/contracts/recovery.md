# 복구 계약

설계 근거: [ADR-003](../adr/ADR-003-journal-record.md), [ADR-011](../adr/ADR-011-file-format.md), [ADR-013](../adr/ADR-013-availability.md).
구현: `crates/oms-node/src/recovery.rs`, `crates/oms-journal/src/segment.rs`, `snapshot.rs`, `Tx::boot`(`oms-core/src/decide.rs`).

## C-JOURNAL 저널에서 상태 복원

| 항목 | 내용 |
|---|---|
| 입력 | 데이터 디렉터리: `INSTANCE`, `snapshot-*.snap`, `journal-*.oj` |
| 전제 | 디렉터리 잠금을 얻었다(다른 프로세스가 쓰고 있지 않다) |
| 변경 | 메모리에 `Core` 재구성. 디스크는 불완전한 꼬리가 있을 때만 변경(보존 후 자름) |
| 외부 효과 | **없다.** 복구 코드는 게이트웨이를 갖지 않고, `Core::replay`는 명령을 만들 수 없다 |
| 자원 상한 | 세그먼트 하나(64 MiB)를 메모리로 읽는다 |

절차:

1. `INSTANCE`를 읽는다. 없고 디렉터리가 비었으면 새로 만든다. 없는데 저널이 있으면 거부한다.
2. 가장 새 스냅샷부터 검사한다(길이, 체크섬, 상태 스키마, 해석 가능 여부, `instance_id`, 상태 다이제스트). 통과한 첫 스냅샷을 쓴다. 실패한 것은 건너뛰고 사유와 함께 보고한다.
   어느 검사에서 떨어져도 시작을 거부하지 않는다. 스냅샷은 지름길일 뿐이다.
3. 스냅샷 순번 다음부터 저널을 읽는다. 프레임마다 체크섬과 순번 연속을 확인하고, 기록의 `seq`가 프레임 순번과 같은지, `at`이 감소하지 않는지 확인한 뒤 이벤트를 적용한다.
4. 끝에서 꼬리 판정([ADR-011](../adr/ADR-011-file-format.md) §7의 표). 꼬리를 자르는 일은 **다른 모든 검사가 통과한 뒤에** 한다. 거부하는 디렉터리는 발견한 그대로 둔다.
5. 구조 불변조건을 검사한다. 실패하면 거부한다.

| 상황 | 결과 |
|---|---|
| 깨끗한 저널 | 마지막 내구 기록까지의 상태 |
| 불완전한 꼬리 | 꼬리를 `torn/`에 보존하고 자른 뒤 시작. 보고서의 `torn_tail`에 위치와 크기 |
| 중간 손상, 빈틈, 다른 인스턴스, 읽을 수 없는 스키마 | 시작 거부(종료 코드 3). 파일을 건드리지 않는다 |
| 스냅샷 전부 무효 | 저널을 처음부터 재생. 처음 세그먼트가 없으면 거부 |
| 스냅샷이 저널보다 새것(저널이 그 순번까지 없다) | 거부. 파일을 건드리지 않는다 |
| 스냅샷은 있는데 세그먼트가 하나도 없다 | 거부. 세그먼트를 지우는 기능이 없으므로 정상 상태에서는 생기지 않는다 |
| 가장 새 세그먼트의 헤더가 불완전(회전 중 중단) | 그 파일을 `torn/`에 보존하고 지운 뒤 앞 세그먼트에 이어 쓴다. 스냅샷이 앞 세그먼트의 끝까지 덮고 있어도 같다 |
| 가장 새 세그먼트가 헤더뿐이고 기록 스키마가 이 빌드와 다르다 | 첫 기록을 쓸 때 그 빈 세그먼트를 새 스키마의 헤더로 바꿔 쓴다(임시 파일 → rename) |
| 복구 중 프로세스 중단 | 다시 실행하면 된다. 꼬리 자르기는 "보존 → fsync → 자르기 → fsync" 순서라 어느 지점에서 죽어도 원본 바이트가 남는다 |
| 복구를 두 번 실행 | 같은 상태. 두 번째는 꼬리가 없다 |

오프라인 검증: `oms-node verify --data-dir <dir> [--re-decide]`는 잠금 없이 읽기만 한다. 모든 체크섬·순번, 기록마다 불변조건,
`--re-decide`면 기록된 입력을 다시 판단한 결과가 기록된 이벤트와 같은지 확인한다.

## C-SNAP 스냅샷

| 항목 | 내용 |
|---|---|
| 시점 | 마지막 스냅샷 이후 기록이 5만 건(설정)을 넘을 때, 운영자 요청, 정상 종료 |
| 읽는 상태 | 읽기 모델의 `Core` 복제본. 내구화된 기록만 반영돼 있다 |
| 변경 | `snapshot-<seq>.snap` 파일. 임시 이름 → fsync → rename → 디렉터리 fsync |
| 중간에 멈추면 | `.tmp` 파일이 남고 무시된다. 완전한 스냅샷만 이름을 얻는다 |
| 같은 요청이 다시 오면 | 쓰는 중이면 건너뛴다. 같은 순번의 스냅샷을 다시 쓰면 같은 이름으로 바뀐다 |
| 누가 언제 보는가 | 다음 시작의 복구만 읽는다. 실행 중인 프로세스는 스냅샷을 읽지 않는다 |
| 복구 뒤 | 스냅샷 쓰기를 이어서 하지 않는다. 다음 주기에 새로 쓴다 |
| 일관성 | 스냅샷의 `seq`는 저널의 내구 순번 이하다. 저널보다 앞선 스냅샷은 만들어질 수 없다 |
| 실패 | 기록만 남기고 계속한다. 스냅샷은 지름길일 뿐이고 저널이 완전하다 |
| 자원 | 상태 복사와 직렬화. 측정(`evidence/perf/core-bench.json`): 주문 20만 건일 때 복사 111 ms, 직렬화 212 ms, 166 MB |

스냅샷 쓰기는 별도 스레드다. 쓰는 중에 다음 요청이 오면 건너뛴다.
쓰는 도중 프로세스가 죽으면 `.tmp` 파일이 남고 무시된다.

## C-BOOT 재시작

복구 직후, 다른 어떤 입력보다 먼저 `Boot` 입력이 코어에 들어간다.

| 항목 | 내용 |
|---|---|
| 변경 | `Booted { boot }`: 부팅 번호 증가, 링크를 내려간 상태로. 첫 부팅이면 체결 바닥 시각을 `현재 − absence_margin`으로 |
| | 결과 기록이 없는 `PendingSend` 주문마다 `OrderInDoubt(Restart)` |
| | 진행 중이던 취소 시도마다 `CancelOutcomeNoted(LostOnRestart)` |
| 외부 효과 | 없다. `Boot`는 어떤 명령도 만들지 않는다 |
| 이어서 | 설정 파일을 `Config` 입력으로 제출. 활성 설정과 같으면 변화 없음, 버전이 크면 활성화, 같은 버전에 다른 내용이면 거부하고 프로세스 종료 |
| 차단 | `LinkDown` → (접속 뒤) `Resync` → 해제. 결과 불명 주문이 있으면 `InDoubt` |

### 복구 후 다시 실행하는 것과 반복하면 안 되는 것

| 동작 | 재실행 | 이유 |
|---|---|---|
| 신규 주문 전송 | **하지 않는다** | 이미 놓였을 수 있다. 중복 주문이 된다 |
| 취소 전송 | 한다(요청이 남아 있고 주문이 미종결이면) | 반복해도 효과가 같다 |
| 상태·체결·열린 주문·포지션 조회 | 한다 | 읽기 전용이고 답은 멱등하게 적용된다 |
| 전략에 대한 응답 | 하지 않는다 | 연결이 사라졌다. 전략이 같은 키로 다시 물으면 `duplicate`로 답한다 |
| 구독 이벤트 | 하지 않는다 | 전략은 재접속 뒤 조회로 맞춘다 |

## 종료

| 종료 방식 | 남는 것 | 다음 시작 |
|---|---|---|
| SIGTERM/SIGINT | 큐에 있던 입력까지 처리·내구화, 최종 스냅샷. 열린 주문은 거래소에 남는다 | 스냅샷에서 빠르게 |
| 치명 상태(flush 실패, 코어 결함) | 마지막 내구 기록까지. 종료 코드 2. 종료 신호를 받은 뒤 남은 입력을 처리하다 실패해도 2다 | 저널 재생 |
| panic | 마지막 내구 기록까지. 프로세스가 abort한다(종료 코드가 아니라 SIGABRT). 로그 마지막 줄에 사유 | 저널 재생 |
| SIGKILL, 전원 | 마지막 내구 기록까지(전원은 A-05) | 저널 재생 |

## 검증

| 주장 | 시험 |
|---|---|
| 꼬리·중간 손상·빈틈·잠금·스키마 | `oms-journal`의 `journal.rs` 16건, `snapshot.rs` 2건, `frame.rs` 4건 |
| 거부한 디렉터리를 건드리지 않음, 세그먼트 없는 스냅샷, 회전 직후의 스키마 변경, 헤더가 불완전한 새 세그먼트 | `review_journal.rs` 7건 |
| 다이제스트가 맞지 않는 스냅샷을 건너뜀 | `review_node::a_snapshot_whose_digest_does_not_match_is_skipped_not_fatal` |
| 여러 세그먼트에 걸친 저널의 프로세스 수준 복구 | `review_node::many_small_segments_survive_a_kill_and_a_clean_restart` |
| `--re-decide`가 입력과 맞지 않는 기록을 잡음 | `review_node::re_decide_detects_a_record_whose_events_differ_from_the_decision` |
| 종료 중의 저널 실패가 정상 종료로 보고되지 않음 | `review_node::a_journal_failure_during_the_shutdown_drain_is_not_reported_as_a_clean_stop` |
| 커밋 경계마다의 중단 | `crash_points.rs` 5건 |
| 실제 노드의 손상 처리 | `e2e::journal_damage_is_handled_by_position` |
| 재시작이 재전송하지 않음 | `scenarios::restart_puts_outstanding_sends_in_doubt_and_never_resends`, `e2e::a_kill_during_send_does_not_duplicate_the_order` |
| 정상 종료 뒤 같은 상태, 스냅샷 사용 | `e2e::vertical_slice_new_partial_fill_cancel_restart` |
| 설정 버전 규칙 | `e2e::configuration_changes_need_a_new_version`, `scenarios::configuration_changes_are_validated_against_existing_exposure` |
| 반복 강제 종료 | `e2e::random_kills_under_load_keep_books_consistent`(스냅샷 주기 150으로 낮춰 스냅샷 경로도 지난다) |

확인하지 않은 것: 전원 장애. 스냅샷 쓰기 도중의 강제 종료를 겨냥한 시험(무작위 종료에서 우연히 지날 뿐이다). panic으로 인한 종료.
여러 쪽에 걸친 배치가 순서 없이 디스크에 닿는 경우(전원 장애에서만 생긴다): 앞쪽이 빠지고 뒤쪽이 남으면 중간 손상으로 읽혀 시작을 거부한다. 그 기록들은 응답도 전송도 나간 적이 없으므로 거부는 지나치게 보수적인 쪽이다. 실제로 그런 모양이 생기는지는 모른다.
