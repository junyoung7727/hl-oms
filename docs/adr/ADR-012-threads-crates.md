# ADR-012 스레드·큐 구성과 채택하지 않은 최적화

상태: 채택.

## 1. 문제와 발생 가능한 실패

판단(코어)과 저장(flush)을 어떻게 배치하느냐가 지연과 과부하 동작을 정한다.
flush는 측정상 약 1 ms다. 코어가 flush를 직접 기다리면 그동안 체결 통보도 처리하지 못한다.
반대로 단계를 나누면 스레드 간 전달과 순서 보장이 추가된다.

## 2. 일반적으로 만족해야 하는 성질

판단 순서가 하나다. I/O가 판단 경로를 막는 시간에 상한이 있다. 단계 사이의 큐에 상한이 있다.
구성을 바꿔도 [ADR-004](ADR-004-commit-gate.md)의 순서 보장은 같다.

## 3. 제약

요구 부하는 초당 20건(정상), 200건(피크 설계 기준)이다. 지연 기준은 로컬 응답 p99 20 ms.
brief §7은 I/O 분리와 제한된 큐를 기본으로, 전용 ring buffer·busy-spin·CPU 고정은 측정으로만 채택하라고 한다.

## 4. 필수 조건과 선택 조건

필수: 단일 writer, 제한된 큐, output commit. 선택: flush 중에도 코어가 진행, 높은 부하에서의 여유.

## 5. 대안

| 대안 | 구성 |
|---|---|
| A. 인라인 커밋 (가장 단순) | 코어 스레드가 배치를 판단한 뒤 직접 write·fdatasync하고 출력을 낸다 |
| B. 커밋 스레드 | 코어 스레드는 판단만 한다. 커밋 스레드가 대기 중인 배치를 모아 한 번에 flush하고 출력을 낸다 |
| C. B + Disruptor식 ring buffer, busy-spin, 코어 고정 | LMAX 원형에 가까운 구성 |

## 6. 비교: 측정

조건: 개발 호스트(i9-14900K, governor `powersave`), 저널은 Samsung SSD 970 EVO Plus 2TB(ext4, 사용률 4%), release 빌드, 커밋마다 fdatasync,
가상 거래소(자동 전량 체결), 연결 4개, open-loop 부하 10초씩. 지연은 "의도한 전송 시각 → 응답 도착"이다.
수용 한도는 풀었다(연결당 창 512, 전략 빈도 한도 초당 100만, 열린 주문 10만, 진행 중 전송 4096). 파이프라인이 감당하는 양을 보기 위한 설정이고 운영 설정이 아니다.
측정 동안 load average는 2 안팎이었고 노드가 잰 fdatasync 중앙값은 2.6~2.8 ms였다.
결과 파일: `evidence/perf/nvme-compare-thread.json`, `evidence/perf/nvme-compare-inline.json`(노드 설정 전문과 환경 포함). 재현: `cargo run --release -p xtask -- perf --rates 200,2000,8000 [--inline]`.

| 부하(건/초) | 구성 | 응답 p50 | 응답 p99 | 최대 | 오류 |
|---:|---|---:|---:|---:|---|
| 200 | A 인라인 | 4.0 ms | 8.4 ms | 11.5 ms | 0 |
| 200 | B 커밋 스레드 | 4.1 ms | 8.6 ms | 13.5 ms | 0 |
| 2000 | A | 4.6 ms | 11.3 ms | 16.6 ms | 0 |
| 2000 | B | 6.5 ms | 15.1 ms | 23.5 ms | 0 |
| 8000 | A | 0.07 ms | 1046 ms | 1102 ms | 80,000건 중 51,214건 overloaded |
| 8000 | B | 7.2 ms | 16.9 ms | 24.8 ms | 0 |

구성마다 한 번, 10초씩 쟀다. 실행 사이의 변동이 크다(같은 빌드, 다른 장치·조건에서 초당 200건 p99가 8 ms에서 29 ms까지 나왔다). 작은 차이에는 의미를 두지 않는다.

읽는 법:

- 초당 2000건(요구 피크의 10배)까지 두 구성의 차이는 실행 간 변동 안이다.
- 초당 8000건에서 A는 무너졌다. 코어가 flush에 묶여 있는 동안 거래소 결과가 처리되지 않아 진행 중 주문이 쌓였고,
  신규 주문 판단이 열린 주문 수에 비례해 느려져([ADR-008](ADR-008-risk-reservation.md) §8) 큐가 찼다. 과부하 보호(거절)는 설계대로 작동했다.
- B는 같은 부하를 오류 없이 처리했다. 대기 중인 배치를 한 번의 flush로 묶는다(초당 8000건에서 커밋당 기록 중앙값 79).
- flush 꼬리가 길었던 980 500GB(디스크 100%)에서는 A가 초당 200건에서도 p99 238 ms였고 B는 29 ms였다.
  그 결과 파일은 덮어썼다. 이 문장은 보관된 근거가 없는 기록이다.

C는 측정하지 않았다. B에서 스레드 간 전달이 차지하는 시간은 큐 대기 안에 들어 있고 그 대부분은 flush 대기다.
전달 자체를 ring buffer로 바꿔 줄일 수 있는 몫은 마이크로초 단위다(추정).

| 기준 | A | B | C |
|---|---|---|---|
| 요구 부하(초당 200건)에서의 지연 | B와 비슷(측정). flush가 느릴 때는 꼬리가 길어진다(보관된 근거 없음) | 측정 | 미측정 |
| 과부하 여유 | 8000건/초에서 붕괴(측정) | 8000건/초 처리(측정) | 미측정 |
| 추가 코드 | 없음 | 제한 채널 하나, 스레드 하나. 커밋 코드는 A와 같다 | ring buffer, 대기 전략, 코어 고정, 전용 코어 |
| 유휴 시 CPU | 없음 | 없음 | busy-spin이면 코어 하나를 상시 사용 |

## 7. 선택과 이유

B를 기본으로 한다.

- 필수 조건은 A와 B가 같은 코드(`Committer::commit`)로 만족한다. 차이는 그 함수를 어느 스레드가 부르느냐뿐이다(`Sink` enum).
- B를 택한 근거는 측정이다: flush가 느린 장치 상태에서의 꼬리 지연과 과부하 여유, 그리고 brief의 기본 방침(I/O 분리). 추가 비용은 채널 하나다.
- A는 `runtime.inline_commit = true`로 남겨 둔다. 이 비교를 재현하기 위한 것이며 운영 권장이 아니다. 두 구성 모두 같은 flush 실패 주입 시험을 통과한다.

스레드 구성:

| 스레드 | 수 | 하는 일 | 막히는 곳 |
|---|---:|---|---|
| `oms-core` | 1 | 입력 배치를 꺼내 판단·적용·인코딩 | 입력 큐(비었을 때), 커밋 채널(가득 찼을 때) |
| `oms-commit` | 1 | write, fdatasync, 읽기 모델 갱신, 출력 해제 | fdatasync, 게이트웨이 명령 큐(가득 찼을 때) |
| `oms-snapshot` | 1 | 상태 복사본을 직렬화해 스냅샷 기록 | 파일 I/O |
| `oms-io`(tokio) | 2(설정) | 소켓, 게이트웨이, 대조기, 타이머, HTTP | — |

### 채택하지 않은 최적화와 그 이유

| 최적화 | 판단 | 근거 |
|---|---|---|
| 전용 ring buffer(Disruptor) | 채택 안 함 | 병목은 flush다. 판단은 수십 µs, 기록은 수 ms다(측정). 스레드 간 전달을 줄여도 지연이 줄지 않는다 |
| busy-spin 대기 | 채택 안 함 | 유휴 코어를 상시 점유한다. 얻는 것은 마이크로초 단위(추정) |
| CPU 고정, NUMA | 채택 안 함 | 단일 소켓. 측정된 필요 없음 |
| 자체 lock-free 구조, 성능 목적 `unsafe` | 채택 안 함 | 작업 공간 전체가 `unsafe_code = "forbid"` |
| 커스텀 allocator, 버퍼 재사용 | 채택 안 함 | 기록당 인코딩 0.5 µs. flush의 0.06% |
| 바이너리 저널 형식 | 채택 안 함 | [ADR-011](ADR-011-file-format.md) §6 |
| 차단 사유 계산을 카운터로 | 보류 | 기본 상한(열린 주문 500)에서 22 µs. 상한을 올릴 때 적용. 증거금 정책을 켜면 레버리지 검사의 합 때문에 66 µs다(2026-11-16). 그 합도 열린 주문 수에 비례한다 |
| 세그먼트 사전 할당 | 보류. 측정으로 이득은 확인했다 | 미리 0으로 채운 블록을 덮어쓰면 이 장치에서 동기 쓰기가 중앙값 0.95 ms → 0.44 ms로 줄고 꼬리가 짧아진다(`evidence/perf/prealloc-probe.json`). 구현하지 않은 이유는 아래 |

중단 조건과 현재 상태: "수용 기준 A-LAT-1, A-CAP-1을 만족하면 중단"으로 정했다. 저널을 970 EVO Plus 2TB에 두고 잰 최종 측정에서 둘 다 만족했다
(초당 200건의 응답 p99 9.06 ms, 기준 20 ms. [성능 문서](../performance/README.md)). 그래서 멈춘다.
같은 빌드를 거의 찬 980 500GB에 두고 쟀을 때는 A-LAT-1을 넘었다(27.2 ms). 그 지연은 fdatasync의 꼬리(p99 15.4 ms)와 그것을 기다리는 시간이었고,
코어의 판단은 수십 µs였다. 위 표에서 fdatasync 시간을 줄이는 것은 세그먼트 사전 할당 하나뿐이다. 더 느린 장치에서 운용해야 하면 그때 다시 본다.

사전 할당을 지금 구현하지 않은 이유: 복구의 판정 규칙([ADR-011](ADR-011-file-format.md) §7)이 "손상된 프레임 뒤에 유효한 프레임이 있으면 중간 손상"이다.
덮어쓰기에서는 전원 장애 때 내구화되지 않은 배치의 뒤쪽 블록만 디스크에 남을 수 있고, 그러면 버려도 되는 꼬리를 중간 손상으로 읽어 시작을 거부한다.
구별하려면 프레임에 "이 배치 이전까지 내구화된 순번"을 싣는 형식 변경이 필요하다. 그 판정은 전원 장애에서만 드러나는데 전원 장애를 시험할 수단이 없다.
측정된 이득(지연)과 검증할 수 없는 위험(복구 판정)의 교환이고, 지금 장치에서는 기준을 이미 만족하므로 하지 않는다. 필요해지면 설계 결정을 따로 쓰고 시험 수단을 갖춘 뒤에 한다.

## 8. 포기한 장점, 남은 위험, 가정

- 코어의 메모리 상태가 커밋 채널에 있는 배치(최대 8개)만큼 저널보다 앞선다([ADR-004](ADR-004-commit-gate.md) §7).
- 읽기 모델 잠금: 커밋 스레드가 배치마다 쓰기 잠금을 잡는다. 조회가 많으면 커밋이 지연될 수 있다. 측정하지 않았다.
- 측정은 한 호스트, 한 장치, 짧은 실행이고, 그 장치의 상태가 하루 사이에 크게 달랐다. 그 변동의 일부는 내 도구가 만들었다(변이 점검의 작업 사본 2.7 GB가 저널 디스크를 100%까지 채웠다). 다른 장치에서의 flush 지연은 [성능 문서](../performance/README.md)의 probe로 먼저 잰다.
- 응답 지연은 장치의 flush 시간에 직접 묶여 있다. 다른 작업과 디스크를 나눠 쓰면 그 작업이 지연을 정한다.
