# ADR-023 우리 주문의 체결이 아닌 실행: 펀딩, 거래소가 만든 포지션 변경, 분류 못 한 실행. 기록 스키마 2

상태: 채택(구현). 실제 거래소에서 이런 실행이 어떤 모양으로 오는지는 확인하지 않았다(Bybit testnet 항목, 설계 TN T15).

## 1. 문제와 발생 가능한 실패

- Bybit는 우리 주문의 체결과 같은 실행 흐름(`execution` 스트림, `/v5/execution/list`)으로 펀딩 지급, 자동 감축(ADL, `AdlTrade`), 청산 포지션 인수(`BustTrade`), 인도(`Delivery`), 정산(`Settle`)을 보낸다. 종류는 `execType`(문서에 14가지)으로 갈린다.
- 코어는 체결(`Fill`)만 알았다. 펀딩을 체결로 넣으면 포지션과 체결 수가 틀어지고, 버리면 현금 흐름이 저널에 없다.
- 거래소가 스스로 옮긴 포지션은 다음 대조에서 `PositionOutOfRange`로만 보였다. 무슨 일이 있었는지는 저널에 없고, 그 차이를 고치려면 운영자가 수량을 직접 계산해 `adjust`해야 했다.
- 게이트웨이가 모르는 `execType`이 조용히 지나가면 포지션이 아무도 모르게 바뀔 수 있다.

## 2. 일반적으로 만족해야 하는 성질

- 저널만 읽어도 포지션을 다시 만들 수 있다: 포지션 = 체결 + 외부 체결 + 거래소 포지션 변경 + 포지션 조정의 합(감시자 W2가 이것을 쓴다, 설계 TN §7.5).
- 펀딩은 현금이다. 포지션, 주문, 예약, 체결 수를 바꾸지 않는다.
- 거래소가 만든 변경과 분류 못 한 실행은 사람이 볼 때까지 포지션을 늘리는 주문을 막는다.
- 같은 실행이 두 번 와도(REST 재동기화) 한 번만 기록된다.
- 이 변경 전에 쓴 저널은 그대로 다시 읽힌다.

## 3. 제약

| 사실 | 출처 |
|---|---|
| `execType` 14가지, 실행 목록과 스트림 모두 이 필드를 준다. `execution.fast`는 Trade만 | Bybit v5 문서, 설계 TN 수정 R2 |
| 펀딩·ADL·청산 인수 행의 실제 모양은 미확인 | 설계 TN testnet 항목 T15 |
| 불일치 차단은 증거금 정책이 있으면 일반 주문만 막고 감소 전용은 통과시킨다. Bybit 설정은 증거금 정책을 쓴다 | `HoldReason::refuses_only_plain_orders`, ADR-008 §7 |
| 외부 체결(우리 주문이 아닌 체결)은 이미 계좌와 미귀속 장부에 기장되고 `ExternalFill` 불일치를 낸다 | C-FILL 7 |
| 저널 세그먼트 하나는 한 기록 스키마만 담고, 쓰는 스키마가 바뀌면 새 세그먼트를 연다 | ADR-011, `oms-journal` |
| 운영자 `PositionAdjusted`는 스키마 1에 이미 있다 | `event.rs` |

## 4. 필수 조건과 선택 조건

필수: 위 2의 다섯 성질. 스키마 1 기록이 그대로 해석됨.
선택: 펀딩 금액의 누적(손익)은 코어가 아니라 프로젝터(U14)가 저널에서 계산한다.

## 5. 대안

| 대안 | 설명 |
|---|---|
| A. 게이트웨이가 펀딩은 버리고 나머지는 외부 체결로 | 코어 변경 없음 |
| B. 새 입력 셋 + 새 이벤트 넷, 기존 불일치 차단 재사용, `PositionAdjusted`에 `reason` | 이 결정 |
| C. B에 새 차단 이유(`VenueChange`)와 `clear_hold` 명령 | 설계 TN 수정 R5 그대로 |

## 6. 비교

| 기준 | A | B | C |
|---|---|---|---|
| 펀딩이 저널에 있음 | 아니다 | 있다 | 있다 |
| 거래소 변경의 종류가 저널에 있음 | 아니다(외부 체결로 보임) | 있다 | 있다 |
| 다음 포지션 응답으로 자동 맞춤 | 아니다 | 그렇다 | 그렇다 |
| 차단과 해제 | 기존 불일치 | 기존 불일치(`ack`) | 새 차단 + 새 명령 |
| 새 개념 수 | 0 | 입력 3, 이벤트 4, 불일치 종류 2 | B + 차단 1 + 명령 1 |

A는 2의 첫 두 성질을 만족하지 않아 제외했다.

## 7. 선택과 이유

B.

- 입력: `VenueInput::Funding(FundingIn)`, `VenueInput::PositionChange(VenuePositionChangeIn)`(종류 `adl`, `takeover`, `delivery`, `settle`), `VenueInput::UnclassifiedExecution`. 키는 게이트웨이의 체결 키(C-GW G-8)이고 체결과 같은 집합(`seen_fills`, 바닥 시각)에서 중복을 거른다.
- 이벤트: `FundingBooked`, `VenuePositionChanged`, `UnclassifiedExecutionNoted`, `VenueChangeSettled`. 불일치 종류: `VenuePositionChange`, `UnclassifiedExecution`.
- 우리 것이 아닌 주문의 `Trade`는 새 종류(`foreign_order`, 설계 TN R2)를 만들지 않고 기존 외부 체결로 보낸다. 같은 사실에 길이 둘이면 감시자도 둘을 따로 세야 한다.
- 차단은 기존 불일치 차단이다. 일반 주문만 막고(증거금 정책이 있을 때), 재생 뒤에도 남고, 상태 화면에 미확인 불일치로 나오며(U14가 `[OMS P1]`로 보낸다), 운영자가 사유와 함께 `ack`해야 풀린다. R5의 차단 목록과 `clear_hold`는 그것이 필요한 단위(U18b, U19b)에서 만든다.
- 거래소 변경 뒤 포지션: 그 종목은 "거래소 포지션 대기"가 된다. 현재 세션에서 변경 기록 시각보다 뒤에 물은 첫 포지션 응답이 포지션을 정한다. 다르면 `PositionAdjusted { ledger: unattributed, reason: snapshot_after_venue_change }`, 같으면 `VenueChangeSettled`. 어느 쪽이든 대기가 끝난다.
- `PositionAdjusted.reason`은 기본값이 `operator`이고 그 값일 때는 쓰지 않는다. 운영자 조정은 스키마 1과 같은 바이트다.
- 넘침: 변경을 더하면 포지션이 넘치는 경우 기장하지 않고 불일치만 낸다. 차이가 넘치면 맞추지 않고 기존 범위 검사에 맡긴다. 둘 다 결함(프로세스 중단)으로 만들지 않는다.
- 기록 스키마: `RECORD_SCHEMA = 2`, 읽는 스키마 `[1, 2]`. 바뀐 것은 열거형 변형 추가와 기본값 있는 필드 하나라서 스키마 1 기록은 변환 없이 해석된다. 상태 스키마는 그대로 1이다. 새 상태 필드(`venue_change_wait`, 통계 두 개)는 비어 있거나 0이면 쓰지 않으므로 옛 스냅샷의 바이트와 다이제스트가 그대로다.

## 8. 포기한 장점, 남은 위험, 가정

- 포기: R5의 차단 이름(`VenueChange`)으로 화면에서 원인을 바로 보는 것. 지금은 불일치 종류로 본다.
- 위험: 포지션 응답이 변경보다 늦게 물어졌지만 거래소가 변경을 아직 반영하지 않은 값을 주면 코어가 틀린 값으로 맞춘다. 거래소가 응답 시각 기준으로 일관된다는 것은 가정이다(기존 대조와 같은 가정, ADR-014). 감시자 W2가 독립적으로 다시 본다.
- 위험: 스키마 2 세그먼트가 생긴 저널은 스키마 1만 읽는 옛 바이너리로 되돌릴 수 없다(runbook §9).
- 가정: 펀딩·변경·분류 못 한 실행의 키가 체결 키와 겹치지 않는다. Bybit는 모두 `execId`를 쓴다(C-GW G-8 Bybit 행).
