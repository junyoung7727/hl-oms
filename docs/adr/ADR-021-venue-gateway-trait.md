# ADR-021 게이트웨이 trait 하나와 구동기 하나

상태: 채택(구현). 동작 변화 없음.

## 1. 문제와 발생 가능한 실패

- 가상 거래소와 Hyperliquid 게이트웨이가 같은 배선을 각자 복사해 갖고 있었다: 명령마다 작업 하나를 세마포어 아래 띄우는 명령 루프, 조회 루프, 상시 작업(스트림, Hyperliquid는 dead-man switch).
- 세 번째 게이트웨이(Bybit, U16~U17)가 이것을 또 복사하면 동시 실행 상한이나 시작 순서가 구현마다 달라질 수 있다. 상한을 잘못 옮기면 명령이 몰릴 때 작업이 무한히 늘거나 조회가 막힌다.
- 코드 어디에도 "게이트웨이가 무엇을 제공해야 하는지"가 타입으로 적혀 있지 않았다. 의무는 문서([C-GW](../contracts/gateway.md))에만 있었다.

## 2. 일반적으로 만족해야 하는 성질

- C-GW의 의무 13가지는 그대로다. 이 결정은 배선의 위치만 바꾼다.
- 명령 하나에 결과 하나(G-1, G-5), 재전송 금지(G-3), 입력을 버리지 않음(G-9)이 구동기를 거쳐도 유지된다.

## 3. 제약

| 사실 | 출처 |
|---|---|
| 명령은 `SendOrder`, `SendCancel` 둘뿐이고 조회는 `QueryReq` 일곱 종류 | `oms-core` `VenueCommand`, `venue/mod.rs` |
| 명령 동시 상한은 `node.rs`가 `max_inflight_sends + 16`으로 준다. 조회 상한은 가상 거래소 8, Hyperliquid 4 | 변경 전 `simnet.rs`, `hyperliquid/mod.rs` |
| `impl Future`를 돌려주는 trait 메서드는 `dyn`으로 쓸 수 없다 | Rust 1.96 |
| `tests/hl_live.rs`가 `hyperliquid::spawn_with_key`를 직접 부른다 | 시험 코드 |
| 이번 단위에서 기록·이벤트·시험 기대값·Hyperliquid 요청을 바꾸지 않는다 | 설계 TN U12 |

## 4. 필수 조건과 선택 조건

필수: 동작 변화 없음(기존 시험을 고치지 않고 전부 통과). 세 번째 게이트웨이를 `oms-core`를 건드리지 않고 꽂을 수 있음. 명령·조회 동시 상한이 지금과 같음.
선택: 설계 TN §6.5가 나열한 나머지 메서드(정정, 일괄 취소, 고객 주문번호 조회, 계정 보고, 요청 등급, 부재 규칙, 주문번호 변환).

## 5. 대안

| 대안 | 설명 |
|---|---|
| A. 그대로 둔다 | 게이트웨이마다 배선을 복사한다(가장 단순) |
| B. 지금 쓰는 네 가지만 담은 trait + 정적 디스패치 구동기 | `send_order`, `send_cancel`, `query`, `spawn_tasks`, 상수 `QUERY_CONCURRENCY`. `venue::start<G>` |
| C. 설계 TN §6.5의 메서드를 모두 담은 trait | B에 정정, 일괄 취소 등 7가지를 더한다 |
| D. B를 `dyn` trait 객체로 | 미래를 `Box`에 담아 돌려준다 |

## 6. 비교

| 기준 | A | B | C | D |
|---|---|---|---|---|
| 세 번째 게이트웨이의 배선 복사 | 필요 | 불필요 | 불필요 | 불필요 |
| 동작 변화 | 없음 | 없음(시험으로 확인) | 없음, 그러나 쓰이지 않는 메서드를 두 구현이 채워야 한다 | 명령마다 할당 하나 추가(정성 판단, 측정 안 함) |
| 의무가 타입에 드러남 | 아니다 | 지금 쓰는 것만 | 전부, 그중 일곱은 호출자가 없다 | B와 같다 |
| 시험 가능성 | 구현별 | 가짜 게이트웨이로 구동기를 한 번 시험 | 호출자 없는 메서드는 시험할 경로가 없다 | B와 같다 |

A는 필수 조건 "세 번째 게이트웨이를 꽂을 수 있음"을 만족하지 않아 제외했다.

## 7. 선택과 이유

B. `crates/oms-node/src/venue/mod.rs`의 `VenueGateway`와 `start`.

- 조회는 메서드 하나(`query(QueryReq)`)로 둔다. 각 구현의 `match`가 이미 모든 조회 종류를 다루도록 강제하므로 일곱 메서드로 나누면 코드만 옮기고 검사는 늘지 않는다.
- 두 게이트웨이의 trait 구현은 기존 고유 메서드를 경로(`Gateway::send_order(self, cmd)`)로 부른다. 프로토콜 코드는 한 줄도 바꾸지 않았다.
- `node.rs`의 `VenueConfig` 분기는 남는다. 게이트웨이마다 만드는 설정이 다르기 때문이다. 만든 뒤에는 모두 `start`를 지난다.
- C의 메서드는 그것을 쓰는 단위에서 더한다: 주문번호 변환·부재 규칙·중립 증거금 보고는 U13, 요청 예산은 U17(Bybit), 일괄 취소는 U18b(킬 스위치). 정정은 아직 쓰는 단위가 없다.

## 8. 포기한 장점, 남은 위험, 가정

- 포기: 설계 TN §6.5 trait 전체를 한 번에 보는 것. 나머지는 단위마다 생긴다.
- 위험: 고유 메서드를 지우면 trait 구현의 `Gateway::send_order(self, cmd)`가 trait 메서드 자신을 가리켜 무한 재귀가 된다. 막는 것은 컴파일러다. 검토(2026-11-20)에서 가상 거래소의 고유 `send_order` 이름을 바꿔 보니 컴파일 오류(E0277)와 `unconditional_recursion` 경고가 났고, clippy `-D warnings`가 경고도 오류로 만든다. 시험으로 남기지는 않았다.
- 가정: 조회 동시 상한 8과 4는 기존 값을 옮긴 것이며 그 값이 맞는지는 이 결정의 범위가 아니다.

## 9. 근거

- 변경 전 `simnet.rs`의 `spawn`과 `hyperliquid/mod.rs`의 `spawn_with_key`(같은 두 루프, 조회 상한만 다름).
- 시험: `venue::tests::a_gateway_plugged_in_through_the_trait_gets_each_command_and_query_once`, `venue::tests::the_driver_bounds_concurrent_commands_and_queries_and_drops_none`(주장 V-GW-SEAM-1). 가상 거래소 경로의 동작 유지는 기존 `e2e` 전체가 본다.
- 설계 TN(암호화폐 거래 통합 설계 v1.0) §6.5, §7.2. 저장소 밖 문서다.

## 10. 재검토 조건

- 게이트웨이를 실행 중에 바꾸거나 둘 이상을 한 프로세스에서 동시에 돌려야 할 때(그때는 D).
- 명령 종류가 늘 때(정정, 일괄 취소): trait에 메서드를 더하고 구동기의 분기를 넓힌다.
