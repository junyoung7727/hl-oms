# ADR-002 결정적 코어: 시간·설정·외부 정보를 입력으로

상태: 채택.

## 1. 문제와 발생 가능한 실패

판단 로직이 시계, 설정 파일, 네트워크 응답을 직접 읽으면 같은 상황을 다시 만들 수 없다.
장애 조합을 시험으로 재현할 수 없고, 복구 때 "그때 무엇을 근거로 판단했는가"를 답할 수 없다.

## 2. 일반적으로 만족해야 하는 성질

- 같은 상태와 같은 입력이면 같은 결과가 나온다.
- 판단에 쓴 외부 정보가 기록에 남는다.
- 판단 로직을 실행 환경 없이 시험할 수 있다.

## 3. 제약과 우선순위

시뮬레이션으로 수만 가지 장애 순서를 돌려야 한다. 코어 시험이 파일이나 소켓을 요구하면 불가능하다.

## 4. 필수 조건과 선택 조건

필수: 코어는 I/O·시계·난수에 접근할 수 없다. 시간은 입력으로 받는다. 설정은 상태다.
선택: 플랫폼이 달라도 비트 단위로 같은 결과.

## 5. 대안

| 대안 | 설명 |
|---|---|
| A. 규칙으로만 금지 | 코어 코드에서 시계와 I/O를 쓰지 않기로 약속한다. 가장 단순 |
| B. trait으로 주입 | `Clock`, `Config` trait을 코어에 주입하고 시험에서 바꿔 끼운다 |
| C. 의존성 경계 + 값으로 전달 | 코어 crate가 I/O 가능한 의존성을 갖지 않는다. 시간은 `handle(at, input)`의 인자, 설정은 입력 |

## 6. 비교

| 기준 | A | B | C |
|---|---|---|---|
| 위반 방지 | 리뷰에 의존 | 주입 우회가 가능 | `Cargo.toml`에 없으면 컴파일되지 않는다. `std::fs`·`std::time`은 여전히 쓸 수 있으므로 완전하지는 않다 |
| 기록 가능성 | 별도 작업 | trait 호출을 기록하려면 별도 작업 | 입력이 곧 기록이다 |
| 복잡성 | 낮음 | 제네릭 또는 동적 호출이 코어에 퍼진다 | 낮음. 함수 인자뿐 |
| 재생 | 보장 없음 | 주입 구현에 의존 | 기록의 시각과 이벤트만으로 재생 |

정성 판단이다.

## 7. 선택과 이유

C. `oms-core`의 의존성은 `serde`와 `serde_json`뿐이다. 진입점은 둘이다.

- `Core::handle(at, &Input) -> Output`: 판단. `at`은 실행 계층이 부여한 시각이다.
- `Core::apply(at, &Event)`: 결정된 이벤트의 적용. 복구가 쓴다.

구체적인 입력화:

| 외부 정보 | 입력 | 기록 |
|---|---|---|
| 시간 | 모든 입력의 `at`. 코어 스레드가 벽시계를 읽어 부여하고 감소하지 않게 보정한다 | 기록의 `at` |
| 시간 경과 | `Tick` 입력 | 이벤트가 생길 때만 기록 |
| 설정 | `Config` 입력 → `ConfigActivated` 이벤트(전체 내용 포함) | 저널. 복구는 설정 파일을 읽지 않는다 |
| 거래소 통보·조회 결과 | `Venue(...)` 입력 | 이벤트가 생길 때 입력과 함께 기록 |
| 참조 가격 | `RefPrice` 입력 → `RefPriceUpdated` | 저널. 수용 이벤트에도 쓴 가격을 남긴다 |
| 저장 공간 | `Storage` 입력 → 변할 때만 `StorageLowChanged` | 저널 |
| 연결 상태 | `Link` 입력 → `LinkChanged` | 저널 |

코어 안에서 순서가 결과에 영향을 주는 컬렉션은 모두 `BTreeMap`/`BTreeSet`이다. 해시 순서에 의존하지 않는다.
숫자는 정수뿐이다([ADR-009](ADR-009-numeric.md)).

## 8. 포기한 장점, 남은 위험, 가정

- `std`의 시계·파일 API는 의존성 경계로 막히지 않는다. `oms-core/src`에 `SystemTime`, `Instant`, `std::fs`, `std::net`이 없다는 것을
  `cargo run -p xtask -- verify`의 소스 검사가 확인한다.
- 벽시계가 뒤로 가면 `at`이 멈춘다(코어 스레드가 직전 값보다 작은 시각을 부여하지 않는다). 시간 기반 판단(만료, 재시도)이 그만큼 늦어진다.
  이쪽은 안전한 방향이다: 수용이 줄거나 결과 불명이 오래갈 뿐이다.
- 벽시계가 **앞으로** 뛰는 것은 안전하지 않다. 로컬 시계가 거래소보다 여유(`absence_margin`) 넘게 앞서면, 거래소가 아직 놓을 수 있는 요청을
  "만료 + 여유가 지났는데 없다"고 보고 `NotPlaced`로 닫는다([ADR-005](ADR-005-unknown-outcome.md) §8, 가정 A-02).
  시뮬레이션의 `absence_rule_depends_on_the_clock_margin`이 이 경우를 일부러 만들어 위반이 잡히는 것을 보인다.
  어느 방향이든 중복 전송은 생기지 않는다. 프로세스는 호스트 시계의 동기화 상태를 확인하지 않는다(G-OPS-07).
- 이벤트가 생기지 않은 입력은 기록되지 않는다. 따라서 "같은 입력이 왔지만 아무 일도 없었다"는 저널에 없다.
  대신 상한이 있는 진단용 목록(최근 500건, 휘발성)에 남는다.

## 9. 근거

- 시나리오 시험 54건은 매 입력 뒤에 "이벤트만 적용한 그림자 상태 = 살아 있는 상태"를 확인한다.
- `recorded_inputs_re_decide_to_the_recorded_events`: 기록된 입력을 다시 판단하면 같은 이벤트가 나온다.
- 시뮬레이션의 `a_seed_reproduces_the_same_run`: 같은 seed는 같은 저널을 만든다.
- 프로세스 시험 뒤 `oms-node verify --re-decide`가 실제 저널에 대해 같은 것을 확인한다.

## 10. 재검토 조건

판단에 부동소수점이나 외부 라이브러리의 비결정적 결과가 필요해질 때. 그 값은 입력으로 받아 기록해야 한다.
