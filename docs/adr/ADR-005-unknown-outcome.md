# ADR-005 결과를 모르는 전송의 복구: 재전송 금지와 만료 기반 부재 판정

상태: 채택. 동작 계약은 [C-SEND, C-DOUBT](../contracts/order-lifecycle.md).

"결과 불명(in doubt)"은 주문 요청을 보냈거나 보냈을 수 있는데 거래소가 받았는지 모르는 상태다.

## 1. 문제와 발생 가능한 실패

요청을 보낸 뒤 응답이 오지 않는 경우는 세 가지이고 OMS는 구별할 수 없다.
요청이 거래소에 닿지 않았다. 닿았고 처리됐지만 응답이 사라졌다. 아직 가는 중이며 나중에 닿는다.

- "실패"로 간주해 예약을 풀면: 주문이 실제로 놓였을 때 예약 없는 체결이 생긴다.
- "실패"로 간주해 다시 보내면: 같은 주문이 두 번 놓인다.
- 영원히 불명으로 두면: 한도가 계속 묶이고 신규 주문이 계속 차단된다.
- 프로세스가 전송 도중 죽으면 같은 문제가 재시작 뒤에 나타난다.

## 2. 일반적으로 만족해야 하는 성질

- 재생과 복구가 주문을 다시 보내지 않는다.
- 불명 상태에서는 그 주문이 체결될 수 있는 최대량을 계속 예약한다.
- 불명은 거래소의 계약에 근거한 증거로만 해소한다.
- 해소 수단이 없으면 사람이 해소한다. 시스템이 추측하지 않는다.

## 3. 제약: Hyperliquid가 제공하는 것과 제공하지 않는 것

출처는 [research/hyperliquid-protocol.md](../research/hyperliquid-protocol.md) §2, §3이다.

| 사실 | 확신도 |
|---|---|
| `orderStatus`를 클라이언트 주문 ID(cloid)로 조회할 수 있다. 없으면 `unknownOid`를 준다 | 문서 명시, testnet 비인증 실측 |
| `unknownOid`는 부재의 증명이 아니다. 요청이 아직 가는 중일 수 있다. nonce 유효 창은 2일이다 | 문서 명시(창), 추론(귀결) |
| `expiresAfter`를 붙이면 그 시각 뒤에는 액션이 거부된다 | 문서 명시. 비교 기준 시계는 문서에 없다 |
| 같은 cloid를 다시 보냈을 때 거부된다는 서술은 어디에도 없다 | 문서에 명시 없음 |
| API 서버는 블록에 포함된 뒤에 응답한다. 응답을 받았으면 결과는 확정이다 | 문서 명시 |
| 조회는 API 서버의 로컬 상태에서 답한다. 최신 블록보다 늦을 수 있다 | 추론. 지연 한도는 문서에 없다 |

## 4. 필수 조건과 선택 조건

필수: 신규 주문을 자동으로 재전송하지 않는다. 불명 동안 예약 유지. 증거 없는 종결 금지.
선택: 불명이 사람 개입 없이 유한 시간 안에 해소된다.

## 5. 대안

| 대안 | 해소 방법 |
|---|---|
| A. 운영자만 해소 (가장 단순) | 불명 주문은 운영자가 거래소 화면을 보고 닫는다 |
| B. 같은 cloid로 재전송 | 거래소가 중복을 거부한다고 믿고 다시 보낸다 |
| C. 조회로 발견 + 만료 뒤 부재 판정 | 모든 전송에 `expiresAfter`를 붙인다. 조회로 찾으면 정상 진행. 만료 + 여유 뒤의 조회에서도 없으면 "놓이지 않음"으로 닫는다 |
| D. C + `noop`으로 nonce 소진 | 시간 초과 시 같은 nonce의 `noop`을 보내 원 요청을 무효화한다. 만료를 기다리지 않아도 된다 |

## 6. 비교

| 기준 | A | B | C | D |
|---|---|---|---|---|
| 중복 주문 위험 | 없음 | 있음. cloid 중복 거부는 문서 근거가 없다 | 없음 | 없음 |
| 예약 없는 체결 위험 | 없음 | 없음 | 가정 A-01, A-02가 깨지면 있음 | C와 같음 |
| 해소 시간 | 사람 대기 | 즉시 | 만료 시각 + 여유(기본 10초) | 시간 초과 직후 |
| 의존하는 거래소 계약 | 없음 | 문서에 없는 동작 | `expiresAfter` 거부(문서 명시) | 이미 쓰인 nonce에 대한 `noop` 응답(문서에 없음) |
| 운영 부담 | 높음. 시간 초과마다 호출 | 낮음 | 낮음 | 낮음 |
| 구현 복잡성 | 가장 낮음 | 낮음 | 중간 | 높음. nonce를 코어가 추적하거나 게이트웨이가 상태를 가져야 한다 |

이 표의 값은 모두 정성 판단이거나 거래소 문서의 서술에서 온 것이다. 측정값은 없다. "해소 시간"의 10초는 설정의 기본값이다.

## 7. 선택과 이유

C를 채택한다. B는 필수 조건을 문서에 없는 가정으로만 만족하므로 제외한다. D는 해소가 빠르지만
"이미 쓰인 nonce로 보낸 noop이 어떻게 응답하는가"가 문서에 없어 그 응답으로 원 주문의 적용 여부를 단정할 수 없다. testnet 실험 뒤에 재검토한다.

규칙:

1. 전략은 모든 신규 주문에 절대 시각 `expires_at`을 붙인다. 게이트웨이는 이를 거래소의 `expiresAfter`로 보낸다.
2. 게이트웨이는 결과를 보수적으로 분류한다. 요청의 어떤 바이트도 나가지 않았음이 확실할 때만 `NotSent`,
   거래소의 명시적 거부일 때만 `Rejected`, 나머지는 모두 `Unknown`이다.
3. `Unknown`이면 주문은 전송 대기 상태에 머물고 결과 불명 표시가 붙는다. 예약은 그대로다. 계좌 전체의 신규 주문이 차단된다.
4. 대조기가 cloid로 상태를 조회한다. 찾으면 정상 주문이 된다. 스트림 통보나 체결이 먼저 도착해도 같다.
5. 조회 결과가 "없음"이고, 그 조회를 보낸 시각이 `expires_at + absence_margin` 이후이면 `NotPlaced`로 닫고 예약을 푼다.
   그 전의 "없음"은 무시한다.
6. 프로세스가 재시작하면 결과 기록이 없는 모든 전송 대기 주문에 불명 표시를 붙인다(사유: 재시작). 이후는 3~5와 같다.
7. 거래소가 만료를 강제하지 않는 환경(`venue_enforces_expiry = false`)에서는 5를 적용하지 않는다. 운영자가 근거를 적어 닫는다.

필수 조건의 성립: 전송 명령은 `OrderAccepted` 이벤트에서만 한 번 파생되고(재생은 명령을 만들지 않는다),
불명 표시는 예약을 건드리지 않으며, 종결은 5의 조건이나 실제 증거에서만 일어난다.

취소는 다르게 다룬다. 취소 요청은 반복해도 안전하므로 결과 불명이면 간격을 두고 재시도한다(상한 5회).

## 8. 포기한 장점, 남은 위험, 가정

- 불명 주문 하나가 계좌 전체의 신규 주문을 `expires_at + 여유`까지 막는다. 전략이 만료를 짧게(수 초) 잡아야 한다.
  만료된 액션은 거래소의 계좌 한도를 5배 소모한다(문서 명시). 만료를 지나치게 짧게 잡으면 한도를 낭비한다.
- 가정 A-01: 거래소는 `expiresAfter`가 지난 요청을 놓지 않는다.
- 가정 A-02: 로컬 시계와 거래소의 기준 시계 차이, 조회가 최신 블록보다 늦는 시간의 합이 `absence_margin`보다 작다.
- 두 가정이 깨지면 닫은 주문이 뒤늦게 나타난다. 그때는 전송 응답, 상태 통보, 열린 주문 대조 가운데 먼저 오는 것이 `OpenAfterClose` 불일치를 제기하고 신규 주문을 차단한다.
  체결이 오면 기장하고 `FillAfterClose`를 제기한다. 예방이 아니라 탐지다. 그 사이에 풀린 예약만큼 한도를 넘을 수 있다.
- 로컬 시계가 앞으로 뛰는 것은 A-02를 깨는 한 방법이다([ADR-002](ADR-002-deterministic-core.md) §8).
- `orderStatus`의 조회 가능 기간이 문서에 없다. 부재 판정 규칙은 전송 대기 주문에만 적용되므로, 접수된 주문이 나중에 `unknownOid`로 바뀌어도 그 주문을 닫지 않는다.
  대신 그 주문의 재확인이 끝나지 않아 신규 주문이 막힌 채로 남는다. 이것이 조용히 지속되지 않도록 `StatusConflict` 불일치를 제기하고, 운영자가 거래소에서 확인한 뒤 수동으로 닫는다.

## 9. 근거

- 시나리오 시험: `unknown_send_outcome_keeps_the_reservation…`, `not_found_closes_an_in_doubt_order_only_after_expiry_plus_margin`,
  `not_found_never_closes_when_the_venue_does_not_enforce_expiry`, `restart_puts_outstanding_sends_in_doubt_and_never_resends`.
- 시뮬레이션: 요청 유실·지연·응답 유실·재시작을 섞은 실행에서 단일 전송, 단일 주문, I-BRIDGE가 유지된다(주장 V-SIM-1, 프로파일마다 seed 3000개의 실행은 V-SIM-4).
  가정을 깨는 두 반례 실행(거래소가 만료를 무시, 시계 차이가 여유 초과)은 주문·포지션에 관한 속성의 위반으로 잡힌다(V-DOUBT-3. 시험이 어떤 속성으로 잡혔는지 확인한다).
- 간격 검토의 재현 시험: `f3_placed_evidence_for_an_order_closed_as_not_placed_is_flagged`, `an_acknowledged_order_the_venue_no_longer_knows_is_reported_not_closed`.
- 프로세스 시험: `a_lost_request_is_closed_only_after_its_send_window`, `a_kill_during_send_does_not_duplicate_the_order`.
- 실제 거래소에서 확인하지 않은 것: `expiresAfter`의 기준 시계와 거부 응답 형태, 조회 지연의 크기. testnet 실험 목록에 있다.

## 10. 재검토 조건

testnet에서 `expiresAfter`가 기대와 다르게 동작할 때. `noop`의 응답 계약을 실험으로 확인했을 때(D 채택 검토).
거래소가 cloid 중복 거부를 문서화했을 때.
