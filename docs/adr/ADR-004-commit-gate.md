# ADR-004 커밋 게이트: 기록 → 내구화 → 공개·응답·전송

상태: 채택.

## 1. 문제와 발생 가능한 실패

기록, 내구화, 상태 적용, 응답, 거래소 전송의 순서를 잘못 잡으면 장애 뒤에 다음이 남는다.

- 전송은 됐는데 기록이 없다. 재시작한 OMS는 그 주문을 모른다. 예약 없이 체결이 일어난다.
- 응답은 갔는데 기록이 없다. 전략은 주문이 있다고 믿고, OMS는 없다고 믿는다.
- 조회 화면이 기록되지 않은 상태를 보여 준다.

## 2. 일반적으로 만족해야 하는 성질

외부에서 관측 가능한 모든 것(응답, 전송, 조회 결과, 구독 이벤트)은 내구화된 기록으로 설명된다.
이를 output commit이라 부른다. 장애 뒤 복구된 상태는 장애 전에 밖으로 나간 모든 출력과 양립한다.

## 3. 제약과 우선순위

허용 데이터 손실 0(프로세스·OS 재시작 기준). 지연 기준은 로컬 응답 p99 20 ms.
측정한 fdatasync는 저널 장치(970 EVO Plus 2TB)에서 중앙값 2.5 ms, p99 2.9 ms다(`evidence/perf/fsync-nvme.json`, 단독 측정). 500GB SSD에서는 단독 0.9 ms였지만 부하 중 꼬리가 15~18 ms였다([성능 문서](../performance/README.md)).

## 4. 필수 조건과 선택 조건

필수: 내구화 전에는 응답·전송·공개가 없다. 내구화 실패 시 그 배치의 출력은 영원히 나가지 않는다.
선택: 여러 입력이 한 번의 flush를 공유한다. flush 중에도 코어가 다음 입력을 판단한다.

## 5. 대안

| 대안 | 순서 |
|---|---|
| A. 먼저 기록, 그다음 판단 (LMAX 원형) | 입력 기록·flush → 코어 판단 → 출력 |
| B. 판단, 기록, flush, 출력을 요청마다 순차로 (가장 단순) | 한 스레드가 입력 하나씩 끝까지 처리 |
| C. 판단은 즉시, 출력은 flush 뒤 (그룹 커밋) | 코어가 배치를 판단 → 커밋 단계가 배치를 한 번에 쓰고 flush → 출력 해제 |

비동기 flush(주기적으로만 flush하고 응답은 먼저)는 필수 조건을 어기므로 후보가 아니다.

## 6. 비교

| 기준 | A | B | C |
|---|---|---|---|
| output commit | 성립 | 성립 | 성립 |
| 기록 내용 | 입력만 가능(판단 전이므로) | 입력+이벤트 가능 | 입력+이벤트 가능 |
| 요청당 flush | 배치 공유 가능 | 요청마다 1회. 처리량 상한 ≈ 1/flush 시간(측정 기준 약 1100건/초) | 배치 공유 |
| 코어의 메모리 상태 | 저널보다 앞서지 않는다 | 앞서지 않는다 | 진행 중인 배치만큼 앞선다 |
| flush 실패 처리 | 코어가 아직 판단 전 | 그 요청만 실패 | 앞선 상태를 버려야 한다 → 프로세스 정지 |
| 복잡성 | 단계 둘 + 순번 관문 | 가장 낮다 | 단계 둘. 출력은 커밋 단계에서 순차 해제 |

A는 [ADR-003](ADR-003-journal-record.md)에서 택한 "입력+이벤트 기록"과 맞지 않는다.

## 7. 선택과 이유

C. 구현은 `crates/oms-node/src/pipeline.rs`다.

```text
코어 스레드:   입력 배치를 꺼냄 → 각 입력에 시각 부여, 판단, 적용 → (기록, 응답, 명령)을 커밋 단계로
커밋 단계:     배치의 기록을 write → fdatasync → [여기서부터 공개]
               1. 읽기 모델에 이벤트 적용
               2. 응답 전달
               3. 전송 명령을 게이트웨이로
               4. 구독자에게 이벤트
```

필수 조건이 성립하는 이유는 코드의 순서다. `Committer::commit`에서 `writer.sync()`가 `Ok`를 돌려준 뒤에야
읽기 모델 갱신, 응답 송신, 명령 송신 코드에 도달한다. `Err`이면 함수가 즉시 반환하고, 호출자는 치명 상태를 걸고
입력 큐를 닫는다. 그 배치의 응답 채널은 버려진다(전략은 "결과 미확인" 오류를 받는다).

읽기 모델을 응답보다 먼저 갱신한다. 응답을 받은 전략이 곧바로 조회해도 그 주문이 보인다.

코어의 메모리 상태가 저널보다 앞서는 것은 안전하다. 앞선 부분에서 나온 출력이 하나도 나가지 않았으므로,
그 부분이 사라져도 외부의 누구도 모순을 볼 수 없다. 대가는 "flush 실패 = 프로세스 정지"다.
실패한 flush를 다시 시도하지 않는다. 실패 뒤의 재시도가 성공해도 데이터가 유실됐을 수 있기 때문이다
([research/lmax-durability-rust.md](../research/lmax-durability-rust.md) Part 2 (e)).

커밋을 코어 스레드에서 직접 할지 별도 스레드에서 할지는 [ADR-012](ADR-012-threads-crates.md)에서 측정으로 정한다.

## 8. 포기한 장점, 남은 위험, 가정

- 로컬 응답이 flush 한 번을 기다린다. 측정상 중앙값 약 1 ms다.
- 가정 A-05: `fdatasync` 성공은 장치 내구화를 뜻한다. 소비자용 SSD(전원 손실 보호 없음)에서 이를 소프트웨어로 확인할 수 없다.
  전원 장애 시험은 하지 않았다.
- 구독 이벤트는 내구화 뒤에 나가지만 전달은 최선 노력이다. 느린 구독자는 끊긴다.

## 9. 근거

- `outputs_follow_durability_with_a_commit_thread`, `…_with_inline_commit`: flush 실패를 (쓰기 전에) 주입하면 응답·명령·읽기 모델 변경이 전혀 없다.
- 경계마다 프로세스를 멈추는 시험 5건(`crash_points.rs`, 주장 V-COMMIT-4): 쓰기 전, 쓴 뒤 flush 전, flush 뒤 공개 전, 응답 뒤 전송 명령 전, 쓴 뒤의 flush 오류.
  [C-COMMIT](../contracts/commit.md)의 경계별 표의 행과 하나씩 대응한다. 프로세스 중단이지 전원 장애가 아니다.
- 시뮬레이션의 커밋 모델: 충돌 시 미내구 기록과 그 출력을 함께 버린다. 이 모델에서 단일 전송·단일 주문 성질이 유지된다(주장 V-SIM-1, 더 긴 실행은 V-SIM-4).
- 프로세스 시험 `random_kills_under_load_keep_books_consistent`: 무작위 SIGKILL 뒤 거래소 쪽 장부와 일치한다(V-COMMIT-2, V-COMMIT-5).
- 변이 점검 M01: flush의 실패를 무시하고 출력을 내보내게 고치면 위의 첫 시험이 실패한다([verification](../verification/README.md)).
- panic은 프로세스를 끝낸다(빌드 프로파일의 `panic = "abort"`). 코어 스레드만 죽고 소켓이 살아 있는 상태는 생기지 않는다. 시험은 없다(G-REL-05).

## 10. 재검토 조건

로컬 응답 p99가 기준(20 ms)을 넘을 때. 저장 장치의 flush가 수십 ms인 환경(HDD: 측정 중앙값 47 ms)으로 옮길 때.
그때의 선택지는 전원 손실 보호가 있는 장치이지, flush 생략이 아니다.
