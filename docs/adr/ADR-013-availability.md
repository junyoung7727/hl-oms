# ADR-013 가용성: 단일 인스턴스와 중복 실행 방지

상태: 채택.

## 1. 문제와 발생 가능한 실패

- 같은 계좌에 OMS 두 개가 동시에 주문한다. 각자의 한도 계산이 서로를 모른다. 같은 주문 ID를 두 주문에 쓴다.
- 죽은 줄 알았던 옛 프로세스가 살아 있어 계속 전송한다.
- 서버가 사라지면 저널도 사라진다.

## 2. 일반적으로 만족해야 하는 성질

한 계좌의 주문 판단 주체는 어느 순간에도 하나다. 새 주체가 시작되기 전에 옛 주체의 전송 능력이 실제로 없어져야 한다.
번호(epoch)만 비교하는 것으로는 멈춘 옛 프로세스의 전송을 막지 못한다.

## 3. 제약

단일 호스트, 단일 운영자. 허용 중단은 분 단위. 자동 승격은 요구하지 않는다.

## 4. 필수 조건과 선택 조건

필수: 같은 데이터 디렉터리에 writer 하나. 재시작 뒤 대조 전에는 신규 주문 없음.
선택: 다른 호스트에서의 중복 실행 방지, 서버 유실 시 저널 보존.

## 5. 대안

| 대안 | 설명 |
|---|---|
| A. 디렉터리 잠금만 (가장 단순) | 데이터 디렉터리의 `LOCK` 파일에 배타 잠금 |
| B. A + 수동 승격 대기 노드 | 저널을 다른 호스트로 복제하고 운영자가 승격 |
| C. 합의 기반 복제 + 자동 승격 | 3노드 이상, 선출, 전송 차단 |

## 6. 비교

| 기준 | A | B | C |
|---|---|---|---|
| 같은 호스트 중복 실행 | 막는다 | 막는다 | 막는다 |
| 다른 호스트 중복 실행 | 못 막는다 | 절차에 의존 | 선출이 막는다. 전송 차단은 별도 필요 |
| 서버 유실 시 기록 | 사본 주기만큼 유실 | 복제 지연만큼 유실 | 과반 커밋이면 유실 없음 |
| 복구 시간 | 수동, 분 단위 이상 | 수동 승격 | 자동, 초 단위 |
| 개발·운영 비용 | 최저 | 중간 | 높음 |

정성 판단이다.

## 7. 선택과 이유

A.

- `oms_journal::recover`가 `LOCK` 파일에 `File::try_lock`을 건다. 잠겨 있으면 시작을 거부한다(종료 코드 3). 잠금은 프로세스가 죽으면 커널이 푼다.
- `instance_id`는 데이터 디렉터리마다 다르다. 세그먼트 헤더와 스냅샷에 있고 다르면 시작을 거부한다.
  거래소에 내는 클라이언트 주문 ID의 상위 64비트이므로, 다른 디렉터리에서 낸 주문은 대조에서 "남의 주문"으로 보인다.
- 재시작하면 링크가 올라와 대조가 끝날 때까지 `LinkDown`/`Resync` 차단이 걸린다.
- 게이트웨이 세션 번호의 상위 32비트는 부팅 번호다. 이전 프로세스에서 온 늦은 통보는 세션이 달라 "신선한 증거"로 세지 않는다.

서버 장애 복구 절차는 [운영 문서](../operations/runbook.md) §7.6에 있다. 요지:

- **옛 호스트가 다시 살아나지 않음을 사람이 확인한 뒤에만** 새 호스트를 띄운다.
- 마지막 내구 기록까지 있는 저널(디스크를 그대로 옮긴 경우)이면 그것으로 띄운다.
- 과거 시점의 사본밖에 없으면 **그 사본으로 거래를 재개하지 않는다.** 빈 디렉터리로 새 인스턴스를 띄우고, 거래소의 포지션은 운영자가 `adjust`로 장부에 넣는다.

과거 사본으로 재개하면 안 되는 이유: 사본 이후에 낸 주문의 번호를 새 주문이 다시 쓴다. 클라이언트 주문 ID가 `instance_id + 주문 번호`이므로
옛 주문과 새 주문의 ID가 같아지고, 조회가 옛 주문의 상태를 새 주문의 증거로 돌려줄 수 있다.
사본 이후의 주문은 열린 주문 대조에서 `OrphanOrder`로 드러나 신규 주문을 막지만, 운영자가 그것을 확인 처리하고 재개하면 충돌이 생긴다.
소프트웨어는 이 실수를 막지 못한다. 2026-10-02의 간격 검토에서 찾은 위험이며, 주문 번호를 건너뛰게 하는 복구 도구는 만들지 않았다.

## 8. 포기한 장점, 남은 위험, 가정

- 다른 호스트에서 저널 사본으로 두 번째 인스턴스를 띄우는 실수를 소프트웨어가 막지 못한다(A-06).
  두 인스턴스는 `instance_id`가 같으므로 cloid가 충돌한다. Hyperliquid는 서명자별 nonce를 추적하므로 같은 agent 키를 쓰는 두 프로세스는 nonce 충돌로 일부 요청이 거부될 수 있지만,
  그것에 기대지 않는다. 문서는 "프로세스당 API 지갑 하나"를 권한다.
- 서버가 죽어 있는 동안 거래소의 주문은 살아 있다. 완화 수단은 거래소의 예약 취소이며 U-05에 남긴다.
- 잠금은 로컬 파일 시스템의 권고 잠금이다. NFS 등에서는 보장이 다르다. 저널을 네트워크 파일 시스템에 두지 않는다.

## 9. 근거

- `a_second_writer_is_refused`(저널), `only_one_node_can_own_a_data_directory`(프로세스), `a_journal_of_another_instance_is_refused`.
- 재시작 시험 전부(차단 → 대조 → 재개).

## 10. 재검토 조건

허용 중단 시간이 초 단위로 줄 때. 서버 유실 시 기록 유실이 허용되지 않을 때. 계좌를 여러 호스트에서 나눠 운용할 때.
