# ADR-006 멱등성 키와 식별자

상태: 채택. 동작 계약은 [C-IDEM](../contracts/idempotency.md), 식별자 수명은 [identifiers](../contracts/identifiers.md).

## 1. 문제와 발생 가능한 실패

전략은 별도 프로세스다. 응답을 받지 못하면 같은 요청을 다시 보낸다(연결 끊김, OMS 재시작, 시간 초과).
OMS가 재전송을 구별하지 못하면 한 번의 의도가 두 주문이 된다.
반대로 중복 판별 기록을 영원히 들고 있으면 메모리가 무한히 자란다. 기록을 지우면 늦게 온 재전송이 새 주문이 된다.

## 2. 일반적으로 만족해야 하는 성질

- 같은 키의 같은 요청은 효과를 한 번만 낸다. 재시작을 넘어서도 그렇다.
- 같은 키의 다른 요청은 조용히 받아들여지지 않는다.
- 중복 판별 기록의 크기에 상한이 있고, 기록을 지워도 위 성질이 깨지지 않는다.

## 3. 제약

전략과 OMS는 같은 호스트이므로 시계가 같다. 주문에는 [ADR-005](ADR-005-unknown-outcome.md) 때문에 어차피 만료 시각이 필요하다.

## 4. 필수 조건과 선택 조건

필수: (전략, 키)마다 주문은 최대 하나. 재시작 뒤에도 유지. 기록 삭제 뒤에도 유지.
선택: 거절된 요청도 같은 답을 돌려준다.

## 5. 대안

| 대안 | 방식 |
|---|---|
| A. 키를 영구 보관 (가장 단순) | 모든 키를 메모리와 스냅샷에 계속 둔다 |
| B. 전략별 단조 증가 번호 | 전략이 증가하는 번호를 붙이고 OMS는 최고 번호와 작은 창만 기억한다 |
| C. 불투명 키 + 요청의 만료 시각 | 키는 요청이 만료될 때까지만 기억한다. 만료된 요청은 거절한다 |

## 6. 비교

| 기준 | A | B | C |
|---|---|---|---|
| 정확성 | 완전 | 완전 | 완전(만료 거절과 결합할 때) |
| 메모리 상한 | 없음 | 전략 수에 비례 | 수용률 × max(종결 주문 보존 시간, 만료 한도 + 여유). 주문 수 상한으로 강제 |
| 전략의 부담 | 고유 키 생성 | 재시작을 넘어 번호를 이어야 한다 | 고유 키 + 절대 만료 시각 |
| 재시작 뒤 | 스냅샷이 계속 커진다 | 문제 없음 | 문제 없음 |

이 표의 값은 모두 정성 판단이다. 측정값은 없다.

## 7. 선택과 이유

C.

- 키는 `(strategy, client_order_id)`. 전략이 정한다. 범위는 한 OMS 인스턴스(데이터 디렉터리) 안이다.
- 요청에는 절대 시각 `expires_at`이 필수다. 상대 시간(TTL)을 받지 않는 이유는, 재전송된 요청이 원래 요청과 바이트 단위로 같아야
  "같은 요청"으로 판별할 수 있기 때문이다.
- 판별: 키가 이미 있으면 주문의 필드(종목, 방향, 수량, 가격, TIF, reduce_only, 만료 시각)를 요청과 직접 비교한다. 해시를 쓰지 않는다.
  같으면 `duplicate`와 현재 상태를 답하고 아무것도 바꾸지 않는다. 다르면 `conflict`를 답하고 아무것도 바꾸지 않는다.
- 삭제: 주문은 종결 후 보존 시간이 지나고, **그리고** `expires_at + dedup_grace`가 지난 뒤에만 메모리에서 제거된다.
- 삭제 뒤에 온 같은 키의 요청은 만료 시각이 이미 지났으므로 `Expired`로 거절된다. 그래서 두 번째 주문이 생기지 않는다.
- 만료 한도: `expires_at − 현재`가 `max_expiry_horizon`(기본 60초)을 넘으면 거절한다. 키를 기억해야 하는 시간이 이것으로 묶인다.
  기록 수의 상한은 따로 강제한다: 메모리의 주문이 100,000건(설정)에 이르면 신규 주문을 `capacity_exhausted`로 거절한다.
  종결 주문은 조회용으로 1시간 남으므로, 기본값에서 초당 약 27.8건을 넘는 수용이 한 시간 이어지면 이 상한에 닿는다. 거래소의 IP 한도(초당 20건)로는 닿지 않는다.
- 거절은 키를 소모하지 않는다. 거절된 요청은 주문을 만들지 않으므로 "키당 주문 하나"에 영향이 없다. 같은 키로 다시 보내면 새로 평가된다.

재시작 뒤: 색인 `by_client`는 `OrderAccepted` 이벤트의 적용으로 재구성되므로 저널 재생만으로 같은 답이 나온다.

### 식별자

| 식별자 | 정하는 쪽 | 범위와 수명 |
|---|---|---|
| `client_order_id` | 전략 | (전략, 키). 요청 만료까지 기억 |
| `order_id` | 코어 | 인스턴스 안에서 1부터 증가, 재사용 없음. 저널에 영구 |
| `instance_id` | 데이터 디렉터리 생성 시 난수 | 디렉터리의 수명. `INSTANCE` 파일과 세그먼트 헤더에 기록 |
| 거래소 클라이언트 ID(cloid) | 파생: `instance_id`(상위 64비트) + `order_id`(하위 64비트) | 저장하지 않는다. 다른 인스턴스나 수동 주문과 구별된다 |
| 거래소 주문 ID(oid) | 거래소 | 접수 증거와 함께 알게 된다 |
| 체결 키 | 게이트웨이가 거래소 필드로 구성 | 체결 동기화 시점 기준 24시간 기억. 그보다 오래된 통보는 재전달로 본다 |
| 저널 순번 `seq` | 코어 스레드 | 1부터 빈틈 없이 증가 |
| 링크 세션 | 게이트웨이. 상위 32비트가 부팅 번호 | 재시작과 재접속을 넘어 증가 |

## 8. 포기한 장점, 남은 위험, 가정

- 거절 응답을 못 받은 전략이 같은 키로 다시 보내면, 상황이 바뀌어 이번에는 수용될 수 있다. 만료 시각이 그 창을 묶는다.
- 전략이 서로 다른 의도에 같은 키를 쓰면 두 번째는 `conflict`로 거절된다. 키의 고유성은 전략 책임이다.
- 전략의 시계가 OMS와 다르면(다른 호스트) 이 설계는 성립하지 않는다. 같은 호스트라는 결정에 기댄다.
- 데이터 디렉터리를 새로 만들면 키 기억이 사라진다. 새 `instance_id`가 cloid를 구분해 주지만, 전략이 옛 키를 다시 보내면 새 주문이 된다.

## 9. 근거

- 시나리오: `same_key_same_request_creates_one_order_and_one_send`, `same_key_different_request_is_a_conflict_without_effect`,
  `a_rejection_does_not_consume_the_key`, `the_duplicate_answer_survives_restart`, `a_key_is_forgotten_only_after_its_request_expired`.
- 시뮬레이션 `purge` 프로파일: 보존 시간을 1초로 줄이고 재전송을 20%로 올린 실행에서 키당 수용 1회, 키당 전송 1회가 유지된다(주장 V-IDEM-2, seed 3000개의 실행은 V-SIM-4).
- 프로세스: `a_repeated_request_never_creates_a_second_order`(8개 연결이 같은 요청을 동시에 보냄, 강제 종료 뒤에도 유지).

## 10. 재검토 조건

전략이 다른 호스트에서 접속하게 될 때(시계 가정 붕괴). 만료 한도를 분 단위 이상으로 늘려야 하는 주문 유형이 생길 때.
