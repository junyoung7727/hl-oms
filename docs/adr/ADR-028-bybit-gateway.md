# ADR-028 Bybit 게이트웨이

상태: 만드는 중. U16b: 설정, 서명, REST 클라이언트, 시작 확인, IP 확인, cancel-all. U16c: 조회 일곱 가지와 실행 분류표, 증거금 보고. U16d: 비공개 스트림, `VenueGateway` 구현과 노드 연결, 상태 API의 막힘 이유. U17a: REST 주문·취소, 응답 분류표, 요청 한도, 틱·수량 단위 확인. U17b: WS Trade 연결, 주문·취소의 첫 경로(REST는 WS Trade가 아무것도 쓰지 않았을 때만). U17c: 참조 가격(공개 스트림의 mark price)과 가짜 Bybit 서버에 대한 노드 끝에서 끝까지 시험(저널 flush 실패 포함). U17d(이 판): 교차 계좌의 유지증거금률 규칙(증거금 보고의 `totalMaintenanceMargin`·`totalMarginBalance`, 코어 규칙 `AccountMm`, 한도 5000 bps). 실제 거래소에 나간 주문은 아직 없다(가짜 서버 시험만, U-01).

[ADR-017](ADR-017-hyperliquid-gateway.md)의 틀을 따른다.

## 1. 문제와 발생 가능한 실패

- 키가 다른 계좌(마스터 계좌, 다른 서브계정)의 것이면 엉뚱한 계좌에서 거래한다.
- 계좌가 교차 증거금이 아니거나(격리, 포트폴리오), 헤지 모드이거나, 종목이 USDT 정산이 아니면, 코어의 장부·한도·정리 범위가 거래소와 다른 것을 가리킨다.
- 서명 문자열과 보내는 바이트가 다르면 모든 요청이 거부된다. 거부를 시간 문제로 오인하면 같은 거부를 계속 보낸다.
- 거부된 키(만료, IP 불일치, 잘못된 키)로 계속 요청하면 거래소가 IP를 막을 수 있고, 운영자는 원인을 모른다.
- 요청이 키에 묶이지 않은 IP에서 나가면(호스트 이동, NAT 변경) 다음 주문부터 실패한다. 미리 알아야 한다.
- 비밀이 로그·저널·오류 문장에 남는다.

## 2. 일반적으로 만족해야 하는 성질

- 시작 확인은 읽기만 한다. 거래소 설정을 바꾸지 않는다(ADR-018과 같다).
- 확인 하나라도 어긋나면 거래하지 않는다. 확인할 수 없으면(응답 없음) 통과로 보지 않는다.
- 다시 시도해도 바뀌지 않는 거부는 다시 시도하지 않는다.
- 서명한 바이트 = 보낸 바이트.
- 비밀은 파일 하나에만 있다.

## 5–6. 대안과 비교

| 결정 | 대안 | 고른 것과 이유 |
|---|---|---|
| 비밀의 위치 | 환경 변수(Hyperliquid 방식), 설정 파일 안, 별도 파일 | 별도 파일(0600, 데이터 디렉터리 밖, 절대 경로). 설정 파일은 운영 문서와 함께 복사·공유되고, 환경 변수는 `/proc/<pid>/environ`과 자식 프로세스로 퍼진다. 파일은 권한을 검사할 수 있다 |
| 질의 문자열 | 인코딩해서 보냄, 그대로 보냄 | 그대로 보내고 뜻을 바꾸는 문자는 거절. 거래소가 주는 커서는 이미 인코딩되어 있어 다시 인코딩하면 커서가 깨진다(SDK도 그대로 보낸다) |
| 서명 시험값 | 문서 예시, 직접 계산 | 문서의 서명할 문자열(조립 확인) + RFC 4231 사례 2(HMAC 자체) + Python `hmac`으로 따로 계산한 값(같은 문자열, 정한 비밀). 문서 예시의 서명은 비밀이 없어 쓸 수 없다 |
| 키 거부 코드 | 범위에 적힌 셋(10003, 10010, 33004), 인증 계열 전부 | 여섯(+10004, 10005, 10007). 서명 오류·권한 없음·인증 실패도 다시 보내서 낫지 않는다(판단) |
| 묶이지 않은 키 | 허용, 거절 | 거절. 90일 뒤 무효가 되고, IP 확인이 의미가 없다 |
| IP 불일치 뒤 | 다음 확인이 맞으면 풂, 재시작까지 막음 | 재시작까지 막음. 범위가 "키 거부처럼"이라고 했고, 키 거부는 다시 시도하지 않는다 |
| 막힘 상태 | 칸 하나(마지막 결과가 덮어씀), 출처마다 칸 | 출처마다 칸: 시작 확인, IP 확인, 키 거부. 연결은 세 칸이 모두 빌 때만 올라온다. 각 출처는 제 칸만 비운다. 칸이 하나면 IP 재확인 통과가 시작 확인의 막힘(헤지 모드, 격리, 확인 못 함)을 지운다(독립 검토가 찾음). 키 거부는 어느 출처에서 오든 키 거부 칸으로 가고 재시작까지 남는다 |
| HTTP 403 | 요청 한도(10006·429와 같음), 따로 | 따로(`IpBanned`). 거래소는 403 뒤 모든 HTTP를 멈추고 10분 이상 기다리라고 한다(F18 L186). 짧은 한도처럼 60초마다 다시 보내면 차단이 끝나지 않는다. 멈춤 시간 상수 `IP_BAN_PAUSE` = 600초. 멈춤을 지키는 반복은 U16d |
| cancel-all 응답 | retCode만 봄, `result.success`도 봄 | `success = "1"`일 때만 성공. 아니면 거부(F20 Q11.4: `"0"` = 실패). 취소 수가 500(한 번의 최대, 넘으면 거래소가 무작위로 500개만 취소, F20 Q11.3)이면 `maybe_more`로 알려 호출자가 다시 보낸다 |
| 나가는 주소 | 시스템 기본, IPv4만 | IPv4만(`LOCAL_ADDRESS`). 확인 서비스와 Bybit가 다른 주소 계열로 닿으면 IP 확인이 거짓으로 막는다. IPv4에 대응된 IPv6 주소(`::ffff:a.b.c.d`)는 IPv4로 비교한다 |
| 확인 실패 시 | 노드를 멈춤, 게이트웨이만 막음 | 게이트웨이만 막음(`Block`): 연결이 올라오지 않아 코어의 LinkDown 보류가 새 주문을 막는다. 저널·상태 API·대시보드는 계속 돈다. 막힌 이유를 상태 API에 싣는 것은 U16d |

## 7. 선택과 이유 (U16b)

`crates/oms-node/src/venue/bybit/`:

| 모듈 | 하는 일 |
|---|---|
| `sign.rs` | REST 서명, 비공개 스트림 인증 서명(`GET/realtime` + expires), 질의 문자열 |
| `rest.rs` | 자격 파일(`Credentials::load`), 서명한 GET·POST, 응답 분류(`classify`, `RestError`) |
| `checks.rs` | 시작 확인(`boot`), IP 재확인(`recheck_ip`), 막힘 상태(`Health`, `Block`) |
| `mod.rs` | 엔드포인트, `cancel_all`(`CancelAll`) |

| 단계 | 입력 | 처리 | 출력 | 실패하면 |
|---|---|---|---|---|
| B1 키 | `GET /v5/user/query-api` | `isMaster = false`, `userID = sub_account_uid`, `readOnly = 0`, `ContractTrade`에 `Order`·`Position` | 키의 `ips` | `Block::Account`, 거부 코드면 `Block::AuthRejected` |
| B2 IP | `GET <ip_echo_url>` | 본문 = 주소. 키의 `ips`에 있어야 한다. `ips`가 비었거나 `*`면 거절 | — | 다름 → `AuthRejected`(재시작까지), 묶이지 않음 → `Account`, 응답 없음 → `Unchecked` |
| B3 계좌 | `GET /v5/account/info` | `marginMode = REGULAR_MARGIN`, `unifiedMarginStatus` 3–6 | — | `Account` |
| B4 종목 | 종목마다 `instruments-info`, `position/list`(category linear, symbol) | `settleCoin = USDT`, 모든 행 `positionIdx = 0`, 행이 없으면 확인 못 함 | — | `Account` 또는 `Unchecked` |

설정(`[venue] kind = "bybit"`): `network`, `credentials_file`, `sub_account_uid`, `ip_echo_url`(https), `ip_check_secs`(60, 10 이상), `recv_window_ms`(5000, 1000–20000), `request_timeout_ms`, `mainnet_confirmed`, `fills_lag_ms`. 검증:
- mainnet은 `mainnet_confirmed`와 `[core.policy.margin]`이 있어야 한다(Hyperliquid와 같다).
- `[core.policy]`는 `venue_enforces_expiry = true`, `absence_not_found_needed = 2`(ADR-024).
- 증거금 정책이 있으면 `isolated = false`(교차 계좌)와 `account_mm_rate_max_bps`(1..=9999, 결정값 5000, U17d §7g). 다른 거래소는 그 값을 거부한다.
- `credentials_file`은 `..`를 담지 않고, 심볼릭 링크와 상대 데이터 디렉터리를 풀어 비교해도 데이터 디렉터리 밖이어야 한다.
- 자격 파일은 한 번 열어 그 핸들로 검사하고 읽는다: 일반 파일, 심볼릭 링크 아님(`O_NOFOLLOW`), OMS를 돌리는 사용자 소유, 그룹·기타 권한 없음.

## 7b. 조회와 실행 분류표 (U16c)

`venue/bybit/query.rs`(`Queries::answer`가 `QueryReq` 하나에 입력 목록 `Answer`를 돌려준다. 노드 연결은 U16d), `venue/bybit/exec.rs`(실행 행 하나 → 입력 하나, 스트림도 같은 함수를 쓴다).

| 조회 | 요청 | 처리 | 출력 | 못 읽으면 |
|---|---|---|---|---|
| Status | `GET /v5/order/realtime`, 없으면 `GET /v5/order/history` 두 번: 기간 없이(최근 7일)와 코어가 주문을 받은 시각 − 1분부터 7일(category linear, settleCoin USDT, 우리 `orderLinkId`) | 우리 `orderLinkId`의 행만 본다. 상태표: `New`·`PartiallyFilled` = 열림, `Filled`, `Cancelled`(사유 `cancelType`), `Rejected`(사유 `rejectReason`). `cum` = `cumExecQty`, 시각 = `updatedTime` | `OrderStatus` 또는 셋 다 없을 때 `StatusNotFound`(첫 요청 전 시각) | 입력 없음 |
| Fills | `GET /v5/execution/list`(linear, USDT, limit 100, cursor) | `since` − 2분부터 지금 − `fills_lag_ms`까지 7일 이하 창(2분은 늦게 실리는 행을 다음 조회가 다시 읽게 한다. 같은 키는 코어가 거른다). 창 시작은 1ms 앞에서(경계 포함 여부가 문서에 없다). 행마다 분류표, 같은 키는 한 번 | 창마다 실행 입력들 + `FillsSynced { up_to: 창 끝 − 1µs }` | 그 창부터 멈춤(앞 창의 선언은 남는다) |
| OpenOrders | `GET /v5/order/realtime`(linear, USDT, limit 50, 모든 쪽) | 열린 상태의 행만. `remaining` = `leavesQty` | `OpenOrders` | 입력 없음 |
| Positions | `GET /v5/position/list`(linear, USDT, limit 200, 모든 쪽) | 단방향 행만, 수량 = `side` 부호 × `size` | `Positions` | 입력 없음 |
| Margin | `wallet-balance`(UNIFIED), `account/info`, `position/list`(모든 쪽), 처음 보는 종목은 `instruments-info` | 계좌 가치 `totalEquity`, 포지션마다 `positionValue`, 증거금 `positionIM`, 레버리지 정수, 증거금 모드 = 계좌의 `marginMode`, `maxLeverage` | `MarginReport` | `MarginReportInvalid`(응답 없음이면 입력 없음) |
| VenueSetting | `account/info`, `position/list`(symbol) | 행 하나, 단방향, 그 종목. 격리 = `ISOLATED_MARGIN` | `VenueSetting` | 입력 없음 |
| AccountMode | `account/info` | `marginMode` 그대로(64자 이하) | `AccountMode` | 입력 없음 |

실행 분류표(`exec::classify`):

| `execType` | 입력 |
|---|---|
| `Trade` | `Fill`. `orderLinkId`가 이 인스턴스의 `Base32Pair`이면 그 주문, 아니면 `order_id` 없음(외부 체결, 코어는 `orderId`로도 찾는다). `fee` = `execFee`, `is_maker` = `isMaker`, 조회 행의 `recv_ns`는 비움 |
| `Funding` | `Funding`. 금액 = `execFee`(양수 = 계좌가 냄, F20 Q9.5) |
| `AdlTrade`, `BustTrade`, `Delivery`, `Settle` | `PositionChange`(adl, takeover, delivery, settle). 수량 = `side` 부호 × `execQty`, 가격 = `execPrice` |
| 그 밖, 없음 | `UnclassifiedExecution`(종류 32자, 행의 주요 값) |

체결 키는 `<symbol>:<execId>`. 행을 읽을 수 없으면(키·종목·시각·수량·가격·수수료) 입력이 아니라 오류다: 조회는 그 창을 완료로 선언하지 않고, 스트림(U16d)은 끊고 다시 붙는다(G-9).

| 결정 | 대안 | 고른 것과 이유 |
|---|---|---|
| 마지막 쪽 | 빈 커서 = 끝, 빈 커서 + 덜 찬 쪽 = 끝 | 둘 다일 때만 끝. 빈 커서의 뜻은 이 엔드포인트들의 문서에 없다(F20 Q9.9). 다 찬 쪽에 커서가 없으면 스냅숏은 넘기지 않고, 체결 창은 반으로 나눠 다시 읽는다 |
| 상태 조회의 정산 범위 | 주문의 종목, `settleCoin` | `settleCoin=USDT`. linear는 셋 중 하나가 필요하고(F20 Q10.4), `orderLinkId`가 우선한다. `QueryReq::Status`에 종목이 없다 |
| `cum` | 비움(Hyperliquid), 채움 | 채움. `cumExecQty`의 뜻이 문서에 하나다(Hyperliquid의 `sz`는 두 뜻으로 적혀 있어 비웠다). 코어는 체결 합이 그 값과 같으면 닫고, 모자라면 체결 동기화 뒤 `MissingFills` 불일치를 낸다. 거래소가 종결 상태를 최종 수량보다 먼저 낮은 값으로 말하면 일찍 닫힌다(가정: 종결 상태의 `cumExecQty`는 최종이다) |
| 조건부·스팟 상태 | 열림·닫힘으로 번역, 결론 없음 | 결론 없음(`Untriggered`, `Triggered`, `Deactivated`, `PartiallyFilledCanceled`). OMS는 그런 주문을 내지 않는다(G-13). 열린 주문 목록에는 `Untriggered`도 넣는다(남의 주문이라도 걸려 있다) |
| 계좌 가치 | `totalEquity`, `totalMarginBalance` | `totalEquity`(모든 자산의 USD 합). 하루 손실 규칙이 보는 계좌 전체 값이다(판단) |
| 포지션의 증거금 모드 | 포지션 필드, 계좌 모드 | 계좌 모드(`account/info`). 통합 계좌는 모드가 계좌 하나에 하나이고 포지션의 `tradeMode`는 폐기되었다(F18 §6). 그래서 증거금 보고마다 요청이 셋이다 |
| 소수 레버리지 | 내림, 거절 | 거절. 보고 전체가 `MarginReportInvalid`, 설정은 모름으로 남는다(코어가 일반 주문을 막는 쪽). 문서는 0.01 단위를 허용하는 것으로 보인다(F20 Q8.5) |
| `maxLeverage` | 보고마다 읽음, 프로세스당 한 번 | 한 번(종목마다 캐시). 유지증거금 규칙은 격리 포지션에만 쓰고 이 계좌는 교차다. 보고에는 0이 아닌 값이 있어야 한다 |
| 계좌 모드 허용 목록 | 아무 값, `REGULAR_MARGIN`만 | 설정 검증이 `REGULAR_MARGIN` 밖의 값을 거절한다 |
| 주문 내역의 기간 | 기간 없이, 접수 시각부터 | 둘 다. 기간이 없으면 최근 7일만 답한다(F20 Q10.7). 오래 꺼져 있다 켜면 체결된 옛 주문이 realtime(닫힌 주문 500건, 거래소 재시작 때 비움)과 최근 7일 내역 모두에 없어 `StatusNotFound`가 되고, 코어가 `NotPlaced`로 닫아 예약을 일찍 푼다(독립 검토가 찾음). 그래서 코어가 `Need::OrderStatus`와 `QueryReq::Status`에 주문을 받은 시각(`accepted_at`)을 싣고, 게이트웨이는 그 시각 − 1분부터 7일을 따로 묻는다. 기간이 생성 시각을 거르는지 갱신 시각을 거르는지는 문서에 없어 두 요청을 다 한다 |
| 체결 다시 읽기 | `since`부터, 앞으로 당겨서 | `since` − 2분부터(판단). 끝을 지금 − 2초로만 잡으면 거래소가 늦게 싣는 행(펀딩·ADL·외부 체결)은 `FillsSynced` 뒤에 나타나 다시 읽히지 않는다. 우리 주문은 `cum` 검사가 `MissingFills`로 드러내지만 나머지는 아무것도 잡지 않는다(독립 검토가 찾음). 2분보다 늦은 행은 여전히 놓친다 |
| 체결 한 번의 일 | 끝까지, 쪽 수 상한 | 30쪽. 다 읽은 창은 `FillsSynced`로 선언했으므로 다음 조회가 거기서 잇는다(400일 공백은 여러 번에 나눠 읽는다) |

## 7c. 비공개 스트림과 노드 연결 (U16d)

`venue/bybit/stream.rs`(보내는 메시지와 받는 메시지의 해석), `venue/bybit/gateway.rs`(`VenueGateway` 구현, 시작 확인·IP 반복, 스트림 반복, 조회, IP 차단 멈춤, `spawn`). 노드의 `node.venue`는 `bybit:<network>`이다.

| 단계 | 입력 | 처리 | 출력 | 실패하면 |
|---|---|---|---|---|
| D1 시작 확인 | B1–B4(§7) | 통과할 때까지 10초마다(IP 확인 주기가 더 짧으면 그 주기) 다시 한다. 통과 전에는 시작 칸이 "아직 확인 안 함"이다 | 시작 칸 비움 | 칸에 막힘. 키 거부면 반복을 멈춘다 |
| D2 IP 반복 | `ip_check_secs`마다 query-api + 공인 IP | 다름 → 키 거부(재시작까지). 응답 없음 → 앞의 결과 유지 | IP 칸 | 403이면 D5 |
| D3 연결 | 막힘 없음 | IPv4로 접속, `auth`(만료 = 지금 + `recv_window_ms`), 확인 뒤 `subscribe`(`order.linear`, `execution.linear`), 확인까지 10초 | `Link { up: true, session }`(부팅 번호 + 연결 번호, 매번 새 번호) | 인증 거부 → 키 거부, 다시 붙지 않음. 업그레이드의 HTTP 403 → D7. 구독 거부·시간 초과 → 0.5초부터 두 배씩 10초까지 기다린 뒤 다시. 연결이 올라가 첫 pong을 받았으면 기다림은 0.5초부터 다시. pong 전에 끊긴 연결은 기다림을 늘린다(같은 고장이 접속마다 되풀이되면 0.5초마다 다시 붙어 5분 500회 접속 한도에 다가간다, 재검토) |
| D4 흐름 | 주문·실행 메시지 | 거래하는 종목의 행만. 주문 행 → `query::order_status` → `OrderStatus`(Stream). 실행 행 → `exec::classify`(받은 시각 ns) | 코어 입력 | 읽을 수 없는 메시지·행, `symbol`이 없는 행 → 앞의 읽은 행은 넘기고 끊는다(G-9) |
| D5 생존·막힘 | `ping_interval_ms`(5초)마다 ping. 250ms마다 막힘 칸 | ping 뒤 `ping_interval_ms` 안에 pong이 없으면 끊김. 코어 입력 큐가 차서 기다린 시간은 이 기한에 넣지 않는다(기한을 그만큼 늦춘다). 소켓에 이미 온 메시지를 기한보다 먼저 읽는다. 막힘이 생기면 끊음 | `Link { up: false }` | — |
| D6 조회 | `QueryReq` | 키 거부·IP 차단 중이면 보내지 않는다. 아니면 `Queries::answer`, 입력을 넘기고 실패를 본다 | 코어 입력 | `Auth` → 키 거부(연결이 내려간다), `IpBanned` → D5 멈춤 |
| D7 IP 차단 멈춤 | HTTP 403(어느 요청이든: REST, IP 확인, 스트림 업그레이드) | `IP_BAN_PAUSE`(600초) 동안 REST·스트림 접속 모두 멈춤. 차단 칸이 연결을 내린다 | 멈춤이 끝나면 차단 칸 비움, 다시 붙음 | — |
| D8 주문·취소 | `SendOrder`, `SendCancel` | U16d에서는 보내지 않았다. U17a부터 §7d | `SendResult`/`CancelResult` 하나씩 | — |

재연결 뒤 REST로 다시 읽기는 게이트웨이가 따로 하지 않는다. 연결마다 세션 번호가 새로우므로 코어가 그 세션의 체결 동기화, 열린 주문, 포지션을 받을 때까지 `Resync`로 새 주문을 막고 조정기가 조회를 보낸다(`needs_resync`, C-RECON). 체결은 코어가 동기화한 시각 − 2분부터 다시 읽는다(§7b).

상태 API: `gateway.block`에 막힘 이유(`auth_rejected: …`, `ip_banned: …`, `account: …`, `unchecked: …`, U17a부터 `clock: …`)가 실린다. 막힘이 없거나 Bybit가 아닌 게이트웨이면 null이다.

| 결정 | 대안 | 고른 것과 이유 |
|---|---|---|
| 토픽 | 넷(order, execution, position, wallet, 설계 계획), 둘 | 둘(`order.linear`, `execution.linear`). position·wallet 메시지는 바뀐 종목 하나만 알린다(F18 §1.4–1.5, wallet은 구독 때 스냅숏도 없다). 코어의 포지션·증거금 입력은 전체 스냅숏이라 한 종목 메시지를 넣으면 나머지를 0으로 말하게 된다. 증거는 조회(§7b)다 |
| 종목 범위 | linear 전부, 설정한 종목만 | 설정한 종목만. 분류 토픽은 USDC 정산 linear도 싣는다(정산 코인 필터가 없다). 다른 종목의 행은 `settleCoin=USDT`로 거른 조회가 읽는다 |
| 생존 확인 | 메시지가 없으면 끊김, ping-pong | ping-pong. 조용한 비공개 스트림과 반쯤 열린 연결은 겉으로 같다(설계 계획). 간격과 기다림이 같다(`ping_interval_ms`, 1–20초, 기본 5초). 게이트웨이가 코어 큐를 기다리는 동안은 소켓을 읽지 않으므로, 그 시간을 기한에 넣으면 제때 온 pong을 없다고 보고 끊는다(독립 검토). pong 모양은 둘 다 받는다(`op = "pong"`, `op = "ping"` + `ret_msg = "pong"`, F20 Q2.9–2.10). U18b의 정리 스위치가 쓸 10초 규칙은 U18b에서 정한다(U18b2, [C-KILL](../contracts/kill.md): 마지막 생존 증거 뒤 `kill_after_ms`, [ADR-030](ADR-030-kill-switch-holds.md)) |
| 인증 실패 | 다시 시도, 키 거부 | 키 거부(재시작까지). 실패 응답의 모양과 코드는 문서에 없다(F20 Q2.6). REST 확인이 같은 키로 통과한 뒤이므로 남은 원인은 서명·시각·키 상태이고, 다시 보내도 낫지 않으며 IP 차단을 부를 수 있다(판단). 시계가 1초 넘게 틀려도 이렇게 막힌다(안전한 쪽) |
| 인증과 구독 | 한꺼번에 보냄(pybit, F20 Q2.8), 차례로 | 차례로. 거부가 키 때문인지 토픽 때문인지 갈라야 키 거부만 재시작까지 막을 수 있다 |
| 인증 만료 시각 | 1초(pybit), `recv_window_ms` | `recv_window_ms`(기본 5초). REST가 받아들이는 시계 차이와 같게 둔다. 최대 허용값은 문서에 없다 |
| IP 반복의 응답 없음 | 막음, 앞의 결과 유지 | 유지. 확인 서비스가 한 번 답하지 않을 때마다 연결을 내리면 매번 `Resync`가 돈다. 바뀐 IP는 주문이 10010으로 거부될 뿐이고, 다음 확인이 잡는다(판단). 시작 확인의 응답 없음은 여전히 통과가 아니다 |
| 403 멈춤의 범위 | REST만, 스트림 접속까지 | 둘 다. 거래소는 모든 HTTP 세션을 멈추라고 한다(F18 L186). 웹소켓 접속도 HTTP 업그레이드다 |
| 참조 가격 | 공개 시세 스트림을 같이 붙임, U17 | U17. 비공개 스트림에는 가격이 없다. 그때까지 코어는 `RefPriceUnavailable`로 일반 주문을 거절한다(안전한 쪽) |
| 주문 명령 | 거절 안 함(무시), `NotSent` | `NotSent` 하나씩(G-1, G-5). 한 바이트도 나가지 않았으므로 맞는 분류다(U17a에서 §7d로 바뀜) |
| 조회 동시 수 | 1, 4(Hyperliquid) | 4. 조회는 요청 한도 예산에 넣지 않는다(§7d) |

## 7d. REST 주문과 취소 (U17a)

`venue/bybit/orders.rs`(요청 본문, 보내는 시각 규칙, 요청 한도, 결과), `venue/bybit/answer.rs`(응답 분류표), `oms-core::rate`(요청 한도, 시각을 입력으로 받는 순수 규칙).

| 단계 | 입력 | 처리 | 출력 | 실패하면 |
|---|---|---|---|---|
| R1 종목 | `SendOrder`(취소는 거르지 않는다) | 설정한 종목이 아니면 보내지 않는다 | — | `NotSent` |
| R2 한도 | 주문 또는 취소 | `RateBudget::take`: 요청 하나는 자리를 잡은 때부터 응답이 온(또는 실패한) 때 + 1초까지 센다. 보낸 뒤 응답이 없으면(시간 초과, 끊김) 그 요청은 `요청 시각 + recv_window + 1초`(로컬 시각)까지 거래소에 닿을 수 있으므로 그때 + 1초까지 센다. 주문은 세는 요청이 8개 미만일 때, 취소는 10개 미만일 때. 차 있으면 알려 준 시각까지 기다린다(버리지 않는다). 아무 바이트도 나가지 않았으면(막힘, 보내는 시각 규칙, 접속 실패) 자리를 바로 돌려준다 | 자리 하나 | — |
| R3 막힘 | 기다린 뒤의 `Health` | 키 거부, IP 차단, 시작·IP 확인 막힘이 있으면 보내지 않는다. 시계 막힘은 생성만 막는다(`create_block`) | — | `NotSent`(막힘 이유) |
| R4 보내는 시각 | 로컬 시각 하나(ms) | 주문: `시각 + recv_window + 1초 ≤ expires_at`일 때만(G-4). 같은 시각으로 서명한다 | 서명한 요청 | `NotSent` |
| R5 전송 | `POST /v5/order/create` 또는 `/v5/order/cancel` | 생성: `category=linear`, `symbol`, `side`, `orderType=Limit`, `qty`, `price`, `timeInForce`(GTC, IOC, PostOnly), `orderLinkId`(우리 고객 주문번호), `reduceOnly`, `positionIdx=0`. 취소: `category`, `symbol`, `orderLinkId`. 다시 보내지 않는다 | HTTP 상태와 본문 | 접속 실패 → `NotSent`. 보낸 뒤 시간 초과·끊김 → `Unknown` |
| R6 분류 | 상태와 본문 | `answer::classify`(아래). 생성의 retCode 0은 `Placed { status: Open, cum: 없음 }`(접수만 뜻한다, 처리는 비동기, F18 §3.1), `orderId`가 없으면 `Unknown`. 취소의 0은 `Confirmed` | 코어 입력 | — |
| R7 부수 효과 | 상태와 분류 | HTTP 403, retCode 10018(IP 요청 한도) → IP 차단 멈춤(D7). HTTP 401, 키 거부 retCode → 재시작까지 키 거부 | `Health` | — |
| R0 시계 | `/v5/market/time`의 `timeNano`, 요청 앞뒤의 로컬 시각 | 시작 확인보다 먼저, IP 확인 주기마다, 막혀 있는 동안은 `boot_retry`(10초)마다. 앞섬 상한 = 응답 뒤 로컬 시각 − 거래소 시각(왕복 시간을 앞섬으로 친다). 500ms를 넘으면 막힘. 왕복이 250ms를 넘는 측정은 판정하지 않는다(`Unchecked`: 시작 확인 전이면 막힘, 뒤면 앞의 결과 유지). 시계 확인이 IP 차단을 만나면 그 회차의 나머지 확인은 건너뛴다 | 시계 칸 | `clock: …` 막힘. 생성만 막는다. 만료 규칙(G-4)은 생성에만 걸리므로 취소와 스트림은 그대로 둔다 |

응답 분류표: retCode 0은 접수. 오류 문서(B/v5/error, 2026-11-21에 읽음, UTA의 0 아닌 코드 201개와 WS OE 7개, 겹치는 2개를 빼고 206개)의 0 아닌 코드는 `UNKNOWN_CODES`에 있지 않으면 거부(`Rejected`)다. `UNKNOWN_CODES` = 10000(서버 시간 초과), 10014(중복 요청), 10016(서버 오류·재시작), 10019(WS Trade 재시작), 10429·429(시스템 과부하 보호), 20006(reqId 중복), 40004(바꾸는 중 수정됨), 110030(orderId 중복), 110072(orderLinkId 중복), 110079(처리 중), 3400214(서버 오류). 서버가 실패했거나, 같은 주문이 이미 있을 수 있거나, 아직 처리 중이라는 뜻이라 거부의 증거가 아니다. 문서에 없는 코드, 2xx가 아닌 HTTP 상태, 읽을 수 없는 본문, retCode 없는 본문은 모두 `Unknown`이다(G-2, G-13). `Unknown`은 코어가 결과 불명으로 두고 조회로 푼다(다시 보내지 않는다).

## 7e. WS Trade 주문·취소 (U17b)

`venue/bybit/trade.rs`(연결 작업, 메시지, 응답을 기다리는 요청 목록, 핸들), `venue/bybit/orders.rs`(경로 고르기). 한도, 막힘, 보내는 시각 규칙은 §7d 그대로이고 경로를 고르기 전에 한 번 한다.

| 단계 | 입력 | 처리 | 출력 | 실패하면 |

| T1 연결 | 막힘 없음(키 거부, IP 차단 멈춤, 시작·IP 확인. 시계 막힘은 아니다) | `/v5/trade`에 IPv4로 접속(비공개 스트림과 같은 `connect`). `auth`(비공개 스트림의 서명 `GET/realtime` + 만료, 만료 = 지금 + `recv_window_ms`, 모양은 WS Trade 문서의 `{"op":"auth","args":[…]}`). 응답의 retCode 0이면 올라간다. 10초 안에 확인 | 핸들에 이 연결의 요청 대기열을 건다 | 0이 아닌 retCode(또는 retCode 없는 `auth` 응답) → 키 거부(재시작까지). 업그레이드의 HTTP 403 → D7. 응답 없음, 읽을 수 없는 메시지 → 비공개 스트림과 같은 기다림 뒤 다시 |

| P3 해석 | `tickers.<symbol>` 메시지 | 거래하지 않는 종목은 버림. `type` = `snapshot`·`delta`, `data.symbol` = 토픽의 종목, `markPrice`(있으면 0보다 큰 십진 문자열, 1e-8 단위), `ts`(ms 정수 → µs). 스냅숏에는 `markPrice`가 있어야 한다 | `Ticker` | 그 밖은 읽을 수 없는 메시지 → 끊고 다시 붙는다 |

| P5 내보냄 | mark가 있는 종목의 티커 메시지 | 그 종목의 마지막 내보냄에서 `ref_price_interval_ms`가 지났을 때만(연결이 바뀌어도 이어서 센다) | `RefPrice { instrument, px = mark, venue_ts = 메시지의 ts }` | 코어 큐가 닫혔으면 끊음 |

| 결정 | 대안 | 고른 것과 이유 |
|---|---|---|
| 가격 | 마지막 체결가, 중간값(Hyperliquid), mark price | mark(판단). 거래소가 정하는 공정 가격이라 체결 하나로 움직이지 않는다. 가격 범위의 기준이고 청산도 이 값으로 한다 |
| 다시 보내기 | 마지막 가격을 타이머로 다시 보냄, 메시지가 올 때만 | 메시지가 올 때만. 거래소가 멈춘 종목의 가격을 OMS가 살려 두지 않는다. 코어의 `ref_price_max_age_us`가 낡음을 판정하고 가격 범위가 있는 주문을 거절한다(안전한 쪽) |
| 간격 | 연결마다 새로, 연결을 넘어 | 간격은 연결을 넘어 센다(판단, 스펙 밖). mark는 연결마다 비우지만, 재연결이 잦아도 코어에 가는 가격이 간격보다 잦지 않다. 새 연결의 첫 스냅숏이 간격 안이면 다음 메시지가 간격 뒤에 보낸다 |
| `markPrice` 없는 스냅숏 | 버림, 읽을 수 없음 | 읽을 수 없음(판단, 스펙 밖). 스냅숏은 모든 칸을 싣는다고 본다. 없으면 그 뒤 델타를 해석할 수 없다 |
| 간격 범위 | 제한 없음, 1초 이상 + 낡음 한도의 절반 이하 | 1초 이상, `ref_price_max_age_us`의 절반 이하(판단). 한 번 빠져도 가격이 낡지 않는다. 기본 5초, 낡음 한도 기본 15초 |
| 구독 확인 전의 티커 | 버림, 읽음 | 읽음. 스냅숏은 구독마다 한 번 오므로 두 번째 구독의 확인을 기다리는 동안 첫 구독의 스냅숏을 버리면 그 연결 내내 mark가 없다 |

노드 시험(`tests/bybit_node.rs`): `failpoints` 기능으로 만든 바이너리만 `OMS_TEST_BYBIT_WIRING`(JSON: `rest`, `private_ws`, `trade_ws`, `public_ws`, `ip_echo_url`)을 네트워크의 엔드포인트 대신 읽고, 주소 다섯 개의 호스트가 모두 `127.0.0.1`이 아니면 시작하지 않는다. 쓰면 `warn`을 남긴다. 설정 파일은 그대로 testnet과 https 확인 서비스를 적는다. 노드는 실제 바이너리로 따로 돌고, 가짜 REST(`http-fake`)와 가짜 웹소켓 셋은 시험 프로세스 안에 있다. flush 실패는 기존 failpoint `OMS_CRASH_AT=sync_error_after_write`(새 주문의 기록을 쓴 뒤 flush가 실패하고 프로세스는 살아서 상태 2로 멈춘다)를 쓴다. 새 failpoint는 없다.

## 7g. 교차 계좌의 유지증거금률 (U17d)

소유자 질문(11-20, "교차 계좌에 규칙을 더할지, X %")에 11-21까지 답이 없어 질문에 적은 기본값을 따랐다: 규칙을 더하고 X = 50 %(판단, 모형이 아니다). 소유자가 규칙을 뺄 수 있다(한도를 없애려면 Bybit 설정 검사도 함께 바꿔야 한다). 규칙의 숫자와 경계는 [C-MARGIN](../contracts/margin.md) "계좌 유지증거금률", 규칙 목록은 [ADR-018](ADR-018-margin-rules.md) §7의 11이다.

| 단계 | 입력 | 처리 | 출력 | 실패하면 |
|---|---|---|---|---|
| M1 조회(`query.rs` `margin`) | `wallet-balance?accountType=UNIFIED`의 UNIFIED 계좌 하나 | `totalEquity` → `account_value`, `totalMaintenanceMargin` → `account_mm.maintenance`, `totalMarginBalance` → `account_mm.margin_balance`(셋 다 USD 소수 문자열, 1e-8 단위). `accountMMRate`는 보고마다의 `info` 로그 한 줄(`bybit margin report`)에만 싣는다 | `MarginReport { account_mm: Some(..) }` | 셋 가운데 하나라도 없거나 문자열 소수가 아니면 `MarginReportInvalid`(사유에 필드 이름) |
| M2 판정(코어) | 받은 보고, `account_mm_rate_max_bps` | `유지증거금 > 0`이고 `유지증거금 × 10 000 ≥ 한도 × 잔고`면 `enter_reducing(AccountMm)`(열린 일반 주문 취소, 감소 전용 주문은 남김). 순서: 유지증거금 여유 → 이것 → 일 손실, 먼저 건 것이 래치에 남는다 | `ReducingEntered { rule: account_mm }`, `CancelRequested { by: Rule(AccountMm) }` | 한도가 있는데 `account_mm`이 없거나 유지증거금이 음수 → `MarginReportRejected` |
| M3 설정(`config.rs`) | `[core.policy.margin]` | Bybit에서 정책이 있으면 `account_mm_rate_max_bps`가 있어야 하고(1..=9999), Hyperliquid와 가상 거래소는 그 값을 거부한다 | 시작 | 시작 거부 |
| M4 보기 | `status` | `core.margin.account_mm = {maintenance, margin_balance}`(없으면 키 없음), `core.margin.reducing.rule = account_mm`, `detail`에 숫자 | 운영자 | — |

| 결정 | 대안 | 고른 것과 이유 |
|---|---|---|
| 비율의 원천 | `accountMMRate`, `totalMaintenanceMargin / totalMarginBalance` | 두 금액의 비. 둘 다 문서에 정의가 있다(F18 §6, F20 13.2). `accountMMRate`는 비율인지 백분율인지 문서에 없다(F20 13.4). 판정에 쓰면 100배 틀릴 수 있다 |
| 계산 | 나눗셈, 곱의 비교 | `i128` 곱의 비교. 잔고 0에서 나누지 않고, 반올림이 경계를 바꾸지 않는다 |
| 잔고 0 이하 | 판정 안 함, 건다 | 유지증거금이 있으면 건다(거래소는 이미 청산 구간이다). 유지증거금이 0이면 걸지 않는다(청산될 것이 없다. 잔고 0·유지증거금 0은 스펙의 "걸지 않음") |
| 두 숫자가 없는 보고 | 판정 없이 기록, 거부 | 거부(스펙). `max_leverage = 0`과 같다. 마지막 정상 보고가 나이를 먹어 30초 뒤 일반 주문 거절, 60초 뒤 취소 |
| 음수 유지증거금 | 판정 안 함, 거부 | 거부(판단, 스펙 밖). 규칙이 쓸 수 없는 값이고, 받으면 규칙이 조용히 꺼진다 |
| 해제 | 조건과 상관없이 받음, 조건이 참이면 거절 | 거절 `account_mm_active`(판단, 스펙 밖). 유지증거금 여유의 `mm_buffer_active`와 같은 원칙이고, 풀어도 다음 보고(5초)가 다시 건다 |
| 판정 순서 | 맨 앞, 유지증거금 여유와 일 손실 사이, 맨 뒤 | 사이(판단). 청산에 가까운 규칙이 먼저 이름을 남긴다 |
| 기록 스키마 | 3으로 올림, 2 그대로 | 2 그대로. 없으면 쓰지 않는 선택 필드와 열거형 값 하나를 더한 것이다(U16a `is_maker`, U13c `AbsenceNoted`와 같다). 옛 기록은 바이트가 같고 변환 없이 읽힌다. 한도를 담은 설정 기록(정책은 모르는 키를 거부한다)과 규칙 이름 `account_mm`이 든 기록은 이 판 전의 바이너리가 읽지 못한다. 숫자만 담은 보고 기록은 옛 바이너리가 그 필드를 버리고 읽는다. 그런 기록이 생긴 저널은 옛 바이너리로 되돌리지 않는다(runbook §9 "이벤트에 선택 필드 추가") |

## 8. 포기한 장점, 남은 위험, 가정

- 위험(U17d로 바뀜): 교차 계좌에는 유지증거금 여유 규칙(C-MARGIN)이 걸리지 않는다(격리 포지션에만 있다). U17d가 계좌 유지증거금률 규칙(§7g)을 더했다.
- 위험: query-api에서 묶이지 않은 키의 `ips` 모양은 문서에 없다. 빈 목록과 `*`를 둘 다 묶이지 않음으로 본다. 다른 모양(예: `""` 한 칸)은 주소로 읽히지 않아 IP 불일치로 막힌다(안전한 쪽).
- 위험: 헤지 모드 종목이 행을 둘 주는지는 문서에 없다. 어느 행이든 0이 아니면 막는다.
- 위험: 서버가 질의 순서를 요구하는지 모른다(정렬해서 보낸다). 실제 응답은 testnet에서 확인한다.
- 위험: IP 확인은 확인용 서비스를 믿는다. https만 받는다.
- 가정: `REGULAR_MARGIN`이 교차 증거금이다(F18 §6).
- 확인하지 않음: 실제 Bybit 응답(이 단위의 시험은 loopback 가짜 서버만 쓴다).
- 확인하지 않음: 다른 사용자 소유 파일의 거절(시험에 root가 필요하다).
- 위험: `api.bybit.com`이 IPv6로만 닿는 경우는 생각하지 않았다. IPv4만 쓰므로 그때는 연결이 안 되어 막힌다(안전한 쪽).
- 위험(U16c): 거래소 변경(ADL 등) 직후의 포지션 응답이 거래소 쪽에서 늦은 값이면(문서가 변동이 클 때 `position/list`의 지연을 경고한다, F20 Q12.9) 코어가 변경을 되돌리는 `PositionAdjusted`를 쓴다. ADR-023 §8의 가정(응답 시각 기준 일관성)과 같은 위험이고 감시자 W2가 다시 본다. 포지션 행의 `seq`·`updatedTime`으로 변경보다 오래된 응답을 거르는 것은 코어 입력을 바꾸는 일이라 하지 않았다.
- 위험(U16c): 취소·거부된 주문은 주문 내역에 24시간만 남는다(F18 §1.7). 체결 없이 닫힌 주문을 하루 뒤에 물으면 "없음"이 된다. 체결이 없으므로 예약을 푸는 결과는 같지만 열려 있던 주문이면 상태 불일치가 날 수 있다.
- 위험(U16c): `totalEquity`는 담보로 쓰지 않는 자산까지 더한다. 그런 자산이 있으면 계좌 레버리지 상한과 하루 손실이 실제 담보보다 넉넉하게 계산된다. 서브계정에 USDT만 둔다는 운영 가정이다.
- 위험(U16c): 같은 `execTime`의 행은 정렬이 흔들릴 수 있다고 문서가 쓴다. 커서가 그런 행을 건너뛰지 않는다는 보장은 없다(중복은 걸러도 빠진 행은 못 찾는다).
- 위험(U16c): 숫자가 소수 9자리 이상이면(코어는 1e-8 단위) 그 응답은 못 읽은 것이 된다. 증거금 보고면 보고 전체가 무효라 일반 주문이 막힌다(안전한 쪽). 실제 자릿수는 testnet에서 본다.
- 위험(U16c): 같은 밀리초에 쪽 한도(100)의 배수만큼 실행이 있고 거래소가 마지막 다 찬 쪽에 빈 커서를 주면, 1ms 창까지 나눠도 끝을 알 수 없어 동기화가 멈춘다(오류 기록, 주문이 닫히지 않는 쪽).
- 가정(U16c): `execFee`는 Trade에서 양수 = 비용이다. maker 리베이트의 부호는 문서에 없다(F20 Q9.5).
- 가정(U16c): ADL·청산 인수 행의 `side`는 우리 포지션이 움직인 쪽이다(T15 전까지).
- 확인하지 않음(U16c): 펀딩·ADL 행이 실행 목록에 실제로 실리는지, maker 체결에 `orderLinkId`가 있는지(F20 Q9.6, Q14).

- 위험(U16d): 스트림이 재연결 뒤 놓친 메시지를 다시 주는지는 문서에 없다(F18 §1.7). 조회가 메우지만 그 사이(재연결 → 조회 응답)의 주문 상태는 스트림이 아니라 조회가 말한다.
- 위험(U16d): 비공개 스트림이 비거래 실행(펀딩, ADL)을 싣는지는 문서에 없다(F20 Q14). 실리지 않아도 조회의 체결 동기화가 읽는다.
- 위험(U16d): 시작 확인과 연결 사이, IP 확인 사이(60초)에 바뀐 IP는 다음 확인까지 모른다.
- 가정(U16d): `success: true`가 아닌 인증 응답은 거부다. 거래소가 일시 오류를 같은 모양으로 주면 재시작이 필요하다.
- 확인하지 않음(U16d): 실제 Bybit 스트림(가짜 웹소켓 서버만 쓴다), TLS 접속(시험은 ws://), 거래소가 끊기 전 보내는 마지막 메시지.

- 위험(U17a): 접수(retCode 0)가 처리되지 않는 경우가 있는지 문서에 없다. 그런 주문은 열린 주문 조회까지(조정기 주기) 예약을 잡고 있다가 부재 규칙으로 닫힌다.
- 위험(U17a): 거부로 분류한 코드 가운데 실제로는 처리된 요청이 있다면 예약이 일찍 풀린다. 문서의 문장으로만 골랐다(T6, testnet). 그런 주문이 체결되면 열린 주문·포지션 조회가 불일치로 잡는다.
- 위험(U17a, 독립 검토): 취소의 retCode 0도 접수일 뿐이다(처리는 비동기, F20 11.5). 코어는 `Confirmed`를 받으면 그 시도를 다시 보내지 않고 상태를 기다리며(`AwaitingCancelResult`), 확인된 취소는 `CancelStuck` 감시에서 빠진다. 접수됐지만 적용되지 않은 취소는 주문이 열린 채로 남고 알림이 없다. 코어 전체(Hyperliquid 포함)의 규칙을 바꾸는 일이라 이 판에서는 하지 않았다. 정리 스위치(U18b)와 감시자(U19)의 확인 고리에서 "확인된 취소 뒤에도 열린 주문"을 잡아야 한다.
- 위험(U17a): 틱·수량 단위는 시작할 때만 본다. 거래소가 운영 중에 단위를 바꾸면 다음 주문이 거부되거나(안전), 잘려 받아질 수 있다(문서에 없음).
- 위험(U17a, 수정분 재검토): 시계는 확인 사이(IP 확인 주기 60초)에 앞으로 뛸 수 있다. 그 사이의 생성은 다음 확인까지 막히지 않는다. NTP의 계단 보정을 끄는 것(slew만)이 운영 쪽 대책이다(runbook).
- 위험(U17a, 수정분 재검토): 시계 막힘 중의 취소는 로컬 시계가 1초 넘게 앞서면 거래소가 거절한다(10002). 그 취소는 `Rejected`가 되고 코어가 상태를 묻는다. 막힘 중에 취소가 나간다고 반드시 적용된다는 보장은 아니다.
- 위험(U17a, 수정분 재검토 2): 응답 없는 요청의 한도 상한(`요청 시각 + recv_window + 1초`)은 로컬 시계가 1초 넘게 앞서지 않는다는 가정이다(G-4와 같은 가정). 시계 막힘 중의 취소는 이 가정이 깨진 채 나갈 수 있어, 시간 초과된 취소가 늦게 닿으면 창 하나를 넘길 수 있다. 시간 초과와 늦은 도착이 겹쳐야 하는 드문 경우다. 거래소가 만료로 거절한 요청(10002)을 한도에 세는지는 문서에 없다.
- 위험(U17a, 수정분 재검토 2): 망이 늘 느리면(왕복 250ms 넘음) 시작 뒤의 시계 확인이 계속 판정되지 않고 앞의 결과가 남는다. 경고 기록만 있다. 1초 넘게 앞서면 거래소가 10002로 거절하므로 피해는 그 안이다. 연속 미판정 횟수 알림은 감시(U19)의 몫으로 둔다.
- 위험(U17a, 수정분 재검토 2): `/v5/market/time`이 시계가 아닌 이유로 거절하면(`Refused` → `account`) 그 막힘도 시계 칸에 들어가 생성만 막는다. 공개 엔드포인트라 드물다.
- 위험(U17a): 한도는 프로세스 하나 안의 창이다. 감시자(U19)의 cancel-all이나 다른 프로세스가 같은 UID로 보내는 요청은 세지 않는다. 감시자는 비상 때만 보내고 취소이므로 예약 2개 안에 든다고 본다(판단).
- 가정(U17a): 접속 단계 오류(`is_connect`)는 요청의 어느 바이트도 나가지 않았다는 뜻이다(A-08과 같은 가정, reqwest).
- 확인하지 않음(U17a): 실제 Bybit 주문 응답과 코드(T6), WS Trade와 REST가 한도를 공유하는지(T8).

- 위험(U17b): WS Trade 연결이 끊기면 응답을 기다리던 요청이 모두 결과 불명이 된다(10019도 그렇다). REST보다 결과 불명이 잦을 수 있고, 코어가 조회로 풀 때까지 예약이 남는다(안전한 쪽).
- 위험(U17b): 쓰기가 실패하면 바이트가 하나도 나가지 않았어도 결과 불명으로 둔다(쓰기를 시작하기 전에 대기 목록에 넣는다). 안전한 쪽이다.
- 위험(U17b): WS OE의 10003은 "같은 UID의 세션이 너무 많음"인데 번호가 UTA의 키 무효(10003, 키 거부 코드)와 같다. WS Trade 응답의 10003도 키 거부로 재시작까지 막는다. 안전한 쪽이지만 운영자가 원인을 보고 다시 시작해야 한다.
- 위험(U17b): 키 거부·IP 차단 효과는 연결 작업과 주문 작업이 둘 다 건다(같은 상태로 두 번, 멈춤 끝이 몇 ms 늦어지고 오류 기록이 두 줄). `reqId` 없는 키 거부·10403 응답도 `retCode`가 있으면 효과를 건다.
- 위험(U17b): 비공개 스트림과 WS Trade가 따로 다시 붙는다. 둘 다 첫 pong 직후에 끊기기를 되풀이하면 연결마다 0.5초 + pong까지(5초 이하)마다 접속해 5분에 약 110회다. 접속 한도(5분 500회) 안이다.
- 가정(U17b): WS Trade의 `X-BAPI-TIMESTAMP`·`X-BAPI-RECV-WINDOW`는 REST의 같은 머리글과 같은 규칙(요청 시각 + 창, 1초 앞섬 한도)으로 검사된다. G-4(§7d R4)가 여기에 기댄다. 문서는 같은 이름과 기본값(5000)만 준다.
- 확인하지 않음(U17b): 실제 WS Trade의 응답 모양(`data`, `header`, `connId`), 실패한 `auth`와 pong의 실제 모양(두 pong 모양을 다 받는다), TLS 접속(시험은 ws://), `reqId` 중복의 범위와 기간, 무응답 때 거래소의 동작.

- 위험(U17c): 공개 스트림이 내려가 있거나 한 종목의 티커가 멈추면 `ref_price_max_age_us`(기본 15초) 뒤 가격 범위가 있는 그 종목의 새 주문이 모두 거절된다. 열린 주문과 취소는 영향이 없다. 안전한 쪽이지만 거래가 멈춘다(runbook 7.5).
- 위험(U17c): `markPrice`의 소수가 8자리를 넘으면(코어는 1e-8 단위) 그 메시지는 읽을 수 없는 것이 되어 연결이 끊기고 다시 붙는다. 연결은 모든 종목이 함께 쓰므로, 그런 종목이 하나라도 있으면 구독 직후의 스냅숏마다 연결이 끊겨(첫 pong 전이라 대기가 10초까지 는다) 그 연결의 모든 종목에 가격이 오지 않고, 가격 범위가 있는 모든 종목의 새 주문이 거절된다(안전한 쪽). 실제 자릿수는 testnet에서 본다.
- 위험(U17c): 델타가 빠지면(거래소가 순서 번호 `cs`를 주지만 읽지 않는다) mark가 한 번 늦을 수 있다. mark는 다음 `markPrice` 델타나 다음 연결의 스냅숏이 고친다. 가격 범위는 넓은 비율(bps)이라 짧은 늦음은 거절·허용을 바꾸지 않는다고 본다(판단).
- 위험(U17c): 간격은 로컬 단조 시계로 잰다. 코어의 낡음 판정은 기록 시각(`at`)으로 한다. 거래소의 `ts`는 `venue_ts`로 기록만 한다. 거래소가 오래된 `ts`의 메시지를 늦게 보내도 낡음으로 보지 않는다(Hyperliquid와 같다).
- 위험(U17c): 시험용 연결 주소(`OMS_TEST_BYBIT_WIRING`)는 `failpoints` 빌드에만 있다. 배포 바이너리에 그 기능이 켜지면 환경 변수 하나로 거래소 주소가 바뀐다(127.0.0.1만 받으므로 다른 호스트로는 못 간다). 배포 빌드에 기능이 없다는 것은 빌드 절차가 지킨다(코드 검토만).
- 위험(U17c): 간격 안에 바뀐 mark는 간격이 지난 뒤의 다음 티커 메시지에 실려 간다. 그 메시지가 오지 않으면 코어는 그 전 가격을 `ref_price_max_age_us` 동안 쓴다. 늦음은 많아야 간격 + 메시지 사이 시간이다. 재연결 직후에도 같아서, 새 연결의 스냅숏이 간격 안에 오면 다음 메시지까지 앞 연결이 보낸 마지막 가격으로 판정된다(낡음 한도 안).
- 가정(U17c): 공개 linear는 구독마다 스냅숏을 한 번 보내고 그 뒤 바뀐 칸만 델타로 보낸다(11-18 수집기 설계, md-bybit). 스냅숏에는 `markPrice`가 있다.
- 위험(U17d): 50 %(5000 bps)는 판단이다. 너무 낮으면 정상 거래가 자주 멈추고(되돌리려면 해제 또는 한도 변경), 너무 높으면 거래소의 청산과 사이가 좁다. 5초 조회가 급한 가격 변화를 건너뛸 수 있고, 새 보고를 받지 못하는 동안에는 판정하지 않는다. testnet에서 다시 본다.
- 위험(U17d): 잘못 걸린 래치(예: 거래소의 `totalMaintenanceMargin`이 청산 판정의 숫자가 아님)는 조건이 참으로 읽히는 동안 `clear-reduce`로 풀 수 없다(`account_mm_active`). 운영자는 한도를 바꾼 설정을 켜야 한다. 다만 한도는 1..=9999 bps이고 Bybit 메인넷은 증거금 정책이 필수라, 증거금 잔고가 0 이하로 읽히는 잘못된 보고(유지증거금 > 0)가 이어지면 어떤 설정으로도 풀리지 않고 코드를 고쳐야 한다. 그동안 감소 전용 주문은 나간다(검토 참고).
- 위험(U17d): 계좌 모드가 `ISOLATED_MARGIN`이면 거래소는 계좌 단위 필드가 맞지 않는다고 한다. 게이트웨이는 모드보다 지갑 필드를 먼저 읽으므로, 그런 계좌의 보고는 지갑 이유의 `MarginReportInvalid`가 된다. 주문은 계좌 모드 확인과 낡은 보고로 이미 막히지만(안전한 쪽), 운영자에게 보이는 이유가 실제 원인(모드)과 다르다.
- 위험(U17d): 한도를 처음 켠 직후, 마지막으로 기록된 보고가 이 필드 전의 것이면 다음 보고(약 5초)까지 계좌 조건은 거짓으로 읽힌다.
- 위험(U17d): 잔고가 음수이고 유지증거금이 0인 계좌는 이 규칙이 걸지 않는다(판단). 그런 계좌의 손실은 일 손실 규칙이 계좌 가치로 본다.
- 가정(U17d): `totalMaintenanceMargin`과 `totalMarginBalance`는 거래소가 교차 계좌의 청산을 판정하는 숫자이고 같은 시각의 값이다(문서의 정의만 읽었다. "All account wide fields are not applicable to isolated margin", F18 §6. 이 계좌는 교차다).
- 확인하지 않음(U17d): 실제 `wallet-balance` 응답의 두 필드와 `accountMMRate`의 형식(가짜 HTTP 서버만), 노드 프로세스를 거친 진입(Bybit 노드 시험은 증거금 정책 없이 돈다).
- 확인하지 않음(U17c): 실제 공개 스트림(가짜 서버만), 구독 거부 응답의 실제 모양(`success: false`로 본다), TLS 접속(시험은 ws://), 연결 하나에 둘 수 있는 토픽 수(거래하는 종목 수가 적어 한도에 닿지 않는다고 본다).
