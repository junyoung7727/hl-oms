# ADR-017 Hyperliquid 게이트웨이

상태: 채택(구현). 실주문 검증은 하지 않았다(U-01).

근거 자료는 [research/hyperliquid-protocol.md](../research/hyperliquid-protocol.md)다. 아래의 "문서"는 Hyperliquid 공식 문서를 뜻한다.

## 1. 문제와 발생 가능한 실패

- 서명이 한 바이트라도 다르면 요청이 이유 없이 거부된다. 문서는 서명 절차를 규정하지 않고 Python SDK를 보라고 한다.
- 문서가 침묵하거나 스스로 모순되는 부분이 있다. cloid 중복 처리, 주문의 `sz` 의미, 페이지 크기, HTTP 상태 코드, 응답이 없을 때의 계약.
- 낙관적으로 해석하면 실거래에서 처음 어긋난다. 응답 유실을 실패로 읽으면 예약 없는 주문이 생긴다.

## 2. 일반적으로 만족해야 하는 성질

게이트웨이 계약([C-GW](../contracts/gateway.md))의 의무 12가지. 그중 결과 분류(G-2), 재전송 금지(G-3), 만료 전달(G-4),
체결 동기화의 정직성(G-7), 체결 키(G-8)가 정합성에 직접 영향을 준다.

## 3. 제약

| 사실 | 출처 |
|---|---|
| 주문은 `POST /exchange`, 조회는 `POST /info`, 통보는 WebSocket | 문서 |
| IP당 분당 1200 weight. 주문·취소는 1, `orderStatus`·`clearinghouseState`는 2, 그 외 조회는 20 이상 | 문서 |
| 서명은 msgpack 해시 + EIP-712. 절차는 SDK에만 있다 | SDK |
| 공식 Rust SDK는 2025-10 이후 커밋이 없고 `expiresAfter`, `noop`이 없다 | 저장소 확인 |
| 자산 인덱스는 mainnet과 testnet이 다르다(실측: testnet BTC는 3) | 문서, 실측 |

## 4. 필수 조건과 선택 조건

필수: C-GW. 서명의 정확성. 비밀 키가 게이트웨이 밖으로 나가지 않음. mainnet 오조작 방지.
선택: WebSocket으로 주문 전송(지연 감소), 배치, 요청 예약 구매.

## 5. 대안

| 대안 | 설명 |
|---|---|
| A. 공식 Rust SDK | `hyperliquid-rust-sdk` |
| B. 커뮤니티 SDK | 문서가 링크하는 `hypersdk`(MPL-2.0) |
| C. 필요한 부분만 직접 구현 | 서명, 주문·취소·예약 취소 액션, 조회 넷, 스트림 셋 |

## 6. 비교

| 기준 | A | B | C |
|---|---|---|---|
| `expiresAfter` | 없다 | 확인하지 않았다 | 구현 |
| 결과 분류를 우리 계약대로 | SDK의 오류 타입에 맞춰야 한다 | 같다 | 직접 정한다 |
| 자동 재시도 여부 통제 | SDK 내부에 의존 | 같다 | HTTP 호출 한 곳 |
| 유지보수 | 11개월 무커밋 | 활발(조사 시점) | 우리 부담 |
| 서명 검증 | SDK를 믿는다 | 같다 | SDK 시험 벡터로 대조 |
| 코드량 | 적음 | 적음 | 약 900줄 |

B는 조사에서 깊이 읽지 않았다. 그래서 B의 칸은 대부분 미확인이고, B를 고르지 않은 것은 비교의 결과가 아니라 조사 범위의 한계다.
A와 C의 칸은 저장소와 문서에서 확인한 사실과 정성 판단이다. 측정값은 없다.

## 7. 선택과 이유

C. `crates/oms-node/src/venue/hyperliquid/`(`sign.rs`, `wire.rs`, `mod.rs`).
[ADR-005](ADR-005-unknown-outcome.md)의 복구 정책이 `expiresAfter`에 의존하는데 A에는 그것이 없다. 결과 분류와 재시도 금지를 한 곳에서 통제하는 것이 정합성에 중요하다.

### 서명

`keccak256(msgpack(action) ‖ nonce 8바이트 BE ‖ 0x00 ‖ [0x00 ‖ expiresAfter 8바이트 BE])`를 `connectionId`로 하는
`Agent { source: "a"(mainnet) | "b"(testnet), connectionId }`를 EIP-712로 서명한다. 도메인은 `Exchange`, `1`, chainId 1337, 검증 계약 0.
액션 구조체의 필드 순서가 해시의 일부이므로 `wire.rs`의 구조체 필드 순서를 바꾸면 안 된다.

SDK 시험 벡터(commit 2fdb18f)로 대조한 것: 액션 해시, 임의 액션, 주문, cloid가 있는 주문, 예약 취소 2종. mainnet과 testnet 모두.
벡터가 없는 것: `expiresAfter`가 붙은 서명(바이트 배치만 SDK 소스와 대조), `cancelByCloid` 액션.

### 문서의 공백에 대한 해석

| 공백 또는 모순 | 해석 | 그 해석의 결과 |
|---|---|---|
| 같은 cloid의 재전송이 거부되는가 | 거부되지 않는다고 본다 | 신규 주문을 재전송하지 않는다 |
| HTTP 200이 아닌 응답의 의미 | 처리 여부를 알 수 없다고 본다 | `Unknown`. 만료 뒤 조회로 해소 |
| 응답의 주문 상태가 문서의 세 가지(resting, filled, error)가 아님 | 알 수 없다고 본다 | `Unknown` |
| 최상위 `status: "err"` | 문서에는 이 형태의 예가 없고 SDK의 타입에만 있다. 주문이 놓이지 않았다는 증거로 **보지 않는다**(기본) | `Unknown`. 만료 뒤 조회로 해소. 실주문으로 뜻을 확인한 뒤 `trust_top_level_error = true`로 바꾸면 `Rejected` |
| 주문의 `sz`가 잔량인지 체결량인지 | 쓰지 않는다 | 최종 누적 수량을 알리지 않는다. 종결은 체결 동기화로 닫는다 |
| "filled" 상태가 IOC 부분 체결에도 쓰이는가 | 알 수 없다고 본다 | 모든 종결 상태를 "수량 미상의 종결"로 전달한다. 기장된 체결이 주문 수량과 같으면 코어가 전량 체결로 닫는다 |
| 체결 통보에 cloid가 있는가 | 없을 수 있다고 본다 | 거래소 주문 ID로 주문을 찾는다. 모르면 코어의 대기 목록 |
| 열린 주문 목록에 cloid가 있는가 | 없을 수 있다고 본다 | 거래소 주문 ID로도 우리 주문을 인식한다 |
| 체결 조회의 페이지 크기(2000 또는 500) | 어느 쪽인지 가정하지 않는다 | 500건보다 짧은 쪽만 마지막 쪽으로 본다. 그보다 길면 마지막 체결 시각부터 다시 묻고, 새 체결이 없는 가득 찬 쪽이나 누적 1만 건에서는 완료를 선언하지 않는다 |
| 조회 가능한 체결은 최근 1만 건 | 그보다 밀리면 복원할 수 없다고 본다 | 완료를 선언하지 않고 오류를 남긴다. 신규 주문이 막힌 채로 남는다 |
| 조회가 최신 블록보다 얼마나 늦는가 | 2초 이내로 본다(`fills_lag_ms`) | 체결 조회의 종료 시각을 2초 전으로 잡고 그 직전까지만 완료를 선언 |
| 문서의 표에 없는 상태 이름 | 아무 결론도 내지 않는다 | 코어로 넘기지 않고 오류로 남긴다. 주문은 그대로이고, 열린 주문 대조와 운영자가 처리한다 |
| 같은 계좌의 spot 체결 | 이 OMS의 범위 밖이다 | perp 종목 목록에 없는 종목의 체결은 기장하지 않고 경고를 남긴다. 체결 동기화는 계속된다 |
| 읽을 수 없는 스트림 통보, 구독 오류 | 스트림을 믿을 수 없다고 본다 | 연결을 끊고 다시 붙는다. 재확인이 조회로 메운다 |

### 결과 분류 (G-2)

| 상황 | 분류 |
|---|---|
| 전송 전 만료 시각이 지남, 종목이 거래소 목록에 없음, 로컬 요청 예산 소진, 서명 실패 | `NotSent` |
| 연결 수립 실패(`reqwest`의 connect 오류) | `NotSent` |
| 시간 초과, 연결 끊김, HTTP 200이 아님, 본문 해석 불가, 문서에 없는 형태 | `Unknown` |
| `resting`, `filled` | `Placed` |
| 주문별 `error` 문자열 | `Rejected` |
| 최상위 `err` | `Unknown`(기본). 설정으로 `Rejected` |

### 그 밖의 선택

- nonce: ms 시각과 `이전 + 1` 중 큰 값을 CAS로 발급한다. 저널에 넣지 않는다.
- 요청 예산: 1200까지, 초당 20 보충. 주문은 100을 남기고, 조회는 300을 남기고 쓴다. 취소는 전부 쓸 수 있다.
- 종목 규칙 대조: 시작할 때 `meta`를 읽어 설정의 `qty_step`, `px_tick`, `px_max_sig_figs`가 거래소 규칙보다 거칠거나 같은지 확인한다. 아니면 링크를 올리지 않는다.
- 링크: `orderUpdates`와 `userFills` 구독이 모두 확인되면 올린다. 15초 안에 확인되지 않으면 끊고 다시 붙는다(시세 구독이 연결을 살려 두므로 침묵만으로는 알 수 없다).
  75초 동안 메시지가 없으면 끊고 다시 붙는다(거래소는 60초 무송신이면 끊는다). 50초마다 ping. `error` 채널의 통보를 받으면 끊고 다시 붙는다.
- HTTP: 리디렉션을 따라가지 않는다. 따라가면 서명한 요청이 다시 전송된다.
- 참조 가격: `allMids`에서 종목별로 5초에 한 번.
- 예약 취소(dead man's switch): `schedule_cancel_secs`가 양수면 그 3분의 1 간격으로 갱신한다. 기본은 꺼짐(U-05).
  거래소가 갱신을 거부하면(일일 횟수 제한, 계좌 조건) 오류 로그에 "걸려 있지 않다"고 남긴다. 화면에는 나타나지 않는다.
- mainnet: 설정에 `mainnet_confirmed = true`가 있어야 한다. 키는 환경 변수로만 받는다.
- 쓰지 않는 것: 배치, 정정, WebSocket post, 요청 예약 구매, 서브계정·vault.

## 8. 포기한 장점, 남은 위험, 가정

- **주문 경로는 실제 거래소에서 실행된 적이 없다.** 확인한 것은 서명 벡터, 문서 예제의 해석, testnet 읽기 전용 호출뿐이다.
- `reqwest`가 요청을 다시 보내는 경로: 리디렉션은 껐다. 간격 검토에서 0.13.5의 소스를 읽은 결과, 기본 재시도는 서버가 처리하지 않았다고 프로토콜 수준에서 알린 요청에 한한다고 판단했다.
  실험으로 확인한 것은 아니다(가정 A-08).
- 최상위 오류를 `Unknown`으로 두면, 거래소가 액션을 통째로 거부할 때마다(서명 오류, 요청 한도 초과 등) 그 주문이 만료 + 여유까지 결과 불명으로 남고 계좌 전체의 신규 주문이 막힌다.
  안전한 쪽이지만 가용성을 잃는다. 실주문으로 뜻을 확인하는 것이 U-01의 첫 실험이다.
- 스트림 재접속 사유들과 예약 취소의 거부 처리는 코드만 있고 시험이 없다.
- agent 지갑의 만료·교체, 상장 폐지나 업그레이드 중의 제한 같은 거래소 주도 사건을 다루지 않는다(P-VEN-12, P-VEN-13).
- 계좌 단위 요청 한도를 조회하지 않는다(P-VEN-04).
- 청산·ADL·funding을 다루지 않는다(P-VEN-08).
- 시계가 거래소와 2초 이상 어긋나면 체결 동기화 선언이 틀릴 수 있다(가정 A-02).
- testnet 실험 목록 35건이 조사 문서 §4에 있다. 그중 이 설계가 기대는 것: `expiresAfter`의 거부 동작과 기준 시계, 체결의 `time`이 스트림과 REST에서 같은지, 페이지 크기, IOC 부분 체결의 응답과 상태, 열린 주문·체결의 cloid 유무.

## 9. 근거

- `venue::hyperliquid::sign::tests` 7건(SDK 벡터), `wire::tests` 7건(문서 예제, 상태 이름 표 전체, 종목 이름 변환), `tests` 2건(요청 예산, 체결 쪽 판정).
- 간격 검토가 찾은 결함과 수정: spot 체결 하나가 체결 동기화를 영구히 멈추던 것, 1만 건 밀린 체결을 완료로 선언하던 것, 리디렉션, 무시되던 구독 오류와 예약 취소 거부([gap-review](../verification/gap-review.md)).
- `hl_live::the_gateway_reads_the_real_testnet`: 2026-10-02 실제 testnet에서 메타 대조 통과, 스트림 구독, `unknownOid`, 빈 열린 주문·포지션, 체결 동기화, BTC 참조 가격 수신.

## 10. 재검토 조건

testnet 실주문 실험 결과. 문서 갱신. 공식 Rust SDK가 `expiresAfter`를 지원하게 될 때.
