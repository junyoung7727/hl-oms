# ADR-003 저널에 무엇을 기록하는가: 입력과 결정된 이벤트를 한 기록으로

상태: 채택.

## 1. 문제와 발생 가능한 실패

복구는 저널에서 상태를 다시 만든다. 무엇을 기록하느냐에 따라 다음 실패가 갈린다.

- 판단 로직을 고친 새 빌드가 옛 기록을 재생했더니 다른 결과가 나온다. 이미 거래소로 나간 주문이 "거절된 주문"으로 재구성된다.
- 여러 기록이 한 전이를 나눠 담고 있어, 중간에서 잘리면 반쪽 상태가 남는다.
- 거절·중복처럼 상태를 바꾸지 않은 요청의 흔적이 없어 사후 설명이 불가능하다.

## 2. 일반적으로 만족해야 하는 성질

- 한 상태 전이는 전부 기록되거나 전혀 기록되지 않는다.
- 재생 결과는 외부로 나간 효과와 모순되지 않는다.
- 기록 형식은 빌드가 바뀌어도 읽을 수 있거나, 읽을 수 없음이 명확히 드러난다.

## 3. 제약과 우선순위

위험 한도와 검증 규칙은 운영 중 가장 자주 바뀌는 코드다. 그 변경이 복구를 위험하게 만들면 안 된다.
기록량은 거래소 한도(초당 약 20건)로 묶여 작다.

## 4. 필수 조건과 선택 조건

필수: 전이의 원자성. 판단 로직 변경에 대한 재생 안정성. 재생이 전송 명령을 만들지 않음.
선택: 작은 기록 크기, 빠른 인코딩, 사람이 읽을 수 있는 형식.

## 5. 대안

| 대안 | 기록 내용 | 복구 |
|---|---|---|
| A. 입력만 (LMAX 원형, 가장 단순) | 입력과 시각 | 입력을 판단 로직에 다시 통과시킨다 |
| B. 이벤트만 | 결정된 상태 전이 | 이벤트를 적용한다 |
| C. 입력 + 이벤트를 한 기록에 | 입력, 시각, 그 입력이 만든 이벤트 목록 | 이벤트를 적용한다. 입력은 감사와 재판단 검증에 쓴다 |

## 6. 비교

| 기준 | A. 입력만 | B. 이벤트만 | C. 입력 + 이벤트 |
|---|---|---|---|
| 원자성 | 입력 하나 = 기록 하나 | 한 입력의 이벤트들을 한 기록에 담으면 성립 | 성립 |
| 판단 로직 변경 | 재생 결과가 바뀔 수 있다. 업그레이드 전에 옛 빌드로 스냅샷을 떠야 하고, 그 절차를 빠뜨리면 조용히 어긋난다 | 영향 없음 | 영향 없음 |
| 이벤트 적용 로직 변경 | 해당 없음 | 스키마 버전 관리 필요 | 스키마 버전 관리 필요 |
| 감사("무엇을 요청받았나") | 완전 | 요청 원문이 없다 | 완전 |
| 결정성 검증 | 재생 자체가 검증 | 불가 | 입력을 다시 판단해 기록된 이벤트와 비교할 수 있다 |
| 기록 크기 | 가장 작다 | 중간 | 가장 크다(측정: 평균 455바이트) |
| 코어 구현 규율 | 낮음 | 모든 변경이 이벤트를 거쳐야 한다 | B와 같다 |

## 7. 선택과 이유

C. 기록 하나는 `Record { seq, at, input, events }`다(`crates/oms-core/src/record.rs`).

- 복구는 `events`만 적용한다(`Core::replay`). 판단을 다시 하지 않으므로 판단 로직 변경이 과거를 바꾸지 못한다.
- `input`은 감사 근거이고, `oms-node verify --re-decide`가 "이 빌드가 같은 입력에서 같은 이벤트를 결정하는가"를 확인하는 재료다.
  판단 로직을 바꾼 빌드에서는 이 검사가 실패할 수 있다. 그것은 복구 실패가 아니라 "판단이 달라졌다"는 정보다.
- 한 입력의 모든 이벤트가 한 프레임에 들어가므로 부분 기록이 없다.
- 이벤트가 하나도 없는 입력은 기록하지 않는다(시간 경과, 중복 통보, 중복 요청). 상태가 변하지 않았기 때문이다.

A를 택하지 않은 이유는 필수 조건 "판단 로직 변경에 대한 재생 안정성"이다. A는 운영 절차로만 이를 지킬 수 있다.

### 코어 구현에 주는 규율

모든 상태 변경은 `Tx::emit(event)`를 거친다. `emit`은 `Core::apply`를 호출하고 이벤트를 출력 목록에 넣는다.
`apply`는 살아 있는 처리와 복구가 함께 쓰는 유일한 변경 함수다. 전송 명령은 이벤트에서 파생된다
(`Core::command_for`: `OrderAccepted` → `SendOrder`, `CancelSent` → `SendCancel`). 복구는 `command_for`를 부르지 않는다.

## 8. 포기한 장점, 남은 위험, 가정

- 기록이 크다. 기록 하나가 평균 455바이트이고, 주문 하나가 접수·거래소 접수·체결과 종결로 기록 약 3건, 약 1.4 KiB를 남긴다(성능 측정의 저널 크기 ÷ 주문 수).
  거래소의 IP 한도인 초당 20건을 하루 내내 채우면 약 2.5 GB다(계산값. 실제 사용량은 전략의 주문 빈도에 달렸다).
- 이벤트 스키마를 바꾸면 옛 기록을 읽는 코드를 유지해야 한다. 세그먼트 헤더의 `record_schema`가 다르면 복구가 시작을 거부한다([ADR-011](ADR-011-file-format.md)).
- 기록되지 않는 입력이 있으므로 저널만으로는 "중복 요청이 몇 번 왔는가"를 알 수 없다.

## 9. 근거

- 측정: 기록 인코딩 중앙값 0.5 µs, 크기 평균 455바이트(`evidence/perf/core-bench.json`, release 빌드). fdatasync(빠를 때 중앙값 약 0.9 ms)에 비해 무시할 수 있다.
- 시험: 모든 시나리오 시험이 "이벤트만 적용한 상태 = 살아 있는 상태"를 매 입력 뒤 확인한다. 시뮬레이션은 충돌 뒤 저널만으로 상태를 다시 만든다.
- 프로세스 시험: 강제 종료 뒤 실제 저널에서 복구하고 `verify --re-decide`를 통과한다.

## 10. 재검토 조건

기록량이 저장 용량을 압박할 때(페이로드 인코딩 교체는 한 함수의 변경이고 `record_schema`를 올린다).
입력 원문을 보관하면 안 되는 정보(예: 인증 토큰)가 입력에 들어가게 될 때.
