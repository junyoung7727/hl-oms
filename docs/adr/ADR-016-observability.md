# ADR-016 관측과 대시보드의 경계

상태: 채택.

## 1. 문제와 발생 가능한 실패

- 관측 코드가 코어의 판단 경로에 잠금이나 I/O를 끼워 넣어 지연을 만든다.
- 화면이 아직 기록되지 않은 상태를 보여 준다.
- 화면에서 실수로 거래를 멈추거나 재개한다.
- 연결되지 않은 기능이 "정상"으로, 실행하지 않은 시험이 "통과"로 표시된다.
- 로그가 없다는 이유로 "일어나지 않았다"고 판단한다. 시각이 가깝다는 이유로 인과를 단정한다.

## 2. 일반적으로 만족해야 하는 성질

관측은 처리 결과를 바꾸지 않는다. 관측 비용에 상한이 있다. 보이는 값마다 출처와 기준 시점이 있다.
관측과 변경의 권한 경계가 분리된다. "확인하지 않음"과 "정상"이 구별된다.

## 3. 제약

운영자 1인, 같은 호스트의 브라우저. 설계·검증 근거와 실행 상태를 한곳에서 대조해야 한다(brief §10).

## 4. 필수 조건과 선택 조건

필수: 화면은 읽기 전용. 코어 스레드는 관측 때문에 기다리지 않는다. 화면은 내구화된 상태만 보여 준다.
실행하지 않은 시험을 통과로 표시하지 않는다.
선택: 실시간 갱신, 외부 지표 수집기 연동, 알림.

## 5. 대안

| 대안 | 설명 |
|---|---|
| A. 로그만 (가장 단순) | JSON 로그를 남기고 사람이 읽는다 |
| B. 코어 상태를 직접 읽는 화면 | 코어에 잠금을 걸고 상태를 읽는다 |
| C. 읽기 모델 + 읽기 전용 HTTP | 커밋 단계가 내구화된 기록으로 갱신하는 복제본을 화면이 읽는다 |

## 6. 비교

| 기준 | A | B | C |
|---|---|---|---|
| 처리 경로에 주는 비용 | 로그 쓰기 | 코어가 잠금을 기다린다 | 커밋 스레드가 배치마다 쓰기 잠금을 잡는다. 코어 스레드는 무관 |
| 보이는 상태 | 사후 재구성 | 내구화 전 상태가 섞인다 | 내구화된 상태 |
| 주문 추적 | 로그 검색 | 가능 | 가능. 저널 기록 자체를 보여 준다 |
| 설계·검증과의 대조 | 불가 | 별도 작업 | registry와 검증 결과를 같은 화면에서 |

이 표의 값은 모두 정성 판단이다. 조회가 커밋 스레드를 얼마나 늦추는지는 측정하지 않았다.

## 7. 선택과 이유

C. 구성:

| 요소 | 위치 | 역할 |
|---|---|---|
| 읽기 모델 | `crates/oms-node/src/published.rs` | `Core` 복제본, 주문별 추적, 최근 기록, 단계별 지연, 계수기 |
| 상태 문서 | `crates/oms-node/src/status.rs` | 운영 상태를 한 JSON으로. 로컬 API와 HTTP가 같이 쓴다 |
| HTTP | `crates/oms-node/src/http.rs` | GET만. loopback만. Host 헤더 검사. 화면이 근거 문서와 코드를 함께 보여 줄 수 있도록 `docs/`, `crates/`, `registry/` 아래의 `.md`, `.rs`, `.toml`을 글자 그대로 내준다(설정 파일과 데이터 디렉터리는 내주지 않는다) |
| 화면 | `dashboard/` | 정적 파일. registry와 검증 결과(`dashboard/data/*.json`)와 실행 중인 노드의 API를 읽는다 |

### 화면

| 화면 | 자료 | 실행 중인 노드 없이 |
|---|---|---|
| 고려사항·설계 결정 | `registry.json` | 볼 수 있다 |
| 동작 탐색 | `registry.json`(계약, 이벤트 색인) | 볼 수 있다 |
| 주문 실행 추적 | `/api/orders`, `/api/orders/{id}` | "노드 없음"으로 표시 |
| 검증 현황 | `registry.json`의 주장 + `evidence.json`, `perf.json`, `mutants.json` | 볼 수 있다 |
| 운영 상태 | `/api/status` | "노드 없음"으로 표시 |

`oms-node dashboard`는 노드 없이 정적 화면만 띄운다. 그때 실행 화면은 값을 비워 두고 "연결되지 않음"이라고 표시한다. 정상으로 표시하지 않는다.

### 표시 규칙

- 값마다 판정 종류를 붙인다.

| 종류 | 뜻 | 예 |
|---|---|---|
| 관측 | 이 프로세스가 직접 센 값이나 저널의 기록 | 내구 순번, 큐 깊이, 체결 기록 |
| 추론 | 관측에서 계산한 값 | 차단 사유, 필요한 조회, 설명 가능한 포지션 범위 |
| 기대 | 설계가 정한 값 | 큐 상한, 수용 기준 |
| 미확인 | 이 프로세스가 알 수 없는 것 | 거래소의 현재 실제 상태, 결과 불명 주문의 존재 여부 |

- 실행 종류를 화면 상단에 고정 표시한다: "설명용(노드 없음)", "시뮬레이터 실행(가상 거래소)", "실제 시스템(hyperliquid:testnet 또는 mainnet)".
- 모든 실행 화면에 출처, 기준 시각(`as_of`), 그 시각과 브라우저 시각의 차이, 내구 순번, 바이너리의 소스 다이제스트를 표시한다.
- registry의 소스 다이제스트와 실행 중인 노드의 다이제스트가 다르면 경고한다. 문서가 다른 코드를 설명하고 있을 수 있다.
- 주장의 상태는 결과 파일에서 계산한다(통과, 실패, 미실행, 이전 버전 결과). 손으로 적지 않는다.
- 주문 추적의 각 기록에서 이벤트 이름을 누르면 그 이벤트를 정의한 계약, 설계 결정, 코드 파일, 시험으로 간다(`registry.json`의 `event_index`).
- 주문 추적은 저널 순번 순서다. 시각은 참고용이다. 게이트웨이의 전송 시작·종료 시각은 로컬 시계의 값이고 거래소 시각과 직접 비교할 수 없다는 점을 화면에 적는다.
- "이벤트 없는 입력" 목록(중복 요청, 중복 통보)은 상한이 있는 휘발성 목록이다. 화면에 "여기 없다는 것은 아무것도 증명하지 않는다"고 적는다.

### 관측이 처리 경로에 주는 비용과 놓치는 것

| 항목 | 비용 또는 한계 |
|---|---|
| 읽기 모델 갱신 | 커밋 스레드가 배치마다 이벤트를 한 번 더 적용하고 추적 항목을 만든다(기록 복제 1회) |
| 조회 | 읽기 잠금. 커밋 스레드의 쓰기 잠금과 경합한다. 조회가 길면 응답 해제가 그만큼 늦어진다. 측정하지 않았다 |
| 단계별 지연 | 히스토그램 버킷이라 최대 12.5% 크게 보고된다 |
| 주문별 추적 | 주문당 200건까지. 넘으면 오래된 것을 버리고 `truncated`를 표시한다. 저널에는 전부 있다 |
| 메모리에서 제거된 주문 | 화면에서 사라진다. `oms-node trace --order N`으로 저널에서 찾는다 |
| 이벤트 없는 입력 | 최근 500건만. 시간 경과와 저장 공간 보고는 넣지 않는다 |
| 내구화 전 상태 | 보이지 않는다. 코어가 저널보다 얼마나 앞서 있는지는 큐 깊이로만 짐작한다 |
| 표본 추출 | 하지 않는다. 계수기와 히스토그램은 모든 입력을 센다 |

### 권한 경계

| 동작 | 경로 | 감사 |
|---|---|---|
| 조회 | HTTP(loopback), 로컬 API | 없음 |
| 운영 변경(중지, 재개, 취소, 확인, 조정) | 운영 소켓만 | 저널에 사유와 함께 |
| 장애 주입 | 가상 거래소 프로세스의 제어 명령만. OMS에는 그런 경로가 없다 | 가상 거래소 쪽 |

## 8. 포기한 장점, 남은 위험, 가정

- 알림이 없다(U-11). 외부 지표 수집기 연동이 없다.
- 대시보드는 호스트의 모든 로컬 사용자가 볼 수 있다([ADR-015](ADR-015-api-trust.md) §8).
- 화면 자체의 자동 시험이 없다. HTTP 경로는 수동으로 확인했다. 자동 시험은 문서 열람 경로의 범위 검사 하나다(V-DASH-1).
- 브라우저를 거친 공격면의 검토는 G-SEC-13에 있다.

## 9. 근거

수동 확인 기록은 [verification/README.md](../verification/README.md)의 대시보드 절에 있다. 히스토그램의 오차 한계는 `histogram_bounds_hold_for_every_value`.

## 10. 재검토 조건

원격 열람, 알림, 여러 인스턴스의 통합 화면이 필요해질 때.
