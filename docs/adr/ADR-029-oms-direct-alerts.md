# ADR-029 OMS 직접 알림: 공개된(내구화된) 상태를 읽는 노드 안의 평가 스레드

상태: 채택(구현, U18a2). 송신기는 `crates/alert-direct`(U6, U18a1)다. 계약은 [C-ALERT](../contracts/alerts.md). [ADR-016](ADR-016-observability.md) §8의 "알림이 없다(U-11)"를 대신한다.

## 1. 문제와 발생 가능한 실패

- 노드는 주문을 거절하고, 감소 전용 상태를 걸고, 불일치를 올리고, 저널 실패로 멈춘다. 대시보드를 보지 않으면 아무도 모른다(U-11). 무인 운용에서 차단이 몇 시간 방치될 수 있다.
- 알림이 내구화되지 않은 상태를 보고 나가면, flush에 실패해 없어질 사건(복구한 노드는 모르는 사건)을 사람에게 알린다. 운영자는 저널에 없는 감소 전용 상태나 중지를 찾게 된다(ADR-004의 "내구화 전에는 아무것도 밖으로 나가지 않는다"를 알림이 깬다).
- `/api/status`를 30초마다 읽는 바깥 스크립트(초안 PR #3, `tools/alert/hl_alert.py`)는 두 번 읽는 사이에 생겼다 풀린 상태를 놓치고, 노드가 죽은 뒤에는 치명 상태를 읽을 수 없다.
- 알림 경로가 커밋 단계를 느리게 하거나 막으면(텔레그램 무응답, 잠금) 주문 지연이 텔레그램에 묶인다.
- 연결이 다시 붙을 때마다 지나가는 상태(연결 끊김, 재확인)를 모두 알리면 알림이 소음이 되고 정작 중요한 것을 놓친다.
- 노드가 치명 상태로 멈출 때 마지막 알림이 나가기 전에 프로세스가 끝나면 아무도 모른다.

## 2. 일반적으로 만족해야 하는 성질

- 알림이 읽는 상태는 내구화된 기록에서만 온다(단 하나의 예외는 3과 7에 적는다).
- 알림 경로는 커밋 단계와 코어 스레드를 기다리게 하지 않는다.
- 알림은 저널에 아무것도 쓰지 않는다(입출력의 결과를 저널에 넣지 않는다).
- 지속 조건은 시작 1번, 5분마다 1번, 해소 1번(설계 §7.7, alert-direct의 반복 규칙).
- 치명 종료는 알린다. 그 문장은 실패한 묶음의 내용을 담지 않는다.
- 토큰은 로그·상태·오류 문장 어디에도 나오지 않는다.

## 4. 필수 조건과 선택 조건

필수: 2의 여섯 성질. 차단 사유 전부, 전략 중지, 불일치 종류별, 증거금 보고의 신선도, 게이트웨이 막힘. 치명 종료 알림과 종료 전 전송 대기.
선택: 둘째 채널 — 인터페이스만(어느 서비스인지는 D3, 정하지 않음). 텔레그램 상태 탐침 — 하지 않음(보낼 것이 없을 때의 장애는 모른다).

## 7. 선택과 이유

D. `crates/oms-node/src/alerts.rs`, 스레드 `oms-alert`.

| 단계 | 입력 | 처리 | 출력 | 실패하면 |
|---|---|---|---|---|
| A1 시작 | `[alert]` 설정 | 설정을 읽을 때 토큰 파일을 alert-direct 규칙으로 읽는다(절대 경로, 0600, 심볼릭 링크 아님, 저장소 밖). 게이트웨이보다 먼저 송신기와 평가 스레드를 띄운다. 거래소 이름은 설정에서(`sim`, `hyperliquid:<network>`, `bybit:<network>`) | 송신기, 평가 스레드 | 파일을 못 읽음 → 설정 오류(종료 코드 2). 스레드를 못 띄움 → 종료 코드 3 |
| A2 평가 | 공개된 읽기 모델(읽기 잠금), 게이트웨이 막힘, 알림 시계 | 100 ms마다 치명 상태를 먼저 본다. 아니면 `durable_seq`가 바뀌었거나 `eval_ms`(1초)가 지났을 때 잠금 안에서 `conditions()`를 계산하고 잠금을 푼 뒤 치명 상태를 다시 보고(걸렸으면 아무것도 `set`하지 않는다) 조건마다 `set`을 부른다 | 조건의 시작·반복·해소(alert-direct가 정한다) | — |
| A3 유예 | 조건마다 처음 본 시각 | 평가마다 계속 있으면 `grace_ms`가 지난 뒤 시작을 보낸다. 한 번이라도 없으면 처음부터 다시 센다 | 시작 | 유예 안에 끝난 조건은 아무것도 보내지 않는다 |
| A4 치명 | `fatal` 래치 | 처음 본 때 한 번 `once`: 사유와 마지막 내구 seq만. 그 뒤에는 평가하지 않는다(시작도 해소도 없다) | 치명 알림 | — |
| A5 종료 | 종료 코드, 치명 래치, 설정 활성 여부 | drain 뒤 평가 스레드를 멈춘다. 래치가 걸렸으면 코드는 무엇이든 2이고 치명 알림(A4와 같은 한 번, 시작 중 Boot·Config flush 실패 포함). 아니면 0에 정지 알림(걸린 주문 수), 설정 활성 뒤의 3에 `OMS 시작 실패(exit 3): <종류>`(종류만). 그다음 `exit_flush_ms`(15초)까지 전송을 기다린다. 활성 전의 3은 보내지 않는다 | 전송 | 기다려도 못 보낸 것은 잃는다(상태 파일 없음) |

결정과 이유:

- **공개된 상태만:** 평가 스레드가 가진 상태의 출처는 공개된 읽기 모델 하나다. 커밋 단계가 flush 성공 뒤에만 고치므로, flush에 실패한 묶음의 사건은 볼 수 없다. 구조로 보장한다(평가 스레드는 살아 있는 코어에 닿는 길이 없다).
- **게이트웨이 막힘은 예외:** 막힘에는 저널 이벤트가 없다. "게이트웨이가 보내지 않는다"는 사실만 알리고 저널의 어떤 값도 담지 않으므로 저널과 어긋날 수 없다(판단(모델 아님)).
- **치명 알림은 예외:** 내구성이 실패했다는 알림이다. 사유 문장(`commit failed: <io error>`, 코어 결함은 입력 이름만)과 마지막 내구 seq만 담는다.
- **유예:** 래치와 운영자 행위(감소 전용, 계좌·전략 중지, 불일치)는 0. 연결이 다시 붙거나 시작할 때마다 지나가는 상태(연결 끊김, 재확인, 결과 불명, 거래소 설정, 계좌 모드, 증거금 보고 신선도, 게이트웨이 막힘)와 저장 공간 부족은 `grace_ms`(30초, 판단(모델 아님); 소유자 질문 3). 저장 공간은 5초마다 재는 값이고 코어에 이력 현상(hysteresis)이 없어 문턱 근처에서 들락거리므로 래치가 아니라 지나가는 상태로 다룬다(리뷰 S2). 들락거리는 상태는 유예 한 번에 시작과 해소를 많아야 하나씩 보낸다.
- **차단 문장은 와일드카드 없는 `match` 하나:** 새 차단 사유는 문장과 유예가 생길 때까지 컴파일되지 않는다(U18b의 사유가 이렇게 알림을 얻는다). `Mismatch`는 종류별 조건이, `OperatorStrategy`는 `halt_strategy:<s>`가 맡는다.
- **키의 수는 유한:** 차단 종류 + 종목 + 전략 + 불일치 종류(16) + 2. 보관함은 긴 텔레그램 장애 동안의 반복으로만 찬다.
- **상태 파일 없음:** `set`이 평가 스레드에서 fsync하지 않는다. 노드는 사람이 띄우므로 다시 시작한 뒤 걸려 있는 조건마다 시작 알림을 다시 보내는 편이 낫다(판단(모델 아님)).
- **시작·정지 알림:** 시작마다 한 번 `OMS 시작 (boot n, config v). 활성 조건 k개(유예 중 m개)`(k는 그 평가에서 시작이 나간 조건, m은 유예 안의 조건, 리뷰 N4), 정상 종료에 한 번 `OMS 정상 종료. 걸린 주문 n개는 거래소에 남음`. 경로가 살아 있는지도 보여 준다(소유자 질문 4의 기본값).
- **mainnet은 `[alert]` 없이 시작하지 않는다:** 증거금 정책과 같은 규칙(소유자 질문 1의 기본값).
- **둘째 채널:** `alerts::start`가 `SecondChannel`을 받는다. 설정은 `second_channel = "none"`만 받는다(D3).
- **시험용 훅:** `failpoints` 빌드에서만 `OMS_TEST_TELEGRAM_API`(loopback http 주소만)를 읽어 경로를 그 하나로 바꾸고 토큰 파일의 저장소 규칙을 건너뛴다. 배포하는 바이너리는 이 변수를 무시한다(시험이 확인한다).

## 8. 포기한 장점, 남은 위험, 가정

- 포기: 평가 두 번 사이(보통 100 ms 미만)에 생겼다 풀린 유예 0 조건. 운영자가 푸는 래치라 실제로는 드물다(C-ALERT).
- 포기: 프로세스를 넘는 반복 규칙. 다시 시작하면 걸린 조건의 시작을 다시 보낸다.
- 위험: 종료 전 전송이 실패하면 그 알림은 잃는다. SIGKILL·abort·panic은 아무것도 보내지 못한다. 관측 경로(프로젝터의 `oms_up` = 0, U14/U20b)와 감시자의 W5(U19b)가 맡는다.
- 위험: 보낼 것이 없을 때의 텔레그램 장애는 모른다(탐침 없음). 둘째 채널이 없으면 텔레그램 장애 자체를 알릴 곳이 없다(D3).
- 위험: 시계가 크게 뒤로 가면 유예가 그만큼 길어진다(처음 본 시각보다 앞선 시각은 유예를 채우지 않는다).
- 가정: 텔레그램 Bot API의 동작은 PR #3과 alert-direct가 정한 대로다. 실제 텔레그램에 보낸 적은 이 단위에서 없다(loopback 가짜만).

## 9. 근거

## 10. 재검토 조건

- D3이 둘째 채널 서비스를 정할 때: `second_channel` 값과 그 구현.
- U18b: 새 차단 사유(`KillLatched`, `WatcherMismatch`, `VenueChange`, `StrategyLink`)의 문장과 유예 0, 감시 없음 상태.
- 유예 30초가 연결 끊김에 너무 길다고 소유자가 정할 때(소유자 질문 3).
- 노드를 자동으로 다시 띄우게 될 때(U-06): 다시 시작마다의 시작 알림이 소음이 되면 상태 파일.
