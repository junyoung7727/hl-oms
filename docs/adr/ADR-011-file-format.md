# ADR-011 저널·스냅샷 파일 형식, 손상 처리, 버전 호환

상태: 채택.

## 1. 문제와 발생 가능한 실패

- 쓰는 도중 죽으면 마지막 기록이 반만 남는다.
- 저장 장치가 중간의 바이트를 바꾼다.
- 세그먼트 파일이 하나 빠진다.
- 새 빌드가 옛 형식을, 옛 빌드가 새 형식을 읽는다.
- 스냅샷이 저널보다 앞선 상태를 담는다.

각각을 구별하지 못하면 손상된 기록을 건너뛰고 "복구 성공"이라고 말하게 된다.

## 2. 일반적으로 만족해야 하는 성질

기록마다 길이·순번·체크섬이 있다. 마지막의 불완전한 기록과 중간 손상을 구분한다.
중간 손상은 자동으로 고치지 않는다. 형식과 스키마의 버전이 파일에 적혀 있다. 스냅샷은 원자적으로 나타난다.

## 3. 제약: 의존하는 파일 시스템 보장

출처는 [research/lmax-durability-rust.md](../research/lmax-durability-rust.md) Part 2다.

| 의존하는 보장 | 근거 | 프로세스 종료 시험으로 확인 가능한가 |
|---|---|---|
| `write`가 돌아오면 프로세스가 죽어도 데이터는 페이지 캐시에 남는다 | 추론(직접 문장 없음) | 예 |
| `fdatasync`는 데이터와, 읽는 데 필요한 메타데이터(파일 크기)를 내구화한다 | fdatasync(2) | 아니오. 전원 장애 시험 필요 |
| 파일을 만들거나 이름을 바꾼 뒤에는 디렉터리를 fsync해야 한다 | fsync(2) | 아니오 |
| flush 실패 뒤 재시도는 안전하지 않다 | PostgreSQL wiki "Fsync Errors" | 주입으로만 |
| 여러 블록에 걸친 append는 원자적이지 않다. 꼬리가 잘릴 수 있다 | Pillai 외 2014 | 부분적으로 |
| rename은 원자적으로 관측된다 | rename(2) | 예(동시 관측). 전원 장애는 아니오 |
| 장치가 flush를 지킨다 | 확인 불가 | 아니오 |

## 4. 필수 조건과 선택 조건

필수: 내구화를 확인한 기록은 복구에서 빠지지 않는다. 손상을 건너뛰지 않는다. 다른 인스턴스의 저널을 섞지 않는다.
선택: 빠른 인코딩, 사람이 읽을 수 있음, 작은 크기.

## 5. 대안

| 영역 | 대안 |
|---|---|
| 저장소 | A. SQLite(가장 단순해 보임). B. 직접 만든 append 파일 |
| 페이로드 | JSON, postcard, 직접 만든 바이너리. bincode는 유지보수 중단(RUSTSEC-2025-0141)으로 제외 |
| 꼬리 손상 | 시작 거부(기존 Go 구현), 보존 후 잘라내기 |

## 6. 비교

| 기준 | SQLite | append 파일 |
|---|---|---|
| 내구성 의미 | 성숙. 설정(WAL, synchronous)에 의존 | fdatasync 한 번. 직접 설명 가능 |
| 의존성 | C 라이브러리 | `crc32fast` 하나 |
| 그룹 커밋 | 트랜잭션으로 | 배치 쓰기로 |
| 손상 시 동작 설명 | 내부 구조에 의존 | 이 문서로 전부 |

| 기준 | JSON | postcard |
|---|---|---|
| 인코딩 시간 | 중앙값 0.5 µs/기록(측정) | 더 빠를 것으로 예상(미측정) |
| 스키마 변경 내성 | 필드 이름 기반. 필드 추가에 견딘다 | 위치 기반. enum 순서나 필드 추가가 옛 기록을 깨뜨린다 |
| 도구 접근 | `jq`, 대시보드가 바로 읽는다 | 전용 디코더 필요 |
| 크기 | 평균 455바이트 | 더 작을 것으로 예상(미측정) |

인코딩 0.5 µs는 flush(빠를 때 900 µs)의 0.06%다. 더 빠른 형식이 줄일 수 있는 것은 그 0.06% 안쪽이다.

## 7. 선택과 이유

append 파일 + 고정 바이너리 프레임 + JSON 페이로드. `crates/oms-journal`.

```text
세그먼트 파일  journal-<첫 순번 20자리>.oj
  헤더:  "OMSJRNL\x01" | u32 길이 | JSON {format, record_schema, instance_id, first_seq, created_at_us, writer} | u32 CRC
  프레임: u32 페이로드 길이 | u32 CRC-32(순번 + 페이로드) | u64 순번 | 페이로드(JSON Record)
스냅샷 파일   snapshot-<순번 20자리>.snap
  첫 줄 JSON {format, state_schema, seq, len, crc32, state_digest, ...}, 이어서 페이로드
```

쓰기: 배치의 프레임을 메모리에 모아 `write_all` 한 번, `fdatasync` 한 번. 세그먼트는 flush 직후 크기가 64 MiB를 넘으면 회전한다.
그래서 한 배치가 두 세그먼트에 걸치지 않는다. 새 세그먼트는 헤더를 쓰고 fsync한 뒤 디렉터리를 fsync한다.

복구 시 손상 판정:

| 발견한 것 | 판정 | 동작 |
|---|---|---|
| 마지막 세그먼트의 끝에 불완전하거나 체크섬이 틀린 바이트, 그 뒤에 유효한 프레임 없음 | 불완전한 꼬리 | 바이트를 `torn/`에 보존하고 fsync한 뒤 세그먼트를 그 지점까지 자른다. 복구 보고에 남긴다 |
| 틀린 프레임 뒤에 유효한 프레임이 있음 | 중간 손상 | 시작 거부. 파일을 건드리지 않는다 |
| 마지막이 아닌 세그먼트의 손상 | 중간 손상 | 시작 거부 |
| 순번이 이어지지 않음, 세그먼트 누락 | 빈틈 | 시작 거부 |
| 헤더가 불완전한 가장 새 세그먼트(프레임 없음) | 회전 중 종료 | 보존 후 제거 |
| 다른 `instance_id` | 다른 인스턴스의 파일 | 시작 거부 |
| 읽을 수 없는 `record_schema` | 호환되지 않는 빌드 | 시작 거부 |

꼬리를 자동으로 자르는 이유: flush가 끝나지 않은 기록은 어떤 출력도 내보내지 않았으므로([ADR-004](ADR-004-commit-gate.md)) 버려도 외부와 모순이 없다.
자르지 않고 시작을 거부하면 운영자가 바이너리 파일을 손으로 고쳐야 한다. 원본 바이트는 보존한다.

스냅샷: 임시 이름으로 쓰고 fsync, rename, 디렉터리 fsync. 스냅샷은 읽기 모델(내구화된 기록만 반영)에서 뜨므로 저널보다 앞서지 않는다.
복구는 스냅샷의 체크섬, 상태 스키마, 해석 가능 여부, 인스턴스, 상태 다이제스트(다시 계산해 헤더와 비교)를 확인한다.
어느 하나라도 맞지 않는 스냅샷은 건너뛰고 더 오래된 것을 쓴다. 쓸 수 있는 것이 없으면 저널을 처음부터 재생한다. 지우거나 고치지 않는다.
스냅샷 때문에 시작을 거부하는 경우는 하나뿐이다: 스냅샷이 저널이 가진 것보다 뒤의 순번을 가리킬 때(저널이 잘려 나갔다는 뜻이다).

복구가 파일을 바꾸는 것은 불완전한 꼬리의 보존과 절단뿐이고, 그것도 다른 검사(인스턴스, 스키마, 순번 연속, 스냅샷과의 관계)가 모두 통과한 뒤에 한다.
간격 검토 전에는 절단이 먼저였다. 그래서 거부하면서도 파일을 고치는 경우가 있었다.

### 버전 호환

| 바뀌는 것 | 영향 | 절차 |
|---|---|---|
| 판단 로직(한도, 검증) | 재생에 영향 없음 | 그냥 교체 |
| 설정 | 새 `version`으로 활성화. 저널에 기록 | 버전을 올려 재시작 |
| 상태 스키마(`STATE_SCHEMA`) | 옛 스냅샷을 못 읽는다 | 스냅샷은 건너뛰고 저널을 처음부터 재생한다. 저널이 처음부터 남아 있어야 한다 |
| 기록 스키마(`RECORD_SCHEMA`) | 옛 기록의 해석 | 새 빌드가 옛 스키마를 읽을 수 있어야 한다. 쓰는 스키마가 다르면 새 세그먼트를 시작한다. 옛 빌드는 새 세그먼트를 거부한다 |
| 프레임 형식(`FORMAT`) | 파일을 못 읽는다 | 변환 도구 필요. 현재 없음 |

## 8. 포기한 장점, 남은 위험, 가정

- **마지막 기록에만 생긴 손상은 불완전한 꼬리와 구별할 수 없다.** 내구화를 확인한 마지막 기록이 장치 손상으로 깨지면 꼬리로 보고 버린다.
  그 기록이 주문이었다면 재시작 뒤 열린 주문 대조가 OrphanOrder로 드러낸다.
- 세그먼트 전체를 메모리로 읽는다(최대 64 MiB).
- 프레임 길이 필드는 체크섬에 직접 포함되지 않는다. 길이가 틀리면 범위가 달라져 체크섬이 틀리게 된다(2^-32 확률로 놓친다).
- 전원 장애와 장치의 flush 준수는 검증하지 않았다(A-05).
- 압축과 보관 계층 이동은 없다.

## 9. 근거

- `every_truncation_and_every_bit_flip_is_detected`: 프레임의 모든 절단 위치와 모든 비트 반전.
- `recovery_returns_the_longest_valid_prefix`: 임의 크기·배치·절단 위치에 대한 property test.
- `damage_in_the_middle_is_refused_and_nothing_is_modified`, `a_missing_middle_segment_is_a_gap`, `a_failed_sync_is_final`,
  `a_schema_change_starts_a_new_segment`, `damage_in_the_last_record_is_treated_as_an_incomplete_tail`(한계를 시험으로 고정).
- 프로세스 시험 `journal_damage_is_handled_by_position`: 실제 노드가 꼬리는 보존 후 시작, 중간 손상은 종료 코드 3.
- CRC 기대값은 Python `zlib.crc32`로 따로 계산했다.

## 10. 재검토 조건

저널 크기가 운영 부담이 될 때(페이로드 형식 교체, 압축). 전원 손실 보호가 없는 장치에서 실제 유실이 관측될 때.
세그먼트가 커서 복구 메모리가 문제가 될 때.
