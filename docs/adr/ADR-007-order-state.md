# ADR-007 주문 상태 모델과 체결 식별

상태: 채택.

## 1. 문제와 발생 가능한 실패

거래소 통보는 순서가 보장되지 않고, 중복되며, 끊긴 동안의 것은 빠진다.
Hyperliquid 스트림에는 순번이 없고 주문 통보와 체결 통보는 다른 채널이다([조사 E](../research/hyperliquid-protocol.md)).

- 상태 이름 하나로 "거래소의 실제"와 "우리가 아는 것"을 함께 표현하면, 응답 유실을 "주문 없음"으로 읽게 된다.
- 종결 통보를 받는 즉시 예약을 풀면, 뒤이어 도착하는 체결이 예약 없이 기장된다.
- 체결 통보가 접수 응답보다 먼저 오면, 주문을 못 찾아 외부 체결로 잘못 기장한다.
- 재접속 때 다시 오는 과거 체결을 새 체결로 기장한다.

## 2. 일반적으로 만족해야 하는 성질

- 상태는 가진 증거를 말한다. 증거가 없는 것을 단정하지 않는다.
- 포지션은 체결로만 움직이고 체결은 한 번만 기장된다.
- 예약은 "아직 기장되지 않은 체결의 최대량"을 항상 덮는다.
- 통보 순서가 바뀌어도 최종 상태가 같다.

## 3. 제약

Hyperliquid의 주문 상태 통보에서 잔량 필드(`sz`)의 의미가 문서 안에서 엇갈린다(잔량인지 체결량인지).
체결 통보에 cloid가 있는지 문서 타입에는 없다. 체결 키 `tid`는 전역 유일이 아니며 문서가 `(block_time, coin, tid)`를 권한다.

## 4. 필수 조건과 선택 조건

필수: 체결 중복 기장 없음. 종결 뒤 예약 0은 "더 올 체결이 없다"는 근거가 있을 때만. 결과 불명 중 예약 유지.
선택: 거래소가 최종 누적 수량을 알려 주면 그만큼 빨리 닫는다.

## 5. 대안

| 대안 | 설명 |
|---|---|
| A. 누적 보고 방식 (기존 Go 구현, 가장 단순) | 거래소의 "누적 체결량" 보고를 그대로 주문에 덮어쓴다. 체결 건별 식별 없음 |
| B. FIX 식 단일 상태 필드 | `New/PartiallyFilled/Filled/Canceled/PendingCancel/...` 한 필드 |
| C. 증거 단계 + 체결 건별 기장 | 단계(phase)는 증거 수준, 포지션은 체결 키별 기장, 취소·불명은 별도 축 |

## 6. 비교

| 기준 | A | B | C |
|---|---|---|---|
| 체결 건별 수수료·가격 | 평균만 | 가능 | 가능 |
| 중복·역순 통보 | 누적값은 단조 증가만 허용하면 견딘다 | 상태 전이표가 조합마다 필요 | 체결 키와 단조 규칙으로 견딘다 |
| 누적 수량 필드가 신뢰할 수 없을 때 | 성립하지 않는다 | 영향 받음 | 체결 동기화 시점으로 대신 닫는다 |
| 취소 중 체결 | 최종 조회에 의존 | `PendingCancel` 등 상태 증가 | 취소는 별도 축이라 단계와 독립 |
| 복잡성 | 낮음 | 전이표가 크다 | 중간 |

이 표의 값은 모두 정성 판단이다. 측정값은 없다.

## 7. 선택과 이유

C. 네 개의 축으로 나눈다(`crates/oms-core/src/model.rs`).

| 축 | 값 | 의미 |
|---|---|---|
| 단계 `phase` | `PendingSend` | 내구화되고 게이트웨이로 풀렸다. 거래소 증거 없음 |
| | `Working` | 거래소가 주문을 가졌다는 증거가 있다(응답, 스트림, 조회, 체결 중 어느 것이든) |
| | `Closing` | 거래소가 종결을 알렸지만 기장된 체결이 최종 누적에 못 미친다 |
| | `Closed` | 더 올 효과가 없다. 예약 0 |
| 결과 불명 `doubt` | 없음 / 사유 | `PendingSend`에만 붙는다([ADR-005](ADR-005-unknown-outcome.md)) |
| 취소 `cancel` | 없음 / 요청·시도·확인 | 단계와 독립. 취소 요청은 예약을 풀지 않는다 |
| 증거 신선도 `evidence_session` | 링크 세션 번호 | 재접속 뒤 다시 확인됐는지 |

부분 체결은 단계가 아니다. `Working`이면서 `cum_qty > 0`인 것이다.

### 예약 규칙

```text
PendingSend, Working:  reserved = qty − cum_qty
Closing:               reserved = max(final_cum − cum_qty, 0)   최종 누적을 알 때
                       reserved = qty − cum_qty                 모를 때
Closed:                reserved = 0
```

### 종결 규칙

거래소의 종결 통보는 `VenueTerminal` 이벤트가 되어 단계를 `Closing`으로 바꾼다. `Closed`로 가는 조건은 둘 중 하나다.

1. 최종 누적 수량을 알고, 기장된 체결의 합이 그와 같다.
2. 최종 누적 수량을 모르고, 체결 동기화 시점(`fills_up_to`)이 종결의 거래소 시각 이상이다.
   즉 "그 시각까지의 체결은 모두 받았다"는 게이트웨이의 확인이 있다.

체결의 합이 주문 수량에 도달하면 종결 통보 없이도 닫는다(더 체결될 것이 없다).
최종 누적보다 체결이 부족한 채로 동기화 시점이 지나면 MissingFills 불일치를 제기하고 예약을 유지한다.

Hyperliquid 게이트웨이는 `sz`의 의미가 확인될 때까지 최종 누적을 알려 주지 않는다(규칙 2 사용).

### 체결 식별

- 포지션과 예약은 `FillBooked`로만 움직인다. 주문 상태 통보의 누적값은 `reported_cum`에 기록만 하고 기장하지 않는다.
  `reported_cum > cum_qty`이면 대조기가 체결을 다시 가져온다.
- 체결 키는 전역 집합 `seen_fills`에 거래소 시각과 함께 둔다. 주문이 메모리에서 제거된 뒤에도 재전달을 걸러 내기 위해서다.
- `fill_floor`: 이 시각보다 오래된 체결 통보는 재전달로 보고 무시한다. 바닥은 `fills_up_to − 24시간`으로만 올라간다.
  동기화가 확인된 구간만 잊는다. 첫 부팅 때는 `부팅 시각 − 여유`로 둔다. 새 인스턴스가 계좌의 과거 체결을 떠안지 않기 위해서다.
- 주문을 찾을 수 없는 체결: 거래소 주문 ID만 있고, 아직 그 ID를 모르는 우리 주문이 있으면 대기 목록에 둔다(`FillParked`).
  ID를 알게 되면 기장한다. 주인이 될 수 있는 주문이 없어지거나 120초가 지나면 외부 체결로 기장하고 불일치를 제기한다.
- 주문 수량을 넘는 체결, 종결 뒤의 체결도 **기장한다**. 실제 일어난 일을 자르지 않는다. 불일치를 제기해 신규 주문을 막는다.

## 8. 포기한 장점, 남은 위험, 가정

- 규칙 2는 가정 A-03(동기화 확인의 완전성)에 기댄다. 깨지면 주문이 먼저 닫히고 체결이 뒤에 온다. FillAfterClose 불일치로 탐지된다.
- 24시간보다 오래 끊겼다가 돌아오면 그 사이의 체결 재전달은 바닥 아래가 아니다(바닥은 동기화 시점 기준). 다만 Hyperliquid는 최근 10000건만 조회할 수 있어 그보다 많은 체결이 끊긴 동안 생기면 API로 복원할 수 없다. 포지션 대조가 차이를 드러낸다.
- 체결 정정(bust)은 모델에 없다. 문서에도 없다. 일어나면 포지션 대조에서 범위 이탈로 나타난다.

## 9. 근거

- 시나리오 시험: 체결과 접수 응답의 순서 역전, 중복 체결, 종결이 체결보다 먼저, 최종 누적을 모를 때의 종결, 초과 체결, 대기 체결 등 15건.
- 시뮬레이션이 찾아낸 결함 넷이 이 설계에 반영됐다. (1) 동기화 시점이 조회 시각과 같으면 같은 시각의 체결을 놓친다 → 시점을 하나 앞으로.
  (2) 주문 제거 뒤 재전달된 체결을 외부 체결로 이중 기장 → 전역 체결 집합과 바닥. (3) 대기 체결을 5초 만에 외부로 처리 → 주인 후보가 있는 동안 대기.
  (4) 종결 통보 없이 사라진 주문을 영원히 열린 것으로 본다 → 열린 주문 목록에 없는 주문을 다시 조회.
- 간격 검토가 찾아낸 결함도 반영됐다: 다른 체결이 거래소 주문 ID를 알려 줬을 때 대기 체결을 꺼내지 않던 것, 닫은 주문의 존재 증거를 버리던 것,
  옛 세션의 통보가 접수 증거일 때 현재 세션의 증거로 세던 것, 한 거래소 주문 ID가 두 주문에 붙는 통보에서 색인이 깨지던 것([gap-review](../verification/gap-review.md)).
- `weak_evidence` 프로파일(최종 누적 없음, 체결에 cloid 없음) 통과(주장 V-SIM-1, V-SIM-4).

## 10. 재검토 조건

testnet에서 `sz`의 의미와 체결 통보의 cloid 유무를 확인했을 때(최종 누적 사용, 대기 목록 단순화).
거래소가 체결 정정을 도입할 때.
