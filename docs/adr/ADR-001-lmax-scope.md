# ADR-001 LMAX 원칙의 채택 범위와 단순화

상태: 채택. 기준일 2026-10-02.

LMAX는 외환 거래소 LMAX가 공개한 아키텍처다. 핵심은 "업무 로직을 메모리에서 단일 스레드로 실행하고,
입력을 먼저 기록해 재생으로 복구한다"는 것이다. Disruptor는 그 구조에서 스레드 사이에 데이터를 넘기는 데 쓴 ring buffer다.

## 1. 문제와 발생 가능한 실패

주문 상태·예약·포지션을 여러 스레드가 나눠 쓰면 두 가지가 어려워진다.
검사와 예약을 원자적으로 묶기(두 전략이 같은 한도 여유를 쓰는 실패), 그리고 장애 뒤에 "무엇이 일어났는가"를 한 순서로 설명하기.

## 2. 이 종류의 설계가 일반적으로 만족해야 하는 성질

- 상태 전이의 전체 순서가 하나 존재하고 기록된다.
- 기록에서 상태를 다시 만들 수 있다.
- 외부 효과는 기록에 근거해서만 일어난다.
- 느린 I/O가 판단 경로를 막지 않거나, 막는 시간이 상한 안에 있다.

## 3. 이번 프로젝트의 제약과 우선순위

단일 노드, 단일 운영자, 초~수백 ms 단위 전략. 거래소 요청 상한은 초당 약 20건이다.
우선순위는 정합성 > 복구 가능성 > 이해 가능성 > 지연이다.

## 4. 필수 조건과 선택 조건

필수: 검사와 예약의 원자성, 재생으로 같은 상태 복원, 기록보다 앞선 외부 효과 없음, 큐·메모리 상한.
선택: 마이크로초 단위 지연, 코어 수에 따른 확장.

## 5. 대안

| 대안 | 설명 |
|---|---|
| A. 공유 상태 + 잠금 | 주문 맵과 한도 카운터를 `Mutex`로 보호하고 요청마다 태스크가 처리한다. 가장 흔한 구조 |
| B. DB 트랜잭션 중심 | 주문과 예약을 관계형 DB의 트랜잭션으로 처리한다. 가장 단순해 보이는 구조 |
| C. LMAX 방식 단일 writer + 저널 | 한 스레드가 상태를 소유하고, 사실을 저널에 기록한다 |

## 6. 비교

| 기준 | A. 잠금 | B. DB | C. 단일 writer |
|---|---|---|---|
| 검사·예약 원자성 | 잠금 범위를 모든 경로에서 맞게 잡아야 한다 | 트랜잭션 격리가 보장한다 | 구조상 성립한다(한 스레드, 한 입력) |
| 전체 순서의 설명 | 잠금 획득 순서에 의존. 재현이 어렵다 | 커밋 순서. 재현 가능 | 저널 순번. 재현 가능 |
| 결정적 재현 시험 | 어렵다(스케줄링에 의존) | DB를 포함한 통합 시험 | 코어만으로 가능 |
| 복구 | 별도 기록이 필요하다 | DB 복구에 맡긴다 | 저널 재생 |
| 지연 | 잠금 경합에 따라 변동 | 요청마다 DB 왕복 | 요청마다 fdatasync 1회(배치 공유) |
| 운영 부담 | 낮음 | DB 운영이 추가된다 | 저널 파일 관리 |
| 개발 비용 | 낮음, 정확성 검증 비용은 높음 | 중간 | 중간. 코어의 순수성 유지에 규율이 든다 |

지연과 운영 부담 평가는 정성 판단이다. C의 지연은 측정했다([성능](../performance/README.md)).

## 7. 선택과 이유

C를 채택한다. 필수 조건 네 가지가 규율이 아니라 구조에서 나온다.
원자성은 "한 입력을 한 스레드가 끝까지 처리한다"에서, 재현은 "코어에 I/O가 없다"에서 나온다.
B도 필수 조건을 만족하지만 결정적 시뮬레이션(장애·순서 조합을 seed로 재현)을 DB 없이 돌릴 수 없다.
이 프로젝트의 검증은 그 시뮬레이션에 크게 기댄다.

## 8. LMAX에서 따르는 것과 단순화한 것

원문 근거는 [research/lmax-durability-rust.md](../research/lmax-durability-rust.md) Part 1이다.

| LMAX 원칙 | 원문 | 이 프로젝트 | 달라지는 보장 |
|---|---|---|---|
| 업무 로직은 단일 스레드, 메모리 내 | Fowler: Business Logic Processor | 따른다. `oms-core`가 한 스레드에서 실행된다 | 없음 |
| 로직은 외부를 직접 호출하지 않는다. 호출은 출력 이벤트, 결과는 입력 이벤트 | Fowler | 따른다. 전송은 명령으로 나가고 결과는 입력으로 돌아온다 | 없음 |
| 변경 전에 완전히 검증한다. 롤백 없음 | Fowler: "fully valid before doing any mutation" | 따른다. 판단이 실패하면 프로세스를 멈춘다 | 없음 |
| 입력을 저널에 기록한 뒤 로직이 처리한다 | Fowler: 저널·복제·역직렬화가 끝난 뒤 로직 | **다르다.** 로직이 먼저 결정하고, 입력과 결정된 이벤트를 함께 기록한 뒤에야 출력을 내보낸다([ADR-003](ADR-003-journal-record.md), [ADR-004](ADR-004-commit-gate.md)) | 코어의 메모리 상태가 저널보다 앞설 수 있다. 외부에서 보이는 것은 같다 |
| 복구는 입력 재생 | Fowler | **다르다.** 기록된 이벤트를 적용한다. 판단을 다시 하지 않는다 | 판단 로직을 바꿔도 과거 기록의 재생 결과가 바뀌지 않는다 |
| 출력은 재생 시 무시 | 원문은 "비선두 노드의 출력은 무시"만 말한다. 재전송 억제는 다루지 않는다 | 재생 경로는 명령을 만들 수 없게 했다. 미확정 전송은 별도 정책([ADR-005](ADR-005-unknown-outcome.md)) | 원문에 없는 부분을 직접 설계했다 |
| 복제 노드와 자동 승격 | Fowler: 세 노드가 같은 입력을 처리 | **없다** | 서버가 죽으면 수동 복구. 대기 노드 없음 |
| 야간 스냅샷 | Fowler | 기록 수 기준 주기 + 종료 시 | 없음 |
| Disruptor(ring buffer, busy-spin) | Disruptor 논문 | **쓰지 않는다.** `Mutex`+`Condvar` 큐와 표준 채널 | 스레드 간 전달 지연이 마이크로초 단위로 커진다. 요구 범위에서 의미 없음 |
| 사전 할당, GC 회피 | 원문은 Java 맥락 | 해당 없음. 기록당 할당은 있다 | 측정상 fdatasync에 가려진다 |

LMAX의 "초당 600만 주문"은 2011년 하드웨어의 Java 단일 스레드 로직 처리량이고 I/O를 포함하지 않는다.
이 프로젝트는 그 수치를 목표로 하지 않으며 달성했다고 주장하지 않는다.
Disruptor나 lock-free 구조를 쓰지 않으므로 그 성능 특성도 주장하지 않는다.

## 9. 포기한 장점, 남은 위험, 가정

- 포기: 무중단 승격, 코어 수에 따른 처리량 확장.
- 위험: 코어 스레드의 한 입력이 오래 걸리면 모든 입력이 기다린다. 신규 주문 판단은 열린 주문 수에 비례한다(측정: 500개일 때 중앙값 22 µs).
- 가정: 계좌 하나의 전체 주문 흐름이 한 스레드로 충분하다. 거래소 한도가 이를 뒷받침한다.

## 10. 근거와 재검토 조건

근거: LMAX 원문 조사, 코어 처리 시간 측정(`cargo run -p xtask -- core-bench`), 시뮬레이션과 프로세스 시험.

재검토: 계좌가 여럿이 되어 한 스레드의 처리량이 부족할 때(계좌별 코어로 분할 검토),
자동 승격이 요구될 때(복제와 전송 차단 설계가 필요), 열린 주문이 수천 개로 늘어 판단 시간이 지연 기준을 넘을 때.
