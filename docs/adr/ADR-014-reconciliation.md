# ADR-014 거래소 상태 대조

상태: 채택. 동작 계약은 [reconciliation](../contracts/reconciliation.md).

대조(reconciliation)는 OMS가 아는 것과 거래소의 실제가 같은지 확인하고, 모르는 것을 채우는 일이다.

## 1. 문제와 발생 가능한 실패

- 스트림이 끊긴 동안의 체결·취소를 모른다.
- 거래소 스냅샷과 로컬 상태를 그대로 비교하면, 스냅샷을 뜬 뒤 도착한 체결 때문에 거짓 불일치가 난다.
- 불일치를 발견하고 로컬 상태를 거래소 값으로 덮어쓰면, 왜 달랐는지가 사라지고 전략별 귀속이 깨진다.
- 대조 로직이 스스로 상태를 가지면, 재시작 때 "어디까지 확인했는가"가 또 하나의 복구 대상이 된다.

## 2. 일반적으로 만족해야 하는 성질

- 대조는 몇 번을 반복해도 결과가 같다.
- 스냅샷의 시점과 로컬 처리 시점의 차이를 고려한다.
- 차이는 기록되고, 소유자가 명시적으로 조정한다.
- 대조가 끝나기 전에는 새 위험을 받지 않는다.

## 3. 제약

Hyperliquid: 스트림에 순번이 없다. `orderUpdates`는 재구독 스냅샷이 문서에 없다. 체결은 재구독 스냅샷과 REST 조회로 메운다.
조회에도 IP 한도가 적용된다(`orderStatus` weight 2, 그 외 20 이상).

## 4. 필수 조건과 선택 조건

필수: 재접속·재시작 뒤 모든 미종결 주문의 상태를 다시 확인한다. 체결을 빠짐없이 한 번씩 기장한다. 외부 활동을 탐지한다. 거짓 불일치로 거래를 막지 않는다.
선택: 대조 시간 최소화, 조회 비용 최소화.

## 5. 대안

| 대안 | 설명 |
|---|---|
| A. 스냅샷 덮어쓰기 (가장 단순) | 열린 주문과 포지션 스냅샷으로 로컬 상태를 교체 |
| B. 코어가 대조 절차를 상태 기계로 진행 | 조회 발행·재시도·시간 초과를 코어 상태와 저널에 둔다 |
| C. 코어는 "필요한 증거"만 말하고, 무상태 대조기가 가져온다 | 답은 일반 입력으로 들어와 멱등하게 적용된다 |

## 6. 비교

| 기준 | A | B | C |
|---|---|---|---|
| 차이의 감사 가능성 | 없음 | 있음 | 있음 |
| 전략별 귀속 보존 | 깨진다 | 보존 | 보존 |
| 재시작 뒤 대조 상태 | 없음 | 저널에서 복구해야 한다 | 복구할 것이 없다 |
| 저널 잡음 | — | 조회마다 기록 | 상태가 바뀔 때만 기록 |
| 조회의 반복 안전성 | — | 상태 기계가 보장해야 한다 | 구조상 안전(읽기 전용 조회 + 멱등 입력) |

이 표의 값은 모두 정성 판단이다. 측정값은 없다.

## 7. 선택과 이유

C.

### 구성

- `Core::needs()`(`crates/oms-core/src/needs.rs`): 상태에서 계산하는 순수 함수. "어떤 주문의 상태", "어느 시각 이후의 체결", "열린 주문 목록", "포지션"이 필요한지 말한다.
- 대조기(`crates/oms-node/src/venue/reconciler.rs`): 읽기 모델에서 `needs()`를 읽어 게이트웨이에 조회를 넘긴다. 주문별 조회는 0.5초→1초→2초→5초로 간격을 벌린다.
  15초(설정)마다 필요 여부와 무관하게 체결·열린 주문·포지션을 훑는다.
- 답은 `Venue(...)` 입력으로 코어에 들어간다. 코어는 통보와 조회 결과를 같은 규칙으로 적용한다.

거래소에 **쓰는** 동작(주문, 취소)은 대조기가 하지 않는다. 그것은 코어의 이벤트에서 파생된 명령으로만 나간다.

### 링크 세션과 재확인

게이트웨이는 스트림이 붙을 때마다 더 큰 세션 번호로 `Link up`을 알린다. 코어는 다음이 모두 현재 세션에서 확인될 때까지 `Resync` 차단을 건다.

1. 모든 `Working` 주문에 현재 세션의 상태 증거가 있다.
2. 체결 동기화가 현재 세션에서 한 번 완료됐다.
3. 열린 주문 훑기가 현재 세션에서 한 번 완료됐다.
4. 포지션 검사가 현재 세션에서 한 번 통과했다.

이전 세션에서 모은 답이 늦게 도착하면 내용은 적용하되(사실이므로) 신선한 증거로 세지 않는다.

### 스냅샷 시점 문제의 처리

| 대조 | 규칙 | 시점 차이를 견디는 이유 |
|---|---|---|
| 주문별 상태 | 누적량은 증가만, 종결은 최종 | 정보가 단조롭다. 늦게 와도 틀리지 않는다 |
| 체결 | 체결 키로 중복 제거, 바닥 시각 이전은 무시 | 겹쳐 가져와도 한 번만 기장된다 |
| 열린 주문 | 거래소에 있는데 로컬은 종결: 종결 시각이 조회 발신 시각보다 앞일 때만 불일치. 로컬은 `Working`인데 목록에 없음: 접수 시각이 조회 발신보다 앞이면 그 주문의 상태 조회를 요구 | 조회 발신 시각을 기준으로 앞뒤를 가른다 |
| 포지션 | 거래소 포지션 ∈ `[q − S, q + B]`. 조회 발신 뒤에 체결을 기장했으면 판정을 미룬다 | 아직 기장하지 않은 체결은 예약이 덮는다. 스냅샷보다 로컬이 앞선 경우는 건너뛴다 |

포지션 검사는 I-BRIDGE 그 자체다. 같음을 요구하지 않고 "예약으로 설명되는 범위"를 요구한다.
열린 주문이 없을 때는 구간이 한 점이 되어 같음 검사와 같아진다.

### 불일치

발견한 차이는 `MismatchRaised` 이벤트가 된다. 같은 종류·같은 대상의 미확인 불일치가 있으면 다시 제기하지 않는다.
미확인 불일치가 하나라도 있으면 신규 주문이 차단된다. 운영자가 건별로 확인(`ack`)한다. 하나를 확인해도 다른 것은 남는다.
포지션을 맞춰야 하면 `adjust` 명령으로 명시적 조정 이벤트를 남긴다. 코어가 스스로 거래소 값으로 덮어쓰는 경로는 없다.

| 종류 | 뜻 |
|---|---|
| `ExternalFill`, `ForeignOrder`, `ForeignPosition` | 이 인스턴스가 내지 않은 활동 |
| `OrphanOrder` | 이 인스턴스의 ID를 가졌지만 모르는 주문. 저널 유실이나 부재 판정 가정의 붕괴를 뜻한다 |
| `PositionOutOfRange` | 포지션이 설명 범위 밖 |
| `Overfill`, `FillAfterClose`, `CumExceedsFinal`, `MissingFills` | 체결과 주문 상태의 모순 |
| `OpenAfterClose`, `StatusConflict`, `FillFieldConflict` | 통보끼리의 모순 |
| `CancelStuck`, `ParkedFillOverflow` | 진행이 막힘 |

## 8. 포기한 장점, 남은 위험, 가정

- 재접속마다 신규 주문이 대조가 끝날 때까지 막힌다. 조회 왕복 몇 번의 시간이다.
- 체결이 끊임없이 기장되면 포지션 검사가 계속 미뤄질 수 있다. 대조기는 1초 간격으로 다시 시도한다.
- 외부 주문이 있으면 그 잠재 체결은 예약에 없다. 탐지(`ForeignOrder`)는 하지만 그 주문이 체결되기 전에 막지는 못한다.
- 미확인 불일치를 운영자가 확인하면, 원인이 남아 있는 한 다음 훑기에서 다시 제기된다.
- 조회 비용: 열린 주문 n개의 재확인은 `orderStatus` n회(weight 2n)다. 500개면 weight 1000으로 분당 한도의 대부분이다.
  Hyperliquid 게이트웨이는 열린 주문 목록 한 번으로 여러 주문의 증거를 갱신한다([ADR-017](ADR-017-hyperliquid-gateway.md)).

## 9. 근거

- 시나리오 11건(`link_loss_blocks…`, `stale_session_evidence…`, `position_check_uses_the_reachable_range`,
  `a_position_snapshot_older_than_the_last_booked_fill_is_inconclusive`, `foreign_and_orphan_open_orders_are_flagged` 등).
- 시뮬레이션: 조회 유실 10%, 링크 단절, 재시작을 섞어도 최종 상태가 거래소와 일치하고 거짓 불일치가 0건이다. `external` 프로파일은 외부 체결을 모두 탐지한다.
- 프로세스: `events_missed_while_down_are_recovered_from_the_venue`, `link_loss_holds_new_orders_until_resynchronised`,
  `external_activity_is_detected_and_needs_an_operator`.

## 10. 재검토 조건

수동 거래와 병행 운용이 요구될 때(U-08). 조회 한도가 대조를 방해하는 것이 관측될 때.
