# ADR-008 리스크: 잠재 체결을 포함한 수량 구간 예약

상태: 채택(수량 한도). 금액·증거금 기반 한도는 사용자 결정 U-02로 남는다.

## 1. 문제와 발생 가능한 실패

- 두 전략이 같은 잔여 한도를 각자 읽고 각자 주문한다. 둘 다 체결되면 한도를 넘는다.
- 반대 방향 미체결 주문을 상계해 여유를 계산한다. 한쪽만 체결되면 한도를 넘는다.
- 취소를 요청한 순간 예약을 푼다. 취소 전에 체결되고, 풀린 여유로 낸 새 주문도 체결된다.
- 지연될 수 있는 조회용 포지션으로 검사한다. 방금 체결된 것이 빠져 있다.

## 2. 일반적으로 만족해야 하는 성질

수용된 주문들의 어떤 체결 순서·부분 체결 조합에서도 한도를 넘지 않는다.
검사와 예약이 하나의 전이다. 검사에 쓰는 상태가 권위 있는 상태다.

## 3. 제약과 기존 결정

기존 요구 문서(`../docs/architecture/FIA-OMS-model.md`(상위 디렉터리) R01, R02, `../docs/research/oms-three-guarantees.md`(상위 디렉터리) §2)가
수량 구간 모델과 그 논증을 정해 두었다. 이 ADR은 그것을 구현 수준으로 옮긴다.
계좌 증거금 계산(D1)과 긴급 시장가 수치(D2)는 그 문서에서 미결이며 여기서도 미결이다.

## 4. 필수 조건과 선택 조건

필수: I-QTY(계좌와 전략 모두). 원자적 검사·예약. 권위 있는 상태로 판단.
선택: 자본 효율(상계 인정), 금액 한도.

## 5. 대안

| 대안 | 설명 |
|---|---|
| A. 주문당 한도만 (기존 Go 구현, 가장 단순) | 주문 한 건의 최대 수량·금액만 검사 |
| B. 순포지션 + 순미체결 | 포지션과 미체결의 순액을 한도와 비교 |
| C. 구간 예약 | 매수 가능량 `B`와 매도 가능량 `S`를 따로 누적해 `[q − S, q + B]`가 한도 안에 있게 한다 |

## 6. 비교

| 기준 | A | B | C |
|---|---|---|---|
| 여러 주문의 누적 노출 | 통제하지 않는다 | 통제 | 통제 |
| 한쪽만 체결되는 경우 | — | 넘을 수 있다(반례: 매수4·매도4 열림, 매수4 추가 → +8) | 넘지 않는다 |
| 자본 효율 | — | 높음 | 낮음. 양방향 호가를 내는 전략은 양쪽 모두 예약된다 |
| 계산 비용 | 상수 | 상수 | 상수(장부에 누적값 유지) |

이 표의 값은 정성 판단이다. 판단 시간이 열린 주문 수에 비례한다는 점만 측정했다(`core-bench`, §8).

## 7. 선택과 이유

C. 구현은 `check_new_order`(`crates/oms-core/src/decide.rs`)와 `Book`(`model.rs`)이다.

검사 항목(모두 한 입력 안에서, 코어의 자기 상태로):

| 검사 | 기준 | 요구 |
|---|---|---|
| 전략·종목이 설정에 있고 허용됨 | `StrategySpec.limits` | R01 |
| 수량: 양수, 단위의 배수, 주문당 최대 이하 | `InstrumentSpec` | R01 |
| 가격: 양수, tick의 배수, 유효숫자 규칙 | `InstrumentSpec` | R01, 거래소 규칙 |
| 주문 금액: 최소 이상, 주문당 최대 이하 | 올림한 `가격 × 수량` | R01 |
| 가격대: 참조 가격 대비 공격적 방향으로 n bp 이내 | 신선한 참조 가격 필요 | R03 |
| 계좌 포지션 구간 | `q + B + n ≤ U` 또는 `q − S − n ≥ L` | R02 |
| 전략 포지션 구간 | 같은 식, 전략 장부와 전략 한도 | R02 |
| 열린 주문 수(계좌, 전략), 진행 중 전송 수, 메모리의 주문 수 | `Policy` | 자원 상한 |
| 차단 사유 없음 | `Core::holds` | R06, R07 |
| 만료 시각이 미래이고 한도 이내 | `Policy.max_expiry_horizon_us` | [ADR-006](ADR-006-idempotency.md) |

통과하면 같은 입력 안에서 `OrderAccepted`가 적용되어 `B` 또는 `S`가 늘어난다. 검사와 예약 사이에 다른 입력이 끼어들 수 없다.

차단 사유(`HoldReason`)는 상태에서 매번 계산한다. 저장하지 않으므로 잊히거나 잘못 풀리지 않는다.
여러 사유가 동시에 성립하고, 하나를 풀어도 다른 것은 남는다.

| 사유 | 조건 | 해제 |
|---|---|---|
| `NoConfig` | 설정이 활성화되지 않음 | 설정 활성화 |
| `LinkDown` | 거래소 스트림 끊김 | 재접속 |
| `Resync` | 재접속 뒤 대조 미완 | 주문별 증거 갱신 + 체결·열린 주문·포지션 대조 |
| `InDoubt` | 결과 불명 주문이 있음 | 모든 불명 해소 |
| `Mismatch` | 확인되지 않은 불일치가 있음 | 운영자가 건별로 확인 |
| `OperatorAccount` / `OperatorStrategy` | 운영자 중지 | 운영자 재개(범위별로 따로) |
| `StorageLow` | 저널 저장 공간 부족 | 공간 확보 |

차단은 신규 주문만 막는다. 취소, 체결 기장, 대조는 계속된다. 차단 사유는 두 종류다([ADR-018](ADR-018-margin-rules.md) §7의 개정).

| 모든 신규 주문을 막는다 | 일반 주문만 막는다(감소 전용 주문은 통과) |
|---|---|
| `NoConfig`, `LinkDown`, `OperatorAccount`, `OperatorStrategy`, `StorageLow` | `Resync`, `InDoubt`, `Mismatch`, `Reducing`, `VenueSetting(종목)`, `AccountMode` |

오른쪽 열의 구분은 증거금 정책(`policy.margin`)이 설정됐을 때만 적용한다. 정책이 없으면 모든 차단이 감소 전용 주문을 포함한 모든 신규 주문을 막는다(개정 전과 같다). 그래서 정책 없이 기록된 저널은 다시 판단해도(`verify --re-decide`) 기록된 결과와 같다.

감소 전용 주문의 기준은 거래소의 reduce-only 표시다. OMS가 계산한 '줄이는 방향'이 아니다. 거래소가 계좌 포지션으로 판정하므로 기존 결정 O08의 우려(전략에서 축소인 주문이 계좌에서는 아닐 수 있다)가 이 표시에는 해당하지 않는다. 감소 전용 주문도 §7의 다른 검사는 모두 받는다.

`Reducing`은 증거금 규칙의 티켓 04가, `VenueSetting(종목)`, `AccountMode`는 티켓 08이 추가했고 모두 위 표의 오른쪽 열에 있다. 표는 `HoldReason::refuses_only_plain_orders`(`model.rs`)에 있다.

한도를 현재 노출 아래로 낮추는 설정 변경은 허용한다. 기존 노출은 남고 새 주문만 새 한도로 검사된다. 그 동안 I-QTY는 성립하지 않는다.

## 8. 포기한 장점, 남은 위험, 가정

- 금액·증거금을 검사하지 않는다. 수량 한도 안에서도 가격 변동으로 증거금이 부족해질 수 있다. 거래소가 주문을 거부하거나 취소한다(`marginCanceled`).
- 비용 예산(수수료 상한), 자동 실행 반복 제한(R08), 자전거래 정책(R10)은 구현하지 않았다. 검토 항목 대응표에 미구현으로 남긴다.
- 가정 A-04: 계좌에 이 OMS 밖의 주문이 없다.
- 신규 주문 판단은 차단 사유 계산 때문에 열린 주문 수에 비례한다. 측정: 열린 주문 약 500개에서 중앙값 22 µs, p99 29 µs.
  열린 주문이 수천 개가 되면 수백 µs가 된다(성능 실험에서 진행 중 전송 4096건일 때 p99 831 µs를 관측).
  기본 상한(열린 주문 500, 진행 중 전송 64) 안에서는 지연 기준을 만족하므로 최적화하지 않는다.

## 9. 근거

- 시나리오: FIA 문서 §7.1의 실행 예를 그대로 재현한 `fia_7_1_reservation_follows_potential_fills`와 반례 세 건.
- 시뮬레이션: 매 단계 `check_position_bounds`와 I-BRIDGE 검사.
- 기존 문서의 산술 열거(초기 상태 112개, 체결 prefix 1,582개)는 모델 수준의 확인이며 이 구현의 시험이 아니다.

## 10. 재검토 조건

U-02가 결정되어 증거금 입력과 금액 예약을 추가할 때. 양방향 호가 전략의 자본 효율이 문제가 될 때(공동 시나리오 계산 필요).
열린 주문 상한을 1000 이상으로 올릴 때(차단 사유 계산을 카운터로 바꾼다).
