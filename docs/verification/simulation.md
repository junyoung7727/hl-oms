# 결정적 시뮬레이션

구현: `crates/oms-sim/src/world.rs`(세계와 검사), `venue.rs`(가상 거래소), `rng.rs`(난수). 시험: `crates/oms-sim/tests/sim.rs`.

## 무엇이 실제이고 무엇이 모델인가

| 부분 | 실제 / 모델 | 설명 |
|---|---|---|
| 코어의 판단과 상태 | **실제** | `oms_core::Core` 그대로 |
| 저널 | 모델 | 기록의 벡터와 "여기까지 내구" 표시. 실제 파일이 아니다 |
| 커밋 관문 | 모델 | 기록이 내구화된 뒤에만 응답과 전송 명령을 내보낸다. 실제 스레드가 아니다 |
| 게이트웨이와 네트워크 | 모델 | 요청 유실, 응답 유실, 지연, 통보 중복·지연, 조회 유실, 링크 단절 |
| 거래소 | 모델 | 시험이 지시한 대로 체결·취소한다. 매칭하지 않는다. 만료 시각이 지난 요청을 거부한다 |
| 거래소의 증거금 | 모델 | 계좌 가치 = 현금 + 포지션 × 기준 가격. 체결 대금과 수수료, 펀딩이 현금에서 나간다. 보고의 포지션 증거금은 가치 ÷ 레버리지다. 감소 전용 주문은 포지션을 키우지 못한다. 우리 모형이고 거래소의 산술이 아니다. 청산은 없다 |
| 시계 | 모델 | 가상 시계 하나. 거래소 시계와의 차이를 설정할 수 있다 |
| 전략 | 모델 | 주문, 같은 요청의 반복, 다른 내용으로 같은 키 재사용, 취소(남의 주문 포함) |
| 프로세스 재시작 | 모델 | 내구화되지 않은 기록과 진행 중이던 모든 메시지를 버리고 저널에서 코어를 다시 만든다 |

실제 저널·스레드·소켓·프로세스는 `oms-node`의 프로세스 시험이 다룬다. 시뮬레이션이 통과했다는 것은 **코어의 논리**에 대한 근거이고, 실행 계층에 대한 근거가 아니다.

## 재현

한 실행은 seed 하나와 프로파일 하나로 정해진다. 난수 생성기는 SplitMix64 하나뿐이고 시각은 가상 시계에서만 온다.

```sh
OMS_SIM_SEEDS=400 cargo test --release -p oms-sim --test sim          # 프로파일마다 seed 400개
OMS_SIM_SEED=1234 OMS_SIM_PROFILE=crashy cargo test --release -p oms-sim --test sim profile_crashy -- --nocapture
OMS_SIM_DUMP=1 …                                                       # 위반이 나면 저널을 덤프한다
```

`a_seed_reproduces_the_same_run`은 같은 seed가 같은 저널과 같은 상태 다이제스트를 만드는지 확인한다.

## 장애 프로파일

한 실행은 1500단계다. 각 단계에서 확률(천분율)에 따라 동작과 장애가 일어난다.

| 프로파일 | 추가되는 것 |
|---|---|
| `calm` | 장애 없음. 주문, 취소, 체결, 거래소 주도 취소, 시간 경과만 |
| `lossy` | 요청 반복(8%), 보내지 못함(3%), 요청 유실(4%), 요청 지연(6%), 응답 유실(8%), 통보 중복(15%), 통보 지연(20%), 조회 유실(10%), 링크 단절, 운영자 중지·재개 |
| `crashy` | `lossy` + 임의 시점의 프로세스 재시작. 커밋이 덜 자주 일어나 내구화 전 기록이 더 많이 사라진다 |
| `weak_evidence` | `crashy` + 거래소가 누적 체결량을 알려 주지 않고, 체결에 클라이언트 ID가 없다(코어가 다뤄야 하는 가장 약한 증거) |
| `purge` | `crashy` + 종결 주문 보존 1초, 요청 반복 20%. 실행 중에 키가 잊히고 늦은 반복은 만료로 거절돼야 한다 |
| `skewed` | `crashy` + 거래소 시계가 로컬보다 1초 늦다(여유 안쪽) |
| `external` | `lossy` + OMS가 내지 않은 체결이 계좌에 생긴다 |
| `margin_calm` | `calm` + 증거금 정책(C-MARGIN). 계좌는 100으로 시작한다. 전략은 기준 가격 근처로 주문하고 15%에 감소 전용 표시를 단다. 기준 가격이 한 틱씩 움직이고, 펀딩이 붙고, 운영자가 가끔 감소 전용 상태를 해제한다. UTC 자정 12초 전에 시작해 자정을 한 번 넘는다 |
| `margin_lossy` | `margin_calm` + `lossy`의 네트워크 장애, 링크 단절, 프로세스 재시작. 거래소가 증거금 조회에 0.5~2.5초 동안 답하지 않거나 늦게 답하고(뒤 조회의 답이 앞지른다), 가끔 포지션의 증거금을 0으로 말한다(유지증거금 여유가 걸린다). 주문이 `lossy`보다 오래 걸려 있고, 단절과 재시작은 `crashy`보다 드물다 |
| `margin_days` | 증거금 규칙을 가상 시간 50시간 동안 돌린다(G8). 증거금 시계는 계약 기본값 그대로다(조회 5초, 신선도 30초, 끊김 취소 60초). UTC 자정 1시간 전에 시작해 자정을 세 번 넘는다. 활동은 묶음으로 오고, 묶음 사이 5초~10분 동안은 타이머만 돈다(증거금 조회, 대조, 조회 간격마다 틱 하나. 메시지는 제 시각에 전달된다). `margin_lossy`의 장애가 단계당 더 드물게 들어가고(실행 하나가 약 15,000단계, 입력 약 18만 건이다), 여기에 더해 거래소가 증거금 조회에 1분~1시간 동안 답하지 않고, 자정 둘 가운데 하나는 자정 전 1시간 안의 어느 시각부터 자정 뒤 10분 안의 어느 시각까지 답하지 않고, 증거금 응답의 5%가 두 번 도착하고, 계좌에서 출금과 입금이 일어나고(시작 자금의 0.5~8%), 운영자가 기준을 재설정한다. 실행 하나가 다른 프로파일의 약 100배라서 seed는 표준 실행의 10분의 1만 돌린다(최소 2개: 기본 4개, `sim` 40개, `sim-extended` 300개) |

위 일곱 프로파일(`calm`~`external`)에는 증거금 정책이 없다. 이 실행들은 증거금 규칙이 생기기 전과 같은 난수를 뽑고 같은 저널을 쓴다. `existing_profiles_give_the_same_run_with_margin_off`가 프로파일마다 seed 다섯 개의 저널 해시를 main(84db0f9)에서 기록한 값과 비교한다.

증거금 프로파일의 시계는 계약 기본값의 50분의 1이다: 조회 100 ms(기본 5초), 신선도 600 ms(30초), 보고 끊김 취소 1.2초(60초). 한 실행이 가상 시간으로 25초쯤이기 때문이다. 증거금 조회, 거래소 설정 조회, 계좌 모드 조회, 참조 가격은 노드의 재조정 태스크가 하는 대로 세계가 보낸다.

## 매 단계 검사 (장애 중에도 성립해야 한다)

| 이름 | 내용 |
|---|---|
| `single-placement` | 거래소가 같은 클라이언트 ID의 접수 요청을 두 번 받지 않는다. 받아들여졌든 아니든 |
| `bridge` | 거래소의 실제 포지션이 `[기장 포지션 − 매도 예약, 기장 포지션 + 매수 예약]` 안에 있다. OMS가 모르는 체결이 있어도 예약이 그것을 설명한다 |
| `position-bounds` | 기장 포지션과 예약의 합이 계좌·전략 한도 안에 있다 |
| `venue-position-limit` | 거래소의 실제 포지션이 계좌 한도 안에 있다 |
| 구조 불변조건 | 모든 입력 뒤에 `Core::check_invariants`. 목록은 [04-invariants.md](../04-invariants.md) |
| 키당 주문 하나 | 전략이 받은 응답으로 볼 때 한 키에 주문 번호가 둘 이상 나오지 않는다 |

외부 체결이 일어난 실행에서는 `bridge` 이하를 검사하지 않는다(그 실행의 목적은 탐지다).

증거금 프로파일에서는 매 입력 뒤에 다음도 검사한다.

| 이름 | 내용 |
|---|---|
| `leverage-gate` | 받아들인 일반 주문 뒤의 계좌 노출이 보고된 계좌 가치의 2배 이내이거나, 그 주문이 노출을 올리지 않았다. 노출은 세계가 코어의 장부(포지션, 열린 주문의 예약, 참조 가격)에서 따로 계산한다. 코어의 함수를 부르지 않는다 |
| `margin-fresh` | 일반 주문은 나이가 한도 이내인 증거금 보고가 있을 때만 받아들여진다 |
| `reducing-cancel` | 감소 전용 상태에 들어간 입력이 끝났을 때, 열려 있는 일반 주문마다 취소 요청이 있다 |
| `reducing-accept` | 감소 전용 상태인 동안 일반 주문이 받아들여지지 않는다 |
| `reducing-entry` | 감소 전용 상태는 증거금 보고로만 들어간다(보고 끊김은 상태를 걸지 않는다) |
| `reducing-release` | 감소 전용 상태는 운영자의 해제로만 끝난다. 다른 입력(새 날의 보고, 회복된 계좌 가치, 부팅) 뒤에 상태가 사라지면 위반이다. 재시작 뒤의 상태는 저널이 말하는 것과 같아야 하고, 저널의 `reducing_cleared`는 운영자 해제 입력의 기록에만 있어야 한다 |
| `daily-loss` | 기록된 보고의 계좌 가치가 그 보고 전의 기준 금액보다 5 %를 넘게 낮으면, 그 입력이 끝났을 때 계좌는 감소 전용 상태다. 그 보고가 새 UTC 날의 기준을 정하는 보고여도 같다(자정을 넘는 동안의 손실이 새 기준에 묻히지 않는다) |
| `stale-cancel` | 링크가 올라온 시각(세계가 따로 적어 둔 값)과 마지막으로 기록된 보고의 조회 시각 가운데 늦은 쪽에서 한도보다 오래 지난 뒤의 틱이 끝나면, 열려 있는 일반 주문마다 취소 요청이 있다 |

이 검사들은 "취소 요청이 있다"까지만 본다. 취소가 체결을 이기는지, 주문을 받은 뒤 가격이 움직여 노출이 한도를 넘는지는 보지 않는다. 각 검사는 코어의 규칙을 일부러 고장 내서 실패하는 것을 확인했다(변이 M94~M100, 그리고 티켓 10과 11의 커밋 본문).

프로파일이 규칙에 실제로 닿았는지도 확인한다(seed 40개부터): 판정된 주문, `AccountLeverage` 거절, 감소 전용 상태 진입과 그때 열려 있던 일반 주문, 운영자 해제, 감소 전용 상태에서 넘긴 자정과 회복된 계좌 가치, `margin_lossy`에서는 재시작, 버려진 늦은 보고, `MarginUnavailable` 거절, 보고 끊김 취소, 유지증거금 여유 진입, 거절된 해제. seed 40개 실행의 수는 시험 출력(`--nocapture`)에 있다.

`margin_days`의 두 시험은 정해진 순서 하나를 먼저 돌린다(난수 없음). `profile_margin_days_crosses_three_utc_days_with_restarts`: 자정 10초 전부터 20초 동안 조회가 끊기고 그 사이 100에서 6이 빠져나간다. 새 날의 첫 보고(94)는 전날 기준 100으로 판정돼 감소 전용 상태를 걸고, 그다음에 새 날의 기준이 된다. 이어서 재시작, 둘째 자정(기준 100), 날 중간의 출금(기준은 그대로), 재시작, 셋째 자정(기준 99)을 지나는 동안 상태는 남고, 저널에는 날마다 기준이 하나씩만 있다. `margin_journal_records_stay_within_one_per_poll`: 조용한 하루(링크 세션 하나)는 조회 17,280번과 증거금 기록 17,280건이다. 임의 실행에서는 실행마다 저널의 기준이 자정을 정확히 세 번 넘고(`day_rolls`), 재시작이 한 번 이상 있고, 증거금 기록(입력이 증거금 보고인 저널 기록)이 조회 수 이하이고, 같은 조회의 답이 두 번 기록되지 않고, 조회 수가 5초에 하나와 링크 세션 수의 합 이하다. 닿았는지 확인하는 것: seed 4개부터 감소 전용 상태에서의 재시작, 운영자 해제, 두 번 도착한 응답, 버려진 보고. seed 40개부터(`sim` 묶음과 `sim-extended` 묶음) 감소 전용 상태에서 넘긴 자정, 새 날의 첫 보고가 처음 보여 준 손실. seed 40개 실행에서 재시작 591번, 감소 전용 상태에서의 재시작 199번, 그 상태로 넘긴 자정 37번, 자정을 넘어 처음 보인 손실 6번이었다.

`margin_days`가 보이지 않는 것: 노드 프로세스를 실제로 며칠 돌리는 것(하지 않았다). 저널의 디스크 바이트(세지 않았다. 저널은 지워지지 않는다, U-04). 증거금 기록이 아닌 기록의 수는 묶지 않는다: 이 실행에서 저널 기록의 약 5분의 1만 증거금 기록이고, 나머지는 주로 참조 가격(조회마다 하나), 틱의 `purged` 기록(정리 간격 1초마다 하나), `fills_synced` 기록이다. 이것들은 증거금 규칙 이전부터 있던 동작이다. 메모리 사용량도 재지 않았다.

## 끝 검사 (장애를 멈추고 대조가 끝난 뒤)

| 이름 | 내용 |
|---|---|
| `replay-equivalence` | 저널의 이벤트만 적용해 만든 상태가 살아 있는 상태와 같다 |
| `re-decide` | 저널의 입력을 다시 판단하면 기록된 이벤트가 그대로 나온다 |
| `final-position` | 기장 포지션이 거래소 포지션과 같다 |
| `final-unattributed` | 미귀속분이 외부 체결의 합과 같다 |
| `final-fills`, `final-orders` | 거래소의 우리 주문마다 체결량과 상태가 같다. 코어가 열려 있다고 보는 주문은 거래소에도 열려 있다. "놓이지 않음"으로 닫은 주문은 거래소에 없다 |
| `final-fees` | 수수료 합이 같다 |
| `no-false-mismatch`, `final-holds` | 외부 체결이 없었으면 불일치도 차단 사유도 남지 않는다 |
| `external-detection` | 외부 체결이 있었으면 불일치가 떴다 |

## 깨진 가정으로 돌리는 두 실행

부재 판정("만료 + 여유 뒤에 조회해서 없으면 놓이지 않은 것")은 두 가정에 기댄다. 가정을 깨면 검사가 실패해야 한다. 실패하지 않으면 검사가 아무것도 지키지 않는 것이다.

| 시험 | 깨는 가정 | 기대 |
|---|---|---|
| `absence_rule_depends_on_venue_side_expiry` | 거래소가 만료 시각이 지난 요청도 놓는다(A-01) | seed 60개 안에서 주문·포지션에 관한 속성의 위반이 난다 |
| `absence_rule_depends_on_the_clock_margin` | 거래소 시계가 여유보다 크게 늦다(A-02). 로컬 시계가 앞으로 뛴 것과 같은 상황이다 | 위와 같다 |

두 시험은 위반이 어느 속성으로 잡혔는지 확인한다(`bridge`, `venue-position-limit`, `position-bounds`, `final-orders`, `final-fills`, `final-position`, `no-false-mismatch` 중 하나).
무관한 속성으로 실패하면 시험이 실패한다. 최근 실행에서는 둘 다 `bridge`로 잡혔다.

## 시뮬레이션이 찾아낸 결함

개발 중에 다음 네 건을 찾았다. 모두 손으로 쓴 시나리오 시험은 통과하던 상태였다.

| 결함 | 어떻게 드러났나 | 고친 것 |
|---|---|---|
| 체결 동기화 시각이 조회 시각과 같으면, 같은 시각에 뒤이어 생긴 체결이 빠진다 | `final-fills` | 동기화 선언은 조회 시각보다 엄격히 앞선 시각까지만. 실제 게이트웨이는 2초 뒤처진 시각까지만 선언한다 |
| 주문이 메모리에서 지워진 뒤 같은 체결이 다시 전달되면 외부 체결로 다시 기장된다 | `final-position` | 체결 키를 주문과 별도로 전역 보관(`seen_fills`)하고, 그보다 오래된 체결은 재전달로 본다(`fill_floor`) |
| 주인을 모르는 체결을 5초 뒤 외부 체결로 기장했는데, 그 주인이 결과 불명 주문이었다 | `no-false-mismatch` | 주인일 수 있는 주문이 남아 있는 동안은 기다린다(최대 120초) |
| 종결 통보 없이 사라진 주문을 영원히 열린 것으로 본다 | `final-orders` | 열린 주문 조회에 없는 주문을 다시 조회한다(`order_recheck`) |

간격 검토의 수정 가운데 하나도 시뮬레이션이 되돌려 보냈다. "접수된 주문을 거래소가 모른다고 하면 불일치를 제기한다"는 수정이,
접수 전에 보낸 조회의 답이 접수 뒤에 도착하는 경우에 거짓 불일치를 냈다(`no-false-mismatch`, lossy 프로파일 seed 8).
조회 시각이 접수 시각 + 여유보다 뒤일 때만 제기하도록 고쳤다.

## 한계

- 모델이 실제와 다른 곳은 보지 못한다. 가상 거래소는 Hyperliquid 문서를 읽고 만든 것이다.
- 증거금 모형은 우리가 만든 것이다. 거래소의 계좌 가치와 증거금이 이렇게 계산되는지, 감소 전용 주문을 이렇게 다루는지는 확인하지 않았다(T1, T2, T3, T5). 청산이 없다.
- 종목 하나, 전략 둘로 돈다. 종목 사이의 상호작용은 없다(설계상 종목별 장부는 독립이다).
- 확률은 사람이 정했다. 드문 조합(예: 재시작 직후의 재시작 중 링크 단절)은 seed 수에 비례해서만 나온다.
- 장애가 섞인 프로파일에서는 요청의 일부만 수용된다(대부분 차단 사유로 거절). seed 3000개 실행에서 수용 비율은 `calm` 93%, `lossy` 14%, `purge` 13%, `crashy`·`weak_evidence`·`skewed` 7%, `external` 3%였다.
  장애 경로는 많이 지나지만 정상 경로의 밀도는 낮다. 그래도 수용된 주문이 `crashy`에서 약 10만 건, 재시작이 약 5만 4천 번이다.
- 시간 초과와 재시도의 실제 타이밍, 스레드 경합, 부분 쓰기는 없다.
