# 검증

이 문서는 "무엇을 어떻게 확인했고 무엇을 확인하지 않았는가"를 한곳에 모은다.
주장별 상세(범위, 실제와 모의, 주입한 장애, 판정 기준, 재현 명령, 검증하지 않은 것)는 [generated/claims.md](../generated/claims.md)와 대시보드의 "검증 현황"에 있다.
그 내용의 원본은 `registry/claims.toml`이고, 통과 여부는 결과 파일에서 계산한다. 손으로 "통과"라고 적은 곳은 없다.

## 1. 수용 시험을 다시 실행하는 법

```sh
cargo run --release -p xtask -- verify            # 전체. 결과: evidence/latest/results.json, 묶음별 로그
cargo run --release -p xtask -- verify --quick    # 시뮬레이션 seed와 강제 종료 횟수를 줄인 축약판
cargo run --release -p xtask -- verify --live-testnet   # + 실제 testnet 읽기 전용 조회 (네트워크 필요)
cargo run --release -p xtask -- verify --extended <실제 디스크의 디렉터리>   # + 시뮬레이션 seed 3000개, 강제 종료 60회
cargo run --release -p xtask -- mutants           # 고의로 고장 낸 코드를 시험이 잡는지. 결과: evidence/mutants.json
cargo run --release -p xtask -- fsync-probe --dir <디렉터리> --label nvme   # 장치의 동기 쓰기 시간
cargo run --release -p xtask -- core-bench        # 코어의 판단 시간
cargo run --release -p xtask -- perf --label nvme-final --seconds 60 --dir <실제 디스크의 디렉터리>
cargo run --release -p xtask -- perf --label nvme-default-limits --seconds 60 --rates 2000 --default-limits --dir <디렉터리>
cargo run --release -p xtask -- recovery-time --dir <실제 디스크의 디렉터리>
cargo run --release -p xtask -- docs              # 결과를 주장과 묶어 문서와 화면 자료를 다시 만든다
```

결과 파일에는 소스 다이제스트(`crates/`의 모든 `.rs`, `Cargo.toml`, `Cargo.lock`의 해시)가 들어 있다.

## 2. 검증 수준과 각 수준이 말해 주는 것

| 수준 | 말해 주는 것 | 말해 주지 않는 것 |
|---|---|---|
| 단위·시나리오 | 정해 둔 입력 순서에서 코어가 계약대로 판단한다 | 생각하지 못한 순서 |
| 속성 | 무작위 입력의 넓은 범위에서 성질이 유지된다 | 생성기가 만들지 않는 입력 |
| 시뮬레이션 | 장애가 임의로 섞인 긴 실행에서 불변조건이 유지되고 끝에 장부가 맞는다 | 모델이 실제와 다른 부분. 실제 스레드·파일·소켓 |
| 프로세스 내부 | 실제 스레드와 파일로 순서 보장이 유지된다 | 프로세스 경계 밖 |
| 프로세스 | 실제 프로세스를 죽이고 다시 띄워도 계약이 유지된다 | 전원 장애. 실제 거래소 |

## 3. 확인하지 않은 것

아래는 어떤 시험도 다루지 않는다. 통과한 시험이 많다는 것이 이 목록을 줄여 주지 않는다.

| 대상 | 왜 확인하지 못했나 | 그래서 어떻게 두었나 |
|---|---|---|
| 전원 장애 뒤의 저널 | SIGKILL은 OS의 페이지 캐시를 잃지 않는다. 전원 차단 장비가 없다 | `fdatasync`를 호출한다는 것까지만 보장한다. 저장 장치가 그 요청을 지키는지는 가정 A-05 |
| 실제 거래소의 주문·취소·체결·만료 | 실주문 허가와 키가 없다(U-01) | 서명은 SDK 벡터로, 응답 해석은 문서 예제로 대조했다. 주문 경로는 한 번도 실행되지 않았다 |
| 문서가 비워 둔 거래소 동작 35건 | 실주문으로만 알 수 있다 | 문서에 없는 응답에서는 결론을 내지 않게 했다. 항목별 해석은 [ADR-017](../adr/ADR-017-hyperliquid-gateway.md)의 표에 있고, 그 해석이 틀렸을 때의 결과도 거기에 적었다. 실험 목록은 [조사 문서 §4](../research/hyperliquid-protocol.md) |
| 며칠 이상의 연속 운용 | 하지 않았다 | 가장 긴 실행은 60초 부하(V-PERF-1, V-PERF-2)와 강제 종료 60회(V-COMMIT-5)다. 시뮬레이션의 `margin_days`는 가상 시간 50시간이고 실제 시간이 아니다(V-MARGIN-12) |
| 다른 하드웨어·파일 시스템 | 개발 호스트 한 대 | 측정 조건을 결과에 적었다 |
| 증거금 규칙이 실제 거래소에서 뜻대로 동작하는지 | 실제 거래소에 접속하지 않았다. 증거금 조회는 testnet에도 한 번도 보내지 않았다(U-01) | 규칙의 입력(계좌 가치, 격리 증거금, 최대 레버리지, 거래소 설정, 계좌 모드)의 뜻은 문서에서 읽은 가정 T1~T11이다. §11에 전부 적었다 |
| 증거금 정책을 켠 노드의 응답 지연 | 부하 측정의 설정에 정책이 없다 | 코어만 잰 판단 시간이 있다(V-PERF-5, 성능 문서) |
| 디스크가 실제로 가득 찬 상태 | 만들지 않았다 | 여유 부족 차단은 입력을 주입해 시험했다. 쓰기 실패는 주입으로 시험했다 |
| 다른 uid의 접속 거부, 줄 길이 상한, hello 시간 제한, 느린 구독자의 끊김 | 시험을 쓰지 않았다 | 코드는 있다. [C-API](../contracts/api.md)의 "확인하지 않은 것" |
| panic으로 인한 종료 | 시험을 쓰지 않았다 | 빌드 설정(`panic = "abort"`)에 기댄다. G-REL-05 |
| Hyperliquid 게이트웨이의 스트림 재접속 사유, 예약 취소의 거부, 리디렉션 차단 | 네트워크를 흉내 낸 시험이 없다 | 코드만 있다. 간격 검토 뒤에 추가한 것이다 |
| venue 큐가 가득 차는 상황 | 시험을 쓰지 않았다 | [C-OVERLOAD](../contracts/overload.md) |
| 대시보드 화면의 자동 시험 | 없다 | 아래 §6의 수동 확인 |
| 시계가 뒤로 가거나 크게 뛰는 경우의 프로세스 동작 | 호스트 시계를 실제로 바꿔 보지 않았다. 코어 스레드는 직전보다 작은 시각을 부여하지 않는다(코드, 시험 없음). 앞으로 뛴 시계는 부재 판정의 가정을 깬다 | 가정 A-02, G-OPS-07. 시뮬레이션이 시계 차이가 여유를 넘는 경우의 위반을 보인다(V-DOUBT-3) |

시험하지 않은 장애 조합과 그 이유:

| 조합 | 왜 뺐나 |
|---|---|
| 한 커밋 배치에 주문이 여럿일 때의 경계별 중단 | 경계 시험은 주문 한 건으로 한다. 배치 안의 순서는 `inputs_that_arrive_together_share_a_flush`와 무작위 종료가 지난다. 배치 크기와 중단 지점의 곱을 다 돌리지 않았다 |
| 재시작 도중의 재시작 | 복구는 디스크를 바꾸지 않는다(꼬리 절단 제외. 그것은 보존 → 절단 순서라 반복해도 같다). 시뮬레이션은 연속 재시작을 확률적으로만 지난다 |
| 스냅샷 쓰기 도중의 중단 | 임시 파일 → rename이라 중단되면 임시 파일만 남는다. 저널 crate 시험이 불완전한 스냅샷을 건너뛰는 것을 본다. 프로세스 수준에서 그 순간을 겨냥하지 않았다 |
| 링크 단절 중의 프로세스 중단, 대조 도중의 중단 | 대조기에 복구할 상태가 없으므로 "재시작 뒤 처음부터"와 같다. 시뮬레이션의 `crashy` 프로파일이 섞어서 지난다. 따로 겨냥하지 않았다 |
| 저장 공간 부족 + 체결 폭주 | 실제로 디스크를 채우지 않았다 |
| 취소 폭주 + 느린 거래소 + 재시작 | 명령 큐가 차는 조건을 만들지 못했다(D-CONC-03) |
| 여러 종목에 걸친 조합 | 종목별 장부가 독립이라 한 종목으로 시험했다. 종목 사이의 결함(예: 잘못된 종목의 장부를 갱신)은 `fill_field_conflict` 시험과 설정에 없는 종목의 체결 시험만 본다 |
| 설정 변경 + 열린 주문 + 재시작 | 설정 버전 시험은 열린 주문이 하나인 경우만 본다 |
| 실제 거래소의 모든 조합 | 주문을 보낼 수 없었다(U-01) |

가상 거래소는 이 프로젝트가 Hyperliquid 문서를 읽고 만든 것이다. 문서를 잘못 읽었다면 가상 거래소와 게이트웨이가 같은 오해를 공유하고, 시험은 통과한다.

## 7. 실제 거래소로 확인한 범위

`hl_live::the_gateway_reads_the_real_testnet` (2026-10-02, Hyperliquid testnet, 주문 없음, 계정 없는 주소).

이 시험은 한 번 간헐적으로 실패했다: 조회 넷 가운데 셋이 접속 단계에서 실패했고(요청은 나가지 않았다) 원인은 로그에 남지 않았다.
같은 시험을 이어서 세 번 돌렸을 때 한 번 더 재현됐다. 시험이 조회를 한 번만 보내던 것을 실제 노드의 대조기처럼 반복하게 고친 뒤로는 여덟 번 연속 통과했다.
오류의 원인이 로그에 남도록 고쳤지만, 그 뒤로는 오류가 다시 나지 않아 원인은 확인하지 못했다.

확인된 것: 종목 메타 조회와 설정 대조, 스트림 접속과 `orderUpdates`·`userFills` 구독 확인, 없는 주문 조회의 `unknownOid` 응답 해석,
빈 열린 주문·포지션 응답 해석, 체결 조회와 동기화 선언, `allMids`에서 BTC 참조 가격 수신.

증거금 규칙의 작업(2026-11-15~16)에서는 이 시험을 실행하지 않았다. 그 작업은 실제 거래소에 어떤 요청도 보내지 않기로 했기 때문이다(U-01, 스펙의 범위 밖 항목). 그래서 주장 V-HL-3은 현재 소스에서 "미실행"이다. 실패가 아니고, 통과도 아니다.
위 2026-10-02의 실행에는 증거금 조회(`clearinghouseState`의 증거금 필드, `activeAssetData`, `userAbstraction`)가 없었다. 그 세 조회는 실제 거래소에 한 번도 보낸 적이 없다.

확인되지 않은 것: 그 밖의 전부. 특히 서명한 요청이 거래소에서 받아들여지는지조차 확인하지 않았다(서명은 SDK의 시험 벡터와 바이트 단위로 같다는 것까지만).

### 11.3 스펙과 다르게 했거나 스펙이 비워 둔 곳에서 정한 것

스펙의 결정을 뒤집은 것은 없다. 아래는 스펙에 한 가지를 더했거나, 스펙이 말하지 않은 곳에서 가장 작은 선택을 한 것이다. 사용자가 바꿀 수 있다.

| 티켓 | 내용 |
|---|---|
| 02 | 증거금 조회의 순번은 링크 세션마다 다시 시작하지 않고 노드 프로세스가 사는 동안 계속 오른다(세션 안에서 오른다는 스펙의 조건은 지킨다) |
| 02 | 읽지 못한 보고(`MarginReportInvalid`)에는 순번 검사를 하지 않는다. 순번이 낮은(늦게 온) 보고가 최대 레버리지 0을 담고 있으면 거부 기록 없이 버린다 |
| 02 | `status`의 보고 나이와 신선 여부는 기록 시각이 아니라 조회하는 순간의 프로세스 시계로 계산한다 |
| 03 | 참조 가격의 신선도는 새 값을 두지 않고 가격대 검사의 한도(`ref_price_max_age_us`, 15초)를 쓴다 |
| 03 | 계좌 가치가 0 이하면 노출을 늘리지 않는 일반 주문도 `AccountLeverage`로 거절한다. 노출의 합이 i128에 들어가지 않으면 `Overflow`로 거절한다 |
| 03 | 신선한 보고가 없으면 레버리지 검사를 하지 않는다(사유는 `MarginUnavailable` 하나). `status`의 계좌 노출은 나이와 상관없이 마지막 참조 가격으로 계산한다 |
| 04 | 감소 전용 상태로 들어갈 때 주문의 단계를 보지 않는다(종결 증거를 본 주문에도 요청을 기록한다. 취소는 보내지 않는다). 기준 금액보다 이른 날의 보고도 그 기준으로 판정한다. 기준이 0 이하여도 같은 비교를 한다 |
| 05 | 거절 사유의 글자는 `not_reducing`, `margin_unavailable`, `note_required`이고, 여러 조건이 틀리면 그 순서로 하나만 답한다. 공백뿐인 사유는 빈 것으로 본다. `rebase-day`의 사유는 이벤트가 아니라 입력 기록에 남는다 |
| 05 | `omsctl`의 시험은 실행 파일을 띄우지 않고 그 본문인 `oms_api::ctl::run`을 부른다. 실행 파일의 `main`(인자 수집, 출력, 종료 코드)은 시험하지 않는다 |
| 05 | 시험용 중단 지점(`failpoints`)이 바뀌었다: `OMS_CRASH_ON`으로 증거금 보고의 기록을 겨냥할 수 있고, `after_reply` 지점은 겨냥한 항목에서 정확히 멈추며, 중단이 core dump를 남기지 않는다 |
| 06 | **스펙의 조건에 하나를 더했다.** 링크가 이미 올라와 있을 때 증거금 정책을 켜면 그 설정 기록의 시각부터 60초를 잰다. 링크가 올라온 시각은 정책이 있을 때만 상태에 남긴다 |
| 06 | 보고 끊김 취소는 주문의 단계를 보지 않고, 감소 전용 상태에서도 돈다(그때는 요청할 주문이 없다) |
| 07 | `clear-reduce`의 거절 순서는 `not_reducing`, `margin_unavailable`, `mm_buffer_active`, `note_required`다. 선의 곱이 i128을 넘으면 선 아래로 읽는다. 음수 증거금은 모든 선 아래다. 가치가 0 이하인 포지션은 판정하지 않는다 |
| 08 | 허용 계좌 모드 목록의 기본값은 비어 있고 글자 그대로 읽는다. 운영자가 거래소의 보통 모드를 적기 전에는 일반 주문이 하나도 통과하지 않는다. 설정에 없는 종목의 거래소 설정 입력은 버린다 |
| 08 | 링크가 올라온 뒤의 거래소 설정·계좌 모드 조회는 답을 기록할 때까지 1초마다 다시 보낸다(11.5의 미해결 사항) |
| 09 | 조회 weight 검사는 Hyperliquid 거래소에 증거금 정책이 있을 때만 한다. 1분을 나누지 못하는 간격은 올림한다. 정확히 600은 통과한다. 참조 가격 항(24)은 이 게이트웨이가 그 조회를 보내지 않는데도 스펙대로 센다 |
| 09 | 계좌 모드는 문서에 없는 문자열도 글자 그대로 코어에 넘긴다. 거래소 설정 응답은 물은 종목의 이름을 담고 있어야 받는다. 증거금 보고의 소수는 JSON 문자열, 레버리지는 JSON 정수여야 하고 다르면 보고 전체를 거부한다(실제 응답이 다르면 모든 보고가 거부돼 일반 주문이 멈춘다. 안전한 쪽이다) |
| 09 | `activeAssetData` 응답의 시험 자료는 저장소의 조사 문서에 없어서 구현자가 기억하는 문서의 예로 적었고, 문서와 다시 대조하지 않았다. `userAbstraction`의 값은 설계 합의에 적힌 다섯 개다 |
| 09 | 변이 점검이 작업 사본에 `config/`를 복사한다 |
| 10 | 시뮬레이션의 증거금 시계는 계약 기본값의 50분의 1이다(`margin_calm`, `margin_lossy`). 모형의 포지션 증거금은 가치 ÷ 레버리지이고 손실이 나도 줄지 않는다. 그래서 유지증거금 여유는 가상 거래소가 증거금을 0으로 말할 때만 걸린다 |
| 10 | 포지션보다 큰 감소 전용 주문을 모형은 거절한다(줄여 받지 않는다). simvenue 프로세스는 감소 전용 표시를 받지 않고 모든 주문을 일반 주문으로 다룬다 |
| 10 | `profile_margin_calm_release_invariant`는 `margin_calm`에 재시작이 없어서, 재시작을 시험 머리의 정해진 순서와 `margin_lossy`의 무작위 재시작으로 본다. "규칙에 닿았다"는 확인은 seed 40개가 필요하다 |
| 11 | `margin_days`는 seed를 표준 실행의 10분의 1만 돌린다(한 번이 다른 프로파일의 약 100배다) |
| 12 | 코어 벤치마크의 증거금 경우를 고정하는 시험은 xtask의 단위 시험이고 `xtask verify`의 묶음에 없다. 그래서 어떤 주장도 그 시험을 이름으로 들지 않는다 |

"시험을 먼저 쓰고 실패를 본다"에서 벗어난 것: 여러 시험이 앞선 단계가 이미 만든 동작을 고정했기 때문에 처음 돌렸을 때 통과했다. 그런 시험은 규칙을 작업 사본에서 일부러 깨서(커밋하지 않고) 실패를 본 뒤 커밋했고, 그 실패 줄을 커밋 본문에 적었다. 티켓별 목록은 티켓 파일에 있다.
그 밖에: 티켓 02의 커밋 2e8d1e6은 시험이 자기 준비 단계에서 실패하는 채로 만들어졌고 다음 커밋이 시험을 고쳤다. 티켓 02의 노드 단위 시험에서는 첫 거절만 실패를 봤다. 티켓 03, 08, 12에서는 커밋 하나씩을 push 전에 고쳐 썼다(03과 12는 커밋 글, 08은 시험이 실패하는 채로 만든 커밋의 내용).

### 11.4 규칙이 보장하지 않는 것

- **실제 일 손실은 5 %를 넘을 수 있다.** 규칙은 손실이 난 다음 보고에서 움직인다. 보고가 100이었다가 5초 뒤 88이면 12 %를 잃은 뒤에 감소 전용 상태가 된다.
- 새 보고를 받지 못하는 동안에는 일 손실도 유지증거금 여유도 판정하지 않는다.
- 규칙 취소는 체결과의 경합에서 질 수 있다. 그때는 체결을 기장하고, 감소 전용 상태인데 포지션이 커진다.
- OMS는 포지션을 닫지 않는다. 감소 전용 상태와 보고 끊김 취소 뒤에도 포지션은 그대로다.
- 링크가 내려가 있는 동안에는 아무것도 취소하지 않는다. 링크가 돌아오면 새 세션이 다시 60초를 재므로, 주문은 "끊긴 시간 + 60초" 동안 보고 없이 걸려 있을 수 있다.
- 보고 끊김 취소는 한도를 넘은 뒤 첫 틱에서 나간다(틱 간격만큼 늦다). 취소 시도가 다 된 주문은 다시 요청하지 않는다. 도착했을 때 이미 오래된 보고는 그것만으로 끊김을 끝내지 않는다.
- 가격이 움직여 계좌가 2배를 넘어도 아무 일도 없다. 검사는 새 주문이 올 때만 한다. 참조 가격은 mid이고 거래소의 mark가 아니다. 검사가 받은 주문을 거래소가 거절할 수 있다.
- 유지증거금 여유는 청산 가격의 0.13~0.37 % 앞에서 걸리고(BTC, 거래소 2배) 5초 간격의 조회가 그 사이를 건너뛸 수 있다. 잘못 걸린 유지증거금 여유 상태는 조건이 참으로 읽히는 동안 풀 수 없다(강제 해제가 없다). 거래소가 그 포지션을 더는 말하지 않으면(닫혔거나 청산됐으면) 조건이 거짓이 되어 풀 수 있다.
- 입금은 그 금액만큼의 손실을 기준 재설정이나 다음 UTC 날까지 가린다. 출금은 손실로 읽힌다. OMS는 입출금을 알아채지 않는다.
- 표시(reduce-only) 없는 익절 주문은 감소 전용 상태와 보고 끊김 취소에서 취소된다. 감소 전용 상태에서는 포지션을 줄이는 일반 주문도 거절된다.
- 귀속되지 않은 포지션(수동 거래, 청산)은 전략이 OMS로 줄일 수 없다. 설정에 없는 종목에 포지션이 생기면 그 종목은 참조 가격을 받을 수 없어서, 그 포지션이 0이 될 때까지 모든 일반 주문이 `MarginUnavailable`로 거절된다.
- 자기 포지션 한도에 여유가 있는 전략은 자기 것이 아닌 포지션을 향해 감소 전용 주문을 낼 수 있다. 거래소가 그것을 어떻게 다루는지는 T5다.
- 감소 전용 상태인 채로 `policy.margin`이 없는 설정을 켜면 상태는 남고 차단 표는 꺼진다. 그러면 `Reducing`이 감소 전용 주문까지 막고, 해제도 할 수 없다(`margin_unavailable`). 정책을 다시 켜야 한다.
- 기본 정책에서 계좌 가치가 양수 기준 아래 0 이하로 떨어지면 일 손실과 레버리지 검사가 함께 답한다. 그 조합의 거절 목록을 고정하는 시험은 없다.
- 거래소에서 바뀐 설정은 다음 조회(최대 60초)나 다음 보고에서야 보인다. 계좌 모드가 링크 세션 도중에 바뀐 것은 다음 세션에서 읽는다. 재시작 뒤 링크가 올라오기 전까지는 이전 세션의 설정이 상태에 남아 있다(그동안은 `LinkDown`이 막는다).
- 뒤로 간 시계가 따라올 때까지 시간 기준 동작(신선도, 끊김 취소, 주문 만료)은 멈춘 시각으로 판정한다. 틱이 오지 않으면 보고 끊김 취소도 없다.
- 운영자의 판단이 옳은 것. 해제는 그 시점의 계좌 가치에서 5 %를 더 잃을 여유를 다시 준다.

### 11.5 시험이 닿지 않는 곳과 미해결 사항

- **미해결: 대조기가 모르는 거래소 설정과 계좌 모드를 1초마다 되묻는다**(티켓 09가 찾았고 고치지 않았다. 코드는 티켓 08의 `reconciler.rs`). weight 20짜리 조회라 종목 하나에 분당 최대 1200이고, 이것은 게이트웨이의 로컬 요청 예산이 1분에 다시 채우는 양 전부이며, 설정 검사가 세는 분당 600의 예산 밖이다. 응답을 읽지 못할 때, HTTP가 실패할 때, 그리고 T11이 틀리면(포지션 없는 종목의 설정을 거래소가 말해 주지 않으면) 그 종목에 대해 계속 일어난다. 그러면 로컬 예산이 조회를 줄이고(예약분 300까지), 증거금 보고도 밀려 일반 주문이 거절되고 60초 뒤 보고 끊김 취소가 나간다. 안전한 쪽이지만 거래가 멈춘다. 고치는 일(이 두 조회를 더 천천히 되묻기)은 작지만 간격을 정해야 한다. testnet 예행 전에 정해야 한다.
- Hyperliquid 게이트웨이가 세 조회를 보내고 응답을 번역 함수에 넘기는 부분(세 `match` 갈래), HTTP 오류와 429의 처리는 시험이 없다. weight 값(2, 20, 20)은 문서의 값이고 거래소가 실제로 세는 값과 대조하지 않았다.
- 취소 500건 뒤 증거금 조회가 기다리는 시간(가득 찬 예산에서 0초, 시작 직후 10.1초, 빈 예산에서 15.1초)은 로컬 예산의 산술이다. 조회는 `margin_poll_ms`마다 한 번 시도하고 다른 조회도 같은 예산을 쓰므로 실제 대기는 15.1초보다 길 수 있다.
- 같은 종목 id로 번역되는 코인 이름 둘(`PURR/USDC`와 `PURR_USDC`)은 한 종목의 포지션 둘로 나타난다.
- 프로세스 시험은 조회 간격을 줄여서 돈다(증거금 100 ms, 거래소 설정 200 ms). 기본값 5초와 60초 그대로의 프로세스 실행은 없다(코어 시험과 `margin_days` 시뮬레이션은 계약의 시계를 쓴다).
- 유지증거금 여유와 보고 끊김 취소에는 프로세스 수준의 시험이 없다. `status`의 `mm_buffer`와 `omsctl`의 `mm_buffer_active` 응답은 시험하지 않았다.
- 취소 폭주의 프로세스 시험은 주문 300건이고 가상 거래소에는 요청 예산이 없다.
- 시뮬레이션: 종목은 하나다. 청산은 모형에 없다(계좌 가치가 0 아래로 가도 포지션이 남는다). 검사는 취소 요청이 있는지만 보고 취소가 체결을 이겼는지는 보지 않는다. `margin_lossy`에서 보고 끊김 취소가 주문을 찾는 일은 드물다(seed 40개에 5건, 3000개에 1250건). 자정을 넘는 손실은 무작위 실행 일곱에 하나꼴이다. 한 실행은 자정을 세 번만 넘는다.
- 여러 날의 실행은 가상 시간이다. 노드 프로세스를 실제로 며칠 돌리지 않았다. 저널의 디스크 바이트와 메모리 사용은 재지 않았다. 증거금 기록이 아닌 기록(참조 가격, 틱의 정리 기록)의 수는 묶지 않았다. 저널은 지워지지 않는다(U-04).
- 디스크 유실과 전원 장애는 시험하지 않았다. 중단은 프로세스 `abort()`와 SIGKILL이다.
- 성능: 증거금 정책을 켠 노드의 응답 지연, 감소 전용 상태로 들어가는 입력 하나의 시간은 재지 않았다(성능 문서).
- 코드를 쓰지 않은 사람의 검토는 받지 않았다. 통합 브랜치 전체에 대한 적대적 검토(규칙을 깨 보는 검토)는 main에 머지하기 전 단계이고 이 문서를 쓴 시점에는 아직이다.
