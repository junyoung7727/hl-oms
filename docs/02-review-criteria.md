# 2. 검토 기준

이 문서는 검토 기준 등록부를 읽는 법을 설명한다. 항목 자체는 `registry/considerations-*.toml`에 있고,
표로 펼친 것이 [generated/considerations.md](generated/considerations.md), 화면으로 보는 것이 대시보드의 "고려사항·결정"이다.

## 2.1 왜 등록부를 따로 두는가

설계 문서만 있으면 "생각한 것"만 보이고 "생각하지 않은 것"은 보이지 않는다.
등록부는 특정 구현과 무관하게 **확인해야 할 질문**을 먼저 늘어놓고, 질문마다 이 프로젝트가 어떻게 답했는지와 아직 답하지 못한 것을 적는다.
답이 없는 질문이 그대로 보이는 것이 목적이다.

## 2.2 세 계층

| 계층 | ID | 항목 수 | 질문의 성격 | 주된 출처 |
|---|---|---|---|---|
| 일반 소프트웨어 | `G-*` | 40 | 어떤 소프트웨어에도 해당하는 품질·신뢰성·자원·보안·운영·변경·아키텍처 기술 | ISO/IEC 25010, ISO/IEC/IEEE 42010, NIST SSDF, OWASP ASVS |
| Rust·LMAX·OMS | `D-*` | 40 | 상태 소유권, 결정적 실행, 동시성, 주문 상태, 수치, 리스크, 중복·순서, 결과 불확실성, 영속화, 복구, 가용성, 과부하, 최적화, 검증 | LMAX 원저작, FIX 주문 상태 의미, FIA 권고, Linux 시스템 계약, fsync 연구 |
| 이 프로젝트 | `P-*` | 23 | Hyperliquid의 실제 계약, 성능 목표, 운영 인력과 비용, 전략 귀속, 기존 구현에서의 이행 | Hyperliquid 문서와 SDK, 기존 요구 문서, 지시문 |

## 2.3 항목의 필드

| 필드 | 뜻 |
|---|---|
| 고려사항 | 확인해야 할 질문 |
| 필요성 | 이 질문을 빼면 무엇이 잘못될 수 있는가 |
| 출처 | 이 질문이 어디서 왔는가. [generated/sources.md](generated/sources.md)의 ID |
| 적용 | 적용 / 조건부 / 비적용, 그리고 그 이유 |
| 처리 방안 | 이 프로젝트가 어떻게 다뤘는가 |
| 설계 · 구현 · 검증 | 세 가지를 **따로** 적는다. 아래 §2.4 |
| 연결 | 설계 결정(ADR), 동작 계약, 코드, 검증 주장 |
| 미해결 | 아직 답하지 못한 것 |

## 2.4 상태의 뜻

"검토했다", "설계했다", "구현했다", "검증했다"는 서로 다른 말이다.

| 필드 | 값 | 뜻 |
|---|---|---|
| 설계 | 결정 | 어떻게 할지 정했고 설계 결정이나 계약에 적혀 있다 |
| | 미결 | 정하지 못했다. 대개 사용자 결정이나 실거래소 확인을 기다린다 |
| 구현 | 구현 | 코드가 있다 |
| | 부분 | 일부만 있다. 빠진 부분은 "미해결"에 있다 |
| | 미구현 | 코드가 없다 |
| | 해당없음 | 코드로 다룰 항목이 아니다(문서나 절차) |
| 검증 | 검증 | 연결된 주장의 시험이 그 주장에 적힌 조건 안에서 통과했다 |
| | 부분 | 일부 측면만 시험했다. 빠진 측면은 주장의 "검증하지 않은 것"이나 항목의 "미해결"에 있다 |
| | 미검증 | 시험이 없다 |

"검증"은 표준을 준수한다는 뜻이 아니다. 그리고 손으로 적은 값이므로 생성기가 한 번 더 확인한다:
"검증"인 항목에 연결된 주장이 현재 소스에서 통과 상태가 아니면 문서와 화면에 따로 표시한다.

## 2.5 출처를 쓰는 방식

모수는 등록부의 항목만이 아니다. 출처가 나누어 둔 요소마다 어느 항목이 다루는지, 다루지 않으면 왜인지를 [generated/coverage.md](generated/coverage.md)에 적었다
(원본 `registry/coverage.toml`). 상태는 다룸·비적용·보류·미검토 넷이다. 비적용과 미검토에는 이유를, 보류에는 영향과 재개 조건을 적는다.
"다룸"은 검토 항목이 있다는 뜻일 뿐이고, 그 항목이 구현되고 검증됐는지는 항목의 상태를 봐야 한다.

- 표준과 권고는 **누락을 찾기 위한 분류 축**으로 쓴다. 이 프로젝트가 어떤 표준을 준수하거나 인증받았다고 주장하지 않는다.
- 출처마다 역할(품질 분류, 보안 관행, 참조 의미, 산업 권고, 프로토콜 계약, 시스템 계약, 원저작, 연구), 판과 시점, **실제로 읽은 범위**를 적었다.
  읽지 못한 부분(예: ISO 본문의 유료 절)은 그렇다고 적었고, 그 부분에 기대는 항목은 "조건부"로 두었다.
- 2차 자료에서 가져온 내용은 2차 자료라고 적었다.
- 조사 기록: [research/standards-sources.md](research/standards-sources.md), [research/lmax-durability-rust.md](research/lmax-durability-rust.md), [research/hyperliquid-protocol.md](research/hyperliquid-protocol.md).

## 2.8 등록부가 보장하지 않는 것

- 연결이 **있다**는 것만 생성기가 확인한다. 연결된 시험이 그 질문에 정말 답하는지는 사람이 판단했다.
- 질문 목록이 완전하다는 보장은 없다. 출처의 분류를 따라 누락을 줄였을 뿐이다. 구현과 분리된 검토에서 추가로 찾은 것은 [verification/gap-review.md](verification/gap-review.md)에 있다.
- "검증"은 사람이 적는 값이다. 간격 검토에서 그 값이 시험의 실제 범위보다 앞서 있던 항목이 넷 나왔다(D-PER-02, G-REL-01, P-VEN-02, D-AVL-01). 앞의 둘은 시험을 추가했고 뒤의 둘은 "부분"으로 내렸다.
