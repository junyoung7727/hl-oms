# 1. 목표와 운영 범위

기준: 2026-10-02. 지시문은 [00-brief.md](00-brief.md)다.
이 문서는 "무엇을 만들고 무엇을 만들지 않는가", "어떤 가정으로 진행하는가", "무엇을 달성하면 수용하는가"를 정한다.

용어: OMS(Order Management System, 주문 관리 시스템)는 주문의 접수·위험 검사·생명주기·기록·전송·대조를 맡는다.
거래소(venue)는 주문을 실제로 체결하는 외부 시스템이다. 게이트웨이는 OMS 안에서 거래소와 통신하는 부분이다.

## 1.1 OMS와 매칭 엔진의 구분

| 책임 | 소유자 | 이 프로젝트에서의 위치 |
|---|---|---|
| 주문 매칭, 체결 가격 결정, 증거금·청산 | 거래소 | 범위 밖. 결과만 통보로 받는다 |
| 주문 의도 접수, 사전 위험 검사와 예약 | OMS 코어 | `crates/oms-core` |
| 주문 생명주기와 체결 반영, 포지션 장부 | OMS 코어 | `crates/oms-core` |
| 기록과 복구 | OMS 실행 계층 | `crates/oms-journal`, `crates/oms-node` |
| 거래소 통신, 상태 대조 | OMS 게이트웨이 | `crates/oms-node/src/venue` |
| 시험용 가상 거래소 | 시험 도구 | `crates/oms-sim`, `simvenue` 바이너리 |

가상 거래소는 매칭 엔진이 아니다. 시험이 "이 주문을 이만큼 체결시켜라"라고 지시하면 그대로 체결할 뿐이다.
가상 거래소 통과는 실제 거래소 동작의 검증이 아니다.

## 1.2 확정된 구조적 결정

2026-10-02에 사용자가 네 가지를 확정했다. 모두 추천안이다.

| 항목 | 결정 | 구조에 미치는 영향 |
|---|---|---|
| 첫 대상 거래소 | Hyperliquid perpetual. testnet 먼저. 코어는 거래소 중립 | 거래일 경계 없음. 식별자·조회·한도 계약은 Hyperliquid 문서를 따른다 |
| 가용성 | 단일 노드 + 재시작 복구. 서버 장애는 수동 복구 | 복제·합의·자동 승격 없음 |
| 전략과의 경계 | 같은 호스트의 별도 프로세스, 로컬 소켓 | 요청 재전송이 생기므로 멱등성 키가 필수 |
| 가장 빠른 전략 | 초~수백 ms 단위 | busy-spin, kernel bypass, 전용 ring buffer를 쓰지 않는다 |

## 1.3 운영 범위

| 항목 | v1 범위 | 근거 |
|---|---|---|
| 상품 | 선형 perpetual, 단일 담보 통화 | 기존 `../docs/architecture/OMS.md`(상위 디렉터리) §3.2 |
| 계좌 | 단일 계좌, 다중 전략 | 기존 문서의 사용자 결정 |
| 주문 유형 | 지정가 GTC, IOC, ALO(post-only). `reduce_only` 표시. 취소 | Hyperliquid의 TIF는 이 세 가지뿐이다 ([조사 A](research/hyperliquid-protocol.md)) |
| 시장가 | 별도 유형 없음. 전략이 상한 가격을 정한 IOC로 표현 | Hyperliquid에 시장가 와이어 타입이 없다. 공식 SDK도 공격적 IOC로 만든다 |
| 정정 | 지원하지 않음. 취소와 신규 두 주문으로 처리 | 정정 후 식별자·잔량 승계가 문서에 없다. 독립된 두 주문으로 예약해야 수량 한도가 보존된다 |
| 조건부 주문(TP/SL) | 범위 밖 | 부모·자식 주문의 상태 계약이 별도로 필요하다 |
| 체결 정정·취소 | 지원하지 않음. 발생하면 불일치로 탐지 | Hyperliquid 문서에 체결 정정이 없다. 탐지는 포지션 대조가 맡는다 |
| 거래일·세션 | 없음. 24시간 연속 | 일 단위 초기화가 필요한 한도는 v1에 없다 |

## 1.4 요청량과 용량

수치는 거래소 한도에서 유도한다. 근거 없는 목표를 두지 않는다.

| 항목 | 값 | 출처 |
|---|---|---|
| 거래소 요청 상한(IP) | 분당 1200 weight. 단건 주문·취소는 weight 1, 즉 초당 20건 | Hyperliquid 문서 |
| 거래소 요청 상한(계좌) | 누적 거래 1 USDC당 1건 + 초기 10000건. 소진 시 10초에 1건 | Hyperliquid 문서 |
| 거래소 열린 주문 한도 | 1000건(거래량에 따라 최대 5000건) | Hyperliquid 문서 |
| 거래소 지연 | 중앙값 0.2초, p99 0.9초 | Hyperliquid 문서의 서술. 우리 측정 아님 |
| OMS 정상 요청량(가정) | 초당 20건 이하 | 위 IP 한도 |
| OMS 피크 요청량(설계 기준) | 초당 200건의 로컬 요청. 대부분은 거절되거나 한도에 걸린다 | 한도의 10배. 전략 폭주를 버틸 여유 |
| 활성 주문 수 상한 | 기본 500건(설정값). 거래소 한도의 절반 | 대조 조회 비용과 외부 주문 여유 |

배치 전송(한 요청에 여러 주문)은 v1에서 쓰지 않는다. 배치 내 부분 성공과 순서가 문서에 없기 때문이다.

## 1.5 지연과 신뢰성의 수용 기준

기준은 측정 조건과 함께 적는다. 측정 결과는 [performance/README.md](performance/README.md)에 있다.

| ID | 기준 | 측정 조건 | 근거 | 확인하는 주장 |
|---|---|---|---|---|
| A-LAT-1 | 로컬 요청 접수부터 영속 접수 응답까지 p99가 거래소 지연 중앙값(200 ms)의 10% 이하, 즉 20 ms 이하 | 초당 200건 open-loop 부하, 내구성 설정 그대로(fdatasync), 대상 저장 장치 명시 | OMS가 전체 지연에서 지배 요인이 아니어야 한다 | V-PERF-1 |
| A-LAT-2 | 같은 조건에서 응답 오류·시간 초과 0건 | 위와 같음 | 지연만 보고하지 않는다 | V-PERF-1 |
| A-CAP-1 | 초당 2000건 부하에서 큐·메모리가 상한을 넘지 않고, 넘치는 요청은 기록 없이 거절된다 | 큐 상한과 수용 한도를 기본값 그대로 | 과부하가 무한 대기로 바뀌지 않아야 한다 | V-PERF-2(기본 한도 실행), V-OVL-2 |
| A-DUR-1 | 응답을 받은 요청과 거래소로 나간 주문의 기록이 프로세스 강제 종료 후에도 남는다 | SIGKILL과 경계별 중단, 실제 파일 시스템. 전원 장애는 아니다 | 허용 데이터 손실 0 | V-COMMIT-2, V-COMMIT-4, V-BOOT-1 |
| A-REC-1 | 재시작 후 대조가 끝나기 전에는 신규 주문을 받지 않는다. 대조가 끝나면 장부가 거래소와 일치한다 | 가상 거래소, 무작위 종료 반복 | 복구의 정확성 | V-COMMIT-2, V-RECON-2, V-SIM-2 |
| A-REC-2 | 스냅샷 이후 기록 5만 건의 재생이 5초 이내 | 대상 호스트 | 수동 재시작으로 분 단위 복구 | V-PERF-3 |

성능 목표를 만족하면 추가 최적화를 중단한다(brief §7).

## 1.6 복구 요구의 구분

| 요구 | v1 | 조건과 한계 |
|---|---|---|
| 단일 노드 재시작 복구 | 구현, 검증 | 저널과 스냅샷이 온전할 때. 프로세스 강제 종료로 검증했다. 전원 장애는 검증하지 않았다 |
| 서버 장애 복구 | 절차만 제공. 연습하지 않았다 | 마지막 기록까지 있는 저널(디스크를 옮긴 경우)이면 그것으로 띄운다. 과거 시점의 사본뿐이면 그 사본으로 거래를 재개하지 않고 새 인스턴스로 시작해 포지션을 운영자가 장부에 넣는다([운영 절차](operations/runbook.md) §7.6). 과거 사본으로 재개하면 주문 번호가 다시 쓰인다(가정 A-12) |
| 자동 failover | 범위 밖 | 구 인스턴스의 전송을 막을 실제 수단이 없으면 같은 주문이 두 번 나갈 수 있다 |
| 재해 복구 | 범위 밖 | 거래소의 예약 취소 기능으로 열린 주문만 정리할 수 있다. 포지션은 남는다 |

허용 중단 시간: 수동 재시작 기준 분 단위. 그동안 거래소에 남은 주문은 체결될 수 있다.
허용 데이터 손실: 프로세스·OS 재시작에 대해 0. 저장 장치 유실에 대해서는 사본 주기만큼.

|---|---|---|
| 저널 세그먼트 | 무기한 보관. 64 MiB마다 회전 | 자동 삭제 없음. 정책은 사용자 결정 U-04 |

| 체결 중복 판별 키 | 체결 동기화 시점 기준 24시간 | 그보다 오래된 체결 통보는 재전달로 간주해 무시 |

## 1.8 배포 환경

단일 Linux 호스트, 단일 프로세스 `oms-node`. systemd 등 감독자가 재시작한다.
저널은 로컬 파일 시스템(ext4)에 둔다. tmpfs에 두면 내구성이 없다.
개발 호스트에서는 저장소, 빌드 출력, 측정용 저널을 모두 `/mnt/nvme`(970 EVO Plus 2TB)에 둔다. 측정 조건은 [performance/README.md](performance/README.md)에 적었다.
