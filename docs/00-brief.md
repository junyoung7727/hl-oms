# 프로젝트 지시문 (원문 보존)

수신: 2026-10-02. 이 문서는 프로젝트를 규정하는 지시문의 원문이다. 수정하지 않는다.
다른 문서는 절 번호(`brief §n`)로 이 문서를 참조한다.

2026-10-02에 확정한 네 가지 구조적 결정은 [01-scope.md](01-scope.md) §2에 기록한다.

---

너는 이 프로젝트의 설계·구현·검증을 책임지는 엔지니어다. Rust로 실제 운용 가능한 OMS를 개발하라. LMAX 아키텍처의 핵심 원칙을 적용하면서, 개발과 유지보수 비용 대비 효과가 좋은 최적화를 선택하라.

나는 엔지니어로서 결과물의 전체 구조, 주요 설계 선택의 이유, 중요한 내부 동작, 테스트가 뒷받침하는 범위와 한계를 이해하고 직접 검증해야 한다. 코드, 문서, 대시보드, 재현 가능한 검증 결과를 함께 제공하라.

내가 일반적인 엔지니어링 고려사항을 일일이 찾아서 지적해야 하는 상황을 줄여라. 공통적으로 검토해야 할 항목은 네가 먼저 조사하고 판단하되, 프로젝트 고유의 요구와 내 선택이 필요한 항목을 명확하게 남겨라.

**1. 목표와 운영 범위를 먼저 구체화하라.**

대상 거래소·브로커, 상품, 주문 유형, 계좌 범위, 정상·피크 요청량, 활성 주문 수, 지연 목표, 배포 환경, 허용 중단 시간, 허용 데이터 손실, 보관 기간을 정리하라.

OMS와 매칭 엔진의 범위를 구분하라. 단일 노드 재시작 복구, 서버 장애 시 복구, 자동 failover, 재해 복구를 서로 다른 요구사항으로 다뤄라.

미정 항목마다 합리적인 기본안, 그 근거, 잘못 가정했을 때의 영향, 나중에 변경하는 비용을 제시하라. 구조를 크게 바꾸는 질문부터 최대 5개씩 물어라. 가정으로 진행할 수 있는 조사·시뮬레이터·도메인 구현은 계속 진행하라.

성능과 신뢰성 목표는 측정 조건을 포함한 수용 기준으로 표현하라. 근거 없이 처리량이나 지연 수치를 정하지 마라.

**2. 구현 전에 ‘적용할 검토 기준과 고려사항 목록’을 작성하라.**

검토 기준을 다음 세 층으로 구성하라.

- 일반 소프트웨어: 품질, 보안, 신뢰성, 자원 관리, 운영, 변경과 유지보수.
- Rust·LMAX·OMS 특성: 소유권과 동시성, 결정적 실행, 주문 상태, 리스크, 영속화, 외부 전송과 복구.
- 프로젝트 특성: 대상 시장·브로커·상품, 성능 목표, 운영 인력, 비용, 배포 환경과 관련 의무.

공식 표준, 공식 프로토콜 문서, 라이브러리 문서와 실제 구현의 1차 자료를 우선 조사하라. 참조 후보로 ISO/IEC 25010, ISO/IEC/IEEE 42010, NIST SSDF, 웹/API에 해당하는 OWASP ASVS, LMAX 원문, 대상 거래소 문서 및 해당되는 FIX 명세 등을 검토하라.

각 자료의 역할을 구분하라. 품질 분류 모델, 아키텍처 기술 기준, 구현 의무, 보안 검증 요구, 권고 관행을 동일하게 취급하지 마라. 버전과 실제 접근한 범위를 기록하고, 원문 전체를 확인하지 못했으면 그 한계를 명시하라.

표준을 참고했다는 이유만으로 표준 준수나 인증을 주장하지 마라. 확인하지 않은 조항과 출처를 만들어내지 마라.

검토 항목에는 고유 ID를 부여하고 다음을 기록하라.

| 항목 | 기록할 내용 |
|---|---|
| 고려사항 | 무엇을 검토해야 하는가 |
| 필요성 | 놓치면 어떤 실패나 비용이 발생하는가 |
| 출처 | 표준·공식 문서·일반 관행·프로젝트 요구 중 어디서 왔는가 |
| 적용 판단 | 적용·비적용·조건부 적용과 그 이유 |
| 처리 방안 | 채택한 설계 또는 남은 결정 |
| 연결 | 설계 결정, 동작 계약, 코드, 검증 근거 |
| 미해결 사항 | 영향, 해소 방법, 해소할 단계 |

최소한 아래 영역을 검토하되, 이 목록 자체를 완전성의 증거로 삼지 말고 조사와 시나리오 분석으로 보완하라.

- 주문·체결·취소·정정과 식별자 수명, 거래일·세션 경계.
- 가격·수량·금액의 단위, 정밀도, 반올림, overflow.
- 리스크 검사와 예약, 해제, 체결 반영 및 데이터의 유효성.
- 상태 소유권, 순서, 원자성, 동시성, 취소와 종료.
- 중복 판별, 재전송, 순서 역전, 메시지 누락, 결과 불확실성.
- 영속화, 손상 감지, 재생, 스냅샷, 보관·삭제와 용량 관리.
- 연결 복구, 거래소 상태 대조, 가용성과 중복 실행 방지.
- 과부하, 큐·메모리·진행 요청·재시도의 상한과 공정성.
- 인증·권한·신뢰 경계, 비밀정보, 입력 검증, 감사와 의존성 관리.
- 시작·종료, 배포·롤백, 스키마·설정 변경, 관측과 장애 대응.
- 성능 측정, 시험 가능성, 유지보수성, 호환성과 변경 비용.

모든 항목을 구현하라는 뜻은 아니다. 적용 여부와 처리 이유가 빠짐없이 드러나야 한다.

**3. 중요한 설계마다 ‘왜 이 선택이 적절한가’를 기록하라.**

정합성, 데이터 유실, 외부 효과, 동시성, 보안, 가용성, 성능 또는 큰 변경 비용에 영향을 주는 결정에는 설계 결정 기록을 작성하라.

각 기록에는 다음을 포함하라.

1. 해결하려는 문제와 발생 가능한 실패.
2. 이 종류의 설계에서 일반적으로 만족해야 하는 성질.
3. 이번 프로젝트의 제약과 우선순위.
4. 반드시 만족해야 하는 조건과 선택적으로 개선할 조건.
5. 실제로 채택 가능한 대안과 가장 단순한 대안.
6. 대안별 정합성, 지연, 처리량, 복구, 복잡성, 개발·운영 비용 비교.
7. 선택한 안이 필수 조건을 만족하는 이유.
8. 포기한 장점, 남은 위험, 의존하는 가정.
9. 선택을 뒷받침하는 자료·실험·시험.
10. 요구나 측정 결과가 어떻게 바뀌면 재검토할 것인지.

비교를 위해 비현실적인 대안을 만들지 마라. 측정값·예상값·정성 판단을 구분하고, 근거 없는 점수표를 사용하지 마라.

필수 정합성이나 안전 조건을 성능 점수로 상쇄하지 마라. 근거가 부족한 결정은 작은 실험으로 불확실성을 줄여라.

LMAX 채택 자체도 설명하라. 어떤 원칙을 따르며 무엇을 단순화했는지, 그 차이가 어떤 보장을 바꾸는지 밝혀라.

**4. 핵심 아키텍처는 소유권과 동작 경계가 명확해야 한다.**

도메인 상태는 단일 writer가 소유하는 구조를 기본안으로 삼아라. 코어는 결정적으로 실행되며 네트워크, 파일, DB, 실제 시계와 난수에 직접 접근하지 않도록 하라. 판단에 영향을 주는 시간·설정·외부 정보는 재생 가능한 입력으로 다뤄라.

도메인 코어, 실행 계층, 영속화·복구, 거래소 어댑터, 조회·운영의 책임을 분리하라. 각 상태의 권위 있는 소유자와 조회용 복제본을 구분하라.

리스크 검사와 예약은 일관된 상태 전이 안에서 처리하라. 지연될 수 있는 조회용 상태를 권위 있는 주문 판단에 사용하지 마라.

초기에는 단일 배포 단위와 명확한 모듈 경계를 우선 검토하라. 서비스·crate·trait 분리는 실제 독립성, 교체 필요, 시험 경계 또는 운영상 이유로 정당화하라.

Disruptor나 lock-free 자료구조를 사용하는 사실만으로 LMAX 구조 또는 성능을 달성했다고 주장하지 마라.

**5. 설명의 최소 단위는 ‘중요한 상태 전이와 경계’로 정하라.**

각 단위에서 입력과 전제, 읽는 상태, 상태 소유자, 변경 내용, 확정 시점, 외부 효과, 자원 상한을 설명하라.

중복 입력, 순서 변경, 타임아웃, task 취소, 프로세스 중단, 재실행에 따라 동작이 어떻게 달라지는지 기술하라.

하나의 단계 내부에서 중단 위치에 따라 남는 상태나 복구 방법이 달라지면 그 경계를 더 세분화하라.

반대로 내부 구현을 교체해도 결과·실패 의미·자원 상한이 유지되고 그 계약을 신뢰할 근거가 있으면, 사소한 내부 구현은 간략히 설명해도 된다. 설명을 생략한 라이브러리와 시스템 계층에서는 의존하는 보장과 가정을 명시하라.

직접 작성한 unsafe, atomic, lock-free 코드처럼 정확성이 내부 구현에 의존하는 부분은 안전성 조건과 동기화 근거까지 설명하라.

내가 중요한 지점에서 다음 질문에 답할 수 있어야 한다.

- 여기서 중단되면 무엇이 남는가?
- 같은 입력이 두 번 오면 어떻게 되는가?
- 두 입력의 순서가 바뀌면 어떻게 되는가?
- 누가 언제 이 변경을 볼 수 있는가?
- 시스템은 외부 처리 결과를 실제로 알고 있는가?
- 복구 후 무엇을 다시 실행하며 무엇을 반복하면 안 되는가?

**6. 주문 정합성과 영속화·외부 전송의 관계를 명시적으로 설계하라.**

접수, 영속 접수, 거래소 접수, 체결을 구분하라. 부분 체결, 취소·정정 중 체결, 중복·지연 통보, 순서 역전, 연결 복구, 결과를 모르는 주문을 처리하라. 대상 시장의 체결 정정·취소 등의 지원 범위도 정하라.

멱등성 키와 유효 범위, 동일 키의 다른 요청 처리, 중복 판별 기록의 보존·삭제, 재시작 후 동작을 명시하라.

저널에 무엇을 기록하는지 선택하고, 상태와 전송 의도를 어떻게 복원하는지 설명하라. 여러 기록을 사용하면 원자성과 복구 규칙을 정의하라.

기록, 내구성 확보, 상태 적용, 클라이언트 응답, 거래소 전송의 순서를 명시하고 각 경계에서의 장애 결과를 표로 작성하라.

재생 자체가 외부 주문을 다시 전송하지 않도록 하라. 미확정 전송의 재개는 거래소의 식별자·조회·중복 처리 계약에 근거한 별도 복구 정책으로 처리하라. 외부 지원과 증거 없이 end-to-end exactly-once를 주장하지 마라.

스냅샷 일관성, 저널 순번과 손상, 불완전한 마지막 기록, 중간 손상, 포맷·코드·설정 버전의 재생 호환성을 다뤄라.

과부하와 저장 실패 시 체결 통보를 조용히 버리지 마라. 신규 주문 차단, 취소 처리, 대조와 복구의 허용 조건을 구체적으로 정의하라.

**7. 최적화에는 적용 근거와 중단 조건을 둬라.**

기본적으로 크기가 제한된 큐, I/O 분리, 불필요한 복사·직렬화 감소, 적절한 용량 확보를 적용하라. 큐 밖에서 대기 task나 진행 요청이 무한히 쌓이지 않게 하라.

배치 크기, 버퍼 재사용, 자료구조, 전용 ring buffer, CPU affinity는 프로파일과 실험으로 결정하라. 자체 lock-free, 성능 목적의 unsafe, 커스텀 allocator, busy-spin, kernel bypass, 복잡한 NUMA 튜닝은 초기 기본값으로 사용하지 마라.

각 최적화에 병목 근거, 변경 원리, 전후 측정, 복잡성 증가와 불리한 조건을 기록하라. 합의한 목표를 만족하면 추가 최적화를 중단하라.

내구성·정합성·관측 기능을 약화한 성능을 동일 조건의 개선으로 보고하지 마라.

**8. 검증은 주장과 적용 범위를 함께 제공하라.**

요구사항과 동작 계약에서 검증 항목을 도출하라. 기대 결과를 구현 코드에서 그대로 복제하지 말고, 공식 명세·업무 예제·불변조건·독립적인 참조 모델 등에 근거하라.

위험에 맞게 예제 시험, property-based test, 참조 모델 비교, 동시성 검사, 실제 구성요소를 연결한 통합 시험, 장애 주입, 실제 거래소 검증을 선택하라. 모든 도구를 의례적으로 도입하지 마라.

각 검증에는 다음을 기록하라.

- 확인하려는 성질과 그 중요성.
- 전제, 입력·상태·순서의 범위, 탐색 한도.
- 실제 구성요소와 mock 또는 시뮬레이션의 경계.
- 장애 종류와 주입 지점.
- 판정 기준과 그 기준의 근거.
- 코드·의존성·설정·환경 버전.
- 명령, seed, 입력과 결과 등 재현 정보.
- 결과가 뒷받침하는 주장과 확인하지 않은 범위.

프로세스 강제 종료로 전원 장애나 디스크 유실까지 검증했다고 주장하지 마라. 시뮬레이터 통과를 실제 거래소 동작 검증으로 표시하지 마라.

핵심 보호 로직을 일부러 제거하거나 깨뜨렸을 때 관련 시험이 실패하는지도 선별적으로 확인하라.

정상 시나리오뿐 아니라 중복·타임아웃·재시작 등이 결합하는 중요한 상황을 검토하라. 시험하지 않은 조합과 그 선정 이유를 남겨라.

성능 측정에는 하드웨어, 빌드·내구성 설정, 데이터 규모, 부하 구성, 실행 시간과 표본 수를 포함하라. 코어 처리, 큐 대기, 영속화, 로컬 응답, 외부 응답을 구분하고 지연 분포와 오류·거절·타임아웃을 함께 보고하라. 부하 생성기의 지연과 coordinated omission도 점검하라.

**9. 문서는 선택 이유와 실제 동작을 연결해 탐색할 수 있어야 한다.**

문서의 기본 탐색 순서는 전체 구조, 주요 설계 결정, 정상·장애 시나리오, 내부 동작 계약, 검증 근거로 구성하라.

프로세스·스레드·큐·저장소·외부 연결과 상태 소유권을 표시하라. 정적인 구성도와 실제 실행 순서를 구분하라.

각 중요한 설계에 대해 내가 다음 흐름을 따라갈 수 있어야 한다.

“일반적으로 고려해야 하는 문제 → 이번 프로젝트의 조건 → 비교한 대안 → 선택 이유 → 실제 동작 → 구현 위치 → 검증 근거 → 남은 한계.”

단순 함수의 장황한 설명은 줄이고, 정합성과 복구에 영향을 주는 경계에 설명을 집중하라. 약어와 전문용어는 처음 등장할 때 의미를 설명하라.

문서와 구현의 기준 버전을 연결하고, 변경 시 영향을 받은 계약·시나리오·시험·관측 항목을 함께 갱신하라.

**10. 대시보드는 설계와 실행, 검증 근거를 대조할 수 있어야 한다.**

다음 기능을 제공하라.

| 화면 | 반드시 확인할 수 있는 것 |
|---|---|
| 고려사항·설계 결정 | 적용 기준, 항목별 처리 상태, 대안과 선택 이유, 미해결 사항 |
| 동작 탐색 | 정상·오류 경로, 상태 전이, 중요한 경계와 관련 계약 |
| 주문 실행 추적 | 특정 주문의 입력·판단·상태 변경·영속화·전송·응답 |
| 검증 현황 | 주장별 시험, 조건, 실제 결과, 버전, 재현 방법, 미검증 범위 |
| 운영 상태 | 큐와 처리 지연, 영속화, 미확정 주문, 상태 대조 불일치, 거래 제한 상태 |

중요한 이벤트에서 관련 계약·설계 결정·코드·시험으로 이동할 수 있게 하라.

기대 상태, 실제 관측, 추론, 미확인을 구분하라. 데이터 출처, 기준 시점, 수집 지연과 버전을 표시하라. 로그 부재만으로 동작하지 않았다고 판단하지 마라. 시각만으로 프로세스 간 인과관계를 확정하지 마라.

설명용 예시, 시뮬레이터 실행, 실제 시스템 실행을 명확히 표시하라. 연결하지 않은 기능이나 실행하지 않은 시험에 정상·통과 상태를 표시하지 마라.

기본 관측 화면은 읽기 전용으로 두고, 운영 변경과 장애 주입은 실행 대상·권한·감사 경계를 분리하라. 관측이 처리 경로에 주는 비용과 샘플링으로 놓칠 수 있는 범위도 설명하라.

**11. ‘검토 완료·구현 완료·검증 완료’를 별도로 관리하라.**

체크리스트에 표시했다는 사실을 구현이나 검증의 증거로 취급하지 마라. 항목마다 적용 판단, 설계 상태, 구현 상태, 검증 상태를 구분하라.

정한 기준 전체를 모수로 유지하고, 미검토·비적용·보류·미구현·미검증 항목을 숨기지 마라. 비적용에는 이유를, 보류에는 영향과 재개 조건을 남겨라.

별도의 검토 단계에서 선택한 설계가 틀릴 수 있는 반례, 빠진 경계, 항목 간 충돌, 의존 가정의 실패를 찾아라. 개별 구성요소의 시험 통과가 전체 흐름의 보장을 성립시키는지도 확인하라.

최종적으로 다음 네 종류의 결과를 제시하라.

- 채택한 기준에서 검토와 처리가 끝난 공통 사항.
- 구현됐고 명시된 조건에서 검증된 보장.
- 외부 시스템·라이브러리·운영 환경에 의존하는 가정.
- 남은 공통 미해결 사항과 프로젝트 고유의 판단 사항.

일반적인 검토 공백이 남아 있으면 “커스텀 고려사항만 남았다”고 보고하지 마라. 완료 주장은 명시한 기준·범위·버전 안에서만 하라.

내가 결정해야 하는 항목에는 결정 이유, 추천안, 대안, 영향, 결정을 미룰 수 있는 시점을 함께 제시하라. 일반적인 엔지니어링 선택까지 모두 나에게 떠넘기지 마라.

**12. 작은 실행 가능한 단위로 구현과 증거를 함께 완성하라.**

다음 순서로 진행하라.

1. 범위·가정·검토 기준, 핵심 불변조건과 중요한 설계 결정.
2. 시뮬레이터에서 신규 주문·부분 체결·취소·기록·복구가 연결된 최소 수직 구현.
3. 중복·불확실한 전송·장애·재시작·과부하 처리.
4. 실제 어댑터와 대상 프로토콜 검증.
5. 운영 절차, 문서와 대시보드의 연결.
6. 실제 조건의 성능 검증과 필요한 최적화.
7. 기준 대비 누락·충돌·잔여 위험 검토.

문서 작업만 계속하며 실행 검증을 미루지 마라. 각 단계에서 실행 코드, 갱신된 계약과 설계 근거, 실제 검증 결과, 남은 항목을 제공하라. 자동 생성 가능한 연결과 표는 자동화하되 사람이 읽고 판단할 수 있어야 한다.

최종 결과물에는 재현 가능한 빌드·실행 방법, acceptance suite, 검토 항목 대응표, 설계 결정, 동작 문서, 대시보드, 성능 결과, 배포·복구·업그레이드 절차를 포함하라.

첫 응답에서는 프로젝트 이해, 중요한 미정 사항과 추천 가정, 적용할 검토 기준, 우선 결정할 설계, 첫 수직 구현의 완료 조건을 제시하라. 기존 저장소가 있다면 먼저 실제 구조와 실행 상태를 확인하라.

최종적인 성공 조건은 내가 중요한 설계와 실행 지점을 선택했을 때 “왜 이렇게 만들었는가, 어떤 조건에서 맞는가, 어떻게 동작하는가, 실패하면 무엇이 남는가, 무엇으로 확인했는가, 아직 무엇을 모르는가”를 문서와 실제 근거에서 확인할 수 있는 것이다.
