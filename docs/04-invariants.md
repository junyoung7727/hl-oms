# 4. 핵심 불변조건

불변조건은 "어떤 입력 순서에서도 유지돼야 하는 성질"이다. 시험의 판정 기준은 여기서 나온다.
각 조건에는 성립 범위를 적는다. 범위 밖에서 깨지는 것은 결함이 아니라 가정의 위반이다.

기호: 한 종목·한 장부에서 `q`는 기장된 부호 있는 포지션, `B`는 아직 기장되지 않은 매수 가능량의 합,
`S`는 매도 가능량의 합이다. 장부는 계좌 장부와 전략별 장부가 있다.

## 4.1 구조 불변조건 (항상 성립)

`Core::check_invariants`가 검사한다. 시뮬레이션은 모든 입력 뒤에, 오프라인 검증은 모든 기록 뒤에 검사한다.

| ID | 조건 | 깨지면 |
|---|---|---|
| I-RES | 주문의 예약 수량은 상태가 정한 값과 같다. 미종결이면 `수량 − 기장 체결`, 종결 대기면 `거래소 최종 누적 − 기장 체결`(0 미만은 0), 종결이면 0 | 한도 여유가 실제와 달라진다 |
| I-BOOK | 장부의 `B`, `S`, 열린 주문 수는 그 장부에 속한 주문들의 예약·미종결 수와 같다 | 예약이 새거나 남는다 |
| I-ATTR | 종목별 계좌 포지션 = 전략 포지션의 합 + 미귀속 포지션 | 귀속이 맞지 않는다 |
| I-KEY | (전략, 클라이언트 주문 ID)마다 주문은 최대 하나이고 색인이 그 주문을 가리킨다 | 같은 요청이 두 주문이 된다 |
| I-FILL | 한 체결 키는 한 번만 기장된다 | 포지션이 이중으로 움직인다 |
| I-PHASE | 종결 주문은 종결 기록을 갖고 열린 주문 색인에 없다. 결과 불명 표시는 전송 대기 상태에만 있다 | 차단 사유 계산이 틀어진다 |

## 4.2 수량 한도 (조건부)

```text
I-QTY:  모든 종목, 계좌와 각 전략에 대해   L ≤ q − S   그리고   q + B ≤ U
```

성립 조건: 모든 주문이 이 OMS를 거친다. 한도를 현재 노출 아래로 낮추지 않았다. 불일치가 제기된 적이 없다.

논증: 수용은 `q + B + n ≤ U`(매수)를 검사한 뒤 같은 입력 안에서 `B`에 `n`을 더한다.
체결 기장은 `(q, B) → (q + f, B − f)`로 상단을 바꾸지 않는다. 예약 해제는 `B`를 줄일 뿐이다.
따라서 각 전이가 조건을 보존한다. 출처는 `../docs/research/oms-three-guarantees.md`(상위 디렉터리) §2다.

`Core::check_position_bounds`가 검사한다.

## 4.3 거래소 실제와의 연결 (조건부)

```text
I-BRIDGE:  거래소의 실제 계좌 포지션 ∈ [q − S, q + B]
```

성립 조건: I-QTY의 조건에 더해, 종결로 판정한 주문에는 더 이상 체결이 생기지 않는다.
마지막 조건은 종결 판정 규칙([C-TERM](contracts/order-lifecycle.md), [C-DOUBT](contracts/order-lifecycle.md))이 보장하며,
그 규칙은 거래소 계약에 의존한다(가정 A-01, A-02).

이 조건이 OMS 내부 상태와 실제 세계를 잇는다. 시뮬레이션은 가상 거래소의 실제 포지션으로 매 단계 검사한다.
운영에서는 포지션 대조가 같은 식으로 검사한다([C-RECON](contracts/reconciliation.md)).

## 4.4 전송과 기록 (항상 성립)

| ID | 조건 | 근거가 되는 구조 |
|---|---|---|
| I-WAL | 응답·전송 명령·읽기 모델 변경은 그것을 만든 기록이 내구화된 뒤에만 나간다 | 커밋 단계의 순서([C-COMMIT](contracts/commit.md)) |
| I-ONCE | 한 주문의 신규 전송 명령은 프로세스 생애 전체에서 최대 한 번 나온다 | 명령은 `OrderAccepted` 이벤트에서만 파생되고, 재생은 명령을 만들지 않는다 |
| I-REPLAY | 저널의 이벤트를 순서대로 적용한 상태는 그 이벤트를 만든 살아 있는 상태와 같다 | 살아 있는 처리와 재생이 같은 `Core::apply`를 쓴다 |
| I-DET | 기록된 입력을 이전 상태에서 다시 판단하면 기록된 이벤트가 그대로 나온다 | 코어에 시계·난수·I/O가 없다 |

I-DET는 복구에 필요하지 않다. 복구는 이벤트만 적용한다. I-DET는 같은 빌드에서 판단이 재현됨을 보여 주는 검증 수단이다.

## 4.5 진행성 (조건부)

안전 조건만으로는 "모든 주문을 거절하는 시스템"도 통과한다. 그래서 다음을 따로 요구한다.

| ID | 조건 | 성립 조건 |
|---|---|---|
| I-LIVE-1 | 허용되는 요청은 수용된다. 거절에는 사유 코드가 붙는다 | 차단 사유가 없을 때 |
| I-LIVE-2 | 결과 불명 주문은 결국 해소된다 | 거래소 조회가 결국 응답하고, 거래소가 만료 뒤 주문을 놓지 않을 때 |
| I-LIVE-3 | 장애가 멈추면 장부가 거래소와 일치하고 차단 사유가 사라진다 | 외부 활동이 없을 때 |

시뮬레이션의 최종 검사가 I-LIVE-2, I-LIVE-3을 확인한다. 통신이 무기한 끊기면 보장하지 않는다.

## 4.6 의존하는 가정

불변조건이 기대는 외부 조건이다. 전체 목록은 [generated/assumptions.md](generated/assumptions.md)에 있다.

| ID | 가정 | 깨졌을 때 | 탐지 수단 |
|---|---|---|---|
| A-01 | 거래소는 `expiresAfter`가 지난 요청을 놓지 않는다 | 닫은 주문이 뒤늦게 생긴다 | 전송 응답·상태 통보·열린 주문 대조의 OpenAfterClose, 체결의 FillAfterClose, 포지션 대조 |
| A-02 | 로컬 시계와 거래소 시계의 차이, 조회 지연의 합이 부재 판정 여유보다 작다 | 위와 같다 | 위와 같다 |
| A-03 | 게이트웨이가 "체결 동기화 완료"를 알릴 때 그 시각까지의 체결을 모두 전달했다 | 체결을 빠뜨리고 주문을 닫는다 | FillAfterClose 불일치, 포지션 대조 |
| A-04 | 계좌에 이 OMS 밖의 주문이 없다 | I-QTY, I-BRIDGE가 깨진다 | ForeignOrder, ExternalFill, PositionOutOfRange 불일치 |
| A-05 | `fdatasync`가 성공하면 데이터가 장치에 내구화됐다 | 응답한 주문의 기록이 전원 장애에서 사라진다 | 재시작 후 OrphanOrder. 예방은 못 한다 |
| A-06 | 같은 데이터 디렉터리를 쓰는 프로세스는 하나다 | 두 writer가 같은 주문 ID를 쓴다 | 디렉터리 잠금이 같은 호스트에서는 막는다. 다른 호스트의 사본은 막지 못한다 |
| A-12 | 거래를 이어 가는 저널에는 그 인스턴스가 낸 모든 주문이 들어 있다 | 주문 번호와 거래소로 보내는 ID가 다시 쓰인다 | 사본 이후의 주문이 OrphanOrder로 드러난다. 그것을 확인 처리하고 재개하면 탐지되지 않는다 |
| A-13 | 조회 응답은 조회를 보낸 시각보다 오래된 상태가 아니다 | 거짓 불일치로 거래가 막힌다 | 불일치 자체 |

A-01, A-02를 깨뜨리면 주문·포지션에 관한 검사가 실제로 깨진다는 것을 시뮬레이션의 두 반례 시험이 보여 준다
(`absence_rule_depends_on_venue_side_expiry`, `absence_rule_depends_on_the_clock_margin`). 두 시험은 위반이 어느 속성으로 잡혔는지도 확인한다:
I-BRIDGE나 포지션 한도, 또는 끝 검사의 주문·체결·포지션 일치 가운데 하나여야 하고, 무관한 속성으로 실패하면 시험이 실패한다.
