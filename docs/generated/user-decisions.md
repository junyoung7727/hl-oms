# 사용자 결정이 필요한 항목

> 자동 생성 문서다. 고치려면 `registry/*.toml`을 고치고 `cargo run -p xtask -- docs`를 실행한다.
> 소스 다이제스트 `bc7c58f382a855a8`, 검증 결과의 다이제스트 `762a4acf55af90fb`.

## U-01 testnet 실주문 검증

- 결정이 필요한 이유: Hyperliquid 게이트웨이의 주문·취소·체결·만료 경로는 실제 거래소에서 한 번도 실행되지 않았다. 문서가 비워 둔 동작 35건이 실험 목록에 있다. 간격 검토에서 나온 결함 20건 가운데 6건이 이 게이트웨이였다
- 추천안: testnet 계정의 agent 지갑 키로 실주문 실험을 허가한다. 실험은 최소 금액 주문으로 한다
- 대안: 허가하지 않고 가상 거래소 검증만으로 둔다(주문 경로는 미검증으로 남는다) / 사용자가 직접 실험 절차를 실행한다
- 영향: 허가 전까지 mainnet 운용은 권하지 않는다. 그리고 최상위 오류 응답의 뜻을 확인하기 전에는 거래소가 액션을 거부할 때마다 그 주문이 만료 + 여유까지 결과 불명으로 남아 계좌 전체의 신규 주문을 막는다(안전한 쪽으로 잡은 기본값이다)
- 미룰 수 있는 시점: mainnet 운용 전까지 미룰 수 있다. 그 전에는 반드시 필요하다

## U-02 계좌 담보·증거금 기반 금액 한도 (기존 D1)

- 결정이 필요한 이유: 현재는 수량 한도만 있다. 증거금 부족이나 청산 위험을 OMS가 보지 않는다
- 추천안: 결정됨(2026-11-15, ADR-018): 계좌 레버리지 한도 2배(미체결 주문 포함), 일 손실 5 %와 유지증거금 여유 0.25 %p에서 감소 전용 상태, 해제는 운영자만. 계좌 가치는 거래소 조회를 입력으로 받는다. 세부는 계약 C-MARGIN
- 대안: 수량 한도만 유지하고 거래소의 증거금 거부에 맡긴다 / 모든 잠재 체결 조합을 고려하는 공동 증거금 계산 / 처음 추천안: 주문 금액 ÷ 정책 레버리지의 합이 가용 담보 이하인 gross 모형
- 영향: 코어에 입력과 검사가 추가된다. 양방향 호가 전략의 자본 효율이 낮아진다. 일반 주문은 신선한 증거금 보고가 있어야 받는다
- 미룰 수 있는 시점: 결정됨. 구현됨(2026-11-16, 통합 브랜치 margin-rules, 티켓은 .scratch/margin-rules/issues/). 실제 거래소에서는 확인하지 않았다: testnet 예행과 T1~T11 확인은 U-01의 승인 뒤, mainnet 전

## U-03 긴급 시장가 매수 정책 (기존 D2)

- 결정이 필요한 이유: 기존 문서는 추정 부담 + 버퍼 예약과 계좌당 진행 중 1건을 정했다. Hyperliquid의 시장가는 상한 가격의 IOC라 금액 상한이 수량 × 상한 가격으로 정해진다
- 추천안: 별도 긴급 경로를 만들지 않는다. 전략이 상한 가격을 정한 IOC를 보내고, 가격대 검사(price_band_bps)로 상한을 묶는다. 빈도 제한이 필요하면 전략별 한도로 추가한다
- 대안: 기존 정책 그대로 구현(긴급 사유 분류, 계좌당 1건, 버퍼 수치) / 시장가 성격의 주문을 아예 금지
- 영향: 기존 문서의 §3 정책이 이 OMS에서는 다른 형태가 된다
- 미룰 수 있는 시점: 긴급 진입이 필요한 전략을 붙이기 전

## U-04 저널 보관 기간과 삭제

- 결정이 필요한 이유: 저널은 자동으로 지워지지 않는다. 주문 하나가 약 1.4 KiB를 남기므로(측정), 거래소 한도인 초당 20건을 하루 내내 채우면 약 2.5 GB다(계산). 실제는 전략의 주문 빈도에 달렸다
- 추천안: 스냅샷 이전 세그먼트를 압축해 다른 디스크로 옮기고 원본은 30일 뒤 삭제한다. 삭제 전 `oms-node verify`로 검증한다
- 대안: 무기한 보관 / 스냅샷 이전 세그먼트를 즉시 삭제
- 영향: 삭제하면 그 구간은 `verify --re-decide`와 전체 재생을 할 수 없다. 세무·감사상 보관 의무가 있으면 그 기간을 따른다
- 미룰 수 있는 시점: 디스크 여유가 기준(1 GiB)에 가까워지기 전

## U-05 OMS가 멈췄을 때 거래소에 남은 주문

- 결정이 필요한 이유: 저장 실패나 프로세스 사망 뒤에도 주문은 거래소에 남아 체결된다
- 추천안: 거래소의 예약 취소를 켠다(`schedule_cancel_secs = 60`). 60초 동안 갱신이 없으면 거래소가 모든 주문을 취소한다. 하루 10회 발동 제한이 있으므로 재시작이 잦은 시험 환경에서는 끈다
- 대안: 끈 채로 둔다(주문이 남는다. 지금의 기본) / 저장 실패 시 저널 없이 전체 취소를 시도한다(기록 없는 외부 효과라 구현하지 않았다)
- 영향: 켜면 60초 이상 멈출 때마다 호가가 사라진다. 포지션은 청산되지 않는다
- 미룰 수 있는 시점: 무인 운용 전

## U-06 재시작 뒤 거래 재개 방식

- 결정이 필요한 이유: 지금은 대조가 깨끗하면 자동으로 재개한다
- 추천안: testnet에서는 자동 재개. mainnet 초기에는 시작 직후 운영자 중지를 걸어 두고 상태를 확인한 뒤 재개한다(운영 절차로 가능하다)
- 대안: 항상 자동 재개 / 항상 운영자 승인 뒤 재개(설정 추가 필요)
- 영향: 승인을 요구하면 야간 재시작에서 거래가 멈춘다
- 미룰 수 있는 시점: mainnet 운용 전

## U-07 전략별 손익·수수료·funding 귀속 (기존 D4)

- 결정이 필요한 이유: 지금 장부는 전략별 수량 포지션과 직접 수수료 합까지만 있다
- 추천안: OMS 밖의 별도 원장으로 만든다. OMS의 저널(체결 기록)을 입력으로 삼는다. 주문 판단 경로에 넣지 않는다
- 대안: OMS 코어에 평균 단가와 실현 손익을 추가 / 거래소의 계좌 손익만 사용
- 영향: 전략 성과 판단은 그 원장이 생길 때까지 이 시스템으로 할 수 없다
- 미룰 수 있는 시점: 전략 성과 평가가 필요할 때

## U-08 수동 거래와 다른 프로그램의 허용

- 결정이 필요한 이유: 지금은 외부 주문·체결을 발견하면 운영자가 확인할 때까지 신규 주문을 막는다
- 추천안: 이 계좌에서는 수동 거래를 하지 않는다. 필요하면 서브계정을 나눈다
- 대안: 외부 주문을 '수동' 장부로 받아들이고 한도에 포함한다(코어 변경) / 외부 활동을 경고만 하고 계속 거래한다(수량 한도가 성립하지 않는다)
- 영향: 기존 Go 프로그램과 같은 계좌에서 동시에 돌릴 수 없다
- 미룰 수 있는 시점: 운용 방식 확정 전

## U-10 버전 관리 저장소

- 결정이 필요한 이유: 이 디렉터리는 git 저장소가 아니다. 지금은 소스 다이제스트로 문서와 코드를 연결한다. 요구 R01~R15와 일부 시험 기준은 상위 디렉터리의 문서(docs/architecture/FIA-OMS-model.md 등)에 있어, 이 디렉터리만 독립 저장소로 만들면 그 참조가 끊긴다
- 추천안: `OrderManagementSystem/`에서 git을 초기화하고 이번 상태를 첫 커밋으로 남긴다. 요청하시면 진행한다

- 영향: 변경 이력과 릴리스 태그가 없으면 '어떤 코드를 검증했는가'를 다이제스트로만 말할 수 있다

## U-13 기존 Go 구현과의 관계

- 결정이 필요한 이유: `hyperliquid-trading`의 전략과 OMS가 같은 계좌를 대상으로 한다
- 추천안: 기존 전략을 이 OMS의 클라이언트로 옮긴다(로컬 소켓 프로토콜은 언어 중립). 기존 Go OMS는 참조용으로 남긴다
- 대안: 두 시스템을 서로 다른 서브계정에서 병행 / 기존 시스템 유지, 이 OMS는 새 전략에만
- 영향: 옮기려면 Go 클라이언트(수십 줄)가 필요하다. 작성하지 않았다
- 미룰 수 있는 시점: 첫 전략을 붙이기 전

## U-14 저널을 둘 저장 장치

- 결정이 필요한 이유: 응답 지연의 거의 전부가 저널의 fdatasync다. 저널을 970 EVO Plus 2TB로 옮긴 뒤 지연 기준을 만족했다(초당 200건 p99 9.1 ms). 거의 찬 980 500GB에서는 두 번 다 넘었다. 남은 문제는 내구성이다: 두 장치 모두 소비자용이고 전원 손실 보호가 없다(A-05)
- 추천안: testnet과 개발은 지금처럼 970 EVO Plus에서 한다. 실제 자금으로 운용할 때는 전원 손실 보호(PLP)가 있는 SSD를 저널 전용으로 쓰고, 그 장치에서 `xtask fsync-probe`와 `xtask perf`를 다시 돌린다
- 대안: 970 EVO Plus를 계속 쓴다(지연 기준은 만족. 전원 장애 때 마지막 응답의 기록이 사라질 수 있다는 위험을 받아들인다) / 세그먼트 사전 할당을 구현해 동기 쓰기를 더 줄인다(저널 형식과 복구 판정을 바꿔야 하고 전원 장애 시험 수단이 필요하다. ADR-012)
- 영향: 결정 전까지: 지연 기준은 지금 장치에서 만족한다. 전원 장애에서의 내구성은 확인되지 않은 채로 남는다
- 미룰 수 있는 시점: testnet 운용 중에는 미룰 수 있다. 실제 자금으로 운용하기 전에는 필요하다
