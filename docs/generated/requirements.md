## R03 — 시세·참조 입력의 유효성 및 적용 가능한 주문 가격 검사를 수행

- 출처: FIA24 §§1.3, 3.1
- 판정 경계: stale/gap/이상값·변경 주문
- 로직(코어+가짜): 주장 4: 통과 0 · **■ 미실행 4**
- 실제 Bybit: **■ 시험 없음**
- 확인하지 않은 범위: 참조 가격 없음, 15초 지남, 5 % 가격대만 시험했다. 신선도는 거래소 시각이 아니라 OMS 수신 시각으로 잰다. 0보다 큰 가격은 모두 받는다(이상값·급변 검사 없음). 가격대는 설정하지 않으면 없다. 시세 순번 끊김(gap)은 보지 않는다
- 시험이 없는 규칙:
  - md-feed는 모든 프레임에 recv_ns를 달고, 공백 뒤에는 재구독·재연결·REST 스냅샷과 재생으로 호가창을 다시 맞추며, 자정에는 겹친 연결로 전환하고, 전략과 레이크는 같은 호가창 코드를 쓴다

## R06 — 결과 불명·장애·중복 수신으로 책임이 사라지거나 늘지 않음

- 출처: FIA15 §4, FIA24 §4.1에서 강화
- 판정 경계: 전송 전후 crash·중복
- 로직(코어+가짜): 주장 16: 통과 0 · **■ 미실행 16**

- 시험이 없는 규칙:
  - 연결이 끊겨도 큐에 들어간 요청은 처리되고 그 응답만 버려진다
  - 가상 거래소 게이트웨이의 체결 키는 t<tid>다
  - 가상 거래소 게이트웨이는 상태 응답의 최종 누적 수량(cum)을 늘 채운다(가상 거래소의 값은 정확하다)
  - Bybit REST 클라이언트는 리디렉션을 따라가지 않는다(서명한 요청을 다시 보내지 않는다)
  - 접수 증거와 종결 통보가 한 입력에 함께 오면 OrderAcked를 먼저 기록해 주문이 Working을 거쳐 종결로 간다
  - 이미 접수된 주문에 전송 결과 Rejected나 NotSent가 오면 주문을 닫지 않고 StatusConflict를 제기한다
  - 같은 주문의 전송 결과가 두 번 오면 두 번째는 주문의 단계와 예약을 바꾸지 않는다
  - 종결 통보가 두 번 오면 최종 누적이 같을 때 무시하고, 처음에 몰랐던 최종 누적은 갱신하며, 다르면 StatusConflict를 제기한다
  - 접수된 적이 있는 종결된 주문에 대한 열림 상태 통보는 늦게 온 옛 통보로 보고 무시한다
  - 연결이 내려갈 때 진행 중이던 전송도 게이트웨이가 각각 결과를 돌려주고, 답을 잃은 전송은 Unknown이 되어 주문은 결과 불명이 된다
  - INSTANCE 파일이 없으면 디렉터리에 저널도 스냅샷도 없을 때만 새 인스턴스 ID를 만들고, 저널이나 스냅샷이 있으면 시작을 거부한다
  - 복구는 기록의 seq가 프레임 순번과 다르거나 기록의 at이 앞 기록보다 작으면 시작을 거부한다
  - 복구는 재생 뒤 구조 불변조건을 검사하고 어기면 시작을 거부한다
  - 복구를 두 번 돌리면 같은 상태가 되고 두 번째 복구에는 자를 꼬리가 없다
  - 스냅샷 쓰기는 별도 스레드가 하고, 요청은 크기 1의 큐로 넘기며 큐가 차 있으면 그 요청을 건너뛰고, 같은 순번의 스냅샷은 같은 이름의 파일로 바뀐다
  - 실행 중인 프로세스는 스냅샷을 읽지 않고 다음 시작의 복구만 읽는다
  - 중단된 스냅샷 쓰기는 복구 뒤 이어 쓰지 않고 다음 주기에 새로 쓴다
  - 스냅샷 쓰기가 실패하면 status의 journal.last_snapshot_error에 사유를 남기고 노드는 계속 동작한다
  - 재시작 뒤 구독 이벤트는 다시 보내지 않고, 전략은 재접속 뒤 조회로 맞춘다
  - flush가 오류를 내면 치명 표시(사유), 입력 큐 닫기, 그 배치의 응답 채널 닫기 순서로 처리해, 요청자가 확인되지 않음을 볼 때 노드는 이미 멈춘 것으로 보인다
  - 코어 판단 중 CoreFault가 나면 그 배치 전체를 커밋 단계로 넘기지 않고 치명 상태로 멈춘다
  - 이벤트를 만들지 않은 입력은 기록도 순번도 남기지 않고, 그 응답은 앞선 기록이 내구화된 뒤에 나간다
  - OrderAccepted를 적용할 때 order_id가 다음 ID와 다르거나 이미 있으면 CoreFault다

## R07 — halt 효과의 시점을 정의하고 취소·관측 경로 유지

- 출처: FIA24 §§1.4–1.6
- 판정 경계: 미전송 queue·늦은 fill
- 로직(코어+가짜): 주장 13: 통과 0 · **■ 미실행 13**
- 실제 Bybit: 주장 1: 통과 0 · **■ 미실행 1**
- 확인하지 않은 범위: 일괄 취소와 열린 주문 세기는 테스트넷에서 확인했지만(V-BYBIT-LIVE-3) 킬 루프 전체(래치, 회차, 30초 지켜보기)를 테스트넷에 붙여 돌리지 않았다.
- 시험이 없는 규칙:
  - 워처 실행은 틱마다, W5의 모든 상태에서, clock::Steady의 시각으로 W5에 답을 주고 poll과 fire를 그 순서로 부른다
  - 워처 실행은 시작 기계가 Done이나 StayUpNoRequests를 낼 때 W5를 arm하고, 그 전에는 계좌가 확인되지 않았으므로 무장하지 않는다
  - 워처는 watcher_w5_armed = armed()(Armed에서만 1), watcher_oms_silence_s = silent_ms(now) / 1000(Armed에서만), watcher_kill_halt_owed의 W5 몫 = halt_owed()로 내보낸다
  - 워처 킬의 최악 지연(판단, 기본값)은 마지막 정상 응답에서 첫 일괄 취소까지 10초 침묵 + 0.1초 틱 + 2초 K1 + 5초 K2 + 10초 K3 ≈ 27초이고(마커가 로컬이고 admin.sock이 되면 ≈ 10~14초), 첫 [WATCH P1]은 포지션 읽기 기한 13초를 더해 최악 ≈ 40초다
  - 워처 실행은 stop::Stopper를 reaped()가 참이 될 때까지 들고 poll한다(먼저 버리면 죽인 systemctl 클라이언트가 좀비로 남는다)
  - 워처의 Kill::steps().halt는 K2 단계 자신의 결과라 루프 동안 재시도가 래치해도 Some(false)로 남고, OMS가 래치되었는지는 outcome()과 halt_owed()가 말한다
  - 감소 전용 상태 진입이 한 입력에서 내는 규칙 취소는 열린 주문 상한(기본 500) 이하이고 노드의 명령 채널 용량(전송 중 상한 + 열린 주문 상한 + 64) 안에 있다
  - 같은 운영 명령이 다시 오면 halt는 매번 다시 기록되고(메모가 바뀐다), 중지되지 않은 범위의 resume, 이미 확인한 불일치의 ack_mismatch, 이미 닫힌 주문의 resolve_order는 기록 없이 거절한다
  - 취소 대상은 주문 ID 또는 (전략, 클라이언트 주문 ID)로 고른다
  - 종결된 주문의 취소 요청은 already_closed로 답하고 아무것도 기록하지 않는다
  - 거래 소켓에서 해석하지 못한 줄은 그 전략의 생존 증거로 세지 않는다
  - 연결 상실 규칙의 취소 요청은 전송 결과를 기다리는 주문에도 기록되고, 그 취소는 거래소가 주문을 접수했다고 알릴 때 나간다
  - 호스트 시계가 heartbeat_max_age_us보다 크게 앞으로 뛰면 마지막 하트비트가 오래돼 보여 게이트가 감시 안 됨이 되고(안전한 쪽), 다음 신선한 하트비트가 다시 연다
  - 치명 종료 뒤 종료 전 전송을 기다리는 동안 /api/status는 fatal에 치명 사유를 담아 답한다
  - [kill]이 없으면 킬 마커를 보지 않고 시작할 때 warn 한 줄을 남긴다
  - 워처 실행은 K1의 마커 쓰기를 spawn_blocking에 맡기고 그 결과를 메시지로 받아, 틱 안에서 파일을 다루지 않는다
  - 워처 실행은 K3의 systemctl을 띄우지 못하면 곧바로 Failed(<이유>)와 error 한 줄로 K3를 끝낸다
  - 워처 실행은 틱마다 루프의 다음 입력 전에 Inflight의 기한 끊기, 받은 답 넘기기, Kill::poll의 순서로 돌고, 루프의 답이 기다리면 틱을 기다리지 않고 바로 돈다
  - 킬 동안에도 워처의 시작 단계(OMS 기다림, 재생)와 IP 재확인은 그대로 돈다

## R11 — 독립 근거와 대사하고 차이·정정을 감사 가능하게 처리

- 출처: FIA24 §§4.1, 4.3
- 판정 경계: 누락·외부 주문·bust
- 로직(코어+가짜): 주장 9: 통과 0 · **■ 미실행 9**
- 실제 Bybit: 주장 1: 통과 0 · **■ 미실행 1**
- 확인하지 않은 범위: 체결 정정·취소(bust)는 시험하지 않았다(Bybit의 BustTrade는 청산 인수이지 체결 취소가 아니다). 워처를 실제 OMS와 실제 Bybit에 붙여 돌린 적이 없다
- 시험이 없는 규칙:
  - 대조 입력(열린 주문·포지션 조회)은 포지션을 직접 바꾸지 않고 증거 표시와 불일치 목록만 바꾼다. 예외 하나: 거래소 변경 뒤의 포지션 응답은 PositionAdjusted로 장부를 맞춘다(V-VENUE-EXEC-1)
  - 워처의 요청 제한(10초 창에 60개)은 모든 Bybit 경로와 IP 반향을 합쳐 센다
  - 워처의 확인 횟수(2라운드)는 설정이 아니라 상수이고, 주기와 나이는 [intervals]와 [rules]가 설정으로 둔다
  - W1은 orderStatus가 New·PartiallyFilled·Untriggered인 행만 열린 주문으로 보고 다른 행은 버린다
  - W2는 숫자로 읽히지 않는 updatedTime을 없는 것으로 본다
  - 워처는 앞의 하트비트를 아직 보내는 중이면 새 하트비트를 쌓지 않고 버린다(debug 한 줄)
  - 검사가 모두 실패해도 하트비트는 가므로 OMS의 게이트는 마지막 성공 뒤 10초에서 10 + heartbeat_ms초(기본 10~15초) 사이에 닫힌다
  - 실행은 처음 재생 중에도 읽을 때마다 watcher_journal_seq를 쓴다
  - 처음 재생 중 래치 오류가 나면 실행은 엔진을 시작하고 엔진의 첫 라운드가 래치한다
  - W4에서 끝까지 읽은 훑기가 비교 전에 실패하면(상태, 저널, 기한) 다음 라운드는 같은 워터마크에서 새 훑기를 연다
  - W4는 문서화된 매개변수가 아닌 settleCoin=USDT 거름에 기대지 않고 답에 든 USDC 계약의 체결도 다른 행과 같이 분류하고 비교한다
  - 워처의 W4는 바뀐 행의 정체를 거래소의 방향과 수량(또는 종류와 부호 있는 수량, 형, 없는 필드 이름)으로 정하고, 가격이나 수수료만 바뀐 행은 같은 정체로 보아 비교하지 않는다
  - 대조기의 조회 채널 상한은 256이고, 차 있으면 그 회차의 조회는 내지 않고 다음 회차에 다시 낸다
  - 가상 거래소 게이트웨이는 체결 조회 응답의 venue_now − 1을 FillsSynced의 up_to로 쓴다
  - 전송 응답이나 상태 통보의 거래소 주문 ID가 이미 다른 주문의 것이면 그 ID를 받아들이지 않고 StatusConflict를 제기하며 주문의 상태를 바꾸지 않는다
  - 링크가 바뀐 뒤 도착한 Placed는 접수로 처리하되 현재 세션의 증거로 세지 않으므로 그 주문은 상태 조회로 다시 확인된다
  - 접수된 적이 있는 종결된 주문이 조회 시각이 종결 뒤인 열린 주문 목록에 있으면 OpenAfterClose를 제기한다
  - hold_set, hold_cleared, kill_loop_ended, kill_rearmed는 열린 주문, 체결, 포지션 집합을 바꾸지 않는다
  - 세션 번호가 지금 세션보다 크지 않은 연결 올라감 통보는 무시한다
  - 이미 내려가 있을 때 온 연결 내려감 통보는 무시한다

## R14 — 허용 요청을 처리하고 지원 부하에서 응답/관측 지연을 충족

- 판정 경계: 정상 처리·폭주·포화
- 로직(코어+가짜): 주장 3: 통과 0 · **■ 미실행 3**

- 시험이 없는 규칙:
  - 워처 요청 가드의 최악 경우(판단)는 10초에 W1 10 + W2 10 + W3 5 + W4 2훑기 × 10쪽 + IP 확인 2 = 47요청으로 60 이하다(W1·W2가 한 쪽, 곧 열린 주문 49개·포지션 199개 이하일 때)
  - 응답을 읽지 않는 클라이언트는 응답 버퍼가 차면 그 연결의 응답 전달만 멈추고 다른 연결과 코어는 영향을 받지 않는다
  - 코어 스레드는 배치마다 입력을 runtime.max_batch(기본 256)개까지 꺼내고 나머지는 다음 배치로 미루며, 커밋 스레드는 기다리던 배치를 입력 4096개에 이를 때까지 한 번의 쓰기와 flush로 묶는다
  - 커밋 단계에는 시간 초과가 없어 flush가 느리면 뒤의 입력이 기다린다
  - 연결당 응답 버퍼는 창 × 2 + 64(기본 128)이고, 가득 차면 응답 전달이 기다린다
  - 연결별 응답 채널의 용량은 창 크기 × 2 + 64이고, 차면 응답 전달이 기다린다
  - 큐 밖에서 무한히 쌓이는 대기 태스크는 없다: 요청마다 응답 대기 태스크가 하나이고 그 수는 연결별 창(세마포어)으로 묶인다
  - 차단 사유가 없으면 검사를 통과한 요청은 수용되고 거절에는 사유 코드가 붙는다는 진행성을 임의 순서의 실행에서 판정하는 시험이 없다
