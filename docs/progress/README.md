# 단계별 진행 기록

지시문 §12의 일곱 단계를 따랐다. 단계마다 구현한 범위, 검증한 것, 찾은 제약과 결함, 바뀐 가정을 적는다.
모두 2026-10-02 하루에 진행됐다. 장기 운용 경험에서 나온 내용은 없다.

## 1단계. 목표와 범위

- 사용자에게 구조에 영향을 주는 네 가지를 물었고 모두 추천안으로 확정됐다: Hyperliquid perp(testnet 먼저), 단일 노드 + 재시작 복구, 같은 호스트의 별도 프로세스 전략, 초~수백 ms 전략.
- 산출: [01-scope.md](../01-scope.md)(OMS와 매칭 엔진의 구분, 운영 범위, 요청량의 근거, 수용 기준 6건, 복구 요구 4단계, 미정 항목).
- 조사: Hyperliquid 프로토콜, 표준과 권고의 출처, LMAX·내구성·Rust 관련 1차 자료. 읽은 범위와 읽지 못한 범위를 [research/](../research/)에 적었다.
- 찾은 제약:
  - 공식 Rust SDK는 2025-10 이후 커밋이 없고 `expiresAfter`가 없다. 결과 불명 해소 정책이 그 필드에 기대므로 게이트웨이를 직접 구현하기로 했다.
  - Hyperliquid 문서가 침묵하는 동작이 35건 나왔다. 실주문으로만 확인할 수 있다.
  - 개발 호스트의 루트 디스크가 99% 차 있다. 빌드 산출물을 다른 디스크로 옮겼다.
  - 저장 장치의 동기 쓰기 시간: NVMe 중앙값 0.9 ms, HDD 47 ms. 응답 지연의 하한이 여기서 정해진다.

## 2단계. 가상 거래소에서의 수직 단면

- 구현: 코어(`oms-core`), 저널(`oms-journal`), 실행 계층과 로컬 API(`oms-node`, `oms-api`), 가상 거래소 프로세스(`simvenue`).
- 확인: 접수 → 부분 체결 → 취소 → 정상 종료 → 재시작 뒤 같은 상태(`e2e::vertical_slice_new_partial_fill_cancel_restart`).
- 측정에서 나온 결정: 저널 쓰기를 코어 스레드에서 떼어 커밋 스레드로 옮겼다. 초당 2000건까지는 두 배치가 비슷하고, 초당 8000건에서 인라인 배치는 요청의 3분의 2를 과부하로 거절했다([ADR-012](../adr/ADR-012-threads-crates.md)).

## 3단계. 중복·결과 불명·장애·재시작·과부하

- 구현: 멱등성 키, 결과 불명 처리, 체결 대기 목록, 대조기, 불일치와 운영자 확인, 큐 셋과 빈도 제한, 저장 공간 감시, flush 실패 시 정지.
- 결정적 시뮬레이션(`oms-sim`)을 만들었다. 손으로 쓴 시나리오가 모두 통과하던 상태에서 시뮬레이션이 결함 네 건을 찾았다([verification/simulation.md](../verification/simulation.md)).
- 프로세스 시험에서 고친 것: 시험의 기대가 틀렸던 것 두 건(응답 유실 때 스트림 통보가 먼저 주문을 확인해 준다, 설정 파일의 중복 키), 강제 종료 반복에서 열린 주문이 한도까지 차 버리는 시험 설계.
- 바뀐 가정:
  - 체결 동기화는 "조회한 시각까지"가 아니라 "조회 시각보다 충분히 과거까지"만 선언할 수 있다(A-02).
  - 체결 중복 판별은 주문의 수명보다 길어야 한다. 주문과 별도로 전역에 둔다.

## 4단계. 실제 거래소 어댑터

- 구현: Hyperliquid 게이트웨이. 서명(msgpack + EIP-712), 주문·취소·예약 취소, 조회 넷, 스트림 셋, 결과 분류, 요청 예산.
- 확인: Python SDK의 시험 벡터와 서명이 바이트 단위로 같다. testnet에 읽기 전용 조회와 스트림 구독이 된다.
- **확인하지 못한 것: 주문 경로 전체.** 실주문에는 사용자의 허가와 키가 필요하다(U-01).
- 실측에서 나온 것: testnet의 BTC 자산 번호는 mainnet과 다르다(3). 종목 메타를 시작할 때 읽어 설정과 대조하게 했다.

## 5단계. 운영 기능, 문서, 대시보드

- 구현: 읽기 전용 HTTP와 화면 다섯, `omsctl`, `oms-node verify`·`trace`, 등록부(`registry/`)와 문서 생성기.
- 문서: 설계 결정 17건, 계약 문서 9개, 시나리오, 운영 절차, 검증 문서.
- 화면은 자동 시험이 없다. 수동 확인 기록은 [verification/README.md](../verification/README.md) §6.

## 6단계. 성능 측정

- 부하 생성기는 open-loop다(정해진 시각에 보내고, 밀려도 기다린 시간을 지연에 포함한다).
- 결과: [performance/README.md](../performance/README.md). 수용 기준 넷을 모두 만족했다(970 EVO Plus 2TB, 초당 200건 p99 9.1 ms).
- 처음에는 저널을 거의 찬 500GB SSD에 두고 쟀고, 두 번 다 지연 기준을 넘었다(31.9 ms, 27.2 ms). 지연은 fdatasync의 꼬리가 거의 전부였다.
  첫 측정의 조건은 내가 흐렸다: 변이 점검의 작업 사본 2.7 GB가 그 디스크를 100%까지 채웠다.
  그 SSD에는 작업 출력을 쓰지 말라는 사용자의 요청에 따라 2026-10-05에 저장소 전체를 970 EVO Plus 2TB로 옮기고 다시 쟀다.
- 줄일 수 있는 길을 하나 실험으로 확인했다: 저널 파일을 미리 할당해 덮어쓰면 동기 쓰기가 970에서 1/3, 980에서 1/2로 준다. 구현하지는 않았다.
  복구의 손상 판정을 바꿔야 하고 그 변경은 전원 장애에서만 검증되는데 그 수단이 없다. 지금 장치에서는 기준을 이미 만족한다([ADR-012](../adr/ADR-012-threads-crates.md)).

## 7단계. 간격 검토

- 구현과 분리해, 구현 내용을 모르는 검토자 셋에게 각각 코어, 실행 계층·게이트웨이, 문서·주장을 반례 중심으로 검토하게 했다.
- 결과: 코어 10건, 실행 계층 10건의 결함이 재현 시험과 함께 나왔다. 돈이나 포지션의 정확성을 직접 깨는 것은 없었고, 대부분 "드문 조합에서 거래가 막히거나 운영자가 조치할 수 없게 되는" 종류였다.
  문서 쪽에서는 내가 "검증"이라고 적었지만 시험이 그 성질을 겨냥하지 않던 항목, 사실과 다른 서술(앞으로 뛴 시계는 안전하다, 가장 보수적으로 해석했다), 조건 없는 성능 수치가 지적됐다.
- 조치: 결함을 고치고 재현 시험을 수용 시험에 넣었다. 커밋 경계마다 프로세스를 멈추는 시험, 시험이 없던 거절 사유와 불일치 종류의 시험, 기본 한도에서의 과부하 측정을 추가했다.
  빠졌던 고려사항 8개와 출처 요소별 대응표를 등록부에 넣었다. 그 뒤 수용 시험·변이 점검·성능 측정을 최종 소스로 다시 돌렸다.
- 수정이 다시 결함을 만든 예: "접수된 주문을 거래소가 모른다고 하면 불일치를 제기한다"는 수정이, 접수 전에 보낸 조회의 늦은 답에서 거짓 불일치를 냈다. 시뮬레이션이 잡았다.
- 내가 문서를 쓰다가 찾은 것도 있다: 과거 시점의 저널 사본으로 거래를 재개하면 주문 번호가 다시 쓰여 거래소 식별자가 충돌한다(A-12, 운영 절차 §7.6).
- 실제 testnet 읽기 전용 시험이 한 번 간헐적으로 실패했다. 조회 넷 중 셋이 접속 단계에서 실패했고 원인은 로그에 남지 않았다. 시험이 조회를 한 번만 보내던 것을 실제 노드처럼 반복하게 고치고, 오류의 원인이 로그에 남게 했다.
  원인은 확인하지 못했다.
- 최종 증거 수집을 다섯 번 돌렸다([verification](../verification/README.md)의 표). 세 번째 실행에서, 호스트의 부하가 높아지자 그때까지 늘 통과하던 flush 실패 시험이 간헐적으로 실패했고, 저장 실패 시의 순서 결함이 드러났다(정지 표시보다 응답 채널이 먼저 닫혔다). 고쳤다.
- 결과와 조치: [verification/gap-review.md](../verification/gap-review.md).

## 사고와 실수

- 조사 중 crates.io 조회 요청의 User-Agent에 사용자의 이메일 주소를 넣었다(내가 13회, 조사 에이전트가 약 95회). 사용자의 지시 없이 무관한 서비스에 식별 정보를 보낸 것이다. 그 뒤의 조회는 중립 문자열로 바꿨다.
- 도구 체인 고정 파일이 1.4 GB의 중복 설치를 일으켜 가득 찬 디스크를 더 채웠다. 파일과 중복 설치를 지웠다.
- 시험 기대값을 계산 없이 적었다가(CRC 값) 틀렸다. 독립된 도구로 계산한 값으로 바꿨다.
