## Problem Statement

Since U19a the watcher reads the journal with its own reader, queries Bybit with its own key, runs W1–W4, holds plain orders on a confirmed difference (`watcher_mismatch`) and sends heartbeats. It cannot yet act when the OMS itself is gone. If the OMS process dies or stops answering HTTP, its resting orders stay at Bybit and nobody cancels them: the OMS's own kill loop (C-KILL) runs inside the OMS, and Bybit offers no venue-side dead-man for this account (`docs/contracts/kill.md`, DCP is for institutional clients). Nor does anyone hear of it: the watcher sends no message, and the observability stack is a separate path that may be down too.

U19b adds, inside the `watcher` crate and still sharing no code with the OMS:

1. its own Telegram sender with the PR #3 delivery rules and the prefix `[WATCH P1]`, for a confirmed mismatch, a rejected key (retCode 10010, 10003, 33004 and the rest of the never-retried class), a public IP outside the key's list, and every kill notice;
2. its own cancel-all confirmation loop with its own key (C2–C5 of table 7-8: cancel-all, count the open orders with `/v5/order/realtime`, repeat every 1 s, watch 30 s after the first zero), with the P1 rule of C4 and a position block in every notice;
3. W5: when `/api/status` gives no good answer for 10 s, the watcher writes the kill marker, stops the OMS (`watcher_kill` on `admin.sock`; if that fails, `systemctl stop` of the OMS unit, the only unit it may stop), and only then runs the loop.

## Common decisions (all parts)

### Independence
- Still no dependency on any `oms-*`, `md-*` or other workspace crate (`alert-direct` included); dev `http-fake` only. No new registry crate: the sender uses `reqwest` (already there, with its `resolve()` for the pinned route), the stopper uses `std::process::Command` and `Child::try_wait` (no new tokio feature, so `Cargo.lock` does not change). Each part report shows `tools/ci/watcher_independent.sh` exit 0 and `watcher_independent: ok` at its HEAD.
- The texts of the P1 notices are written anew in the watcher (the OMS's are a model only). Where the watcher's rule differs from the OMS's on purpose, the part says so and C-WATCH part 11 says so too. There are two: the count after a failed cancel-all (C2 failure) and the notice rule (no change notice at once; review 1 S4), both in U19b2 below.

### Clock and waits
- Every timer of U19b (W5 probes and silence, the loop's rounds, watch, notices and order budget, the stop wait, the mismatch notice pace, the repeat rule, the sender's flush pace) reads the injected `Clock`. Nothing sleeps on it: each sans-IO part returns the instant it next wants to run, the runtime's 100 ms tick (`runtime.rs:38`) asks again. The sender's network timeouts (10 s request, 3 s connect) and the client's `request_timeout_ms` are tokio time, as in U19a; each sans-IO request also has a deadline on the injected clock so a lost answer never blocks a machine.
- A task that runs beside the tick (the sender task, U19b1a) never sleeps on the injected clock either: it waits on a `tokio::sync::Notify`; `Handle::once`/`set` notify it, and the runtime's tick notifies it when the sender's `next_flush(now)` on the injected clock is due (review 1 N6). So manual-clock tests move it with the clock, not with real time.
- A clock that steps back holds the timers (`saturating_sub`), as U19a. A clock that steps forward by 10 s or more while the OMS answers slowly can fire W5 early: known limit in C-WATCH part 12 (the effect is a kill, the safe side).

### Errors
- Config refusals exit 2 with one line, as U19a. Nothing of U19b writes a file except the kill marker (U19b3) and its temporary file in the marker's directory.
- Every U19b failure at run time is a log line plus, where listed, a P1; none stops the process.

## U19b1 decisions: the watcher's Telegram sender (U19b1a) and its P1 conditions (U19b1b)

U19b1a builds the config section, the token file, the pure parts and the sender task, and tests them against `http-fake` without the runtime. U19b1b adds the conditions, the engine action and the runtime wiring.

### Config `[telegram]` (U19b1a) (optional section; unknown keys refused)
| Field | Default | Validation |
|---|---|---|
| `token_file` | required in the section | absolute, no `..`, resolved outside `data_dir`; at load: a regular file (not a symlink), owner = this process's uid, mode with no group or other bits (`0600`, `0400`), not inside a git repository (an ancestor directory holds `.git`), JSON `{"token": "<digits>:<[A-Za-z0-9_-]+>", "chat_id": <non-empty string or number>}`. The same format as `alert-direct`'s file (`alert-direct/src/lib.rs:95-170`), so the operator may point both at one file. Errors never quote the file; `Debug` of the loaded value prints the chat id and `token: <hidden>` |

- Mainnet without `[telegram]` → refused (`"mainnet requires [telegram]: the watcher's P1 must reach a person"`), as the OMS refuses mainnet without `[alert]` (`.scratch/oms-direct-alerts/spec.md`; owner question 9). Testnet without it: one `warn` line at start; every P1 is written to the log as `warn: [WATCH P1] (no [telegram]: not sent) <body first line>`.
- The token file is read once at start, after the config and before the start checks (so a key rejected at step 2 is already told). A token file that fails a rule → exit 2.
- The prefix is the constant `[WATCH P1]`; the venue label is `bybit`. Message = `"[WATCH P1] bybit {name} {MM-DD HH:MM:SS KST}\n{body}"` (KST from the injected clock; `name` = the watcher's config name).

### The sender (`watcher::alert`, U19b1a)
- Pure parts, each with unit tests: `split(text, 3500)` (UTF-16 units, cut at line ends, an overlong line by characters, as PR #3); `Outbox` (50 parts, drop the oldest and count, the drop notice after the queue is empty; a part dropped while in flight is not removed twice); `Repeat` (start, every 300,000 ms with the latest text, clear `해소: <start text>`); `outcome(status, body)` → `Delivered` (2xx and `"ok": true`), `Refused` (400, 413), `Retry` (everything else, and network errors).
- One sender task (`alert::spawn(routes, token, clock, metrics, log) -> (Handle, Task)`): woken by its `Notify` (a new message, or the runtime's tick when `next_flush(now)` on the injected clock is due: every 5,000 ms, design value, after the last flush that left parts; Clock and waits above); sends parts in order, one at a time; a `Retry` ends the flush and keeps the part. Routes: DNS, then `api.telegram.org` resolved to 149.154.167.220:443 (SNI and certificate for the host); a network error moves to the next route, an HTTP answer decides; the route that answered goes first next time. Request timeout 10 s, connect 3 s (design values, PR #3). `alert::Handle::once(body)` and `set(key, Option<text>)` only take a lock; nothing that calls them waits for the network.
- Tests use `Endpoints.telegram` routes to loopback fakes (`http-fake`, plain `http`, and the pinned form through `reqwest`'s `resolve` to a second fake address). The binary takes the two production routes from `Endpoints::of(cfg)`; there is no config override (as the REST base).
- Nothing is persisted (U19a principle): the repeat state lives in memory, so a restart sends a lasting condition's start text once more.
- Shutdown: `Task::finish(5_000)`: one last flush, bounded by 5,000 ms of real time (판단(모델 아님)); what is left is dropped and counted in the log line. The runtime calls it from U19b1b on.

- How the runtime learns them: the engine gets a new action `Action::Confirmed { check, details: Vec<String> }` emitted in `judge` at the place that already counts `watcher_mismatches_total` (`engine.rs:808-815`), once per identity (the counter's own rule). The runtime gives it to a sans-IO `MismatchNotices` (per check: last sent instant, collected details) that returns the messages due at `poll(now)`. `auth` and `public_ip` are read by the runtime at every tick and passed to `set(key, …)`, which sends only on a change or a repeat. Their texts need data the U19a accessors do not give (review 1 N1): `auth_rejected()` returns the code only (`rest.rs:307`) and `stop_key`'s reason and the echo's `why` are only logged (`rest.rs:317-329`, `start.rs:238-262`). So U19b1b adds `Client::auth_stop() -> Option<AuthStop {code, http: bool, text}>`, set with the latch from the first answer that latched it (its `retMsg`, or the HTTP status line for 401, `http: true`) or from `stop_key`'s `reason` (code −1), never changed afterwards (the latch keeps the first, as `stop_key` keeps the first code); `auth_rejected()` stays as it is. And `start::PublicIp`, a shared cell (`Arc<Mutex<Option<String>>>`) that `export_public_ip` sets to `Some(why)` with the 0 and to `None` with the 1; the runtime reads it, the gauge stays as it is.
- "One `[WATCH P1]` per mismatch" means per confirmation of an identity, not per `watcher_mismatch` send: the resend after an operator's `clear-hold` (U19a7) sends no new P1 (the OMS's own `hold:watcher_mismatch` alert tells the returning hold). A watcher restart that confirms the same difference again sends one more (memory only).
- Start refusal (review 1 S10): a start check or a boot status rule that refuses the start (exit 2) after the sender is up sends one `[WATCH P1]` `워처 시작 거부: {reason cut to 200}. 워처가 꺼짐: W1~W4와 W5가 돌지 않음` and flushes (≤ 5,000 ms) before the exit. Config, credentials and token file refusals come before the sender and stay log-only. During a kill (U19b3b) the refusal goes through the abort path first.
- Bound (판단(모델 아님)): mismatch P1s ≤ 4 checks × (1 + ⌊T / 60 s⌋) in any window T; each lasting condition ≤ 1 + ⌊T / 5 min⌋ + 1.

## U19b2 decisions: the cancel-all confirmation loop

### POST and cancel-all (`watcher::sign`, `watcher::rest`)
- `sign::post_prehash(ts, api_key, recv_window, body)` = `ts + api_key + recv_window + body`, the same HMAC as GET. Test vectors: the published POST string to sign (facts Q1.10, exact bytes) and HMAC values for a made-up secret computed with Python's `hmac` for this part (allow-listed in `tools/ci/secret_scan_allow.txt` with the reason, as U19a3 did).
- `Client::cancel_all() -> Result<CancelAll, RestError>`: the only signed request that is not a GET, and the only POST to the Bybit REST base. (The watcher has two other POSTs, both unsigned and to other hosts: the VM import push, `metrics.rs:141`, since U19a3, and Telegram `sendMessage`, `alert.rs`, U19b1a; review 1 M1.) There is no generic `post(path, body)`: the path `/v5/order/cancel-all` and the body bytes `{"category":"linear","settleCoin":"USDT"}` are constants in `rest.rs`, the signed string and the sent body are the same bytes, `Content-Type: application/json`, the five headers as GET. It goes through the guard, the 403 pause and the key latch like every request (`rest.rs:397-425`), and counts in `watcher_requests_total{endpoint="/v5/order/cancel-all"}`. So no code path of the watcher can create or amend an order (the watcher key needs the `Order` permission to cancel, which would also allow creating). Test `client::the_only_post_is_cancel_all_with_the_fixed_body` (also: the URL is the REST base plus the path constant, and the signed and sent bytes are the body constant). A source test `client::no_other_post_exists` reads `crates/watcher/src/*.rs` at test time (plain text, a comment counts too, as the independence scan) and asserts: `.post(` appears exactly once in each of `rest.rs` (in `cancel_all`), `metrics.rs` (VM import) and `alert.rs` (Telegram) and in no other file; `Method::`, `.request(`, `.put(`, `.patch(` and `.delete(` appear in no file (so no request can hide behind a generic method). `.get(` is not checked (map lookups use it); every signed GET goes through `Client::get`.
- Answer: the client classes of U19a (`rest.rs:184-215`). retCode 0 with `result.success` absent or `"1"` → `CancelAll { cancelled: result.list.len() }`; `result.success == "0"` → `refused` ("cancel-all answered success 0"); `result.list` not an array → `unreadable`.
- The kill scope is linear/USDT: every configured symbol settles in USDT (start step 5 since U19a4b); orders in other settle coins are not seen by this loop or by W1 (C-WATCH part 11 says so, as table 7-8 text does).

### Start rule for a key that must cancel (`watcher::start`, step 2)
When `[kill]` is configured (U19b2 adds the section with its loop fields; U19b3a makes it required on mainnet), query-api must also show: `readOnly == 0` (integer), `permissions.ContractTrade` a list containing `"Order"`, and no `"Withdraw"` in any list of `permissions`. Otherwise the start is refused (exit 2) with the rule named. Without `[kill]` these are not read (a read-only key is then fine). The `Order` → cancel-all link is inference from the permission names (Q4), not documented: testnet experiment (C-WATCH part 11 lists it under "확인 안 됨"). `Withdraw` is master-only per Q4, so a sub-account key should never carry it; refusing it costs nothing (design §7.4 "출금 권한 없음"; ops doc line 87 said the start does not check it, U19b2 changes that line). The recheck (`IpCheck`) applies the same rules; a failure there is a rule stop (`stop_key`), as U19a4b's other rules (owner question 5).

### The loop (`watcher::kill::KillLoop`, sans-IO)
`KillLoop::new(timing, request_timeout_ms)`; inputs `start(now, header)`, `cancel_done(now, req_id, CancelAnswer)`, `count_done(now, req_id, Result<usize, String>)`, `poll(now)`, `abort(now, why)`; output actions `CancelAll {req_id}`, `Count {req_id}`, `Notice(Notice)`, `Ended(Report)`; accessors `phase()`, `round()`, `remaining()`, `cancel_all_calls()`, `next_wake()`. `CancelAnswer` = `Done(CancelAll)` | `Failed(why)` (sent, and no usable answer or refused) | `NotSent(why)` (the guard's caller saw the key latch, the 403 pause, or a local error: nothing left the host).

| State | Entered | Does | Next |
|---|---|---|---|
| C2 cancel | round `r` starts at `t_r` | `CancelAll` if the order budget admits it, else waits for the budget's instant | `Done` or `Failed` → C3 at once; `NotSent` → C4 |
| C3 count | after a sent cancel-all | `Count`: `/v5/order/realtime?category=linear&settleCoin=USDT&limit=50`, every page by W1's paging rule (`w1.rs:131`; at most 20 pages, more → count error "more than 1000 open orders"), `n` = rows with `orderStatus ∈ {New, PartiallyFilled, Untriggered}`, any `orderLinkId` (foreign orders count) | `n = 0` → C5; `n > 0` → C4; error → C4 (a failed count is never zero) |
| C4 repeat | `n > 0` or a failure | waits until `t_r + round_ms` | C2, round `r + 1` |
| C5 watch | first `n = 0` at `z` | `Count` at `z + k × watch_every_ms`, the last at `z + watch_ms` | `n > 0` → C2 at once (round `r + 1`); count error → C4; the count due at `z + watch_ms` answered 0 → End (however late it answered; a slow answer to an earlier count is not it, as the OMS's N4) |
| End | — | final notice, `Ended(Report {rounds, cancel_all_calls, zero_since})` | idle |
| Aborted | `abort` (shutdown or a start refusal during the loop, U19b3b) | one abort notice, `Ended` with `aborted` | idle |

Never two requests of the loop in flight (review 1 N7): a `Count` or `CancelAll` that is due while one is open waits for its answer or its deadline, then goes at once (so a watch count due at `z + k × watch_every_ms` may go late; the count that ends the watch is the first one emitted at or after `z + watch_ms`), as the OMS's loop.

- **Deliberate difference from the OMS (C2 failure)**: the OMS goes from a failed cancel-all to C4 without a count (`kill.rs:238-259`). The watcher counts after every cancel-all that was sent, also a failed one. The count is the truth (zero open orders is the goal, whoever cancelled them), and the answer of cancel-all when nothing is open is not documented (Q11.7): if Bybit refused a cancel-all with nothing to cancel, a loop that never counts after a refusal would never end. A cancel-all that was not sent (latch, pause) is not followed by a count (the count would not be sent either).
- **Order budget**: at most 2 `CancelAll` in any half-open window `[t, t + 1,000)` ms, counted from emission (design: 2 per second for the emergency path, table 7-8 C4). With config-valid timings (`round_ms ≥ 1,000`, `watch_every_ms ≥ 1,000`) two cancel-alls are never closer than 1,000 ms (the next comes at `t_r + round_ms`, or on the watch path at least `watch_every_ms` after `z ≥ t_r`), so the budget never binds there (review 1 S2). It is a guard against a later change of the timings or the paths, not a rule the valid config ever meets. A cancel-all the budget holds back is emitted at the budget's instant (from `poll`). `KillLoop::new` takes the timings directly (the config ranges are checked at config load only), so the budget test builds it with `round_ms = 100`, `watch_every_ms = 100` (below the ranges), where the budget does bind, and mutant (14) is killed there.
- **Deadlines**: each `CancelAll` and `Count` has a deadline, emission + `request_timeout_ms` + 11,000 ms (the engine's `DEADLINE_EXTRA_MS`, `engine.rs:57`); past it, `poll` takes it as `Failed("no answer before the deadline")` / count error; a late answer with that `req_id` is ignored (one debug line).
- **Bound of the loop**: none in rounds (it runs until zero is confirmed or the process stops), as the OMS's loop and table 7-8. Requests per round ≤ 1 cancel-all + 20 count pages; the request guard (60 per 10 s) is the hard bound; at 500 open orders a round needs 11 count pages and the guard stretches rounds (as U19a9's budget note; the engine is paused during a kill, U19b3).

### Notices (the C4 rule) and their text
- Kinds: **start** (at `start`), **progress** (from `poll`, when `notice_ms` passed since the previous notice of any kind and the loop is not ended), **final** (at End), **abort** (at `abort`). So after the start one progress notice per `notice_ms` while the loop runs, with the latest round, count (known or `모름: <why>`) and error.
- **Deliberate difference from the OMS (notices; review 1 S4)**: the OMS sends a change notice at once when a known count above zero differs from the last shown, plus a repeat every 60 s (`kill.rs:192-235`, kind `Change`); TN `05_trading.html:213` says "60초마다, 그리고 남은 건수가 바뀔 때 보냄". The watcher sends no change notice: a changed count waits for the next progress notice. Reason: the scope's "at most once per 60 s" and the 12-in-10-min bound, which the OMS's change notices do not keep (each count change is one more message). So with both loops running after `watcher_kill`, `[OMS P1] 킬 루프` may show a count change up to 60 s before `[WATCH P1] 워처 킬`. C-WATCH part 11 states it as the second difference. Owner question 2: the scope's "only when the remaining count changes and at most once per 60 s" and table 7-8's "바뀌지 않아도 60초마다 한 번" are read together as "at most once per 60 s, also when the count did not change": a person learns every minute that orders are still open or the loop still fails. A changed count is shown at the next notice, not at once (the scope's "at most once per 60 s").
- Bound: in any window of length T ≤ 1 start + ⌊T / notice_ms⌋ progress + 1 final (+ 1 abort at shutdown): with a 10-minute query failure 1 + 10 + 1 = 12 (design R2 SHOULD 4). The final notice is a separate kind and is never held back by `notice_ms`.
- A notice is text plus a position block read just before it is sent (U19b3b runtime; here: `kill::position_block(rows: Result<&[Value], &str>, kst) -> String` and `kill::notice_text(&Notice, header) -> String`, pure).
- Position block: from `GET /v5/position/list?category=linear&settleCoin=USDT&limit=200` and cursor pages (at most 5, 판단(모델 아님)); `settleCoin` alone returns only rows of size > 0 (Q12.1); rows with `size` 0 or unreadable are left out. Per row: `- {symbol} {매수|매도} {size}, 미실현손익 {unrealisedPnl}, 마크 {markPrice}, 마크에서 강제청산가까지 {d} %`, `d = |mark − liq| / mark × 100` rounded down to 0.01 % with the watcher's `Dec` arithmetic; `liqPrice` empty, zero or unreadable, or `markPrice` ≤ 0 or unreadable → `모름(거래소가 청산가를 주지 않음)` / `모름(마크 가격 없음)`. Head line `포지션(거래소 /v5/position/list, {KST}, 강제청산가는 교차 증거금이면 거래소 추정):`. No row → `포지션 없음`. The query fails (any client class) → `포지션 조회 실패({class}). 수량·손익·마크·강제청산가 모름`. The client is latched or paused → no request, `포지션 조회 안 함({why}). 수량·손익 모름`. At most 20 rows are listed, then `그 밖에 {m}종목` (판단(모델 아님): keeps one notice within one 3,500-unit part, so "12 P1" stays 12 Telegram messages).
- Texts (body; the runtime adds the header of U19b3):
  - start: `워처 킬 시작({header}). 워처 키로 미체결 0건 확인까지 {round_ms/1000}초마다 일괄 취소(linear, USDT 정산). 포지션은 닫지 않음.`
  - progress: `워처 킬 {r}회차: 남은 미체결 {n}건(또는 모름: {why}), 일괄 취소 {k}회. {last_error}`
  - final: `워처 킬 정리 완료: 미체결 0건 확인 뒤 {watch_ms/1000}초 동안 늦은 접수 없음({r}회차, 일괄 취소 {k}회). OMS 래치 해제는 운영자만: omsctl clear-hold --reason kill --note …`
  - abort: `{워처 종료 | 워처 시작 거부: <reason cut to 200>}로 워처 킬 중단({r}회차, 남은 미체결 {n | 모름}, 일괄 취소 {k}회). OMS의 래치·마커는 그대로.` No position read (the watcher is ending), and the notice ends with the fixed line `포지션 조회 안 함(워처 종료 중). 수량·손익·마크·강제청산가 모름`, so it is still "shown as unknown" (review 1 M2); `kill::notice_text` writes that line for `Abort`, the runtime adds no block.
- The OMS's notices say `킬 루프`; the watcher's say `워처 킬`, so a person can tell the two loops apart in one chat (both run when `watcher_kill` latched the OMS).

### Test rig (U19b2)
`crates/watcher/tests/common/kill_rig.rs`: the manual clock, a real `Client` against an `http-fake` with scripted routes for `/v5/order/cancel-all`, `/v5/order/realtime`, `/v5/position/list`, and a step loop: `poll(now)`, perform each action with the client, feed the answer, move the clock to `min(next_wake, now + 100)`. Every loop has a step bound (판단(모델 아님): 20,000 steps); the rig fails the test when it is reached. `http-fake`'s `on_request` hook records the manual clock at each request, so the order-rate assertions use the loop's clock, not real time.
- Guard hang (review 1 S3): `Client::turn` reads the injected clock but waits in real time until the guard admits (`rest.rs:397-425`); the rig moves the clock only between steps, so a 61st request in 10 s of manual time would wait forever. The rig wraps every client call in a real-time `tokio::time::timeout` of 5,000 ms (판단(모델 아님)) that fails the test with `the guard held a request: the rig's clock did not move`. Every rig test stays under 60 requests in any 10 s of manual time, and says its count in a comment: e.g. `kill::more_than_1000_open_orders_is_a_count_error` runs two rounds (2 × 21 = 42 requests) and stops; the 600 s failure tests send ≤ 1 cancel-all + 1 count per 1,000 ms round (≤ 20 per 10 s). The 5 s timeout is only the net under a wrong count.

### W5 (`watcher::w5::W5`, sans-IO, U19b3a)

What W5 sees (review 1 S1): `/api/status` is built from the published state under a read lock (`oms-node/src/status.rs:43-46`), not by the core loop. So W5 fires when the OMS process is gone or no longer answers HTTP; a core or pipeline that hangs while the HTTP task still answers is not seen by W5 (the heartbeat's missing `recorded` only changes `watcher_heartbeat_ok_ts`). The design names `/api/status` as the signal (§7.5 W5), so the rule stays; the limit is written in C-WATCH part 12 and V-WATCH-13 `not_covered`, and owner question 11 asks whether a heartbeat without `recorded` should also count.

States: `Off` (no `[kill]`), `Unarmed`, `Armed {last_good_ms}`, `Killing`, `Rearming`.
- `arm(now)`: `Unarmed → Armed {last_good_ms: now}`. The runtime arms W5 when the start machine returns `Done` or `StayUpNoRequests` (after `auth`: the loop then cannot send, and its notices say so, but the marker and the stop still work). Before that the account is not verified, and a cancel-all must never go to an unverified account (as the OMS, `.scratch/kill-switch/spec.md` "Not armed before the boot checks pass"). Owner question 1: W5 is armed whether or not the OMS ever answered in this process, so a watcher started while the OMS is down kills 10 s after its start checks.
- `poll(now) -> Option<Probe {req_id}>`: in `Armed` and `Rearming`, one probe every `probe_ms` from the previous probe's emission, never two in flight; a probe without an answer at emission + `request_timeout_ms` + 1,000 ms (판단(모델 아님)) is a failed probe. No probe in `Killing`.
- `on_answer(now, req_id, good: bool)`: good = `Status::get` gave 2xx JSON with a 16-hex `core.instance_id` (the boot rule without the cap, `runtime.rs:105-116`). `Armed`: a good answer sets `last_good_ms = now`. `Rearming`: a good answer → `Armed {now}`. A failed or bad answer changes nothing. An answer to a probe that is not in flight is ignored.
- `fire(now) -> Option<Fire {last_good_ms, silent_ms}>`: in `Armed`, when `now − last_good_ms ≥ silence_ms` → `Killing`, once. The probe is W5's own (the engine's status requests do not count), so W5 is one rule that a test can drive.
- `kill_ended()`: `Killing → Rearming`: after a kill, W5 waits for one good answer before it watches again, so an OMS that stays down (stopped by the watcher) does not start a new kill every 10 s.
- `watcher_oms_silence_s` = `(now − last_good_ms) / 1000` while `Armed`; `watcher_w5_armed` = 1 in `Armed` only.

### The kill sequence (`watcher::kill::Kill`, sans-IO, wraps `KillLoop`, U19b3a)
`Kill::new(fire, cfg, now)` → actions in this order, each step waiting for the previous one's outcome:
1. **K1 marker**: `WriteMarker {text}`. The runtime: `symlink_metadata(marker)`; anything there → `AlreadyPresent` (it is not touched or replaced). Else write `text` to `<dir>/.<file name>.watcher-<pid>.tmp` (created new, mode 0600), `sync_all`, `hard_link` it to the marker path (fails if something appeared meanwhile → `AlreadyPresent`), remove the temporary file, `sync_all` the directory. Any error → `Failed(<io kind>)`; the sequence goes on (a missing marker must not delay the stop and the cancel). `text` (≤ 512 bytes, the OMS reads 512, `node.rs:487`): `watcher {name} W5 {UTC RFC 3339 ms}: /api/status gave no good answer for {s} s (last good answer {UTC}); the watcher stops the OMS and cancels every order with its own key. Clear with omsctl clear-hold --reason kill.`
2. **K2 halt**: `Halt {detail}` → `oms::admin_kill(path, name, detail, timeout)`: one connection, `{"id":1,"op":"hello","client":"watcher/<name>"}`, then `{"id":2,"op":"watcher_kill","detail":…}`, each reply within `request_timeout_ms`, the whole within 2 × `request_timeout_ms` (as `admin_send`, `oms.rs:128-160`). `detail` = `W5: /api/status gave no good answer for {s} s; watcher {name}` (≤ 1024 bytes). Halted = the reply is `"latched"` or starts with `"already latched"` (this covers `KILL_REARMED_REPLY`, `input.rs:122-124`). Anything else (an error code, `bad_request`, no socket, a timeout, a lost hello) → not halted, with the reason.
3. **K3 stop** (only when K2 did not halt): `StopUnit {deadline: now + stop_wait_ms}` → `stop::Stopper::start()` runs exactly `<systemctl> [--user] --no-ask-password stop -- <oms_unit>` with `stdin`/`stdout` null and `stderr` piped (at most 4 KiB kept); the runtime calls `try_wait` at every tick; exit 0 → stopped; another exit → failed with the first line of stderr; the deadline on the injected clock passes → the `systemctl` client is killed and reaped, outcome `unconfirmed` (review 1 N5: killing the client does not cancel systemd's stop job, so the OMS may still stop later). The header says `정지 확인 못 함({stop_wait_ms} ms 안에 systemctl이 끝나지 않음)`, not `실패`; for the X8 line below an unconfirmed stop counts as a failure (the safe side). `<systemctl>` is `/usr/bin/systemctl` from `Endpoints::of(cfg)`; tests give the path of a fake script under `OMS_TEST_DIR` (no test ever runs the real `systemctl`). `stop.rs` holds the only `std::process::Command::new` of the crate: test `stop::the_watcher_starts_one_program_only` reads `crates/watcher/src/*.rs` at test time and asserts that the text `Command::new` appears once, in `stop.rs` (plain text search).
4. **Loop**: `KillLoop::start(now, header)` with `header` = `W5: OMS /api/status 무응답 {s}초, 마지막 정상 응답 {KST | 이 프로세스에서 없음}. 킬 마커: {씀 | 씀(OMS가 읽는 경로인지 확인 못 함) | 이미 있음 | 쓰지 못함(<kind>)}. OMS 정지: {admin.sock watcher_kill → <reply> | watcher_kill 실패(<why>) → systemctl stop <unit>: 정지됨 | 실패(<why>) | 정지 확인 못 함(…)}`, and, when K2 failed and K3 did not confirm the stop, `. OMS 정지 실패: OMS가 새 주문을 낼 수 있음. OMS 키 폐기(X8 절차)를 검토` (table 7-8 C1 failure column). The first `CancelAll` is emitted only from here: K1 and K2 (and K3 when it runs) have an outcome before it. This is the done criterion's order.
- Free texts in the header (review 1 S9): the K1 io kind, K2's reply and reason, K3's reason are each cut to 200 characters with control characters replaced by spaces (an `admin.sock` error text is bounded only by the 64 KiB line limit, `oms.rs` `LINE_MAX`). The header is then at most about 1,300 UTF-16 units (판단(모델 아님)), so header + body + 20 position rows stay one 3,500-unit part.
- Marker path not yet checked (review 1 S10): `Kill::new` takes `marker_checked: bool` = the runtime saw a status answer in this process that passed the marker-path rule. When false (e.g. W5 fired before any status answer: the watcher started while the OMS was down), a written marker shows as `씀(OMS가 읽는 경로인지 확인 못 함)`. The marker is written all the same (it is the configured path; refusing to write would lose the latch if the paths agree).
- **`Kill::abort(now, why)`** (review 1 M2), in every step, not only in the loop: before `KillLoop::start` (K1–K3 still running or done) it emits one abort notice whose body is the header built so far, each step not yet ended written `진행 중` (`킬 마커: 진행 중`, `OMS 정지: 진행 중`), then `{워처 종료 | 워처 시작 거부: <reason>}로 워처 킬 중단(일괄 취소 전). OMS가 아직 주문을 낼 수 있음` when no step halted or stopped the OMS, and the fixed position line of the loop's abort notice; then `Ended{aborted}`. A step whose action is running is not cancelled by the abort (K1 finishes, K3's client is left to systemd, as Shutdown below); its outcome is not reported. In the loop, `KillLoop::abort` as U19b2.

The worst time from the last good answer to the first cancel-all (판단(모델 아님), defaults): 10 s silence + 0.1 s tick + K1 (local) + 2 × 2 s K2 + 10 s K3 ≈ 24 s; with a working `admin.sock` ≈ 10–14 s.

The OMS, when `watcher_kill` latched it, runs its own kill loop with its own key at the same time (C-KILL). Both are at ≤ 1 cancel-all per second, ≤ 2 per second on the UID together (table 7-8 C4), far below Bybit's 10 per second per UID for cancel-all (Q11.6). If K2 failed and K3 stopped the OMS, only the watcher's loop runs; the marker latches the OMS at its next start (C-HOLD), and that start runs the OMS's loop again before a person can clear.

### Runtime (U19b3b)
- From config load: the alert sender (wired in U19b1b) beside the metrics push. From the end of the start (`Done` or `StayUpNoRequests`): W5, in every later phase (status wait, replay, run).
- At `Fire`: `watcher_kills_total += 1`, `watcher_kill_active = 1`, one error log line, `Kill::new`. While a kill runs: the engine is not polled (no new rounds, no `watcher_mismatch` send, no heartbeat); answers to its requests in flight are still given to it (its deadlines close them); the boot phases go on (they do not call Bybit); `IpCheck` goes on. Reason: the OMS is gone or halted, rounds would fail at their status request anyway, and their Bybit requests would take the guard's room from the loop's counts (판단(모델 아님)). After `Ended`, the engine is polled again (a late round runs once, U19a) and W5 goes to `Rearming`; `watcher_kill_active = 0`.
- Consequence of the pause on the OMS's monitoring gate (review 1 S5; the pause is kept, owner question 10): when K2 latched a live OMS, the OMS gets no heartbeat during the loop, so after 30 s (`heartbeat_max_age_us`, `oms-core/src/config.rs:126-133`) it records `hold:unmonitored` and its alert follows, while the watcher runs the kill. Keeping the heartbeat would not avoid it: its W1/W2 times would be older than 10 s and the per-check rule closes the gate as well. The hold blocks only plain orders, which the kill latch already blocks; it clears by itself after the loop, at the first heartbeat whose W1 and W2 succeeded again (up to one W1/W2 round after `Ended`). C-WATCH part 12, runbook 7.16 and 7.18 say so: `모니터링 상실이 워처 킬 중에 따라오고, 루프가 끝나고 W1·W2가 다시 성공하면 스스로 풀린다`.
- Start refusal during a kill (review 1 S10): a boot status rule that refuses the start (another instance, the marker-path rule) while a kill runs goes through `Kill::abort(now, "워처 시작 거부: <reason>")` first: the abort notice, then the start-refusal P1 (U19b1b), the alert flush (≤ 5,000 ms), then exit 2. No `tasks.abort_all()` before the notice is queued.
- Notices are sent beside the loop, one at a time in their order: for each `Notice` the runtime reads the position block (its own requests, through the guard, never during the key latch or the pause), composes the message and calls `alert.once`. A slow position read holds back no `CancelAll` or `Count`. At most 16 notices wait (판단(모델 아님)); beyond it the oldest waiting progress notice is dropped (never a start or final), counted in a log line. Before the end, the final notice is queued before `Ended` is acted on.
- Shutdown (SIGTERM/SIGINT) during a kill: `Kill::abort` (in any step) → the abort notice (no position read, the fixed `포지션 조회 안 함` line) and `Ended`; K3's child, if running, is left to finish its job in systemd (not killed: a half-stopped OMS is worse than a stopped one); then the U19a shutdown steps and the alert flush of up to 5,000 ms. The marker stays. A shutdown during K1 lets the marker write finish first (a local file operation).
- Nothing is persisted: a watcher restarted during a kill does not resume it. It arms W5 again at the end of its start; an OMS that is still down is killed again (a new marker is not written, the old one is `AlreadyPresent`), and a new loop confirms zero.

### Boot and shutdown summary
Boot: config (with `[w5]`, `[kill]`, `[telegram]`) → credentials and token file → metrics push and alert sender → start checks (with the U19b2 key rules) → W5 armed → wait for `/api/status` (with the marker-path rule) → replay → engine. Shutdown: as U19a, plus: abort a running kill (one notice), flush alerts ≤ 5 s, exit 0.

### Known limits written in C-WATCH (U19b3a/U19b3b unless noted)
- W5 sees a dead process or a silent HTTP task only: a hung core or pipeline behind an answering `/api/status` is not a W5 kill (review 1 S1; owner question 11).
- During a watcher kill of a live OMS, the OMS's `hold:unmonitored` and its alert follow after 30 s and clear after the loop (review 1 S5).
- A watcher started before the OMS answers, or with a wrong `status_url`, kills the OMS after `silence_ms` (owner question 1; runbook start order).
- A clock step forward of 10 s or more can fire W5 (the safe side: a kill).
- The marker race of U18b1 N4: an operator's `clear_hold kill` whose unlink comes right after the watcher wrote a new marker removes it; the watcher's start and final notices say whether the marker was present when it looked (`킬 마커: …`), and the OMS-side fix (unlink only the inode seen at boot) is a later OMS unit (Out of Scope).
- A kill confirms zero for linear/USDT only (U19b2).
- The `stop` needs a systemd permission that U20b grants; until then K3 fails and the start notice says `OMS 정지 실패` (the loop still runs). A `systemctl` client that does not end within `stop_wait_ms` is killed, but systemd's stop job may still stop the OMS later (`정지 확인 못 함`).
- No persistence: a watcher restart forgets a running kill; W5 kills again if the OMS is still down after the start.
- The 12-message bound counts one sender's kill notices; the lasting conditions (`auth`, `public_ip`) add ≤ 1 + ⌊T / 5 min⌋ each (U19b1b).

## Owner questions (the parts use the default; the runner does not wait)

1. **When W5 starts watching.** Default: at the end of the watcher's start checks, whether or not the OMS ever answered in this process; a watcher started while the OMS is down kills 10 s later (orders left by a crashed OMS get cancelled; the cost is a kill and a `clear-hold` when the watcher is started first by mistake). Alternative: only after the first good answer (no kill at a cold start, but a crashed OMS's orders stay if the watcher restarted after the crash).
2. **Kill notices with an unchanged count.** Default: one progress notice every 60 s while the loop runs, also when the count did not change (table 7-8 "바뀌지 않아도 60초마다"); a changed count waits for the next 60 s mark (the scope's "at most once per 60 s"). Alternative A: a notice only when the count changed (quiet while orders stay stuck). Alternative B: the OMS's rule (`kill.rs:192-235`): a change notice at once for every changed known count above zero, plus the 60 s repeat; it does not keep the 12-in-10-min bound when the count changes often (review 1 S4).
3. **Count after a failed cancel-all** (unlike the OMS). Default: yes, the watcher counts after every sent cancel-all, so an undocumented error answer for "nothing to cancel" cannot keep the loop from ending. Alternative: the OMS's rule.
4. **How the watcher may stop the OMS unit.** Default: `systemctl --no-ask-password stop -- <oms_unit>` on the system manager (`[kill] systemd = "system"`), with the permission for that one unit given by U20b; a failed stop is told in the start notice and the loop still runs. Alternative: both as user units of one user (`systemd = "user"`).
5. **Key permissions checked at start when `[kill]` is set.** Default: refuse a read-only key, a key without `ContractTrade: Order`, and a key with any `Withdraw`. Alternative: only log.
6. **Telegram bot and file.** Default: the same bot as the OMS (Q18); the watcher reads its own `token_file`, which may be the OMS's file (same format). Alternative: a separate bot.
7. **Mismatch P1 pace.** Default: one per confirmation, at most one message per check per 60 s, the rest collected into the next. Alternative: every confirmation at once.
8. **SIGTERM during a kill.** Default: the loop stops at once with one notice; the marker and the OMS's latch stay. Alternative: finish the loop before exiting (a person who stops the watcher then waits up to the loop's end).
9. **Testnet without `[kill]` or `[telegram]`.** Default: allowed with one `warn` each (W5 off, P1 only logged), as the OMS's optional sections on testnet; mainnet refuses both. Alternative: refuse on testnet too.
10. **The engine during a kill.** Default: paused (no checks, no heartbeat, no `watcher_mismatch`), so the loop has the request guard to itself. Cost of the default: when `watcher_kill` latched a live OMS, its monitoring gate goes `unmonitored` about 30 s into the loop (`모니터링 상실` alert) and clears after the loop (review 1 S5); keeping only the heartbeat would not avoid it (its W1/W2 times would age past 10 s). Alternative: keep W1–W4 running.
11. **A hung OMS core behind an answering `/api/status`** (review 1 S1). Default: not a W5 kill; W5 watches `/api/status` only (design §7.5), and the limit is written down (C-WATCH part 12, V-WATCH-13 `not_covered`). Alternative: a `monitor.sock` heartbeat that gets no `recorded` for N s (N 판단(모델 아님), e.g. 30 s) also counts as OMS loss and starts the kill.
