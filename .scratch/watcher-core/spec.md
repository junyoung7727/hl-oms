## Problem Statement

The OMS checks itself: its gateway reconciles open orders, fills and positions against Bybit, and since U18b it can hold plain orders on a watcher's word (`watcher_mismatch`) and stop trading when no watcher reports (the monitoring gate). But nothing yet plays the watcher. A bug in the OMS's journal encoding, its reconciliation, or its Bybit parsing would be checked by the same code that made it. Mainnet is refused without the monitoring gate (`docs/contracts/liveness.md` part 2, U18b4), so without a watcher the OMS cannot trade at all.

U19a adds the watcher: a separate binary that shares no code with the OMS. It reads the OMS journal with its own reader, built only from the documented frame format and the C-TAIL field table. It builds its own open-order, fill and position sets. It queries Bybit with its own key, signer and client. It runs the checks W1 (open orders), W2 (positions), W3 (wallet and margin) and W4 (executions). On a confirmed difference it sends `watcher_mismatch` (not `halt`) to `admin.sock`. Every 5 s it sends a heartbeat with each check's last success time to `monitor.sock`. A CI script proves that it depends on no `oms-*` or `md-*` crate. It sends no alert and has no kill path: W5, the kill marker, stopping the OMS, cancel-all and `[WATCH P1]` are U19b.

## Facts from the existing code

Journal format (what the watcher must reimplement, not reuse):
- Segment file `journal-<first seq, 20 digits>.oj`; header `"OMSJRNL\x01" | u32 LE length | JSON {format, record_schema, instance_id, first_seq, created_at_us, writer} | u32 LE CRC-32 of the JSON` (`docs/adr/ADR-011-file-format.md:69-76`; code `crates/oms-journal/src/segment.rs:28-44`, `:109-143`). `FORMAT = 1` (`segment.rs:44`); header JSON at most 64 KiB (`segment.rs:29`).
- Frame: `u32 LE payload length | u32 LE CRC-32 (IEEE) over bytes 8.. (sequence + payload) | u64 LE sequence | payload` (`crates/oms-journal/src/frame.rs:1-13`, encode `:19-29`, decode `:47-85`). Payload at most 16 MiB; a larger length is damage (`frame.rs:15-17`, `:58-62`). Within a segment the sequence must continue (`segment.rs:210-218`).
- Reading rules for programs outside the OMS (C-TAIL, `docs/contracts/tail.md:7-17`): no `LOCK`, no write; never a record above the durable cap (`journal.durable_seq` of `/api/status`); segment rotation; a header-only segment re-read for a new schema; damage at or below the cap is an error and the position does not move; the reader keeps its own cursor.
- Record payload `{"seq", "at" (µs), "input", "events": [{"<name>": {…}}]}`; only `events` matter; decimals are strings with at most 8 places and no exponent; record schemas 1 and 2; an unknown event name stops the reader (`tail.md:21-28`).
- The sets the watcher must build, event by event (`tail.md:32-52`): order info from `order_accepted` until `purged` (not removed at `order_closed`: a `fill_booked` may come after the close, `tail.md:34`); open orders = accepted without `order_closed`; fills from `fill_booked` (side and instrument from the order info) and `external_fill_booked`; position = Σ `fill_booked` + `external_fill_booked` + `venue_position_changed` + `position_adjusted` quantities (`tail.md:52`); `funding_booked` never changes a quantity (`tail.md:46`). The field table with every event and field is `tail.md:58-267`; it is checked against the encoder by `event_fields::the_field_table_lists_every_field_the_encoder_writes` (`tail.md:56`).
- The OMS core's own sets, for the conformance test: `Core::open: BTreeSet<OrderId>` (`crates/oms-core/src/core.rs:44`), `account: BTreeMap<InstrumentId, Book>` with `Book::pos` (`core.rs:49`, `crates/oms-core/src/model.rs:236-245`), `parked_fills` (`core.rs:52`), `seen_fills: BTreeMap<FillKey, Ts>` (`core.rs:56`; funding and venue-change keys share it, `docs/adr/ADR-023-venue-made-executions.md:60`), `fill_floor` (`core.rs:59`).
- Journals are generated in tests from records the core decided, through the `H` harness of `crates/oms-core/tests/common/mod.rs` (`H::ready` `:131`, `inp` `:265`, `venue` `:288`) and `oms_journal::{recover, Writer}`; model: `crates/oms-projector/tests/projector.rs:7-56` (includes the harness by `#[path]`, writes and syncs every record).

Identifiers:
- Bybit `orderLinkId` = `Base32Pair`: `instance_id` 13 digits `-` `order_id` 13 digits, lower-case base32hex `0-9a-v`, 27 characters, strict decoding (`docs/contracts/identifiers.md:13`, `docs/adr/ADR-022-wire-id-form.md:55-56`; code `crates/oms-core/src/ids.rs:213-245`). Vector: instance `0x0123456789abcdef`, order 42 → `028q5cu4qnjff-000000000001a` (`ids.rs:302-304`; recomputed independently with Python for this spec).
- Fill key of the Bybit gateway: `<symbol>:<execId>` (`docs/contracts/gateway.md:97`, `:117`; code `crates/oms-node/src/venue/bybit/exec.rs:28-33`). Funding and venue changes use the same key (`ADR-023:75`).
- Execution classification of the gateway: `Trade` → fill (external if the `orderLinkId` is not ours), `Funding` → funding, `AdlTrade`/`BustTrade`/`Delivery`/`Settle` → venue position change `adl`/`takeover`/`delivery`/`settle`, anything else → unclassified (`gateway.md:101`; `exec.rs:92-140`).

The OMS interfaces the watcher talks to:
- `/api/status` on the loopback dashboard (`crates/oms-node/src/http.rs:265`); the `Host` header must be `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>` and only GET is served (`http.rs:46-62`); the listener binds loopback only (`http.rs:254-257`) and is off when `[http] listen` is empty (`crates/oms-node/src/config.rs:157`, `:610-618`). Fields used: `core.instance_id` (16 hex digits, `crates/oms-node/src/status.rs:122`), `journal.durable_seq` (`status.rs:155`).
- Sockets: one JSON line per request, at most 64 KiB, `hello` first, replies `{"id", "ok", "result"}` or `{"id", "ok": false, "error": {"code", "message"}}` (`docs/contracts/api.md:7-11`; `crates/oms-api/src/lib.rs:162-193`). `admin.sock` and `monitor.sock` accept the node's own uid only (`crates/oms-node/src/server.rs:188-191`); pools: admin 8, monitor 2 (`api.md:110`).
- `watcher_mismatch {check: W1..W4, detail: non-empty, ≤ 1024 bytes}` on `admin.sock` → `"held"` / `"already held"`; anything else `bad_request`, nothing recorded (`api.md:32`; wire example `oms-api/src/lib.rs:261`). The hold refuses plain orders until `omsctl clear-hold --reason watcher_mismatch`; the first note stays (`docs/contracts/holds.md`, `api.md:100-101`). In the journal: `hold_set {hold, source, note}` and `hold_cleared {hold, note}` (`tail.md:241-245`).
- `heartbeat {watcher: 1–64 chars, checks: W1..W9 → epoch ms or null, W1 and W2 required}` on `monitor.sock` → `"recorded"` after durable; at most 2 per second per connection; a check time more than 1 s after the record time is `bad_request` (`api.md:34`; wire example `oms-api/src/lib.rs:295-316`; `HEARTBEAT_AHEAD_MAX_US = 1_000_000`, `crates/oms-core/src/input.rs:156`). The socket exists only with `[core.policy.monitor]` (`api.md:7`). The gate: no heartbeat for 30 s, or W1 or W2 older than 10 s at the heartbeat's record time → unmonitored; W3..W9 are recorded, not judged (`crates/oms-core/src/config.rs:117-131`, `core.rs:274-290`; U18b4 report "Judgment calls" 1).

The OMS's Bybit code (read only to know the API; the watcher must not reuse it):
- Signing: `hex(HMAC_SHA256(secret, timestamp + api_key + recv_window + payload))`; GET payload = the query string sorted by key, values sent as they are, a value with a character outside `[A-Za-z0-9-_.~%:,]` refused (`crates/oms-node/src/venue/bybit/sign.rs:1-70`); headers `X-BAPI-API-KEY`, `X-BAPI-TIMESTAMP`, `X-BAPI-RECV-WINDOW`, `X-BAPI-SIGN`, `X-BAPI-SIGN-TYPE: 2` (`venue/bybit/rest.rs:251-265`). Independent HMAC values for a made-up secret are in `sign.rs:110-140` and allow-listed in `tools/ci/secret_scan_allow.txt` (the scan fails on any hex run of 40 or more digits that is not allow-listed).
- Answer classification: HTTP 401 and retCodes `10003, 10004, 10005, 10007, 10010, 33004` = key rejected, never retried until restart; `10006`/HTTP 429 rate limited; HTTP 403 = IP ban, every request stops for 600 s; `10002` clock; `10016`/5xx/unreadable = no answer (`rest.rs:97-111`, `:158-195`; `gateway.md:87`). IPv4-only local address so the echo sees the address Bybit sees (`rest.rs:103-107`); no redirects, no proxy (`rest.rs:219-221`).
- Start checks of the OMS key: `GET /v5/user/query-api` (`isMaster = false`, `userID`, `readOnly`, `permissions`, `ips`), a key bound to no IP (`[]` or `*`) is refused (`venue/bybit/checks.rs:186-245`); the public IP from an `https` echo URL whose body is the address (`checks.rs:331-366`; config rule `oms-node/src/config.rs:738-741`), rechecked every `ip_check_secs` (60 s, `gateway.md:95`); every traded symbol must have `settleCoin = USDT` in `/v5/market/instruments-info?category=linear&symbol=…` (`checks.rs:173-176`, `:270-293`).
- Queries: `linear()` = `category=linear&settleCoin=USDT` (`venue/bybit/query.rs:98-103`); open orders `/v5/order/realtime` 50 per page, at most 20 pages, open = `New`, `PartiallyFilled`, `Untriggered` (`query.rs:71`, `:91`, `:355-372`); positions 200 per page (`query.rs:92`); executions `/v5/execution/list` 100 per page with `startTime`/`endTime`/`cursor` (`query.rs:90`, `:670-700`); wallet `/v5/account/wallet-balance?accountType=UNIFIED`, fields `totalEquity`, `totalMaintenanceMargin`, `totalMarginBalance` (`query.rs:512-530`; `docs/contracts/margin.md:257-259`).
- Bybit facts: `execution/list` is sorted by `execTime` descending, `limit` 1..100 (default 50), a window of at most 7 days, `startTime` only → `startTime..startTime + 7 days` (gateway facts Q9.3, Q9.7, Q9.8); that an empty `nextPageCursor` means the last page is not documented for these endpoints (Q9.9); `position/list` has `updatedTime` "Position updated timestamp (ms)" (Q12.7); query-api `expiredAt`/`deadlineDay` are "Only for those api key with no IP bound or the password has been changed", and an IP-bound key's example is `"deadlineDay": -2, "expiredAt": "1970-01-01T00:00:00Z"` (Q4, line 97 of the facts file).
- Margin rule values of the OMS: `daily_loss_bps` 500 (`margin.md:35`), `account_mm_rate_max_bps` for Bybit 5000 (`margin.md:42`, 판단 there), the account-rate formula `maintenance × 10 000 ≥ max_bps × margin_balance` with `maintenance > 0` (`margin.md:125`), the daily-loss formula `(base − value) × 10 000 > daily_loss_bps × base` (`margin.md:104`); `day_base_set {day (UTC day number), set_by, value}` (`tail.md:208-210`).

## Common decisions (all parts)

### Crates and independence
- `crates/watcher`: package `watcher`, a library plus binary `watcher` (`src/main.rs` only parses flags and calls the library). Normal dependencies only from the registry (already in `Cargo.lock` where possible): `serde`, `serde_json`, `toml`, `tokio`, `reqwest` (rustls, no default features), `hmac`, `sha2`, `hex`, `crc32fast`, `rustix` (features `fs` and `process`: owner and mode checks, and `rustix::process::geteuid` for "owner = this process's uid", as the OMS, `rest.rs:63`, `oms-node/Cargo.toml:21`; review 2 N1). Dev dependency allowed from the workspace: `http-fake` only. No dependency on any `oms-*` or `md-*` crate and no other workspace crate (`obs-push`, `alert-direct`, … are refused too, by the plain rule, not because they hold OMS code).
- `crates/watcher-conformance`: package `watcher-conformance`, `publish = false`, an empty `src/lib.rs` and the tests. Dev dependencies: `watcher`, `oms-core`, `oms-journal`, `serde_json`. It is the only package that links the watcher with OMS code.
- `tools/ci/watcher_independent.sh [manifest]` (default `./Cargo.toml`): runs `cargo metadata --format-version 1 --locked --offline --filter-platform <host> --manifest-path <manifest>`, with `<host>` from the `host:` line of `rustc -vV`, and uses `jq` (review 2 M1). Without `--filter-platform` the command needs every package of `Cargo.lock`, also those of other platforms that `cargo build` on Linux never downloads; at `a8f3790` it exits 101 offline ("failed to download `android_system_properties v0.1.6`"), and with `--filter-platform x86_64-unknown-linux-gnu` it exits 0 (both run for this spec). What each rule reads: rules 2, 3 and 5 read `packages[].dependencies`, the declared dependencies of every target of the manifest (a `cfg(windows)` dependency is still seen on Linux); rule 4 walks `resolve.nodes`, the resolved graph of the host platform only. Known limit, written in C-WATCH and ADR-031: a package reachable only through a dependency of another platform is not walked by rule 4 (rule 2 still catches it when the watcher declares it directly). Exit codes (review 1 M1):
  - 0: no finding; prints `watcher_independent: ok`.
  - 1: one or more findings; one line per finding, in the form given below; never prints `ok`.
  - 2: it could not check (cargo metadata failed, `rustc -vV` gave no `host:` line, for example a stale lock under `--locked`; `jq` failed; the output is not the expected JSON); it prints `watcher_independent: cannot check: <reason>` and cargo's own error. CI treats 1 and 2 both as red.
  Findings and their lines:
  1. the package `watcher` is missing → `watcher_independent: missing: package watcher`;
  2. a declared dependency of `watcher` of any kind (normal, `build`, `dev`; any `target`) is named `oms-*` or `md-*` → `watcher_independent: declared: watcher -> <dep> (<normal|build|dev>)`, with `, target <cfg>` inside the parentheses when the dependency has a target;
  3. a declared dependency of `watcher` is a local path package other than `http-fake` with kind `dev` → `watcher_independent: path: watcher -> <dep> (<kind>)`;
  4. the resolved graph reachable from `watcher` through normal and build edges contains a package named `oms-*` or `md-*`, or any workspace member (transitive reuse) → `watcher_independent: reachable: watcher -> <a> -> … -> <pkg>` (one shortest path per such package);
  5. a workspace package other than `watcher-conformance` depends on `watcher` (the OMS must not link the watcher either) → `watcher_independent: reverse: <pkg> -> watcher (<kind>)`;
  6. source pulled in by path (review 3 S3; a `#[path]` or `include!` shares OMS code with no dependency edge, and the repository uses the pattern, `oms-projector/tests/projector.rs:7-8`): a plain text search of every `*.rs` file under the `watcher` package's directory (taken from its `manifest_path` in the metadata: `src`, `tests`, `benches`, `examples`, `build.rs`) for `#[path`, `include!`, `include_str!` and `include_bytes!`, and for `path` followed by optional spaces and `=` inside any attribute (`#[cfg_attr(<cond>, path = "…")]`; review 4 N3). A match is a finding when its argument is not one plain string literal (for example `concat!(env!(…), …)` or a macro variable), is absolute, or, resolved against the directory of the file that holds it, leaves the package directory → `watcher_independent: source: <file relative to the workspace root>:<line>`. A match inside a comment is a finding too (plain text search, 판단(모델 아님): write the comment another way). No exception: the watcher reads `docs/contracts/tail.md` at test time with a file read, never with `include_str!`. A symbolic link anywhere under the package directory is a finding too, whatever it points at (review 4 N3) → `watcher_independent: symlink: <path relative to the workspace root>`.
  CI: a step "Watcher depends on no OMS or market-data crate" right after "Build", on the real tree with `--locked`. After "Build" the host platform's packages are fetched, so `--offline` resolves with `--filter-platform`; the packages of other platforms are not fetched, which is why the filter is needed (review 2 M1 corrected an earlier, false reason here). ### Clock
- Every timer of the watcher reads one injected clock, `trait Clock { fn now_ms(&self) -> u64 }` (wall time, ms since the epoch). The runtime uses `SystemTime`; tests use a manual clock that only moves when the test moves it. Success times on the wire are this clock (the OMS compares them with its own record time on the same host, `api.md:34`).
- A clock that steps back: elapsed times are `saturating_sub`, so timers hold until the clock passes the old value again (as the OMS gate, U18b4 review M1). Known limit, documented in C-WATCH.
- The age rules compare this clock with venue times (`updatedTime`, `execTime`). A host clock ahead of the venue by `min_age_ms` (2 s) or more makes every venue time "old" (the `recv_window` of 5 s lets such a clock still sign requests). The effect is an earlier confirmation, never a missed one. Known limit, written in C-WATCH beside the clock-step limit (review 3 N7).
- No part of the watcher sleeps on the `Clock`. Every wait (the start retries, the 403 pause, the guard, the IP recheck, the rounds) is a sans-IO step that returns the instant it next wants to run; the test moves the manual clock to that instant, and the U19a7 runtime sleeps until it (review 3 S2).

### Errors at start and in a round
- Start refusals exit with code 2 and one line on stderr naming the reason. Nothing at start writes a file.
- In a round, an error ends that round without a success and without a comparison. The next round is the retry. There is no retry inside a round (the interval is the backoff; this keeps the request rate within the design budget).

### Reader (`watcher::journal`)
- `Tail::open(data_dir) -> Tail`, `Tail::read(&mut self, cap: u64, max_records: usize) -> Result<Vec<Record>, JournalError>`. A `Record` is `{seq, at, record_schema, events: Vec<(String, serde_json::Value)>}`; `input` is not parsed.
- It lists `journal-<20 digits>.oj`, keeps (segment first seq, byte offset, next seq) and reads frame by frame from the offset: the 16-byte frame header, then exactly that payload, until `max_records`, the cap or the end of the file (no whole-segment load and no re-read of the rest of a large segment at each call; a frame is at most 16 MiB; review 1 N4). It opens files read-only, never opens `LOCK`, never creates, renames or writes anything.
- Header: magic, length ≤ 64 KiB, CRC, `format == 1`, `record_schema ∈ {1, 2}`, `first_seq` equals the expected next seq, the same `instance_id` in every segment. A segment whose frames were not yet read has its header read again at each call (C-TAIL `tail.md:13`).
- Frame: length ≤ 16 MiB, CRC over sequence + payload, sequence = expected, payload JSON with `seq` equal to the frame's and `at` not below the previous record's (C-JOURNAL step 3, `docs/contracts/recovery.md:21`).
- Cap: a frame whose sequence is above `cap` is not decoded or returned (only its 16-byte header is looked at). Damage at or below the cap (short frame, short header, bad CRC, wrong sequence, missing segment, wrong instance) returns `Err` after the good records before it have been returned by an earlier call; the position does not move, and the same call gives the same error until the files change (C-TAIL `tail.md:14`).
- First segment: the watcher has no persisted state and replays from record 1 at every start. A journal whose first segment does not start at 1 is refused (`JournalError::NoStart`), the start waits and logs (judgment, owner question 9).
- `max_records` per call: 10,000 (판단(모델 아님)), so the boot replay of a long journal is many calls and a round in U19a5+ is never stuck behind it.
- Replay time grows with the journal (it holds every heartbeat, about 17,000 a day at 5 s, plus margin reports and reference prices). U19a2 measures records per second on a generated journal of 100,000 records (release build, this PC) and reports it; C-WATCH states the boot time per million records from that measurement. While the boot replay runs no heartbeat is sent (owner question 9).
- Errors: `Damaged {seq, why}`, `UnknownEvent {seq, name}`, `Schema {segment, schema}`, `Instance {expected, found}`, `NoStart`, `Io(kind)`, and (from the engine, U19a5) "durable sequence went back". Two classes (review 2 S6):
  - **retried**: `Io`, `Damaged`, `NoStart`. The position does not move; the next round (or the next boot step) reads again from the same position, so a passing condition (a file-descriptor limit, a segment listed while it is being created) heals without a restart. A lasting one gives the same error every round, and the checks' ages grow until the OMS gate closes.
  - **latched until restart**: `UnknownEvent`, `Schema`, `Instance`, "durable sequence went back". The reader reads nothing more; every later round fails without a journal read. These do not heal by reading again (the watcher must be taught the event or schema, or the journal is another one).
  `watcher_journal_error = 1` in both classes; it returns to 0 only after a good read in the first class, never in the second. One error line per change of state (error / no error), not per round.

### Signer and client (`watcher::sign`, `watcher::rest`)
- Own HMAC-SHA256 and query string per `gateway.md:93` ("서명" row): GET only; POST signing for U19b's cancel-all is left to U19b (review 1 N3). Sorted keys; values sent as they are; a value with a character outside `[A-Za-z0-9-_.~%:,]` is refused before anything is sent.
- `Client::get(path, params) -> Result<Value, RestError>`: IPv4 local address, connect timeout 3 s, `request_timeout_ms`, no redirects, no proxy, the five headers. `RestError` classes and their effect:

| Answer | Class | Effect |
|---|---|---|
| connect failed, nothing sent | `not_sent` | round fails |
| timeout, HTTP 5xx, unreadable body, no retCode, retCode 10016 | `no_answer` | round fails |
| HTTP 401; retCode 10003, 10004, 10005, 10007, 10010, 33004 | `auth` | **never retried**: every Bybit request stops until the process restarts; `watcher_auth_rejected = 1`; one error line with the code |
| HTTP 403 | `ip_banned` | every Bybit request (and the echo) stops for 600 s (F18 L186, as the OMS, `rest.rs:108-111`) |
| HTTP 429, retCode 10006 | `rate_limited` | round fails |
| retCode 10002 | `clock` | round fails |
| other non-zero retCode | `refused` | round fails |
| retCode 0 but the rows cannot be read | `unreadable` | round fails (counted by the check, not the client) |

  The scope names 10010, 10003 and 33004; the other three codes and HTTP 401 are added because the OMS treats them as not healing (`rest.rs:97-101`) and stopping is the safer side (owner question 3).
- Request guard: at most 60 requests in any 10 s window, all Bybit paths together (판단(모델 아님); see "Budget" (U19a9) for the worst case of 47 and for many open orders); a request beyond waits for the window, it is not dropped. The guard is a sans-IO part on the injected clock: `Guard::admit(now) -> Result<(), u64>` records the request, or returns the earliest instant (ms) at which it may go; the client sleeps until that instant and asks again. So `client::the_guard_holds_requests_beyond_60_in_10_s` drives the guard on the manual clock and needs no real 10 s (review 2 N6). This protects the IP limit the OMS shares (600 per 5 s per IP, design §7.3) from a runaway loop.
- Every request is counted in `watcher_requests_total{endpoint}` before it is sent.

### Start checks (`watcher::start`), in order
1. Config and credentials (above). Refusal → exit 2.
2. `GET /v5/user/query-api`: `isMaster == false`, `userID == sub_account_uid`, `ips` is a list of strings with at least one address and no `*` (a key bound to no IP is refused, as the OMS `checks.rs:186-192`; owner question 2). A readable answer that fails one of these rules (a refusal) → exit 2. An `auth` answer → no exit: the watcher stays up with `watcher_auth_rejected = 1` and never sends another Bybit request (its checks never succeed, so the OMS gate closes; this is visible through the export, which runs from config load, and the log; a restart loop is not). Every other answer (`not_sent`, `no_answer`, `rate_limited`, `clock`, `refused`, `unreadable`, `ip_banned`) → one log line and a retry every 5 s (판단(모델 아님)); after `ip_banned` the first retry waits for the 600 s pause (review 2 S3). The start does not go on until step 2 has a readable answer.
3. `watcher_api_key_days_left`: from `expiredAt`, RFC 3339 UTC `YYYY-MM-DDTHH:MM:SSZ` (own parser; fractional seconds accepted and dropped). Not exported when the field is absent, unreadable (one warn line), or at or before `1970-01-02T00:00:00Z` (the documented "does not apply" example is the epoch). Otherwise `floor((expiredAt − now) / 86,400 s)`, which is negative once expired.
4. Public IP: GET `ip_echo_url` (IPv4, timeout `request_timeout_ms`, body = the address); `watcher_public_ip_ok = 1` if it is in `ips` (IPv4-mapped IPv6 compares as IPv4), else 0 and one warn line. An echo that fails (any client class) or whose body is not an IPv4 or IPv6 address also gives `watcher_public_ip_ok = 0` and one warn line: an unknown IP is not ok (review 2 S3). Not a refusal, and the start goes on: Bybit will answer 10010 and the watcher stops itself (row 2 of the table).
5. Every symbol: `GET /v5/market/instruments-info?category=linear&symbol=<s>`. The row for that symbol must exist and have `settleCoin == "USDT"`; otherwise exit 2 ("<s> settles in <coin>; the watcher's scope is linear/USDT"). Every other answer (`not_sent`, `no_answer`, `rate_limited`, `clock`, `refused`, `unreadable`, `ip_banned`) → one log line and a retry every 5 s (판단(모델 아님)), after `ip_banned` first the 600 s pause; `auth` → stay up without requests, as in step 2 (review 2 S3). The checks do not start until every symbol is confirmed.
6. Every `ip_check_ms` after that: query-api again (the IP list may change) and the echo → `watcher_public_ip_ok`, `watcher_api_key_days_left` refreshed. Answers of a recheck (review 2 S3): an echo failure or a body that is not an address, or a query-api answer that fails (any class but `auth`) → `watcher_public_ip_ok = 0` with one warn line, `watcher_api_key_days_left` keeps its last value, the next recheck comes at the normal pace; `auth` → as in the client table; a readable query-api answer with another `userID`, `isMaster = true` or no bound IP (`[]` or `*`) → every Bybit request stops until restart, as for `auth`, with `watcher_auth_rejected = 1` and one error line naming the rule (the key no longer passes the start check; the safer side). In U19a4b this is a sans-IO step (`IpCheck::poll(now) -> Option<request>`, `on_answer`) on the injected clock, which the test drives; the U19a7 runtime calls it in its loop. These requests are outside the 2.7 req/s reconciliation budget (1 per minute) and inside the guard. The first recheck is due `ip_check_ms` after step 4's echo answered; each later one `ip_check_ms` after the previous recheck's last answer. The runtime runs `IpCheck` from the end of step 5 on, also while it waits for `/api/status` and during the boot replay (the replay yields to the loop between `Tail::read` calls), so `watcher_public_ip_ok` and `watcher_api_key_days_left` stay fresh while the OMS is down (review 3 N2).

## U19a5 and U19a6 decisions: the check engine and W1 (U19a5), W2 (U19a6)

### Engine (`watcher::engine`, sans-IO)
- `Engine::new(cfg, journal_state, start_ms)`; `poll(now) -> Vec<Action>`; `on_venue(now, req_id, Result<Value, RestError>) -> Vec<Action>`; `on_status(now, req_id, Result<Status, String>) -> Vec<Action>`; `on_admin(now, check, Result<String, String>) -> Vec<Action>`. `Action` = `Venue {req_id, path, params}`, `Status {req_id}`, `Mismatch {check, detail}`, `Heartbeat {checks}`. The metrics export is not an engine action: the runtime pushes on its own timer from the moment the config is loaded (U19a7, review 2 S4). The engine reads the journal itself through `Tail` (synchronous, bounded by `max_records`).
- Scheduler: each check and the heartbeat has `next_due`; the first `next_due` of each is `start_ms`, so the first rounds and the first heartbeat come at the first `poll` (review 2 N4). At `poll(now)` a due check starts a round unless its previous round is still open (no overlap, no pile-up); `next_due = round start + interval`. A late round runs once, not several times.
- A round: (1) the venue requests, pages one after another; (2) one `Status {req_id}` request of its own, emitted only after that round's last venue answer (`journal.durable_seq`, `core.instance_id`); (3) the journal is read up to that cap; (4) the comparison. Each status answer is matched by `req_id` to the one round that asked and is used by that round only; two rounds never share an answer (review 1 M2). The venue is read **before** the journal: the OMS sends nothing before its record is durable (C-COMMIT), so anything the venue shows that the OMS made is already in the journal the watcher reads after it.
- `Status` answer refused when: not JSON; no `journal.durable_seq` (u64) or `core.instance_id` (16 hex); `instance_id` differs from the journal headers (→ journal error "instance", the reader stops). Each status request records `seq_at_send`, the state's `last_seq` when it was emitted. A cap below `seq_at_send` → journal error "durable sequence went back" (the OMS published a cap below records the watcher had read before it asked: a different journal). A cap at or below the current `last_seq` (another round read further in the meantime) is not an error: there is nothing new to read, and the round compares against the state it has, which is newer than its venue read (the safe order). Answers may arrive in any order. An unreachable OMS fails the round (no judgment without the journal; owner question 8).
- Success: a round succeeds when every request answered, the journal reached the cap, and every subject was judged (agree, or a difference that counts). Its success time is the clock at the end of the comparison. A failed or deferred round leaves the old success time; `watcher_check_age_s{check}` grows. Wherever this spec says "the time a round saw something" (W1 `foreign` first sighting, W2 observation time), it is this same clock read, at that round's comparison (review 3 N2).
- Lost and stray answers (review 3 N3): an answer whose `req_id` no open request owns (a late answer after a deadline, a duplicate) is ignored with one debug line. Every emitted `Venue` or `Status` request has a deadline, the clock at emission + `request_timeout_ms` + 11,000 ms (the guard's 10 s window plus 1 s, 판단(모델 아님)); at `poll`, a request past its deadline is taken as `no_answer`: its round fails and closes, so one lost answer never keeps a check's round open for good. Test `engine::a_request_without_an_answer_fails_its_round_at_the_deadline_and_a_late_answer_is_ignored`.

### The two-round rule (W1 in U19a5, W2 in U19a6; reused by W4 in U19a8 and W3 in U19a9)
- A difference has an identity `(check, subject, kind, value)`. It is **confirmed** when the same identity was present in the previous completed round of that check and in this one, and at this round the age condition holds (W1: the order's `fact_at` at least `min_age_ms` old; for an order unknown to the journal, the first round it was seen at least `min_age_ms` ago; W2: below). "At least `min_age_ms` old" means `now − t ≥ min_age_ms` everywhere (review 1 N7). A difference present in one round only never alarms. The first round may be fresh: the age is judged at the confirming round (this is what lets W2 confirm within 3 s, see the done criteria).
- A difference whose identity changes (another value, another kind) starts again at 1.
- Round result per difference for W1 (review 1 S1): first sighting → **pending**, the round may still succeed; seen in this and the previous round but the age condition fails → **deferred**, the round is not a success (the OMS gate bounds a deferral at 10 s of W1 age, design R5); seen twice and old enough → confirmed. W2 has its own, stricter rule below (a young difference defers the round even at its first sighting, design R5 SHOULD 2); W4 is in U19a8, W3 in U19a9.
- On confirmation: `watcher_mismatches_total{check} += 1` (once per identity: a later round or sweep that still sees the same identity does not count it again; review 2 N2), one error log line, and the engine emits `Mismatch {check, detail}` subject to the resend rule (U19a7). A confirmed difference stays listed (log and `watcher_differences` excluded) until a round no longer sees it.
- `detail`: `"<check> <kind> <subject>: venue <…>, journal <…>; seen 2 rounds, journal entry <a> s old"`, with `"; and N more"` when the round confirmed several; cut to 1024 bytes at a char boundary (`api.md:32`).
Amendment (U19a5 review 1 S1, S2, N3): a failed round leaves the last completed round's sightings as they are (seen, failed, seen confirms at the third round; test `engine::a_failed_round_keeps_the_sightings_of_the_last_completed_round`), and one identity listed twice in a round (an order on two pages) is one difference (test `w1::an_order_listed_on_two_pages_is_one_difference`); xtask mutants M239 (age not judged) and M240 (went back against the current `last_seq`), the second forms of defects 14 and 30, and M241 (a failed round clears the sightings) and M242 (an identity counted twice in a round), after M238.

### W1 open orders (every `w1_ms`)
- Venue: `GET /v5/order/realtime?category=linear&settleCoin=USDT&limit=50` and `cursor` pages, at most 20 pages (판단(모델 아님), as the OMS `query.rs:71`); more pages → the round fails ("more than 1000 open orders"). Paging rule for W1 and W2 (the OMS's own, `query.rs:263-272`; review 1 S3): a page with an empty `nextPageCursor` that is not full ends the snapshot; a full page with an empty cursor → `unreadable` (it may not be the last); a cursor equal to the previous one → `unreadable`; otherwise follow the cursor (an empty page with a cursor is followed, inside the page cap). Open = `orderStatus ∈ {New, PartiallyFilled, Untriggered}`; other rows are ignored. A row must have `orderLinkId` (string, may be empty), `orderId`, `symbol`, `side`, `qty`; else `unreadable`.
- Journal: the open set and order info.
- Differences:

| Kind | Condition | Subject |
|---|---|---|
| `foreign` | open at the venue; `orderLinkId` does not decode as `Base32Pair` with the journal's instance, or decodes to an order id the journal never accepted | venue `orderId` |
| `closed_in_journal` | open at the venue; the order is closed in the journal | `orderLinkId` |
| `details` | open in both; symbol or side differ | `orderLinkId` |
| `missing_at_venue` | open in the journal, `acked`, not `in_doubt` and not `terminal`; not open at the venue | `orderLinkId` (encoded) |
| `open_after_terminal` | open at the venue; the journal has `venue_terminal` for the order (`terminal`) and no `order_closed`; the age is `fact_at`, which `venue_terminal` moved, so the venue still lists the order at least `min_age_ms` after the journal recorded its end | `orderLinkId` |

  An open journal order with `terminal` that is not at the venue agrees: the journal itself records that the venue ended it, and a missing fill shows in W2 and W4 (review 2 S1). An open journal order that is not acked, or in doubt, and not at the venue is not compared: it may be unsent or its result unknown, and the OMS resolves it itself (C-GW G-1/G-5; owner question 5). Quantity is not compared (amends and partial fills change it; W4 and W2 cover fills).

### W2 positions (every `w2_ms`)
- Venue: `GET /v5/position/list?category=linear&settleCoin=USDT&limit=200` and cursor pages by W1's paging rule, at most 5 pages (판단(모델 아님)); more → round fails. Per row `symbol`, `side` (`Buy` +, `Sell` −, `""` or `None` 0), `size` (decimal), `updatedTime` (ms string, optional). Several rows for one symbol (hedge mode) → `unreadable` (the OMS refuses hedge mode, `checks.rs:313-326`).
- Journal: position per instrument = Σ fills + external fills + venue changes + adjustments (`tail.md:52`). Parked fills are not counted (scope wording; owner question 4).
- Per symbol in either set: `d = venue − journal`. `d == 0` → agree. `d ≠ 0`:
  - Two times are judged: the journal's `last_change_at` of the symbol and the venue's latest change time (below). A time is **young** when it is known and `now − t < min_age_ms`. A time that is not known is **old**: no journal change time (`last_change_at = None`: the journal never changed the symbol, for example a manual trade on the sub-account, a transferred position or a fill the OMS never saw) and no venue time are both old (review 2 M2; owner question 10). The venue's time is known far more often since review 3 S1 (below): an unknown venue time means the size has not changed since the watcher's first round.
  - if a known time is young → **deferred**: no count of its own beyond the candidate value, and the round is not a success (fills are still arriving; a deferral longer than 10 s closes the OMS gate, design R5);
  - else if the previous completed round had the same `d` for the symbol → confirmed;
  - else → first sighting (pending), the round is a success.
  So a venue position in a symbol the journal never changed is confirmed at the second round. An implementation that keeps the time as `Option` must test "known and young", never "known and old".
- Venue observation (review 3 S1). With `settleCoin=USDT` and no symbol, `position/list` returns only rows with size > 0 (facts Q12.1), so a symbol whose venue position went to 0 has no row and no `updatedTime`, exactly when it was just closed. The engine therefore keeps, per symbol, `{size, seen_at}`: the venue's signed size at the last round that read every page (an absent row = 0) and `seen_at`, the time of the first round that saw that size (the round's comparison clock, see "Success"). A round that reads another size than the kept one sets `seen_at` to its own time. Sizes read in the watcher's first W2 round that read every page get no `seen_at` (`None`): they are the state found at start, not a change seen. A round that reads every venue page and then fails before its comparison (status unreachable, journal error) still updates `{size, seen_at}`, with the clock at its last venue answer as the time (review 4 N2): a size change seen while the OMS is down is then old enough when the OMS answers again, not young again. Test `w2::a_size_seen_by_a_round_that_then_fails_keeps_its_seen_time`. Entries exist for every symbol the venue or the journal ever showed; the map is bounded by the venue's linear symbol list (판단(모델 아님): a few hundred).
- Venue's latest change time: the row's `updatedTime` if present and readable; else `seen_at`; and from U19a9, W4's newest agreeing `execTime` for the symbol when it is newer than the time chosen so far. Only when none is known (a size seen unchanged since the first round, without `updatedTime` and without a W4 time) is the time "unknown", taken as old (owner question 10: an unknown time must not block a confirmation).
  - So a position closed at the venue is deferred until 2 s after the round that first saw it flat, like a non-zero row with `updatedTime` (scenario: closed at t, first seen flat at a round r ≤ t + 1 s; deferred while `now − r < 2 s`). A venue size that changes every round without `updatedTime` is young at every round and defers it, so W2 does not report success and the OMS gate closes at 10 s instead of W2 reporting fresh successes while nothing is confirmed.
  - The 3 s done criterion still holds on the manual clock: the plant carries `updatedTime` = its moment, and `seen_at` is used only without `updatedTime`; without it, `seen_at` is at most one interval after the change, so the confirmation is at most 1,000 + 2,000 ms after it.
Amendment (U19a6 review 1 S1, S2, N1): a row whose `side` is `""` or absent counts as 0 only with size 0; with a size it is `unreadable`, and a size that starts with `-` is `unreadable` (the OMS's own rule, `query.rs` `signed_size`), so a position the OMS does not know is never read as flat (test `w2::bad_pages_and_rows_fail_the_round`); a `d` out of the decimal's range is a difference with value `overflow`, not agreement (test `w2::a_difference_too_large_to_subtract_is_still_a_difference`); test `w2::a_round_that_failed_between_pages_leaves_no_observation` (page 1 read, page 2 lost: the next complete read is the first); xtask mutants M243 (a size without a side read as flat), M244 (a partial read observed as complete), M245 (an overflow read as agreement), after M242.

## U19a7 decisions: OMS links, runtime, binary

### `/api/status` client
- `GET status_url` with `Host: 127.0.0.1:<port>` (or `[::1]:<port>`), timeout `request_timeout_ms`, no redirects. Only `journal.durable_seq` and `core.instance_id` are read.

### `admin.sock` client and the resend rule
- One connection per send: connect, `{"id":1,"op":"hello","client":"watcher/<name>"}`, then `{"id":2,"op":"watcher_mismatch","check":"W<n>","detail":"…"}`, read both replies (timeout `request_timeout_ms`), close.
- **Hold off** for check `W<n>` (review 4 S2): the journal state the engine holds shows `holds.watcher_mismatch == false`, and, if a send of `W<n>` was ever answered `"held"` or `"already held"`, that state was read up to the cap of a status request emitted after the latest such answer. The answer comes after the `hold_set` is durable, so such a cap includes it, and a hold that is off at such a cap was cleared by an operator after it; a state read before the cap has caught up would show a hold that is off only because the `hold_set` is not read yet.
- **Owed** (review 2 S2, narrowed by review 4 S2): a confirmed difference is owed from its confirmation until a send that carried it is answered `"held"`. Nothing else pays it: not `"already held"` (the hold was set by another send and its note does not name this difference, `holds.md:94`), not a journal state that shows the hold, not a failure. An owed difference is sent even when later rounds no longer see it (a W4 row that left the window, a W1 order that closed), with its `detail` as it was at the confirmation. So a difference confirmed while an older hold is set (also in the round whose journal read already showed that hold) is sent once that hold is cleared, and the new hold's note names it. This is bounded: each identity is paid by one `"held"` answer, and one send carries all owed differences of its check. Known cost (the safe side): when a `"held"` answer is lost (timeout) but the OMS recorded the hold, the difference is sent once more after the next clear.
- **Due**: a send of `W<n>` is due when the hold is off, `W<n>` has an owed difference or (W1, W2, W3 only) a confirmed difference that a round still sees, and `mismatch_resend_ms` has passed since the start of the previous send of `W<n>` (the instant its connect began; review 3 N2), or there was none. One send carries all of them in its `detail` (first one, then `"; and N more"`). So for W1, W2 and W3 an operator's `clear-hold` while the difference persists brings the hold back (owner question 7). For W4 a paid identity is dismissed at the first hold off instead and is not sent again (U19a8, "W4 executions", review 3 M1).
- **One send per check in flight** (review 4 S6): a send of `W<n>` is not started while the previous send of `W<n>` has neither an answer nor a failure. A send that is due meanwhile waits for it. The client bounds a whole send (connect and both replies) by 2 × `request_timeout_ms` (20 s at the largest config) and reports a failure after it; the engine also takes a send without `on_admin` after emission + 2 × `request_timeout_ms` + 1,000 ms as a failure (판단(모델 아님)), so a lost report never blocks the check's sends. `on_admin(now, check, …)` therefore always belongs to exactly one send, and `"held"` pays exactly the differences that send carried.
- Amendment (U19a7 review 1 S1): the engine's deadline is on the injected wall clock and the client's bound on tokio's monotonic time, so a report can arrive after the engine took its send as failed and started the next one. Each send has an id: `Action::Mismatch {check, send_id, detail}`, `on_admin(now, check, send_id, answer)`; an answer whose id is not the send in flight is ignored (one `debug:` line) and pays nothing (the safe side: what it carried is sent again after the next clear). Test `admin::a_late_report_of_one_send_pays_only_what_that_send_carried`, xtask mutant M246.
- Answers: `"held"` → every difference the send carried is paid. `"already held"` → nothing is paid; sends of `W<n>` wait for the hold to be off. `bad_request` → one error line (a watcher bug), not paid, the same resend pace. `overloaded`, `unavailable`, `unauthorized`, `internal`, any other error code (`oms-api/src/lib.rs:176-193`), a timeout, a refused or missing socket → not paid, the same resend pace (review 4 N4).
- The owed list lives in memory only (nothing is persisted; a restart loses it, known limit in C-WATCH). `watcher_mismatch_active{check}` counts owed differences as well as the still-seen confirmed ones (review 4 S1).

### `monitor.sock` heartbeat client
- One persistent connection: `hello` without a strategy, then every `heartbeat_ms` `{"id":n,"op":"heartbeat","watcher":"<name>","checks":{"W1":<ms|null>,"W2":…,"W3":…,"W4":…}}` (W4 is `null` until U19a8 runs it, W3 until U19a9). Reply `"recorded"` → `watcher_heartbeat_ok_ts`. A closed or failed connection is reopened at the next heartbeat (the pace stays one per `heartbeat_ms`, far below 2 per second per connection, `api.md:34`). This covers a `monitor.sock` that does not exist (an OMS without `[core.policy.monitor]`, `api.md:7`) or refuses: one connect try per `heartbeat_ms`, and one log line per change of state (connected / not connected, with the reason), as the reader logs (review 3 N6). `bad_request` (for example a check time ahead of the OMS's clock) → one error line per minute. Every other error answer (`overloaded`, `unavailable`, `unauthorized`, `internal`) → one error line per minute, the connection is kept. A reply that does not come within `request_timeout_ms` counts as a failed connection: it is closed and reopened at the next heartbeat (review 4 N4).
- The first heartbeat (due at `start_ms`) is all `null` by construction: no round has ended yet. The first heartbeat that can open the OMS gate is the next one, `heartbeat_ms` later (review 3 N6).
- The heartbeat is sent even while every check fails: the gate then sees stale W1/W2 and closes (that is the intended effect). The OMS judges W1/W2 at the heartbeat's record time (`core.rs:270-292`), so the gate closes at the first heartbeat whose W1 or W2 time is older than 10 s, which is 10 to 10 + `heartbeat_ms` s (10 to 15 s at the default) after the last success; C-WATCH part 7 says "10 to 15 s" (review 4 N1).

### Runtime and binary
- `watcher --config <path>` (and `--version`). Boot: config and credentials → the metrics push timer starts (review 2 S4) → start checks (U19a4b) → wait for `/api/status` (retry every 1 s, a log line every 10 s, 판단(모델 아님)) → replay the journal from record 1 to the cap → start the engine. Heartbeats start with the engine (all `null` until a success).
- The runtime is a single-threaded tokio loop: it calls `engine.poll(now)` every 100 ms (판단(모델 아님)), runs each action on its own task (requests in flight at most one per check, plus status, admin and heartbeat), and feeds answers back. The metrics push runs on its own timer beside the engine (above).
- Shutdown on SIGTERM or SIGINT: no new rounds; in-flight requests get at most `request_timeout_ms`; one last metrics push; the monitor connection closes; exit 0. Nothing is persisted.
- The binary has no network override: the REST base comes only from `network`. Tests call the library's `run(cfg, Endpoints, clock, shutdown)` with loopback endpoints. No test starts the `watcher` binary with a config (it would call a real Bybit host); the only binary test runs `watcher --version`. The shutdown test drives the `shutdown` input of `run` and asserts the shutdown steps (review 4 S4). The wiring from SIGTERM/SIGINT to `shutdown` in `main.rs` is a few lines covered by review and listed under "Not verified" in the U19a7 report. A signal sent to the test process itself would hit every test of that binary, so no test sends one.

## U19a8 and U19a9 decisions: W4 (U19a8); W3, the W2 fallback, budget (U19a9)

### W3 wallet and margin (every `w3_ms`)
- `GET /v5/account/wallet-balance?accountType=UNIFIED`; the `UNIFIED` row's `totalEquity`, `totalMaintenanceMargin`, `totalMarginBalance` (decimals); else `unreadable`.
- Violations (identity = kind only, value not part of it):
  - `account_mm_rate`: `maintenance > 0` and `maintenance × 10 000 ≥ account_mm_rate_max_bps × margin_balance` (the OMS's formula, `margin.md:125`);
  - `daily_loss`: the journal's `day_base_set` has `day` = today's UTC day number and `(base − totalEquity) × 10 000 > daily_loss_bps × base` (`margin.md:104`). Without today's base this part is not judged (owner question 6).
- Confirmed on 2 consecutive rounds (design §7.5 "한도 위반 2회 연속"); no journal-age rule.

### W4 executions (every `w4_ms`)
- A **sweep** reads the window `[start, end]` with `GET /v5/execution/list?category=linear&settleCoin=USDT&limit=100&startTime=<start>&endTime=<end>` and its cursor pages. `end` = the clock at the sweep's first page and stays fixed for the sweep, so the cursor's row set does not move under new executions. `start = max(watermark − w4_overlap_ms, ⌈fill_floor / 1000⌉)` (the floor is in µs and is rounded **up** to ms; review 1 S7); a window longer than 7 days is cut to `end − 7 days + 1 ms` with one warn line (the venue's limit, facts Q9.7).
- Pages: at most `w4_max_pages` per round. If the cursor is still not empty, the next round continues the same sweep with the same `start`, `end` and the cursor. The success time moves only at a completed sweep, so `watcher_check_age_s{check="W4"}` rises during a multi-round sweep (scope). Every page is one request in `watcher_requests_total`.
- End of a sweep (review 1 S3; the meaning of an empty `nextPageCursor` is not documented, facts Q9.9): the sweep is complete, and its rows are compared, at the first page that is empty, or whose `nextPageCursor` is empty. A full page (100 rows) with an empty cursor is accepted as the last page **for W4 only**: the done criterion "1,200 executions … 10 pages, then 2" needs 12 full pages with the last cursor empty. This is a known limit written in C-WATCH: if the venue ever ends a full page with an empty cursor while more rows exist, those rows are not compared by W4; W2 still compares the position they make. (The OMS's own fill sync is stricter and splits the window, `gateway.md:96`; W4 does not copy it, because a split costs pages the budget does not have.) A `nextPageCursor` equal to the one just sent is a failed page.
- A failed page (any client error, a page whose `result.list` is not an array or whose `nextPageCursor` is not a string, or an unchanged cursor) fails the round; the next round retries the same page with the same cursor. After 3 failed rounds in a row on one sweep (판단(모델 아님)) the sweep restarts from page 1 with the same `start` and a new `end` (a cursor that the venue no longer accepts must not stop W4 for good; review 1 S2), with one warn line. A sweep that has not completed after 50 rounds (판단(모델 아님); 500 pages at the default cap, 50,000 rows) restarts the same way and logs an error line.
- Initial watermark at start: `now − w4_initial_lookback_ms`, not below `⌈fill_floor / 1000⌉`. Known limit, written in C-WATCH (review 2 N3): executions older than `w4_initial_lookback_ms` (600 s) at the watcher's start are never compared by W4 when the watcher was down longer than that; W2 compares the position they make.
- A sweep that returns no execution at all leaves the watermark where it is (see the watermark rule below); the window grows (up to the 7-day cut). The warn line for a cut window is logged once per change of state (cut / not cut), not every round (review 1 N6).
- Rows are read per `execType`: classify first, then read only the fields the row's type is compared on (review 1 S2; the shape of Funding and ADL rows is untested, design R3 T15, and the OMS reads only `execFee`/`feeRate` from a Funding row, `exec.rs:125-136`).
  - Every row: `execId`, `symbol`, `execType` (non-empty strings) and `execTime` (ms, decimal string); key `<symbol>:<execId>` (`gateway.md:97`).
  - `Trade`, `AdlTrade`, `BustTrade`, `Delivery`, `Settle`: also `execQty` (decimal) and `side` (`Buy`/`Sell`).
  - `Funding` and unknown types: nothing more.
  - A row that lacks a field its type needs is a difference of its own, `unreadable_row` (subject = the key if `execId` and `symbol` are readable, else the row's compact JSON text cut to 200 bytes, 판단(모델 아님); value = the names of the missing fields). It follows the two-sweep rule like `missing_*`, with the age taken from `execTime` if readable, else as old (as owner question 10). An unconfirmed row without a readable `execTime` keeps the watermark where it is: for the watermark rule it counts as older than every other row of the sweep (review 4 S3), so the next sweep has the same `start` and reads it again. So an unreadable row ends in a hold instead of a silent stall of the watermark.
- Rows at the floor (review 1 S7): at comparison, a row with `execTime × 1000 < fill_floor` (the floor of the journal state the round compares against) is ignored: the OMS ignores such a fill too (`decide.rs:1596`), and the journal never holds it.
- Comparison per `execType` (scope, `gateway.md:101`):

| `execType` | Compared with | Difference |
|---|---|---|
| `Trade` | journal fills (`fill_booked`, `external_fill_booked`) by key | key missing (`missing_fill`); qty or side differ (`fill_details`) |
| `AdlTrade`, `BustTrade`, `Delivery`, `Settle` | journal venue changes by key, kind `adl`/`takeover`/`delivery`/`settle` | key missing (`missing_venue_change`); kind or signed qty differ (`venue_change_details`) |
| `Funding` | nothing | ignored (funding never changes quantity) |
| anything else | — | `unknown_exec_type`: **confirmed at once**, no second sweep (scope). "At once" is at the completed sweep: rows are compared only when the sweep completes, so in a multi-round sweep the confirmation comes up to the sweep's length later (review 2 N2) |

- `missing_*`, `*_details` and `unreadable_row` follow the two-round rule across sweeps, with the age condition "the row's `execTime` at least `min_age_ms` old" (`now − execTime ≥ min_age_ms`). A difference seen in one sweep only, or seen twice but young, does not make the sweep fail: W4 is not judged by the OMS gate, and a young row is read again by the next sweep because the watermark does not pass it. The watermark after a completed sweep = `max(old watermark, w)`, where `w` = the newest `execTime` such that every compared row at or below it agrees, is ignored, or is already confirmed. When no compared row qualifies (the oldest compared row is an unconfirmed difference, or the sweep had no row), the watermark stays where it is; it never moves back (review 3 N1). This keeps every unconfirmed row in the next window: a row of this sweep is at or after this sweep's `start`, and when `w` is below the old watermark the watermark, and so `start`, do not change. So an unconfirmed difference is read again by the next sweep, and a confirmed one no longer holds the window back.
- The watermark moves only when a newer execution exists. After a hold the account is usually quiet, so a confirmed row X can stay inside every later window for as long as no execution newer than X arrives (review 3 M1). A W4 difference is a fact about one past execution and does not change; so W4 does not resend it after a `clear-hold` (W1–W3 do, U19a7):
  - **Dismissed**: a confirmed W4 identity `(W4, subject, kind, value)` becomes dismissed when (a) it was paid (U19a7: a send that carried it was answered `"held"`, so its text is in that hold's note; `"already held"` or a journal state that shows the hold does not pay it, review 4 S2), and (b) after the pay, the journal state, once it has read up to the cap of a status request emitted after the pay, shows `holds.watcher_mismatch == false`. Condition (b) needs that later cap: an answer `"held"` is sent after the `hold_set` is durable, so a cap sampled after the answer includes it, and the hold being off at such a cap means an operator's `hold_cleared{watcher_mismatch}` came after it; a cap sampled before the answer may predate the `hold_set` and would dismiss too early.
  - An identity confirmed while an older hold is set is owed, not paid: after that hold is cleared it is sent once, and only after that send is answered `"held"` and the new hold is cleared is it dismissed (review 4 S2). Test `w4::a_row_confirmed_under_an_older_hold_is_sent_once_after_that_hold_is_cleared`: a W1 difference sets the hold; a W4 `missing_venue_change` row is confirmed in a round whose journal read already shows that hold; the test journal writes `hold_cleared{watcher_mismatch}`; asserts exactly one W4 `Mismatch` after the clear, none before it, and none after its `"held"` answer and a second clear.
  - A dismissed identity is never sent or counted again while sweeps still see it. It is forgotten at the first completed sweep that no longer sees it (the row left the window); if the same row were later read again, it would be a new difference and need two sweeps again (the safe side).
  - Another value for the same row (the venue changed the row) is another identity: it is confirmed and sent anew.
  - Memory only: a watcher restart forgets dismissed identities. A dismissed row inside the restart's `w4_initial_lookback_ms` (600 s) is confirmed again after two sweeps and sets the hold once more; the operator clears it once more. Known limit in C-WATCH (the safe side).
  - A lasting position difference is still W2's to resend (review 1 N8).
  - C-WATCH part 8 states this rule in place of the former sentence "the resend after `clear-hold` lasts only that long for W4", which was false for a quiet account (review 3 M1).
  - Test `w4::a_confirmed_row_is_not_sent_again_after_clear_hold_in_a_quiet_account`: a `missing_fill` row X is confirmed, sent and answered `"held"`. The test journal then writes `hold_set` and `hold_cleared{watcher_mismatch}`. No newer execution comes, and 60 s pass on the manual clock. Asserts: the watermark stays at X, every sweep reads X, and there is no second `Mismatch`. Test `w4::a_dismissed_row_that_leaves_the_window_and_a_changed_value_are_sent_anew`.
- `settleCoin=USDT` is sent as the OMS sends it (`query.rs:681`), but it is not a documented parameter of `execution/list` (facts Q9.3). W4 does not rely on that filter: an execution of a USDC contract in the answer is classified and compared like any other row. C-WATCH part 8 says so (review 4 N6).
- W4 also records, per symbol, the newest `execTime` of an agreeing `Trade` or venue-change row (U19a8); U19a9 makes it W2's fallback for a missing `updatedTime`.
- Amendment (U19a8 review 1 S1, S2, S3, N1, N3): a row whose `execTime` is after the sweep's `end` is `unreadable_row` (value `execTime`, age unknown, so it holds the watermark until confirmed), so the watermark never passes the `end` of the sweep that read it and one row from a venue that ignores `endTime` cannot make every later window `[end, end]` (test `w4::a_row_after_the_sweeps_end_is_an_unreadable_row_and_does_not_blind_w4`, xtask mutant M248); a `Trade` or venue-change row of quantity 0 is ignored, as the OMS books neither (`decide.rs` `on_fill` `qty <= 0`, `on_venue_change` `qty == 0`; test `w4::a_trade_or_venue_change_of_quantity_0_is_ignored_as_the_oms_ignores_it`, M249); test `w4::an_already_held_answer_to_a_w4_send_does_not_pay_it` guards that `"already held"` does not pay (M250, after M247); the restart warn line is written once per run of failed rounds, and `W4 pages are read again after a restart` once a page is read (test `w4::the_restart_warn_line_is_logged_once_per_run_of_failed_rounds`); C-WATCH part 8 lists the memory bound at the config maximum (`w4_max_pages` 50: 250,000 rows) for U20b's `MemoryMax`, and that rounds which read pages and then fail count in the run of failed rounds (review 1 N2).

### Budget
- Design budget: W1 1 + W2 1 + W3 0.5 + W4 0.2 = 2.7 requests per second (§7.5), when W1 and W2 take one page and W4 one page per round. The guard (60 per 10 s) is the hard bound; the budget is measured, not enforced.
- **Conflict between the scope and a done criterion** (followed: the scope; owner question 1). The scope's W4 rules (start 10 s before the last confirmed `execTime`, follow every cursor) re-read 10 s of executions every round. With 100 executions every 5 s spread evenly (20 per second) a sweep window holds about 300 rows = 3 pages, so the rate is (60 + 60 + 30 + 36) / 60 ≈ 3.1 requests per second, not ≤ 2.7. With one page per sweep (at most 99 rows in a 15 s window, i.e. at most 33 executions per 5 s) it is (60 + 60 + 30 + 12) / 60 = 2.7. The parts test both: the done criterion at 30 executions per 5 s, a load inside "at most 100 executions per 5 s" for which it holds with margin (a 15 s window holds about 90 rows, one page; 33 per 5 s would sit at the edge, a 15.15 s window holding a full page; review 1 S6), and the even 100-per-5-s load, which is reported as ≈ 3.1 (2.6 % of the venue's 120 per second per IP) with W4 keeping up. The U19a9 report lists this criterion as **not met as written** (owner question 1); the test names and claim V-WATCH-10 carry the load.
- Worst case for the guard (판단(모델 아님)): in 10 s, W1 10 + W2 10 + W3 5 + W4 2 sweeps × 10 pages + IP check 2 = 47 ≤ 60. This assumes one page per W1 and W2 round (at most 49 open orders, 199 positions).
- Many open orders (review 3 N4): the core allows 500 open orders by default (`max_open_orders`, `crates/oms-core/src/config.rs:191`), which is 11 W1 pages per round (10 full pages and one empty last page), 110 requests per 10 s against the guard's 60. The guard then holds requests back (it waits, as designed) and stretches the rounds: the other checks need about 17 of the 60 (W2 10, W3 5, W4 2 at one page), which leaves about 43 for W1, about 4 W1 rounds per 10 s, so a W1 round takes about 2.5 s, and the other checks' rounds stretch too, by the guard's waits (판단(모델 아님); estimate, not measured). That is still below the OMS gate's 10 s for W1 and W2. Test `budget::at_500_open_orders_the_guard_stretches_w1_rounds_below_10_s` (U19a9, model venue with 500 open orders, manual clock): asserts that the W1 and W2 ages at every heartbeat stay below 10 s, and the U19a9 report gives the measured W1 round time. If the assertion cannot hold, the part reports it as a finding; it does not loosen the test.
- Amendment (U19a9 implementation, measured): with 100 executions per 5 s spread evenly, the window `[w − 10 s, end]` is inclusive at both ends and holds 301 rows, so a steady-state sweep is 4 pages, not 3: (60 + 60 + 30 + 48) / 60 = 3.3 req/s in steady state, and 3.2 req/s (192 requests) over the first simulated minute, whose first sweeps are 1, 2 and 3 pages. The estimate ≈ 3.1 above did not count the row at the window's end. At 30 per 5 s the minute is exactly 162 requests (2.7). At 500 open orders the W1/W2 age at a heartbeat reached 7.0 s at most (W1 round time mean 1.9 s, max 7.0 s: the sliding guard window lets 60 go in a burst and then nothing for up to 10 s). The test name `budget::at_100_executions_per_5_s_the_rate_is_about_3_1_and_w4_keeps_up` is kept; it asserts 2.7 < rate ≤ 3.4.

## Owner questions (the parts use the default; the runner does not wait)

1. **Budget at the largest load.** With the scope's W4 rules (10 s overlap, every cursor), 100 executions every 5 s cost ≈ 3.1 requests per second, above the 2.7 of the done criterion. Default: keep the overlap and every page (no execution goes unread); the 2.7 test uses a load of 30 executions per 5 s and the 100-per-5-s case is reported as ≈ 3.1; the criterion is reported as not met as written. Alternatives: cap at 2.7 and let W4 fall behind, or a shorter overlap.
2. **A watcher key bound to no IP.** Default: refuse the start (as the OMS does; such a key expires in 90 days and the design wants IP binding, §7.4).
3. **Codes that are never retried.** Default: 10010, 10003, 33004 (scope) and also 10004, 10005, 10007 and HTTP 401 (the OMS's set; they do not heal).
4. **Parked fills.** Default: not counted (W2 sums booked quantities only; W4 matches booked fills only). A fill parked for more than about 3 s can therefore hold plain orders; a park lasts up to 120 s (`order-lifecycle.md:124`), so both W2 and W4 will set the hold in that case. On Bybit a park needs a fill without our `orderLinkId` while an own order on the same instrument and side has no venue id yet (`decide.rs:1602-1611`): rare, and the hold is the safe side (review 1 N5).
5. **Open journal orders that are not acked or are in doubt** and absent at the venue. Default: not compared (the OMS resolves them; W2 and W4 catch any fill).
6. **W3 limits.** Default: the watcher's own config with the OMS's values (5000 bps account rate, 500 bps daily loss); the daily loss is judged only when the journal holds today's UTC base.
7. **After an operator clears the hold while the difference persists.** Default: for W1, W2 and W3 the watcher sends `watcher_mismatch` again (at most every 10 s), so the hold returns. For W4 it does not (review 3 M1): a W4 difference is one past execution, and its row can stay in every window of a quiet account, so a resend would bring the hold back after every `clear-hold` until a newer execution came. A paid W4 identity is dismissed when the journal shows the hold cleared; W2 still resends a lasting position difference. Alternative: resend W4 too and state that the hold returns until a newer execution or a restart after 600 s (an operator could not keep it cleared). Since review 4 S2 (every check): only a `"held"` answer pays a confirmed difference; one confirmed while an older hold is set is sent once after that hold is cleared, so a clear can bring the hold back once for such a difference even for W4 or when the difference is gone. Alternative: pay it when the journal shows the hold (as before review 4; then no OMS note ever names it, and for W4 nothing reports it).
8. **OMS not answering `/api/status`.** Default: nothing is judged; the checks' ages grow and the OMS's gate closes by itself when it comes back without fresh checks.
9. **Replay at every start.** Default: the watcher keeps no state and reads the journal from record 1 each start; a journal whose first segment does not start at 1 is not read (the start waits). The replay time grows with the journal, and no heartbeat is sent while it runs, so a replay longer than about 30 s makes the OMS refuse plain orders and, 60 s later, cancel resting ones; U19a2 measures and reports the replay speed (review 1 N4). A persisted cursor would remove this; it is out of scope here.
10. **Change time unknown**: the venue's (`updatedTime` absent, the size unchanged since the watcher's first round, and no W4 time) or the journal's (the journal never changed the symbol, review 2 M2). Default: taken as old, so a stable difference, also a venue position the journal never knew, is confirmed at the second round. Since review 3 S1 a venue size the watcher saw change (also a position that went flat and so has no row) has a known time, the round that first saw it, and is deferred for 2 s like a row with `updatedTime`.
11. **A full W4 page with an empty cursor** (review 1 S3). Default: taken as the last page (the 1,200-execution done criterion needs it); known limit in C-WATCH, W2 is the backstop. Alternative: split the window as the OMS's fill sync does (costs pages beyond the budget).
12. **An execution row W4 cannot read** (review 1 S2). Default: a difference of its own (`unreadable_row`); after two sweeps it sets the hold. Alternative: skip the row (W4 would then never compare it).
13. **A key that stops passing the start rules while the watcher runs** (the 60 s recheck shows another `userID`, a master key or no bound IP; review 2 S3). Default: every Bybit request stops until a restart, as for a rejected key (`watcher_auth_rejected = 1`); the checks stop succeeding and the OMS gate closes. Alternative: keep checking and only log.
