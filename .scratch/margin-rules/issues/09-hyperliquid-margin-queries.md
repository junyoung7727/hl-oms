# 09: Hyperliquid gateway: margin report, venue setting and account mode

**What to build:** Against Hyperliquid the node sends the documented queries for the margin report, the per-instrument venue setting and the account mode, and turns the answers into the core's inputs. An answer with a missing, zero or unreadable number is rejected as a whole with a reason; it never becomes a partial report. A position on a coin that is not configured is kept. The shipped example configuration has a margin policy and loads. The steady-state query weight is computed from the configuration and refused above 600 per minute. Nothing here contacts the venue: the fixtures are the documented examples. Scenario rows: S17, S18, S21, S22, S25. Claims: V-MARGIN-10, V-CFG-1.

  - Smallest choices where the spec is silent:
    1. The weight check is enforced only for a Hyperliquid venue with a margin policy. Without a policy the weight is 192 and nothing is refused, so a configuration that loaded before still loads ("without a margin policy the behaviour is the same"). The simulated venue has no budget.
    2. An interval that does not divide a minute rounds its term up. Exactly 600 loads.
    3. The reference-price term (24) is counted as the spec says, although this gateway reads prices from the stream and sends no such query. It is unused room.
    4. The account mode is passed on letter for letter, also a string that is not documented. "Stays unknown" is implemented as "is never rewritten into a documented value"; the core then holds the account unless the allow-list spells the same string. The alternative, dropping an undocumented string, would leave the mode unknown and make the reconciler ask again every second at weight 20. A non-string answer, or one longer than 64 bytes, gives no input.
    5. A venue-setting answer must name the coin that was asked about; otherwise it gives no input.
    6. In a margin report a decimal must be a JSON string and `leverage.value` and `maxLeverage` JSON integers. A JSON number where the documentation shows a string refuses the whole report. This is strict on purpose; if the live venue differs, every report is refused and plain orders stop (the safe side), and the status shows the reason.
    7. The example's `account_modes_allowed` is empty (T10 is not verified). With the example as shipped every plain order is held by `AccountMode` until the operator writes the string the status shows.
  - Deviation from "documented examples already in the repo and the research notes": the `clearinghouseState` fixture is the example in the research note of 2026-11-15. The `activeAssetData` example is in neither place (the design agreement only says it was fetched). The fixture was written from the documentation as the implementer knows it, with the account replaced by `0xUSER`, and was not compared with the documentation again. The `userAbstraction` values are the five listed in the design agreement (D4.4). No request was made to the venue or to its documentation site.
  - Burst numbers (in the contract): 500 cancels leave 700 of a full budget (query at once), 100 of the start-up budget (10.1 s), 0 of an empty one (15.1 s, the longest wait).
  - Finding, not fixed here (reconciler, ticket 08's code): while a venue setting or the account mode is unknown the reconciler asks again every second. At weight 20 that is up to 1200 per minute for each instrument, the whole refill of the local budget, and it is outside the 600 budget, which counts only the 60 s poll. It happens when an answer cannot be read, when HTTP fails, and permanently for a flat instrument if T11 turns out false (no leverage in `activeAssetData` without a position). The local budget then starves the queries, margin reports included, down to its reserve of 300: plain orders are refused and after 60 s the stale cancel fires. Safe side, but it would stop trading. A slower retry for these two queries is a small change in `reconciler.rs`; it needs a decision on the pace.
  - Not guaranteed: everything about the live venue: that its answers look like the documented examples, that `marginUsed` is isolated equity (T1), that the account value includes it (T2), which mode string is standard (T10), whether `activeAssetData` gives leverage without a position (T11). The three match arms of the gateway that post the queries, HTTP errors and HTTP 429 have no test. The weights are the documented ones and were not compared with what the venue counts. The burst test pins the arithmetic of the local budget only: the margin query is tried once per `margin_poll_ms`, and the sweep and the setting queries draw on the same budget, so the real wait can be longer than 15.1 s. Two coins that map to the same instrument id (`PURR/USDC` and `PURR_USDC`) would appear as two positions on one instrument.
