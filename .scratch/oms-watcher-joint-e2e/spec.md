## Problem Statement

The OMS (oms-node, U17/U18) and the independent watcher (U19a/U19b) were each tested only against fakes of the other. No test has ever run them together:
- "No run against a real oms-node process. The OMS side is the rig's OMS model, the fake sockets and http-fake." (`parts/U19a7/report_impl.md:155`); "No real OMS `admin.sock`: `watcher_kill` was sent only to a test `UnixListener`." (`parts/U19b3a/report_impl.md:234`); "No real OMS process booted on the file" (`parts/U19b3b/report_impl.md:213`).
- "The binary with `--config` is never started by a test." (`parts/U19a7/report_impl.md:156`); the binary cannot be pointed at a fake at all (`crates/watcher/src/runtime.rs:71-94`, `src/main.rs:4`, `:57`).
- "The gate was only exercised against simvenue; no Bybit or Hyperliquid node ran with a gate." (`parts/U18b4/report_impl.md:163`); the gate's close time end to end was never measured (`parts/U19a7/report_impl.md:157`).
- `docs/explanation.md` §9 item 11 says it in the living document: "워처는 실제 OMS 프로세스나 실제 Bybit에 붙여 돌린 적이 없고".

So nothing shows that the two programs agree on their written interfaces when they really run: the journal files and C-TAIL field table, `/api/status`, `admin.sock` `watcher_mismatch`/`watcher_kill`, `monitor.sock` heartbeats, the kill marker path, and one shared venue account.

U19c closes these gaps except one: the request `watcher_kill` on a real `admin.sock` is still never written by a test after U19c (J3 is the only scenario where W5 fires, and its stopped OMS never answers `hello`, J3 below). It is listed in Out of Scope and in V-JOINT-3 `not_covered`, with owner question 7 (review round 3, S2).

U19c adds process-level joint tests that start the real `oms-node` binary (Bybit gateway, `failpoints` build so it reads `OMS_TEST_BYBIT_WIRING`) and the real `watcher` binary at the same time against ONE stateful fake Bybit (one order, position and execution book that answers both programs), plus a fake Telegram and a fake `systemctl`, and assert what both programs do through their real interfaces only. Ten tests cover the six scenarios J1–J6 of the scope (J2, J5 and J6 have two tests each) plus one preflight test (J0). A test that fails because the programs disagree is a finding: the PR reports it and fixes the program that breaks the written rule; the test is not weakened. One such finding is already visible in the code (F1 below).

### F1: a disagreement already visible in the code (U19c5)

During the OMS's own kill (J4: private stream down > 10 s) the OMS cancels every order at the venue (`query.rs:396-414`) but its reconciler is off while the link is down (`reconciler.rs:127-130`), so the journal keeps the orders open and acked. The watcher's W1 then reports `missing_at_venue` for each of them after two rounds, because their journal records are old (`w1.rs:182-191`), and sends `watcher_mismatch`. The scope says J4 must raise "no extra mismatch". Neither program breaks its own written rule (`docs/explanation.md` §6 items 4–6 and §9 item 2); the two rules together produce a false mismatch whenever the OMS kills with its link down, and also after a watcher kill when the restarted OMS boots latched (J3). U19c5 writes J4 and J3 first. If J4, or J3 step 7, fails for this reason (a `watcher_mismatch` whose detail names `W1` `missing_at_venue` while the journal holds the kill latch), U19c5 records the failure as finding F1 in the PR and changes the watcher (decision below, ADR-040, owner question 1). If neither fails for this reason (this reading is wrong), U19c5 reports that and makes no change.

### Clock and waits
- The two binaries run on their system clocks (`watcher/src/main.rs:58`, the OMS's wall clock); two processes cannot share an injected clock, and the scope wants the real binaries. So the joint tests run in real time with short configurable timers and a stated budget per test. What is sans-IO in U19c is on an injected clock: the fake's `Book` takes `now_ms` as an argument on every call (its unit tests use fixed instants; the server passes `SystemTime` milliseconds because both programs compare venue times with their wall clocks, `w2.rs` change times, `checks.rs:384-422`).
- Every wait in the rig is bounded: `Budget` holds the test's deadline; each wait polls every 15–50 ms (판단(모델 아님)) until its own timeout or the budget, whichever is first, then panics with the log tails of both programs and the fake's request log. No loop without a bound. Negative assertions ("no hold before 2 s") are windows checked by polling, as `bybit_node.rs:867-876`.
- Processes: each OMS and watcher child has a reaper thread that `try_wait`s every 20 ms and keeps the exit status and time. `Drop` sends SIGCONT then SIGKILL to every live child and waits for it. When the OMS reaper sees the exit it removes `o/oms.pid` before it records the exit, so no later fake `systemctl` call or `Drop` reads a freed pid. After each run `xtask joint` scans `/proc/*/cmdline` for a process whose command line names the run's directory (`r<xtaskpid>-<k>`, below, so another invocation's run is never matched). A match whose `/proc/<pid>/exe` is one of the three test binaries (the joint build's `oms-node`, the copied `watcher` and `omsctl`) gets SIGCONT then SIGKILL and fails the run ("orphan process <pid> <exe>"); any other match (a shell, a `tail -f` on a log) fails the run with its pid and command line and is not signalled. So the joint tests never leave a test binary behind, even if a test thread is killed, and the scan never signals a process that is not theirs.
- One test at a time (`--test-threads=1`): the scenarios are timing-sensitive and each world holds several processes and about ten sockets (판단(모델 아님)); the fd count stays far below the 1,024 that broke parallel in-process worlds (`parts/U19b3c/report_impl.md:194`).

### Directories, ports, keys
- Each test gets `$OMS_TEST_DIR/<tag>-<pid>/` (`tag` at most 3 bytes: `j0`, `j1`, `j2a` … `j6b`; `pid` the test process, at most 7 digits) with `o/` (the OMS: `oms.toml`, credentials 0600, `node.log`, `oms.pid`, data directory `o/d/`), `w/` (the watcher: config, credentials 0600, `watcher.log`), `telegram.json` (0600, shared by both programs: same bot, U19b owner question 6), `s/kill.marker`'s directory `s/` (outside both data directories), `bin/systemctl` (the fake, 0700) and `systemctl.log`. The rig refuses (test fails, the path in the message) a base directory inside a git work tree (the watcher's token rule, `creds.rs:87-96`) and a Unix socket path of 100 bytes or more (SUN_LEN 108; the 8 bytes of margin are 판단(모델 아님)); `xtask joint` checks both before any build (step 1).
