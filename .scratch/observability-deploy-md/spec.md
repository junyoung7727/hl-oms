## Problem Statement

The collector (U5b, U6), the seal (`md-lake seal`) and the archiver (U7) exist as code and three template units, and the qdp auditor (U8) exists in qdp. Nothing describes how the observability stack (VictoriaMetrics, VictoriaLogs, two vmalert instances, Alertmanager, Grafana) runs on this PC, where it keeps its data, how much memory each service may use, or which rules raise which alert. Without rules, a dead collector, a full lake disk, a failed L0 write or a stuck seal is seen only by the direct `[MD P1]` path or not at all, and nobody looks at the market-data numbers the collector already pushes. Without a check, a rule can name a metric that no process exports and stay silent forever, and a collector unit can lose `Restart=always` or its OOM protection in an edit without anyone noticing.

## Solution

Files only, plus one test:

1. **U20a1** — systemd units for the stack, the collector, the seal and the archiver, a `trading.slice`, timers with fixed schedules, an install map, and the first half of the deployment check (units, timers, slices, paths). Runbook `docs/operations/observability.md` with the storage layout, the protection settings, the research-job rule and chrony.
2. **U20a1b** — the qdp audit: `crypto-lake-audit@` unit and timer, the script `bin/crypto-lake-audit.sh` (verify loop + auditor), the audit rules of the check (U12, U16, U17 and the audit rows of U5–U7), and the audit part of the runbook (review 2 S3).
3. **U20a2** — vmalert rule files (market data, lake, system; one log rule file), the metric catalogue, the scrape config, rule tests for `vmalert-tool`, and the rule part of the check (every metric name exists, every alert has a severity, one liveness rule per configured venue, the design's lake and disk rules).
4. **U20a2b** — the Alertmanager config with Telegram (token and chat id from files only), a placeholder dead-man receiver and the inhibit rule, and the Alertmanager part of the check (routes, secrets).
5. **U20a3** — Grafana: `grafana.ini`, provisioning for the VictoriaMetrics and VictoriaLogs datasources, dashboards D2 (market-data collection) and D3 (system), and the dashboard half of the check.

- **JSON syntax for every YAML consumer.** vmalert rules, the scrape config, the Alertmanager config, Grafana provisioning and the vmalert-tool tests are JSON documents (JSON is valid YAML; checked above with the real tools). Rule and Alertmanager files are named `*.json`; Grafana provisioning keeps the `.yaml` name it requires. Reason: the check then parses exactly what the tools parse, with `serde_json` (already a dependency), and no YAML crate enters `Cargo.lock` (no network fetch, no new supply-chain surface). Cost: no comments in those files; every alert carries an `annotations.summary`, and the runbook explains each file. Alternative rejected: a hand-written YAML subset parser in the test (it could accept what vmalert rejects).
- **Install map** `install.toml`: `[[file]] src = "<path under deploy/observability>"`, `dst = "<absolute path>"`, `mode = "0644"`, or `"0755"` for the one executable, `bin/crypto-lake-audit.sh`. Install prefixes (판단(모델 아님)): units → `/etc/systemd/system/`; `bin/` → `/usr/local/lib/hl-oms-obs/`; configs → `/etc/hl-oms-obs/<same sub-path>`; Grafana dashboards → `/etc/hl-oms-obs/grafana/dashboards/`. `vmalert/tests/`, `README.md`, `install.toml`, `venues.toml`, `metrics.toml` are not installed. The runbook's install section is a list of `install -D -m <mode> <src> <dst>` lines generated by hand from this map (the operator runs them; this repository does not).
- **Install-time paths outside the repository** (all placeholders, created by the operator): binaries `/usr/local/bin/{victoria-metrics-prod,victoria-logs-prod,vmalert-prod,alertmanager,md-collector,md-lake,md-archiver}`, Grafana tree `/opt/grafana`; secrets `/etc/hl-oms/alertmanager-telegram-token`, `/etc/hl-oms/alertmanager-telegram-chat-id`, `/etc/hl-oms/grafana-admin-password` (mode 0640, group `hlobs`), and the existing `/etc/hl-oms/telegram.json` of `md-lake seal`; qdp checkout `/opt/qdp-crypto` (D5).

  - `ExecStart=/usr/bin/flock /run/lock/hl-oms-daily.lock /usr/local/lib/hl-oms-obs/crypto-lake-audit.sh %i`. No `ExecStartPre`. The script is `deploy/observability/bin/crypto-lake-audit.sh` (mode 0755, the only executable file of the unit; POSIX `sh`, no `$(` in a unit line, review 1 N2). It does the following, in this order, under the one lock:
    0. It sets `venue=$1` and exits 2 with a line on stderr when `venue`, `LAKE`, `STATE_DIRECTORY`, `QDP_CHECKOUT`, `UV` or `MD_LAKE` is empty (review 3 N2: run by hand outside systemd, `STATE_DIRECTORY` is empty, and the stamps and the state file would go to `/`). Exit 2 means "usage refused", as for the auditor.
    1. For each of the 9 UTC dates from yesterday back to 9 days ago (bound 9, 판단(모델 아님)), it verifies the date when the date has at least one sealed `*.qraw.zst` file under `crypto/l0/venue=<v>/` and one of these is true: no result file `crypto/l0/_verify/venue=<v>/date=<d>.json` exists; no stamp `"$STATE_DIRECTORY/verify-$venue-$d.stamp"` exists; or a sealed file of the date has a status change after the stamp (`find … -cnewer <stamp>`). To verify a date it:
       - touches `"$STATE_DIRECTORY/verify-$venue-$d.stamp.new"`, then `sleep 1`;
       - runs `"$MD_LAKE" verify --venue <v> --lake "$LAKE" --date <d> --json > /dev/null`;
       - on success, renames `….stamp.new` to `….stamp` (`mv` keeps the mtime of the touch); on failure, logs to stderr, keeps the old stamp and goes on with the next date.

       Why a stamp taken before the verify, and not the result file (review 2 S1): the day seal is not under the daily lock, and `verify` lists the date's files once (`sealed_files`, `verify.rs:16–38`) and writes the result when it ends (`:148–156`). A file renamed from `.partial` after the listing and before the result is written is not in the result, and its ctime is older than the result's, so a test against the result would never pick the date again. Against the stamp, that file's ctime is newer, so the next run verifies the date again. GNU `find -cnewer` compares the file's ctime with the reference's mtime (`man find`), and the stamp's mtime is the touch. The `sleep 1` is there because kernel timestamps are coarse: a rename in the same tick as the touch would have an equal time, and `-cnewer` is strict; a rename before the listing is in this run's result anyway. A rename changes a file's ctime but not its mtime, so `-newer` would miss such a file. The implementer confirms this ctime behaviour on ext4 in D11. A date with no sealed file is skipped, so no empty result is written for a day the PC was off or a day before the install. Stamps are empty files, one per venue and date; they are not removed (about 365 a year per venue, 판단(모델 아님)).

       Why 9 dates and not 7 (review 3 S1): the day seal's look-back is 7 days from the day of `last_closed` (`LOOKBACK_DAYS`, `dayseal.rs:23`, `:50`). The 00:05 run of day N has `last_closed` in day N−1, so it can still seal date N−8; a run of day N after 02:30 can seal date N−7, which the audit of day N+1 must still see. With 9 dates, the audit of day N covers N−1 … N−9 and the audit of day N+1 covers N … N−8, so every date a normal seal run can reach is in some later window. A seal run that clears a backlog seals every date from its first sealed hour (`earliest`, `dayseal.rs:51`), and `md-lake seal-days --from D` seals every date from D (`md-lake.rs:6`, `:155`; `dayseal.rs:29–38`): those dates can be older than the window. The runbook (§4) says to run `md-lake verify` by hand for each such date.
    2. `cd "$QDP_CHECKOUT" || exit 2` (with a line on stderr: `uv` must not run in another directory; review 4 N3), then run `"$UV" run --no-sync python -m quant_data.crypto audit --lake "$LAKE" --venue <v> --state "$STATE_DIRECTORY/audit-<v>.json" --vm-url http://127.0.0.1:8428`.
    3. Exit status: 2 from step 0 or a failed `cd`; else the status of the `uv` command when it is not 0; else 5 when a verify failed; else 0. Status 5 is not used by the auditor (it uses 0–4, qdp `audit.py:603`).
  - The auditor audits every date with evidence and reads each date's verify result (qdp `audit.py:463`, `:168`). A sealed L0 file whose date has no verify result counts in `lake_audit_not_audited_files` (`audit.py:505`, `:542`). Dates older than 9 days (after a seal backlog or `md-lake seal-days`) are verified by hand; the runbook (§4) gives the command.
  - Exit 1 (a `fail` date), 3 (write error or bug), 4 (push failed) and 5 (verify failed) leave the unit failed. Each is a real finding. How each is seen:
    - 1 from the auditor: `LakeAuditFailed`.
    - 1 from Python itself, not from the auditor: an exception that `main` does not catch (it catches only `StateError`, `AuditError` and `OSError`, qdp `audit.py:612–619`) or a failed import when the checkout's `.venv` is broken (`--no-sync` does not repair it). Nothing is pushed, so `LakeAuditFailed` stays silent and `LakeAuditStale` reports it after 36 h. The journal (`journalctl -u crypto-lake-audit@<v>`) tells the two exit-1 cases apart: a traceback, or `audit: <date>` lines (review 4 N3). Any other status that `uv` returns for its own errors is passed on the same way and seen the same way.
    - 4, and 3 or 2 raised before the push: `LakeAuditStale` after 36 h. In these cases `lake_audit_last_run_ts` is not pushed (`audit.py:613–619`).
    - 3 from a single date's write error, and 5: only `systemctl --failed`. The auditor still pushes `lake_audit_last_run_ts` in this case (`audit.py:622–641`), and it removes the failed date from its state (`audit.py:480–485`). The runbook's daily step (§4) and a text panel in D3 cover it.
  - The KR pipeline is never touched: `QDP_CHECKOUT` must be a dedicated checkout of qdp main; the check (rule U12) refuses any deploy file that names `/mnt/nvme/gitproject/quant-data-platform` (prefix, so also `-official`) and refuses a `--state` under the lake.
- Order inside a day (UTC): 00:05 seal of hour 23 + day seal → 01:10 archiver (L1 of every day-sealed date without L1) → 02:30 verify the changed dates of the last 9 days, then audit. `--retain-l1-days` stays off (`RETAIN_ARGS=` empty). The runbook gives two conditions for enabling it: an audit `--full` runs right before the archiver (qdp `auditor.md`, "Run `--full` right before `md-archiver --retain-l1-days`"), and a follow-up code unit exports `lake_l1_build_lag_days` from md-archiver with an alert on it. Without that metric, an archiver run that is killed (for example at its 4 GB cap) blocks every later date, because it builds the oldest date first (`crates/md-archiver/src/run.rs:2`), and only `systemctl --failed` shows it.

2. **Q2 Service identity.** Default: stack units run as a new system user `hlobs`; `md-collector@`, `md-lake-seal@`, `md-archiver@` and `crypto-lake-audit@` keep running as root as merged (a change needs the lake's owner moved).
3. **Q3 Grafana address.** Default: `http_addr = 192.0.2.1`, a placeholder address Grafana cannot bind, so it does not start until the operator writes this PC's Tailscale address (never all interfaces).
4. **Q4 qdp checkout for the audit.** Default: `/opt/qdp-crypto`, a dedicated checkout of qdp main with its own `.venv` (`uv sync --frozen` once); never the KR checkouts under `/mnt/nvme/gitproject/quant-data-platform*`.
5. **Q5 P2/P3 thresholds** of D7's second table (2 min silent connection, 10% stale topics, 1,000 ms p99 lag, 10 reconnects or 20 gaps in 10 min, one collector restart in 10 min, 8 MiB queue, 36 h audit age, 10 min missing lake gauge). Default: as listed, reviewed in the weekly noise review.
6. **Q6 Collector crash loop.** Default: `RestartSec=2` with no back-off and no start limit (D3). A crashed collector is back in about 2 s every time, so each crash loses about 2 s of raw data. The cost is a collector that crashes at once on every start: it then opens its venue connections about every 2 s until a person stops it. Two rules see a crash loop: the fast loop (the collector dies before it pushes a heartbeat, so no beat arrives for 60 s) raises `MdCollectorDown` (P1); the slow loop (it lives long enough to beat, then dies again, for example at its `MemoryMax`) raises `MdCollectorRestarting` (P2, D7; review 4 S1). Bybit's per-IP connection limit was not checked at this stage. A back-off needs a documented reset of the systemd restart counter (D3) and the owner's acceptance of the longer gaps.
7. **Q7 Archiver cap.** Default: `MemoryMax=4G` (design value; was 8G). Measured: 2.57 GB for 3.2 M rows, about 5 M rows per topic-day at 4 GB (D4). A busier day is killed at the cap and blocks the later dates until a person runs it with a higher cap. No data is lost: L0 stays, and `--retain-l1-days` stays off.

Decided here and reported, not asked: per-venue templates with the daily-job lock instead of the plan's plain unit names (D4); no verify claim for the check (Documents and registry); `chat_id_file` instead of the scope's `chat_id` (D8: the chat id stays out of the repository like the token, and R11 refuses an inline `chat_id`; review 3 N3); a 9-date verify window instead of 7 (D4, review 3 S1).
